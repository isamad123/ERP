# Handoff: R-305 manager approver follows the subject's employment (CR-116)

- **Wrong:** the `manager` approver asked for the manager of the document's first subject *user*, else of the requester. A request HR or a manager enters for an employee with no sign-in therefore went to the entering person's own manager (FR-XM-32 segregation weakened).
- **Changed:** a document type may declare `subject_employment_field` (text; HR stores the employment id) and `subject_date_field` (date). For such a type `manager` is resolved through the new `IApproverDirectory.ManagersOfSubjectAsync(subject, levels, asOf)` (HR: `HrmApproverDirectory`, same walk up `manager_employment_id` as before, started from the employment), as of the date field, else today. No value or no manager = nobody, so the step's fallback (HR Admin) applies; never the requester or the requester's manager. The engine's rule that the requester and the subject never decide is unchanged. Types without the keys behave as before. No migration, no new package.
- **Routes:** `hrm.regularization` (date `work_date`) and `hrm.duty_request` (date `start_date`) declare the keys; `AttendanceRequestService.SaveAndStartAsync` fills `employment`. Not affected: `hrm.leave_request` and `hrm.leave_cancellation` (own `line_manager` field, R-305 note), strength exception (role), employment events, bank account, compensation, structure and policy changes (role or maker-checker, no `manager` step). Existing open requests keep their tasks; escalation of a task is by the assignee's manager (unchanged).
- **Tests:** `AttendanceRequestTests` (four new `FR_XM_32_FR_KRN_WFL_02_...`: on behalf, own request, manager enters it, no manager; the first and last fail on the old routing), `WorkflowStartupCheckTests` (manifest keys). Contract row in `docs/registers/contracts.md`; R-305 closed; CR-116.
- **Open:** a future module with `manager` steps declares the two keys; `department_head` still resolves from the subject user (S1.22; same gap, not used by any route yet).
