## Summary for the product owner

The core of S1.03 is sound. I tried to get one customer's data through another customer's address and could not:
- The customer is taken only from the web address (host name). The query string, the body and headers such as
  `X-Tenant` or `X-Forwarded-Host` are ignored. A test checks this.
- A valid sign-in token from customer B is refused on customer A's address.
- Each customer has its own database and its own database logins. One customer's logins cannot even connect to another
  customer's database. I checked this in the code and the grants, and a test checks it too.
- Every SQL statement uses parameters. Names that cannot be parameters (database and login names) are checked against a
  strict pattern first.
- No migration file that was already merged was changed.

I found **no high-severity defect**. There are **three medium issues**, all in the operator tools, not in what
customers use:

1. **A backup can delete an earlier backup.** If the operator gives `tenant backup` the name of a file that already
   exists, the command fails. On the way out it deletes that existing file. If that file was the last good backup, it is
   gone. I proved this with a test.
2. **The restore drill fails on any customer that is in use.** The drill restores a backup into a new database. It then
   compares that copy with the customer's live database, not with the backup as it was taken. Any change made after the
   backup counts as a difference. The background worker writes to every customer database every minute (approval
   escalation runs). So on a real customer the drill always fails and never records a successful test. FR-ADM-DAT-08
   asks for verification results, and these would be wrong. I proved this with a test: a single change after the backup
   makes the drill fail.
3. **Random web addresses fill the API host's memory.** Every unknown host name that reaches the API is remembered
   forever, and each one costs a lookup in the shared control-plane database. Anyone can send requests with made-up
   host names, so the memory grows without limit and the control plane takes the extra load. I proved this with a test:
   2,000 made-up names left 2,000 remembered entries.

There are also eight low issues. They need small changes, and they are listed below. Two items need **your decision**:
- Finding 10: should operator commands check the operator's platform role now, or in S1.17?
- Finding 11: should the API connect to the control plane with its own limited login?

I recommend fixing 1 to 3 now. Each is a small change with a test.

## Findings, most severe first

### 1. MEDIUM: `tenant backup` deletes an existing file at the output path

- **Where:** `src/Platform/Erp.Kernel.Infrastructure/ControlPlane/Backup/TenantBackup.cs:37-52`.
  - `new FileStream(outputPath, FileMode.CreateNew, …)` (line 41) is inside the `try`.
  - When the file already exists, it throws `IOException`. The `catch` (lines 48-51) then runs `File.Delete(outputPath)`,
    which deletes the file that was already there.
  - `pg_dump` has already been started (line 37) and is never stopped or awaited on this path.
- **Scenario:** an operator re-runs `scripts/tenant-backup.sh acme /backups/acme-2026-11-19.enc` with the same name as
  this morning's backup. The command fails with "file exists", and this morning's backup has been deleted.
- **Proof:** `Proof_backup_to_an_existing_file_deletes_that_file`.
- **Fix:**
  - Open the output file before starting `pg_dump`, outside the `try`. Then "file exists" fails cleanly and nothing is
    deleted.
  - Delete only a file this call created.
  - On any failure, stop `pg_dump` if it is still running.
- **Test to add:** an existing file at `--out` is left unchanged, and the command reports the clash.

### 2. MEDIUM: the restore drill compares with the live database, so it fails on every customer in use

- **Where:** `TenantBackup.cs:123-134`. `FingerprintAsync(source)` reads the production database at restore time, not
  at backup time. The runbook (`docs/runbooks/tenant-backup-restore.md:36`) says to "run it soon after the backup or on a
  quiet customer".
- **Why that is not enough:**
  - `kernel.workflow_escalate` runs every minute for every active customer (`Access/jobs.json`, `every_minutes: 1`) and
    writes `job.runs` rows.
  - Sign-ins update `iam.sessions` and audit tables grow.
  - A restore of a real customer takes minutes, so the comparison always finds differences. The drill exits with code 4,
    and `last_restore_test_at` is never recorded.
- **Also:**
  - The backup file does not say which customer it belongs to, so restoring customer A's file under `--code b` is only
    noticed as "tables differ".
  - `string_agg(md5(...) order by ...)` builds one string of 32 bytes per row. A table of more than about 30 million
    rows (the audit log of a large customer) goes over PostgreSQL's 1 GB value limit, and the drill then fails.
- **Proof:** `Proof_restore_drill_fails_after_any_write_made_after_the_backup`. One `update org.companies` after the
  backup makes the drill fail with `org.companies` listed as different.
- **Fix:**
  - At backup time, open a `repeatable read` transaction as the backup login and call `pg_export_snapshot()`.
  - Compute the fingerprints in that transaction, then run `pg_dump --snapshot=<id>`. The fingerprints then describe
    exactly what was dumped.
  - Write the customer code and the fingerprints into the encrypted file as a manifest, so they are authenticated like
    the dump itself.
  - Restore compares the copy with the manifest, and refuses a file whose code is not `--code`.
  - Use a fixed-size, order-independent checksum, for example the sum of the first 8 bytes of each row's md5 taken as a
    number, instead of `string_agg`.
  - Update the runbook.
- **Test to add:** back up, write to the customer, restore. The drill is verified, and the restored copy does not have
  the later write.

### 3. MEDIUM: unknown host names are cached without limit, and each costs a control-plane query

- **Where:** `src/Platform/Erp.Kernel.Infrastructure/ControlPlane/Tenancy/TenantDirectory.cs:30-45`.
  - Every lookup stores its result, including "no customer", in `_cache`. Nothing ever removes an entry: an expired
    entry is only overwritten when the same host is asked again, and `Invalidate()` is called only after lifecycle
    changes.
  - The class comment says unknown hosts are cached so that "repeated probes do not reach the control-plane database".
    That is true only when the same name is repeated.
- **Scenario:** behind a wildcard DNS name (`*.erp.example`), or with any client that sets its own `Host` header, an
  attacker sends requests with random host names. Each one opens a control-plane query and adds a permanent entry to the
  API host's memory. Both grow without limit, on a host that serves every customer.
- **Proof:** `Proof_unknown_hosts_fill_the_directory_cache_without_bound`. 2,000 random hosts left 2,000 entries.
- **Fix (either):**
  - Keep the whole host → customer map in memory. It is small (one row per customer domain). Reload it every
    `HostCacheSeconds` and answer unknown hosts from it without a query.
  - Or use a bounded cache (`MemoryCache` with `SizeLimit`) and cap the number of negative entries.
- **Test to add:** many random hosts → the number of cache entries and of control-plane queries stays within the bound.

### 4. LOW: two concurrent branch deletions can leave a company with no branch (rule SC-2)

- **Where:** `V202611150201__kernel__rules_s1_03.sql`, `org.tg_branches_keep_one_per_company`. The "another branch is
  still there" check reads without a lock. Two transactions each delete a different one of a company's two branches.
  Each one still sees the other branch, so both commit.
- **Proof:** `Proof_two_concurrent_branch_deletes_leave_a_company_with_no_branch` → 0 branches left.
- **Fix:** a new rules migration (the merged file stays frozen), emitted the S1.03 way through `rules.yaml`. It starts
  the trigger with `perform 1 from org.companies where id = old.company_id for update`, so branch removals for one
  company take turns.

### 5. LOW: backup and restore clean-up gaps

- `TenantBackup.cs:87`: the cluster secret is read after the restore target was created but outside the `try`. A
  failure there leaves the empty target database behind.
- `TenantBackup.cs:48-51`: when encryption fails, for example because the disk is full, `pg_dump` is left running and its
  process handle is not released.
- The damaged-file case in the test does not check that the half-restored `_bad` database was dropped (see T2).

### 6. LOW: `cluster add` with an existing name silently moves every customer on that cluster

- **Where:** `ControlPlaneAdmin.cs:105-125`.
  - `on conflict (name) do update set host = …, port = …` changes the address of a cluster that already holds customer
    databases.
  - The administrator secret is replaced first (line 110), before the database write.
  - API hosts keep their old pools anyway, because `TenantDataSources` keys pools by customer code and password only
    (`TenantDataSources.cs:24-29`), not by host, port or database.
- **Fix:**
  - Refuse to change host or port of a cluster that has databases, unless the operator adds an explicit flag.
  - Include host, port and database name in the pool key.

### 7. LOW: customer database passwords pass through the server as plain text

- **Where:** `ClusterAdministrator.cs:138-145`. `create role … password '<plain>'` is built with `format(%L)`. With
  `log_statement = ddl` or `all`, or whenever the statement fails (the default `log_min_error_statement = error`, for
  example the R-031 race), the server log of a shared server records the password.
- **Fix:** compute the SCRAM-SHA-256 verifier in C# and send `password 'SCRAM-SHA-256$4096:…'`. PostgreSQL stores a
  verifier as given, so the plain text never reaches the server.

### 8. LOW: the application login can write `meta.schema_history`

- **Where:** `V202611150200__kernel__grants.sql`: `grant select, insert on meta.schema_history to app_rw`. The table
  is append-only, so the generator gave `app_rw` select and insert. Only the migrator (the owner login) writes it.
  Through any future SQL injection, the application login could mark a migration as applied, and the migrator would
  then skip it.
- **Fix:** a new grants migration that revokes `insert` (generator rule: `meta.schema_history` is written only by the owner).

### 9. LOW: the customer list shows a customer twice when it has a scheduled entitlement

- **Where:** `TenantLifecycle.cs:85`: `left join cp.entitlements e … and e.status <> 'superseded'`. Since S1.09b, a
  customer can have a current row and a `scheduled` row, so `tenant list` (FR-ADM-PLT-01) prints two lines for it, one
  with the scheduled edition.
- **Fix:** take the entitlement in force (`EntitlementSelection.InForce`) or a lateral join of the highest
  non-scheduled, non-superseded version.

### 10. LOW (needs your decision): operator commands do not check who the operator is or what role they have

- **Where:** `OperatorCommands.cs` `Context.ActorAsync`.
  - The acting platform user is whatever `ERP_PLATFORM_ACTOR` says.
  - The user's `role` is never checked, so any active platform user can provision, suspend, back up and restore.
- **What the requirement says:** FR-ADM-PLT-10 (release 1.0) asks for mandatory MFA and separation of duties between
  provisioning, licensing and support. The handoff gives platform sign-in to S1.17. Until then, the audit trail records
  a name the operator typed, not a proven identity. The real protection is access to the server and to the secret store
  key.
- **Decision needed:**
  - (a) Record it as a risk and leave it to S1.17. This is my recommendation: a role check on a self-declared name adds
    little.
  - (b) Check the role per command now.

### 11. LOW (needs your decision): the API's control-plane login is not limited

- **Where:**
  - The API reads `ConnectionStrings:ControlPlane` (`ApiHost.cs:65`).
  - The runbook (`tenant-operations.md:19`) does not say which login to use, and the tests use the server superuser.
  - The API only needs to read a few `cp` tables. A superuser login means a single SQL flaw in the API would reach
    every database on that server.
- **Fix:**
  - Document a dedicated `cp_api` login with `select` on the tables `TenantDirectory` and the licence services read, plus
    any write the API really makes.
  - Optionally, `migrate` could create it.
- **Decision needed:** do it now (runbook, plus an optional migrate step), or record it as a risk for the hosting slice.

### 12. LOW: provisioning trusts what is already on the server

- Resuming with a different `--cluster` creates the database on the new cluster
  (`TenantProvisioner.cs:81` uses the cluster from the request). The registry, and every later connection, still point
  to the first cluster. Fix: on resume, use the registered cluster and refuse a different `--cluster`.
- `ClusterAdministrator.cs:53-60` uses an existing database with the customer's name without checking its owner. A
  restore drill target may be named `erp_t_<code>` for a customer not yet provisioned (`TenantBackup.cs:59` only refuses
  the same customer's name). Fix: refuse restore targets that start with `erp_t_`. In provisioning, refuse an existing
  database whose owner is not the customer's owner login.
- `HostNames.Normalize` accepts numeric labels, so `127.0.0.1` can be registered as a customer host. The comment says
  customers are "reached by name only". Fix: refuse a host whose last label is all digits.

## Checked and found correct

- **Host resolution** (`TenantResolution.cs`, `HostNames.cs`):
  - Only `Request.Host` is used. There is no forwarded-headers middleware, so `X-Forwarded-Host` is ignored (and tested).
  - Kestrel refuses an absolute-form request target whose authority differs from `Host`.
  - Normalisation refuses IPv6 literals, bad ports, empty or over-long labels and non-ASCII names.
  - An unknown host, or a `deleted` or unknown status, gives 404. `provisioning`, `offboarding` and `maintenance` give
    503. The registry and database states are checked before the customer database is touched.
- **Token check:**
  - It runs after `UseAuthentication` and before `UseAuthorization`, with a single JWT scheme, so no later step
    authenticates the user without the check.
  - A missing `tenant` claim, or one that does not match, gives 401.
  - The signing keys are shared by all customers. That is safe only because of this check, and it is applied to every
    authenticated request, anonymous endpoints included.
- **Per-customer logins (CR-004):**
  - `revoke all on database … from public`. CONNECT is granted only to the customer's five named logins.
  - No migration or code grants database-level privileges to a group role (searched all of `src`).
  - Logins are `login inherit` with no CREATEROLE, CREATEDB or SUPERUSER.
  - Login and database names cannot collide between customers, because codes have no underscore.
  - R-028's check refuses a pre-existing group role with powers.
- **SQL safety:**
  - Every value is a parameter (`Sql.Command`).
  - The identifiers are customer codes (`TenantCodes.Validate`), restore targets (regex), role names (R-028 regex) and
    `format('%I.%I')` from `pg_class`, all checked before quoting.
  - Passwords and role names go through server-side `format(%I, %L)`.
- **Secrets:**
  - AES-256-GCM file store, with a cross-process lock file, a write to a temporary file and an atomic move.
  - The cache is checked against the file's write time.
  - `DatabaseCredential.ToString` masks the password.
  - `PGPASSWORD` is given only to the child process, not on the command line.
- **Backup cipher:** 1 MiB AES-GCM chunks. The nonce is the file id plus the chunk number, and the final flag and chunk
  number are authenticated, so reordering, truncation and changes are refused. Plain text reaches `pg_restore` only
  after its chunk's tag is verified.
- **Migrator:**
  - One transaction per file, and a per-database advisory lock.
  - A SHA-256 checksum with line endings normalised; a changed file stops the run (tested).
  - Scripts that ran before `meta.schema_history` exists are recorded in the transaction that creates it, and they are
    safe to re-run (checked above).
  - A failure on one customer puts only that customer in `maintenance` and the run continues (tested).
- **Provisioning:**
  - Each step checks before it writes, and the entitlement insert is `on conflict do nothing`.
  - A host that belongs to another customer rolls back the whole registration.
  - A wrong signature or a wrong customer in the entitlement stops the run before anything is written (tested).
- **SC-2 trigger:** the generated UUIDv7 is correct. Bits 52 and 53 turn the v4 version nibble 0100 into 0111, and the
  variant bits are kept from `gen_random_uuid()`.
- **Platform audit:** `cp.platform_audit` has append-only and no-truncate triggers. Every lifecycle, provisioning step,
  backup and restore test writes a row.
- **Rules:** the tests cite FR ids. They use a real PostgreSQL. Business code uses no `DateTime.Now`: the cache uses
  `TimeProvider` on purpose (machine time, S1.09b).
