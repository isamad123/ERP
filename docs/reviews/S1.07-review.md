## Summary for the product owner

Most of the audit work is solid:
- Every change made through the API writes its audit entry in the same transaction. If either the change or the entry fails, both are undone.
- The application can add audit rows only through the database functions, which compute the hashes. It cannot change or delete audit rows.
- The chain check finds a changed byte, a removed row and a rewritten day. Twenty writers at once still produce one unbroken chain.
- Personal values are locked with the person's own key, and destroying the key erases them without breaking the chain.
- A record's history follows the viewer's own data scope and field security.
- Every SQL value is a parameter, and no frozen migration was touched.

I found **one serious defect**:

1. **Some administrators and auditors can see every employee's salary and personal details in the audit search.** This affects anyone who can search the audit log (Tenant Admin, or a customer role with that permission) and who also holds the Employee role or another role limited to some records. That is very common: the HR head who administers the system is also an employee.
   - The Employee role lets a person see salary and personal fields on their **own** records. The audit search wrongly applied that permission to **every** record in the company.
   - I reproduced it. A Tenant Admin who is also an employee searched the log and saw a colleague's gross pay change from `1.0000` to `1235.5000`, and another person's date of birth.
   - The same Tenant Admin without the Employee role saw both fields hidden, which is correct.
   - The CSV export runs the same code, so it leaked the same way. I read this from the code; the reproduction stopped at the search.

There are also **four medium issues**:

2. **A false "chain broken" alarm that can never be cleared.** The daily copy of the audit anchors (the outside copy that guards against tampering) can copy a day that can still receive entries. An entry stamped just before midnight can arrive just after it: the server clock is a little behind, or a busy moment holds the entry back. That entry still lands on the old day and changes the day's anchor. The next copy run then reports a critical mismatch. Every later check of that day says the chain is broken, and because copies are never changed, the alarm stays for good. I reproduced it.
3. **Custom fields hidden from a user are shown in the record's history.** Example: a custom field "secret" that the user's role hides. The record screen hides it correctly, but its value appeared in the history (reproduced).
4. **A protected value of a table without its own screen or API is shown to auditors.** Example: a salary-class value of the payroll calculation trace. The search could not look up who may see it, so it showed it to everyone who can search. It could also make the search fail with a server error. Nothing writes such values today, so this is latent (reproduced with a test entry).
5. **A personal value can be stored under the company key instead of the person's key.** This happens when the system cannot find the person, for example a bank account added in the same step that creates the employment. Erasing that person would then leave the value readable. The r1 decision on R-013 assumed this could not happen. Nothing does this today; the hire flow will (reproduced at the code level).

I fixed all five, each with a test that failed before the fix and passes now.

**Needs your decision (6):** the payroll calculation trace (`hrm.pay_traces`, filled by the payroll engine, not built yet) is audited in plain text, salary inputs included. Anyone who can search the audit log would see them. I recommend marking the trace as salary data in the data design, so its values are encrypted and hidden in the search. That is a data-design change, so it needs a change request. The alternative is to stop auditing the trace (`audit: false`), because the pay result itself is audited. Until you decide, this is recorded as risk R-015.

The low items are listed below and recorded as R-015.

## Findings, most severe first

### 1. HIGH: the change search and export show sensitive fields through roles that cover only some records

- **Where:** `AuditQueryService.PresentAsync` (merged code) built each row's field map with `IFieldAccess.ForAsync(resource.Fields, "read", row.CompanyId)`.
  - That merges every role that grants `resource.read` for the company, whatever rows the role's scope covers.
  - The Employee baseline role (`src/Modules/Hrm/Erp.Hrm.Infrastructure/Access/baseline-roles.json`) has scope `* → own`, a `class:salary → read_only` rule, and the default "editable" for personal fields.
  - So for a person holding both `aud.changes.view` (Tenant Admin, `src/Platform/Erp.Kernel.Infrastructure/Access/baseline-roles.json`) and Employee, every pay and person entry in the company came back with its values. The access log recorded the view, but the values had already left the server.
  - This is the S1.06 review's finding 3 again, in the one place that still used the per-company merge. The record-history endpoint is not affected: it uses the per-record map (`ResourceAccess.ReadAccess` → `PlanAsync`).
- **Evidence:** reproduction `…review_S107_1…`, against the merged code:
  - `GET /api/aud/changes?entityId={pay result}&action=update` as Tenant Admin + Employee → `200 …"changes":[{"after":1235.5000,"class":"salary","field":"gross","before":1.0000}]`.
  - The same search for a person record contained `"1977-03-29"` (date of birth, decrypted with the person's key).
  - Control: Tenant Admin alone → `gross` hidden.
- **Fix (done):**
  - New `IFieldAccess.ForEveryRowAsync`. It counts only the roles whose scope for the resource covers every record of the company: `all`, or `companies` naming it, with no conditions, or any role when the table is not scoped.
  - The search and the export use it.
  - A role that opens a field on some records only (the Employee's own pay) opens it in that record's history, never in a search across records.
  - The Auditor (scope all, salary read-only) still sees values: tested.

### 2. MEDIUM: the anchor of a day still open is copied to the control plane, causing a permanent false tamper alarm

- **Where:** `AnchorPublisher.PublishOneAsync` copied every anchor with `day < today` (the migrator's clock). But ruling P2 places a new entry on its own stamped time whenever that time is after the chain head.
  - While the head is still on day D, an entry stamped 23:59:59 that is appended after midnight lands on D. This can happen with an application clock seconds behind the database, or a writer waiting for the chain lock.
  - That changes D's anchor after D was copied.
  - Copies are never changed (`cp.audit_anchors` refuses update). So every later `anchors-publish` reports `aud.anchor_copy_mismatch`, and every `POST /api/aud/verify` of D reports `control_plane_mismatch` and writes a critical `aud.chain_broken` event, for good. The chain itself is intact.
- **Evidence:** reproduction `…review_S107_2…` (the copy runs with a clock one day ahead, standing for "just after midnight"). On the merged code, the second run returned `Mismatches = ["2026-11-16"]`.
- **Fix (done):** a day is copied only once it is final:
  - the chain already has an entry on a later day (from then on P2 places every new entry after that, never on D), or
  - a full day has passed since D ended (an entry would need a clock more than 24 hours behind).

  Days not yet final are copied by a later run. This is how P5's "finished days" is now read. The runbook says so. No ruling changes.

### 3. MEDIUM: custom-field rules are not applied to audit values

- **Where:** `PresentAsync` judged the whole `custom` column by the `custom` level only. The per-key rules (`custom.<key>`, FR-KRN-MET-02) that `FieldShaping.Shape` applies to the record itself were skipped for the before and after values.
- **Evidence:** reproduction `…review_S107_3…`. A user whose role hides `custom.secret` gets it removed from `GET /api/org/org-units/{id}`. But `GET /api/aud/history/org.org_units/{id}` contained `hush-4711`.
- **Fix (done):** the per-key rule is applied to before and after values in history and search (`FieldShaping.ShapeCustom`, now shared with `Shape`). Hidden keys are removed and masked keys are masked.

### 4. MEDIUM–LOW: classed values of entity types without a resource were shown to everyone who can search

- **Where:** `PresentAsync` gave `ReadOnly` to any field when the entity type had no resource, or the field was not in the catalogue. Five audited tables have no resource today: `hrm.pay_traces`, `iam.role_data_scopes`, `iam.role_permissions`, `iam.user_group_members` and `ntf.preferences`.
  - A `salary`, `personal` or `restricted` value of such an entry would be decrypted and shown to every holder of `aud.changes.view`.
  - In history it needed only the two audit permissions (`aud.history.view` and `aud.changes.view`), with no company limit.
  - None of these tables has a classed column today, so this is latent. It would bite as soon as finding 6 is fixed by classing the trace.
- **Evidence:** reproduction `…review_S107_4…` (a test entry for `hrm.pay_traces` with a salary-class value). On the merged code the search tried to decrypt it and failed with `CryptographicException`. With a real value it would have shown it.
- **Fix (done):** a classed value whose field security cannot be decided is hidden. Unclassed values of such entries (for example `iam.*` event details) are shown as before.

### 5. MEDIUM–LOW (latent): a personal value whose person is unknown was kept under the customer key

- **Where:** `AuditValueProtector.FieldAsync` used the customer key when `subject is null`. The subject of an employment-located table comes from `IWorkforceDirectory.PersonsOfAsync`, which runs on its own connection. So an employment created in the same, uncommitted transaction is not found. That is the shape of a hire flow that adds the bank account with the employment. A kernel-only host with `NoWorkforce` would hit the same path.
  - The value would then survive the person's erasure, against spec 03 R-21.
  - The r1 resolution of R-013 says "the fallback to the customer key cannot happen". The generator check it relies on only guarantees a locator, not that the person can be found.
- **Evidence:** reproduction `…review_S107_5…`. On the merged code, `FieldAsync(…, "personal", …, subject: null)` → `{"field":"account_number","class":"personal","key":"customer","before":"AQEz…","after":"AQGK…"}`.
- **Fix (done):** without a known person, a personal or restricted value is recorded as changed, without values (`"redacted": true`), like encrypted columns (R-013). It is never stored under the customer key.
- **Later:** a hire-flow slice that needs the values should resolve the person inside its transaction.

### 6. MEDIUM (needs a product-owner decision): the payroll calculation trace is audited in plain text

- **Where:** `docs/data-design/hrm-pay.yaml`, `hrm.pay_traces`. Its `trace` column ("inputs, formulas, rule and table versions, rounding steps") has no `field_class`, and the table is audited (no `audit: false`).
  - When the payroll engine writes traces, every input amount goes into `aud.change_log` unencrypted.
  - It would be shown in the change search to every holder of `aud.changes.view`, the Tenant Admin included, who holds no salary permission (Q10, S1.06 Q2).
  - R-010 already notes that this table has no data scope.
- **Options (data-design change, needs a CR):**
  - (a) Recommended: `field_class: {trace: salary}` plus `scope: {via: result_id}`. The trace is then encrypted with the customer key and hidden in search (finding 4's guard). Payroll staff see it through the pay result.
  - (b) `audit: false`, with the reason "calculation trace, rewritten per calculation; the pay result's own entries record the change".
- Not changed in this review.

### 7. LOW: a caller at REPEATABLE READ or SERIALIZABLE could fork the chain

- **Where:** `aud.append_changes` reads the chain head after taking the advisory lock. At READ COMMITTED each statement sees the previous holder's committed rows.
  - In a transaction at REPEATABLE READ or SERIALIZABLE, the snapshot is taken at the transaction's first statement. After waiting for the lock it would not see rows committed in between.
  - Two rows would then link to the same previous hash, and the verifier would report a broken link that is not tampering.
- **Impact:** no code uses another isolation level today (`IsolationLevel.` appears nowhere in `src`).
- **Suggested:** the function refuses to run unless `current_setting('transaction_isolation') = 'read committed'` (a new function migration), or the rule goes in the handoff for S1.11 jobs.

### 8. LOW: smaller points

- **Company of `iam.*` entries:** the change-log entries written for `iam.*` events (`AuditTrail.RecordEventAsync`) have no `company_id`. A role assignment for company A is therefore invisible to an auditor limited to company A.
- **History without a resource:** the history of the five resource-less entity types (finding 4) needs `aud.changes.view` but is not limited by company.
- **Repeated sign-in failures:** they are `info`. Ruling Q7 says "warning for lockouts and repeated failures", but only the lockout is a warning. S1.11 alerts could cover "repeated".
- **CSV export:** it neutralises `=`, `+`, `-` and `@` at the start of a value, but not a leading tab or carriage return (OWASP lists both). The affected columns are server-chosen, so the risk is small.
- **Register rows (fixed):** the rows R-013 and R-014 in `docs/registers/risks-and-changes.md` had the resolution text merged into the "Raised by" cell ("S1.0 Resolution: …"). Repaired, with the text moved to the decision column.

## Checked and found correct

- **Same transaction (KRN-AUD-01):**
  - EF saves write their entries in `SavedChangesAsync`, before commit, in the caller's transaction or in one the interceptor opens.
  - The synchronous `SaveChanges` is refused.
  - Hand-written identity and access writes call `AuditTrail` inside their transaction.
  - Tested: rollback leaves no entry, and a failed audit write rolls back the change.
- **Append-only storage (Q1, P1, CR-031):**
  - The functions are `security definer` with `search_path = pg_catalog, pg_temp`. All names are schema-qualified.
  - `app_rw` and `app_audit` have EXECUTE only. INSERT is revoked from `app_audit`.
  - Updates, deletes and truncates are refused for both logins (tested).
- **Hash chain (Q2, P2, P3, CR-032):**
  - One advisory lock per customer database, and the head is read under it.
  - `occurred_at` is strictly increasing. Entries more than 5 minutes ahead of the database clock are capped, with a warning event.
  - The verifier rebuilds the canonical text from the stored columns in the application, so a changed function cannot hide a changed row.
  - It checks every hash, every link, each day's anchor and the control-plane copy.
- **Control-plane copy (CR-027, P5):** the copies are written once (update and delete are refused by trigger), and a mismatch is a critical event in both places. The "which days" defect is finding 2.
- **Per-person keys (R-21, Q5):**
  - Each key is wrapped by the customer field key, with a purpose bound per table and field.
  - Destroying a key overwrites its bytes and is recorded as a critical event. The chain still verifies after erasure (tested).
  - Salary uses the customer key; `enc`/`hmac` columns are never copied.
- **Access log (Q6):**
  - One row per answer that shows salary, personal or restricted fields unmasked, written before the answer leaves.
  - Masked and hidden fields write none (tested).
  - Decrypted history views and every export are logged.
- **Source and correlation (Q8):** both are decided by the server and never read from the request. The `X-Correlation-Id` answer header is set.
- **Tenancy:** audit endpoints read only the host-bound customer's database, and the isolation suite probes all seven (`AuditProbe`). No `tenant_id` was added to a business table.
- **Module boundary (D-10):** the kernel reaches HR only through `IWorkforceDirectory` and the generated resource catalogue. Architecture tests pass.
- **Other rules:**
  - The injected clock is used in application code. The database clock is used only inside the functions (CR-032) and for the static tamper recorder, as documented.
  - All 22 audit text keys exist in both `audit.en.json` and `audit.ur.json`, and every `errors.audit.*` key the code uses is among them. No new package was added.
