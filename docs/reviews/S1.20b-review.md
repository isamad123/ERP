**Summary for the product owner.** The employment services are careful work. A hire, a change and a user link check the
permission, the data scope and field security, and each runs in one transaction that holds a lock on the employment row. The
events are the record, and the job-details rows are rebuilt from them in stages, so the database rule "no two rows on one day"
is never broken. A finished event cannot be edited: the database refuses it. The backdated change check flags periods and never
refuses a change, as CR-096 requires. The whole test suite passes at `0739d5b`. Two high points must be fixed before the merge:
- **an approval can be side-stepped.** With the default settings a promotion waits for a second HR person, but the same change
  recorded as a "data correction" applies at once, with nobody else involved;
- **a second correction can bring back the date the first one removed.** When a correction moves an event into the future and
  is itself corrected, the original event counts again, and the job history is silently wrong.

Three medium points need a fix or your ruling: a backdated change can alter job details in a branch the user may not touch;
the timeline shows job details that field security hides; and an HR administrator can link their own user to another person's
employment and then act as that employee or as that employee's manager. The seven low points can wait.

## Findings, most severe first

### 1. HIGH: a "data correction" changes job details without the approval the customer configured (FR-XM-32, ruling Q11)
- `src/Modules/Hrm/Erp.Hrm.Infrastructure/Employments/EmploymentService.Changes.cs:183-186` accepts a `data_correction` with no
  `correctsEventId` as long as it changes something, and `AssignmentDelta` (`EmploymentService.cs:354`) lets it set every job
  field: unit, branch, title, grade, manager, cost allocation. `NeedsApprovalAsync` (`:267`, `:396-400`) looks only at the kind
  that was typed. The default of `hrm.employment_events.approval_kinds` (`Settings/settings.yaml`) is promotion, demotion,
  transfer and grade change, so `data_correction` applies at once. The same is true of a correction that names an approved
  promotion: it can replace the approved title or grade with another one, and nobody approves the new values.
- Failure scenario: approval of promotions is on (the default). An HR administrator wants to promote a colleague, or
  themselves, without the second HR person. They post `{kind: "data_correction", reasonCode: "entry_error", effectiveDate: today,
  assignment: {title: "Manager", gradeId: G7}}` to `/api/hrm/employments/{id}/events`. It is effective at once and raises
  `hrm.employee_changed`. The approval route never starts. Correcting an approved promotion from grade G5 to G9 works the same way.
  This undoes the second-person rule that the setting and its `requires_approval: true` were meant to protect. `acting` and
  `secondment` can also move unit and branch outside the default list, but those are kinds the customer can choose to list;
  a correction cannot be listed without holding every correction (employee type, dates) as well.
- **Fix:** decide approval on what the event changes, not only on its label. (a) A correction that names an event needs
  approval when the kind it finally replaces (`corrects_kind`, `RootKind`) is listed. (b) A correction without a target may
  change employment fields only (`employment` section, ruling Q2). Job details change through a kind, or through a correction of
  the event that set them. Refuse `assignment` on an untargeted correction, or treat it as needing approval whenever any
  assignment kind is listed. Add tests: an untargeted correction with a title is refused (or held), and a correction of an
  approved promotion waits for the route.

### 2. HIGH: correcting a correction that is still in the future brings back the event the first correction replaced
- `EmploymentApplier.cs:122-131` (`SetApplied`) cancels the event a correction replaces when that event is `approved`, meaning
  dated in the future. `EmploymentTimeline.cs:59-60` (`Replaced`) counts only the targets of **applied** corrections. When the
  target is itself a correction that is still `approved`, cancelling it also ends its replacement of the event it corrected.
  That earlier event, if it is already `effective`, counts again.
- Failure scenario: a promotion to "Manager" is effective from 1 November. HR finds that it should start on 1 January and records
  correction C1 (dated in the future, so `approved`). Today the record shows "Officer", which is correct. HR then corrects C1 to
  1 December with C2. C1 is cancelled, the promotion is no longer "replaced", and the plan has the promotion from 1 November
  again. The as-of read for today says "Manager" again, the assignment row from 1 November is rebuilt, and
  `hrm.employee_changed` gives later payroll the wrong history. The promotion can now also be corrected directly a second time
  (`AlreadyCorrected` no longer sees it). The throw-away test above confirms this with the real `SetApplied` and `Plan`.
- **Fix:** make replacement follow the chain. A correction keeps replacing its target when it is applied **or** when it is
  itself replaced by a correction that counts. In `Replaced`, walk from each applied correction through `CorrectsEventId` and
  include every link. Alternatively, never cancel a target that is a correction: the later correction replaces it through the
  chain. Use the same rule in the handler's check (`EmploymentEventHandler.cs:59-63`) and in the timeline's `replacedBy`
  (`EmploymentService.Reads.cs:61-62`). Add a unit test for this chain and one for a chain whose root is approved.

### 3. MEDIUM: a backdated change alters job details after its date without a scope check on them
- `EmploymentService.Changes.cs:244-258` checks the data scope of the row in force on the earliest day (`before`) and of the
  row in force on the event's date (`after`). Field security is checked on `before` only. A change carries forward until a
  later event sets the same field (`EmploymentTimeline.Plan`), so it also rewrites the later rows. Those rows may be in another
  branch or unit, and none of them is checked.
- Failure scenario: an employee worked in branch A and was transferred to branch B on 1 June. An officer whose role is limited
  to branch A records an `acting` (or a correction) dated 1 March with a new title or manager. Both checks pass: on 1 March the
  employee was in branch A. The planned rows from 1 June, which are in branch B, now carry the new title or manager. The
  officer has changed a branch-B record they cannot even read, against "data scope before and after every write" and CR-076
  detail l.
- **Fix:** after planning, compare the planned rows with the stored ones (as `SyncRowsAsync` does) and, for every row that is
  added, removed or changed, check the read (or update) scope of both the stored and the planned row. Check field security on
  each such stored row as well. Add a test with a branch-limited role and a later transfer.

### 4. MEDIUM: the timeline and the generated event list show job details that field security or the permission hides
- `EmploymentService.Reads.cs:79` returns each event's `changes` whole. It holds the assignment values (title, grade, manager,
  cost allocation), the employment fields and the impact report, and it is shaped only by the field catalogue of
  `hrm.employment_events`. The generated `GET /api/hrm/employment-events` returns the same column
  (`Erp.Hrm.Api/Generated/EmploymentEventEndpoints.g.cs:99`). The as-of read (`:35-39`) shows the assignment only with
  `hrm.employment_assignments.read` and the assignment row's scope, and leaves out the fields hidden for the role.
- Failure scenario: as in `FR_KRN_IAM_13_a_field_hidden_by_the_role_...`, a role has `title` (or `grade_id`, or
  `cost_allocation`) of `hrm.employment_assignments` hidden, and also has `hrm.employment_events.read`. The as-of read hides the
  title, but `/timeline` shows it in `changes.assignment.title` for every event. A role with event read and no assignment read
  sees every past and future job detail. This breaks FR-KRN-IAM-13, and with S1.34 onward, when salary revisions become events,
  the same path would show pay.
- **Fix:** shape `changes.assignment` with the field map of `hrm.employment_assignments` (and `changes.employment` with that of
  `hrm.employments`), and leave `changes.assignment` out without `hrm.employment_assignments.read`. Do the same for the generated
  read: give `changes` a field class or close its generated read, and serve events only through the timeline. Add the timeline
  to the existing field-security test.

### 5. MEDIUM: a holder of the link permission can link their own user to someone else's employment
- `EmploymentService.Reads.cs:104-153` (`LinkUserAsync`) checks that the user exists, is not a system user and is not linked to
  another person. It does not stop the caller linking **their own** user, and no second person is involved. The user link
  decides who is "the employee" (own scope, the employee excluded as approver) and who is "the line manager"
  (`HrmApproverDirectory`, R-220).
- Failure scenario: an HR administrator (the baseline HR Admin role holds `hrm.employments.link_user`) whose own user is not yet
  linked links it to the employment of a team's manager. From then on, line-manager routes for that team resolve to the
  administrator, who approves their leave and attendance requests as their manager (S1.28 onward), and the "own" scope gives
  them that manager's self-service record. This bypasses the spirit of FR-XM-32, as finding 3 of the S1.20a review did for merges.
- **Fix:** refuse linking `actor.UserId` (and, ideally, linking a user who already holds roles to an employment of a person
  whose name or e-mail does not match), or hold a link of a user other than a new one for a second person (maker-checker,
  `IHeldChanges`). Add a test.

### 6. LOW: the daily job changes events without the employment lock, and event and assignment row versions never move
- `EmploymentEventsDueJob.cs:155-168` updates an event's status and the employment without the `for update` lock that the
  change service and the approval handler take (`EmploymentService.Changes.cs:51`, `EmploymentEventHandler.cs:51`).
  `SetApplied`, the handler, the job and `SyncRowsAsync` change `hrm.employment_events` and `hrm.employment_assignments` rows
  without increasing `row_version`, although the column is a concurrency token (`EmploymentEventPersistence.g.cs:36`,
  `EmploymentAssignmentPersistence.g.cs:41`).
- Failure scenario: the job makes an approved event effective while HR records a correction that cancels it. The trigger
  `tg_employment_events_fixed` refuses the loser, so nothing is corrupted. But the job fails its chunk and retries, or HR gets
  a generic refusal instead of a clear answer. Clients and later slices that rely on `rowVersion` of these rows see version 1
  for rows that have changed.
- **Fix:** take the employment lock in the job before reading its events, and increase `RowVersion` wherever these rows change
  (or make `Stamp` do it).

### 7. LOW: two rules hold under the employment lock only, so two simultaneous requests can break them
- "One human per user" (`EmploymentService.Reads.cs:137-147`) and the reporting-cycle trigger
  (`V202611151218__hrm__rules_s1_20b.sql`, `tg_employment_assignments_manager_cycle`) each read other employments' rows that the
  caller has not locked.
- Failure scenario: two administrators link the same user to employments of two different persons in two companies at the
  same moment, or set A's manager to B and B's manager to A at the same moment. Each transaction sees nothing wrong and both
  commit.
- **Fix:** take a transaction advisory lock on the user id in `LinkUserAsync`. For the cycle, lock the manager's employment row
  (`for share`) before the change, or record the rare race in the register with R-221.

### 8. LOW: the line-manager answer mixes companies
- `HrmApproverDirectory.cs:28` finds the employee's employments by `user_ref` in every company. A person with current
  employments in two companies (one link per company is allowed, ruling Q8 and detail p) gets the managers of both, whatever the
  document's company.
- **Fix:** the kernel contract `ManagersAsync` has no company. Add one (contract change, CR) or record it for S1.20c, when
  transfers make overlapping employments ordinary.

### 9. LOW: an approval applies the event without the checks of the change service and with the impact report of record time
- `EmploymentEventHandler.cs:58-77` re-plans, but does not repeat `PlannedProblemAsync` (the manager may have left since), the
  scope checks of finding 3, or the backdated change check. The report kept in `changes.impact` is the one made when the event
  was recorded, possibly weeks earlier, before a payroll period was locked.
- **Fix:** run the manager check and the impact check again in the handler, and store the new report (the event is still
  `pending_approval`, so the trigger allows it) or raise it with `hrm.employee_changed`.

### 10. LOW: employment-field corrections are not checked against each other
- `EmploymentService.Changes.cs:338-341` accepts any `serviceStartDate`. A correction of the hire can move the joining date after
  the confirmation date (`EmploymentApplier.ApplyEmploymentFieldsAsync`, `:150-160`), which BR-02 forbids for a confirmation.
- **Fix:** after applying, refuse a confirmation date before the joining date, and a service start date after it unless a rule
  says otherwise (S1.20c carry-over).

### 11. LOW: the daily job can leave one company's due events for a day behind another company's events that are not yet due
- `EmploymentEventsDueJob.cs:135-153` takes 400 approved events up to UTC tomorrow, ordered by date and id, and skips those not
  yet due in their company's time zone. If more than 400 skipped events share the earliest date, no event is moved, the loop
  ends (`moved < Chunk`), and due events of other companies wait for the next daily run.
- **Fix:** filter by date per company in the query (join the company's zone), or keep paging past skipped events.

### 12. LOW: test gaps against the slice's acceptance list
- No test shows that the **employee** (a linked subject) cannot approve their own change; the approval test covers the
  requester only. No test covers the subtree scope (Acceptance: "own, team, subtree, company"). No test covers a correction of a
  correction (finding 2), an untargeted correction with job details (finding 1), or the timeline under field security
  (finding 4).
- **Fix:** add them with the fixes above.

## Checked and found sound
- Staged row sync (`EmploymentApplier.SyncRowsAsync`): removed rows are deleted first, kept rows that shrink or change are
  saved second, and rows that grow and new rows are saved last. The planned rows do not overlap, and a growing row's old range
  lies inside its planned one, so the non-deferrable exclusion constraint never sees an overlap at any statement. A middle
  change splits a row, and fields carry forward until a later event sets them (unit test and EMP AC test).
- FR-XM-05: `tg_employment_events_fixed` refuses any change to an approved, effective or cancelled event except approved to
  effective or cancelled, and any delete except of a draft. Corrections are new events with `corrects_event_id` (composite FK
  within the company, indexed). Employments are never deleted, and the employee number is unique per company, so it is never reused.
- FR-XM-32 for listed kinds: the event is `pending_approval` until the route decides, the requester is refused by the engine,
  the employee's user is passed as a subject, the decision runs on the deciding transaction under the employment lock, and a
  problem rolls the decision back (`WorkflowException`). Changing `approval_kinds` and the route both need a second person.
- Hire: permission and override permission first, scope and field security of the company before anything is saved, the
  employee number taken before the transaction (gap allowed, R-224), the seat taken through `ILimitGuard` on the hire's
  transaction (pre-joining counted, so a future hire cannot pass the limit later), `hrm.employee_hired` with ids only, and the new
  person and employment in one transaction (R-111 closed). The partial unique index backs "one current primary employment".
- Database rules: the cost allocation trigger checks exactly one target per share, a department of the assignment's company,
  shares in (0, 1] summing to exactly 1. The reporting-cycle trigger first checks reachability across all dates (cheap
  rejection), then only the dates where the chain's rows start inside the new row's range. Its cost on long histories is
  recorded as R-221.
- Generator: functions and implemented rules of HR schemas go to the HR migrations, which are new files, so frozen ones are
  untouched. `asOf` is added to every effective-dated list. All effective-dated `valid_from/valid_to` ranges in the migrations
  are `[)`, so the filter `valid_from <= d and (valid_to is null or valid_to > d)` is right for each of them.
- Changed tests keep their intent: the two numbering tests still prove the number comes only from the service (now through
  the hire), that a typed number needs the override, and that nothing can change it later. The generator tests count two fewer
  placeholders and name the two rules implemented. `RowFactory` gives a valid cost allocation.
- Tenant isolation: all eight new routes carry `HrmEndpointMetadata`, and `HrmProbe` has a target for each. The isolation suite
  passes. No `tenant_id`, the tenant comes from host and token only, the business date comes from the injected clock and
  `org.time_zone`, and SQL is parameterized.
- Kernel boundary: `IUserDirectory` returns a boolean about ids only (D-10). The HR module reads no kernel table.
- Scope discipline: nothing beyond Build items 5 to 10. Rehire, transfers between companies, probation, separation and screens are
  left to S1.20c, S1.25 and S1.21 as the slice says.

## Verdict
**Not ready to merge.** Fix findings 1 and 2 (high), and fix findings 3 to 5 or have the product owner rule on them. Then
rerun the full suite and CI, and add the tests of finding 12. Findings 6 to 11 are low. They can be fixed now or recorded with
an issue id for S1.20c or S1.21.
