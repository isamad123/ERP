## Summary for the product owner

The core promise of the slice holds: **nobody can approve their own request**. I tried to get around it and could not:
- The requester and the people a request is about are kept out of every task: not as the person named, not from a role's
  queue, not by passing the task on. The database refuses it too, even when someone writes to it directly.
- Two people deciding at the same moment cannot both win; the test really sends the decisions at once.
- A request is never approved without a decision by someone else; when nobody can be found it waits for an administrator.
- Every decision is written to a history that cannot be changed afterwards, with who, when and why.
- Each customer's requests stay in that customer's database; the isolation suite probes every new endpoint.

I found **no high-severity defect**. I found **three medium issues**, each proven with a test on the real database:

1. **Someone allowed to edit routes for one company can change the route for every company.** Approval routes are one per
   document type for the whole customer (ruling Q10). The check only asks "may this person edit routes anywhere?". A
   person whose right is limited to company B can therefore change, or switch off, the leave route of companies A and C
   too. Switching it off stops everyone from sending new requests of that type (ruling R3). No standard role is affected
   today (only Tenant Admin may edit routes, for all companies); it needs a custom role. The second-person approval for
   sensitive routes already asks for "all companies"; the first person should too.
2. **A route can name people who are not allowed to decide, and it is still accepted.** The activation check asks only
   "does this role have a holder?" and "is this user active?". A route that sends requests to, say, the Auditor role (or
   to a named person without approval rights) is activated. Each request then sits in a queue that its holders can see
   but cannot take or decide. It is never approved automatically, but nobody can approve it either until it escalates.
   The same gap lets a step be skipped "because a later step has someone else to decide" when that someone cannot decide.
3. **The engine does not check who sends a returned request back.** After an approver returns a request for correction,
   the module sends it back with the corrected values. The engine accepts this from anyone. If a module lets the approver
   edit the document (an HR officer correcting a claim, for example), that person can resubmit it with values they chose
   (in my test, the amount changed from 50 to 99,999) and then approve it alone. Your ruling Q7 says the requester
   corrects and resubmits; the engine should hold the module to that. **This needs your decision** (see finding 3).

There are also **five low items**. One of them, finding 4, is a claim in the S1.10a handoff that is not true: a module
that forgets its outcome handler is not caught when the host starts; its requests fail only at the final approval.

I recommend fixing findings 1 to 3 before the first HR slice uses the engine (S1.20 leave). Each is a few lines of code
and a test.

## Findings, most severe first

### 1. MEDIUM: route editing checks "any company", but a route applies to every company

- **Where:**
  - `src/Platform/Erp.Kernel.Api/Workflow/WorkflowEndpoints.cs:50-66`: new draft, edit draft, activate and deactivate run
    through `RunAsync(p, WorkflowPermissions.RoutesUpdate, …)`, which is `IPermissionChecker.HasPermissionAsync`.
  - That is `AccessSnapshot.Holds` (`Access/AccessSnapshot.cs:150`): true when any assignment grants the permission,
    whatever its company.
  - `WorkflowAdministrationService` has no company check of its own (there is no company on a route, ruling Q10).
  - By contrast, the second person of a held activation must cover all companies:
    `AccessAdministrationService.Changes.cs:149-151` (`CoversCompanyAsync(RoutesUpdate, null)`).
- **Scenario (probe 1, passes today):** a custom role with `wf.workflow_definitions.update` is assigned to user E for
  company B only. E posts a new draft of the expense route and activates it: 201, 200. The route of every company now
  names E's approver. E then deactivates the route: 200. New requests of that type are refused in every company (ruling
  R3) until an administrator activates a route again. For a sensitive document type E cannot activate (the second person
  must cover all companies) but can still deactivate.
- **Fix:** for the four write actions, require `CoversCompanyAsync(RoutesUpdate, null)`,
  that is a grant "for all companies", as the checker already must. Reading routes can stay "any company" (Company Admin
  reads routes, ruling Q14). Answer 403 `errors.access.forbidden` otherwise.
- **Test to add:** the probe turned round: the company-limited editor gets 403 on draft, edit, activate and deactivate;
  a Tenant Admin still succeeds.

### 2. MEDIUM: a route may name approvers who cannot decide; activation accepts it and requests reach nobody who can

- **Where:**
  - `WorkflowAdministrationService.cs:321-345` (`SpecProblemAsync`): a named user must be active; a role must exist and have
    a holder. Neither check asks whether that person or role may decide: `wf.workflow_tasks.update` and the document
    type's own `decide_permission`, for the request's company (`WorkflowEngine.CanDecideAsync`, `WorkflowEngine.cs:724-726`).
  - `WorkflowEngine.cs:178-183` (`AdvanceAsync`) assigns the task to whoever the step names, with no decide check.
  - `WorkflowEngine.cs:235-247` (`LaterStepDecidableAsync`): "a later step will be decided by someone else" counts any
    person found, including people who cannot decide. So a step whose only approver is the requester is skipped in favour
    of a later step that nobody can decide.
- **Scenario (probe 2, passes today):** a route whose only step is the role `auditor` is activated (the role has a holder).
  A request is started; its queue task is shown in the auditor's inbox; the auditor's claim answers 403
  `errors.workflow.no_decide_permission`. The request stays `running` with no one able to decide it. It is not approved
  automatically (FR-XM-32 holds), but it waits until escalation (S1.10b) moves it up, or an administrator reassigns it.
  The same happens with a named user or a document user field naming someone without approval rights, and with a
  document type whose own decide permission (for example `hrm.leave_requests.approve`) the role does not grant.
- **Fix (needs a ruling because it adds to the activation check of ruling Q10, CR-059):**
  - Activation check: a named user must hold the decide rights for at least one company; a role must grant
    `wf.workflow_tasks.update` and the type's `decide_permission` (role rules, not people); refuse with a new key
    `errors.workflow.approver_cannot_decide` naming the step.
  - At run time: treat people who cannot decide the request's company as "not found" (so the fallback, moving up and
    "cannot assign" apply), and use the same test in `LaterStepDecidableAsync`. A role queue stays one task; it is only
    created when at least one eligible holder can decide.
- **Test to add:** activation refused for an auditor-role step and for a named user without rights; a document-user step
  naming a person without rights goes to the fallback; a requester-only first step is not skipped in favour of a step
  nobody can decide.

### 3. MEDIUM (needs a product-owner decision): anyone can resubmit a returned request, and may then approve it

- **Where:** `WorkflowEngine.cs:119-161` (`ResubmitAsync`). It checks that the request is `returned` and that the values
  are valid, then restarts the route. It does not check who calls it: the caller is recorded in the history
  (`resubmitted`, actor) but is neither required to be the requester nor added to the people kept out of the request
  (requester and subjects are fixed, by design and by the database trigger `tg_workflow_instances_parties_fixed`).
- **Scenario (probe 3, passes today):** the requester claims 50; the approver returns it ("fix"); the approver, through the
  module, resubmits the document with amount 99,999; the request restarts with the approver as the only step's approver;
  the approver approves; the request is `approved`. One person both wrote the values and approved them.
- **Rule:** FR-XM-32 "nobody approves their own request". Ruling Q7: "the module lets the requester correct the document
  and resubmit". The kernel contract says "the requester is the signed-in user" for `StartAsync`, but says nothing for
  `ResubmitAsync` (`WorkflowContracts.cs:30-36`). Today no module calls it; the first will be S1.20 (leave).
- **Options:**
  - (a) *Recommended:* only the requester may resubmit; anyone else gets `errors.workflow.not_requester` (403). Simple, and
    matches Q7 exactly. A module where HR corrects on an employee's behalf would start a new request instead.
  - (b) Anyone the module allows may resubmit, but a resubmitter other than the requester is then kept out of that
    request's decisions. This needs a new column (the people kept out for this round) and so a data-design change (CR).
- **Test to add:** for (a), a resubmit by the approver is refused and the request stays `returned`.

### 4. LOW: a missing outcome handler, or a wrong manifest, is not caught when the host starts

- **Where:** `WorkflowRegistration.cs:18` registers `WorkflowCatalog` as a lazily built singleton; nothing resolves it at
  start (`ApiHost.cs`, `WorkerHost.cs`). The handoff says "checked at host start". `WorkflowEngine.cs:767-768` throws
  `InvalidOperationException` when no `IWorkflowOutcomeHandler` exists for the document type.
- **Scenario:** an HR slice registers its `workflow.json` but forgets its handler. Requests start, are routed and decided
  step by step, and every **final** decision answers 500 and is rolled back. The request can never end. A wrong manifest
  fails the first workflow call (500) rather than the host (the migrator's `WorkflowSetup` does parse the folders).
- **Fix:** resolve the catalogue at host start (API and worker), and refuse there when a registered document type has no
  outcome handler (or two). Correct the handoff line.

### 5. LOW: "sensitive" is copied into the route once; a later change of the document type is not honoured

- **Where:** `WorkflowSetup.cs` copies `requires_approval` into `wf.workflow_definitions` when it first creates the route;
  `WorkflowAdministrationService.cs:166` reads only `definition.RequiresApproval`.
- **Scenario:** a later release marks a document type sensitive in its manifest (for example a loan type). Customers whose
  route was seeded earlier keep `requires_approval = false`, and its routes are activated by one person.
- **Fix:** require maker-checker when either the definition or the document type says so
  (`definition.RequiresApproval || type.RequiresApproval`). Stricter, no data change.

### 6. LOW: the generated read endpoints show tasks and requests of an unlicensed document type

- **Where:** the generated `GET /api/wf/workflow-tasks` and `GET /api/wf/workflow-instances` (read-only since CR-041)
  filter by data scope only. Ruling Q11: "Document types of an unlicensed module are not offered and their tasks are not
  shown"; the engine's own endpoints honour it (`LoadAsync`, `LicensedTypesAsync`).
- **Scenario (probe 4, passes today):** a running request of `test.unlicensed` (a module whose licence ended) is hidden from
  the approver's inbox, but its task is listed by `GET /api/wf/workflow-tasks`, and the request with its frozen values
  by the requester's `GET /api/wf/workflow-instances`. Only the caller's own rows are shown (scope own), so nothing of
  another person leaks.
- **Fix:** either leave it (own data only) and say so in the contracts register, or close the generated reads for
  non-administrators and serve "my requests" and the inbox only. *Recommendation:* record as accepted (R-049).

### 7. LOW: withdraw and a module's resubmit lock in opposite order (possible deadlock)

- **Where:** a decision or withdrawal locks the request (`WorkflowEngine.cs:641`, `:664`) and then the module's outcome
  handler updates the document. A module's save locks its document first and then calls `ResubmitAsync`, which locks the
  request (`WorkflowDb.cs`, `OpenInstanceAsync … for update`).
- **Scenario:** the requester presses "withdraw" and "resubmit" at the same moment (two tabs). PostgreSQL detects the
  deadlock and cancels one; that call answers 500 instead of 409. Nothing is half-written.
- **Fix:** in `ResubmitAsync` and `StartAsync` this order is the module's; document it in the contract ("lock the request
  through the engine before the document", or "the engine may answer `errors.workflow.busy`") and map SQLSTATE 40P01 to a
  409 in the workflow endpoints. Risk R-050 until the first module exists.

### 8. LOW (question): money conditions compare amounts without their currency

- **Where:** `RouteFormat.cs:641-644`: a `money` field is compared as a plain decimal.
- **Question:** a route "above 100,000" treats PKR 100,001 and USD 100,001 alike. Is a money field always in the company's
  currency (the module converts before sending), or should a money value carry its currency? *Recommendation:* state in
  the contracts register that money values are sent in the company's base currency (R-051), and revisit with expenses.

## Checked and found correct

- **Nobody approves their own request (FR-XM-32, KRN-WFL-09, HRM-ROL-04, ruling Q6):**
  - Requester and subjects are removed from every step's approvers (`AdvanceAsync`), from claims (`ClaimAsync`), from
    deciding (`CapacityAsync`), from reassignment targets (`ReassignCoreAsync`), from the administrator path
    (`DecideAsync`) and from the inbox SQL.
  - Database: `tg_workflow_tasks_no_self_approval` refuses an assignee or a decider who is the requester or a subject on
    insert and on update of `assignee_user_id`, `acted_by`, `instance_id`; `tg_workflow_instances_parties_fixed` stops a
    change of requester or subjects. The test writes as the database owner and is refused (`WorkflowEngineTests.cs:140`).
  - A route always reaches someone: ruling R2 is checked on save, activation and the module's default route; the last
    applying step always opens a task (a person, the manager one level up, the fallback, or "cannot assign"), so
    `no_step_applies` cannot be reached. Never auto-approved, never auto-rejected.
- **Concurrency:** every decision locks the request, then the task, in one order (`OnTaskAsync`), so two decisions on one
  task, or on two tasks of one step (ruling R1), run one after the other; the losers get 409. The test fires four
  decisions at once, three times. Route activation locks the definition, then the version; the held activation is
  validated (same order) before it is applied in the same transaction. Starts of one document wait on an advisory lock
  (the unique index of R-023 is S1.11f2's work).
- **Transactions (ruling Q11):** `StartAsync` and `ResubmitAsync` run in the module's transaction; the outcome handler runs
  in the deciding transaction, and a refusal by the handler rolls the decision back (tested). Events go to
  `wf.outbox_messages` in the same transaction; change-log entries of `wf.*` rows are written before commit.
- **Versions (KRN-WFL-10, ruling Q10):** running requests keep their version (resubmit too); an active version is
  frozen; activation retires the old version; the held activation is void when the draft changed (row version).
- **Maker-checker (ruling Q10):** requester and approver must differ (S1.06 rule); the approver must hold
  `wf.workflow_definitions.update` for all companies; the route is re-checked at approval.
- **Conditions (ruling Q5):** money and numbers are exact decimals (no floating point); a value of the wrong type never
  matches; values are frozen in `context`; the company field must equal the request's company; subject fields add to
  the subjects at start and must stay within them at resubmit.
- **SQL:** every value is a parameter. The only built SQL text is constant: the inbox filters (`Filter` puts `$n` in
  constant clauses) and `DelegationCovers` (placeholders only).
- **Tenant isolation:** everything runs on the host-resolved customer's data source; the catalogue and the licence cache
  hold no customer data across requests (`_licensed` lives in a scoped service). `WorkflowProbe` sends B's host and token
  at A's ids for every new endpoint, checks 404, no leak, A's database unchanged, then a positive control.
- **History:** `wf.workflow_history` is append-only in the database (update, delete and truncate triggers, S1.02) and
  ordered in the order things happened (`HistoryAsync`).
- **Generated writes closed (CR-041):** the five `wf.*` tables and `iam.delegations` answer reads only (tested).
- **Other rules:** no `DateTime.Now`/`UtcNow` in business code (the engine uses the injected clock; the role-validity date
  is the UTC date, as in the access engine); every `errors.workflow.*` key has English and Urdu text (tested); no new
  package.
