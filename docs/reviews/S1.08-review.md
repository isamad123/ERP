## Summary for the product owner

The core of the numbering service is sound:
- Gap-free series really are gap-free. 100 posts at once give exactly 1 to 100, and a post that fails gives its
  number back. Gap-allowed series never make users wait.
- A number cannot be typed in or changed through the API.
- A scheme cannot be edited after its first number.
- Every SQL statement uses parameters.
- The two S1.08 migrations are new files and were never edited afterwards.
- Company Admins are kept to their own companies.

I found **one serious defect** and **three medium ones**.

1. **Two series can print the same number, and nothing in the kernel stops it.** I proved this on the real database
   with three ordinary administrator actions:
   - **Example A.** The company scheme for service requests is `SR-{branch}-{seq:5}`, so Karachi's first request is
     `SR-KHI-00001`. Later the administrator gives Karachi its own series with the same pattern (the service accepts
     it). Karachi's next request is `SR-KHI-00001` again.
   - **Example B.** Branch codes `K` and `K1` each have their own scheme `SR{branch}{seq:3}`. Both print `SRK1001`.
     Ruling P2 said a branch scheme's numbers "can never equal another branch's".
   - **Example C.** The administrator retires `EMP-{seq:5}` and creates `EMP-0{seq:4}`. The new scheme prints
     `EMP-00001` again.

   Risk R-018 was accepted on the basis that "the documents' unique keys stop real duplicates". That is only partly
   true:
   - Contract numbers have no unique key (R-016), so a repeated contract number is saved without any error.
   - In a gap-free series (letters, leave, loans, pay runs, expense claims), a repeated number makes the post fail and
     roll back. The failed post gives the number back, so the next post gets the same number and fails too. The series
     stays stuck until an administrator steps in.

   Legal numbers must never be reused (FR-XM-06, a 1.0 rule), so I rate this HIGH.
2. **A user can take numbers in a company they have no rights in.** The generated "create" endpoints take the number
   first and check the user's company scope afterwards. I proved this: a user allowed to create employments only in
   company A sent a request for company B. The request was refused, but by then a number of company B's series had been
   used. If company B had no scheme yet, a default scheme had also been created for it, recorded as a system action.
3. **The same number can be voided twice.** This happens once a series continues under a new scheme (retire the
   scheme, then create one with the same pattern). The void report then lists the number twice. The slice's acceptance
   says a second void is refused.
4. **The void report crashes with a server error** for a company-wide scheme that uses `{branch}` (proved).

The low items are below. My recommendation for finding 1 is a set of simple pattern rules plus a unique key on
contract numbers. A complete guarantee needs a small new kernel table that records every number issued. Either way,
**this needs your decision (CR-058)**.

## Findings, most severe first

### 1. HIGH: different series can print the same number; for contracts it is saved, and a gap-free series can get stuck

- **Where:**
  - A series is identified by its company, branch, document type and exact pattern text:
    `V202611150335__kernel__functions_s1_08.sql:13-22` (`cfg.numbering_series_root`) and
    `NumberingAdministrationService.cs:235-240` (continuation).
  - Nothing compares the numbers that two different series can print.
  - `NumberingAdministrationService.cs:218-221` checks only that a branch scheme contains `{branch}`. A company-wide
    scheme may contain `{branch}` too.
  - `NumberPattern.Validate` (`NumberPattern.cs:205-251`) lets a code token run straight into `{seq}`.
- **Proved (probe tests P1, P2, P3; all three passed, which means the defect is real):**
  - **P1.** Company scheme `SR-{branch}-{seq:5}` issued `SR-<code>-00001` for branch B. Then
    `POST /api/cfg/numbering/schemes` for branch B with the same pattern returned 201. B's next number was
    `SR-<code>-00001` again.
  - **P2.** Branches `K1` (start 1) and `K` (start 1001), both with scheme `SR{branch}{seq:3}`, both gave `SRK1001`.
    This contradicts ruling P2 ("its numbers can never equal the company scheme's or another branch's").
  - **P3.** The administrator retired `EMP-{seq:5}` after it issued `EMP-00001` and created `EMP-0{seq:4}` (201). The
    new scheme's first number was `EMP-00001`.
- **Other ways to reach it, not probed:**
  - Retire a branch scheme. That branch's documents then fall back to a company scheme that uses `{branch}`.
  - Rename a branch code, then give a new branch the old code.
- **Why R-018 does not cover it:**
  - R-018 describes *different* patterns. P1 and P2 use one pattern in two series.
  - R-018 relies on the documents' unique keys, but:
    - `hrm.contracts.contract_no` has none (R-016), so the duplicate is saved without error.
    - A gap-free post that hits a unique key rolls back. The rollback returns the counter value, so every later post
      gets the same number and fails. Leave and expense claims are gap-free-capable types that have a branch.
- **Fix: choose one (CR-058).**
  - **(a) Recommended for 1.0. Pattern rules, no new table:**
    - A company-wide scheme may not use `{branch}`. A branch's own prefix comes only from a branch scheme (P2 already
      makes those contain `{branch}`).
    - `{branch}` and `{company}` must be followed by literal text whose last character is not a letter or digit
      (for example `-` or `/`), or end the pattern. Then one code cannot run into another code's digits.
    - When a retired scheme of the same company and type exists, a new pattern must differ from it in its literal
      text, not only in padding. This closes example C.
    - Add the unique key on `hrm.contracts (company_id, lower(contract_no))` now. This is R-016, brought forward from
      the contracts slice.

    The remaining exposure (code renames, deliberately chosen literals) stays under R-018, with the S1.15 warning.
  - **(b) Full guarantee. New kernel table `cfg.numbering_issued (company_id, document_type, number)` with a unique
    key, written by `cfg.numbering_next`'s caller in the same call:**
    - A collision in a gap-allowed series skips to the next number.
    - A collision in a gap-free series records an automatic void ("number already used"), so the void report explains
      the gap.
    - This is the Q10 alternative that was deferred to Phase 2. It costs one insert per number.
- **Tests to add:** P1, P2 and P3 turned around (refused, or a different number), plus a duplicate contract number
  refused by the database.

### 2. MEDIUM: the generated create takes a number (and may create a default scheme) before the company scope check

- **Where:**
  - The generator: `tools/Erp.CodeGen/Emit/CSharpEmitter.cs:662`.
  - The generated code, for example `EmploymentEndpoints.g.cs:122-123`. `AssignOnCreateAsync` runs before
    `repository.AddAsync`, which is where the data scope is checked.
  - `NumberAllocator.ResolveAsync` (`NumberAllocator.cs:153-179`) creates a missing default scheme.
- **Proved (probe P7):**
  - A user holds `hrm.employments.create`, assigned for company A only.
  - The user posts an employment for company B, which has no employee-number scheme.
  - The answer is `403 errors.access.out_of_scope`. But company B now has a new active default scheme, change-logged
    as the system, and its series has used a number.
- **Further effects:**
  - Such a user can burn another company's gap-allowed numbers in a loop.
  - A company id that does not exist answers `400 errors.numbering.company_unknown` instead of 403, so the answer
    tells the caller whether a company id exists.
- **Fix:** before taking a number, the generated create checks the row against the caller's scope. The repository
  already has the scope check that `AddAsync` uses; emit it first. Alternatively, move the allocation inside `AddAsync`
  after the check.
- **Test to add:** P7 turned around (403, no scheme created, no number used).

### 3. MEDIUM–LOW: the same number can be voided twice once a series continues under a new scheme

- **Where:** `NumberVoids.cs:56-71` records the void against the scheme that matches the pattern, active scheme first.
  The unique key is `(scheme_id, number)` (`V202611150305__kernel__design_s1_08.sql:17-18`).
- **Proved (probe P5):** void `LN-2026-00001` under scheme A, retire A, create B with the same pattern, void the same
  number again. Both voids are accepted, and two void rows exist for one number. The void report (which joins all
  members of the series) lists the number twice.
- **Fix:** record the void against the series owner, `cfg.numbering_series_root(owner)`. The existing unique key then
  covers the whole series, with no database change.

### 4. MEDIUM–LOW: the void report fails with a server error for a company-wide scheme that uses `{branch}`

- **Where:** `NumberingAdministrationService.cs:139,150-151` renders the first and last number with no branch code.
  `NumberPattern.Render` throws `NumberPatternException`, which `NumberingEndpoints.RunAsync` (lines 61-88) does not
  catch.
- **Proved (probe P6):** the report threw `errors.numbering.pattern_branch_not_allowed` out of the endpoint, which is a
  500 in the real host.
- **Related:** `Validate` counts the branch code as 0 characters for a company-wide scheme (`ApplyAsync` line 211). A
  long branch code can therefore pass validation and then fail at run time with `number_too_long`, after a number was
  taken.
- **Fix:** rule (a) of finding 1 removes the case. Otherwise, catch `NumberPatternException` in `RunAsync` and print
  the running values when there is no branch.

### 5. LOW: allocator robustness

- **Second scheme change.** A scheme changed twice during one allocation raises the raw `ER801` `PostgresException`
  (500). The retry is guarded by `attempt == 0` at `NumberAllocator.cs:42,74,90`.
- **Gap-free: failure after the counter moved.** If rendering fails after the counter has moved
  (`number_too_long`, unknown branch), the `NumberingException` leaves the savepoint `erp_numbering` neither rolled back
  nor released (lines 84-97). A caller that catches the error and still commits leaves a gap in a gap-free series.
  Roll back to the savepoint on any exception.
- **Gap-free: stricter isolation.** In a caller's transaction at REPEATABLE READ or SERIALIZABLE, concurrent gap-free
  posts fail with 40001 ("could not serialize") instead of waiting up to 5 seconds. The S1.07 review found the same
  pattern for audit. Refuse such a transaction, or answer `errors.numbering.busy`.

### 6. LOW: the scheme service validates before the company scope check

- **Where:** `NumberingAdministrationService.cs:36-50`. `ApplyAsync` reads the target company's branches, settings and
  schemes, and the active-scheme check runs, before `schemes.AddAsync` checks the scope.
- **Effect:** a Company Admin of company X who names company Y gets `400 branch_unknown`, `continuation_mismatch` or
  `active_scheme_exists` instead of 403. This leaks a little information about Y's schemes and branches. I saw
  `active_scheme_exists` for the tenant-wide person scheme in probe P4.
- **Also:** `LockAsync` (lines 250-253) takes `FOR UPDATE` on any scheme row before the scoped read.
- **Fix:** check `CoversCompanyAsync(permission, companyId)` first.

### 7. LOW: smaller points

- The text of `errors.numbering.manual_in_series` says "Raise the starting number first". After first use this cannot
  be done: the start value is locked, and a continuing scheme must keep it (P1). The text should say to use a number
  outside the series. Needs S1.20/S1.21.
- `cfg.numbering_series_root` and `cfg.numbering_series_state` scan `pg_class` by name prefix on every allocation and
  every "in use" check. Each scheme and period adds one sequence, so this grows with years × companies × types. It is
  fine today (measured under 100 ms per allocation in the slice test). Note it for the 50,000-employee load test.

## Checked and found correct

- **Gap-free (invariant 6).**
  - The counter is an `insert … on conflict do update` in the caller's transaction, so a rollback gives the value back.
  - Two first posts in a new period serialize on the primary key.
  - `lock_timeout 5s` is set on the function and is mapped to `errors.numbering.busy`.
  - The scheme row is held `FOR SHARE` until commit, so an edit or retirement waits for posts in flight. The row
    version check refuses a scheme that changed after it was read.
- **Gap-allowed.**
  - One sequence per series and period, `cache 1`, created by an owner-rights function with a fixed `search_path`,
    and taken on a short connection of its own.
  - The application login cannot call `nextval` or create sequences (tested).
  - The scope key is checked against a regular expression, and names are quoted with `format('%I')`.
- **One active scheme** per company, branch and type: a unique index with `nulls not distinct … where status='active'`.
  Creating the default on first use is race-safe (`on conflict do nothing`).
- **Edit after first use is refused:** the row is locked, then "in use" is read from the series state, which covers
  continuing schemes.
- **Periods.** The business date decides the period, never the server clock; without a date, "today" is in the
  company's time zone from the injected clock. The fiscal-year label and the counter key both follow the fiscal start
  year, so changing the fiscal start month cannot repeat a number.
- **Manual numbers (Q9).** A typed number is refused when the series could still produce it, compared case-insensitively
  like the unique keys. Only `override: yes` types on gap-allowed schemes can take one.
- **Permissions and scopes.** Tenant Admin can do everything; Company Admin only for its own companies; Auditor can read
  and see the void report. A Company Admin cannot create or retire the tenant-wide person-number scheme (probe P4:
  403 and 404). No number is ever handed out through the API.
- **Tenant isolation:** `NumberingProbe` covers every new endpoint with crossed host and token, and checks A's database
  fingerprint.
- **SQL and secrets:** every value is a parameter. No secrets. No `DateTime.Now` or `UtcNow` in business code.
- **Localisation:** every `errors.numbering.*` key exists in English and Urdu. The Urdu texts still need a native
  speaker's review (handoff).
