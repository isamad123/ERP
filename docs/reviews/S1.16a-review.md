**Summary for the product owner.** The everyday path works and is well tested. A file is stored encrypted and virus-scanned before
the import reads it. The check run saves nothing. Every row is written through the same rules as the screens. A commit stopped half
way finishes without doing a row twice. Rollback is refused once a record has changed. A company administrator cannot import into
another company. Build, unit, architecture, integration and tenant-isolation tests all pass.

Three high points must be fixed before the merge:
- **an administrator can make "roll back" delete any record in the system.** The tables that keep the import's own bookkeeping
  can still be written directly through the general-purpose (generated) API, and Tenant Admin holds that right. Adding one line to a
  batch's "records created" list makes the rollback delete that record: another administrator's account, a role assignment, in any
  module, without the right to delete it. The same opening lets someone mark a batch "checked, no problems" without a check, or point a
  batch at any stored file. I reproduced the first two. Earlier engines (jobs, notifications, persons) closed these API routes; this one
  did not.
- **a 1 MB Excel file makes the server use 4 GB of memory.** An Excel file is a compressed package. A small file can unpack to
  gigabytes, and nothing limits that. One API server serves many customers, so one customer's upload can take the service down for
  the others. A second crafted file of 5.7 MB keeps the server busy for 20 seconds per read, and an upload reads it twice.
- **the template "test with a sample file" skips the virus scan** and the size and row limits. The acceptance list says an infected
  file is refused before it is read; on this path it is read. (Graded high because it is the stated acceptance rule for uploaded
  files and it opens the same parser to the memory problem above without the 20 MB setting.)

Seven medium points need a fix or your ruling:
- a template changed after the check is used for the commit, so the commit writes data that was never checked;
- rollback deletes a unit that another unit, created later, now sits under (and would do the same to a unit or location an employee
  is assigned to), and needs no "delete" right;
- a person who may see the import list but may not import users can download other people's user error files (names, e-mails);
- two rows with the same e-mail more than 500 rows apart pass the check and one fails only at commit;
- a commit that stops on an error (not a worker stop) leaves the rows it wrote, and the batch can then be neither resumed nor rolled
  back;
- the server buffers an upload of up to 200 MB in memory, two or three times over, before the 20 MB limit is applied;
- tests miss parts of the acceptance list: locations, the size limit, Excel over the limits, FR-ADM-USR-02, seats, and the
  permission refusals of the designer and the rollback.

Eight low points can wait.

## Findings

### 1. HIGH: the generated write endpoints of the import tables are open, and the engine trusts what they write

`docs/data-design/kernel.yaml:1190`, `:1203`, `:1225`, `:1242` (no `api_actions: [read]` on `itg.import_templates`, `itg.import_batches`,
`itg.import_batch_errors`, `itg.import_batch_rows`); generated `Erp.Kernel.Api/Generated/Itg/ImportBatchRowEndpoints.g.cs:61`,
`ImportBatchEndpoints.g.cs:90-91`, `ImportTemplateEndpoints.g.cs:76-77`, `ImportBatchErrorEndpoints.g.cs:59`; consumers
`ImportService.cs:400-410` (rollback), `:605-639` (rollback check), `ImportJobs.cs:79-90` (load), `ImportFiles.cs:101-123` (read).

The S1.16a engine decides what to delete, what to commit and which file to read from these four tables. Their generated `POST`/`PUT`
routes are still mapped (`/api/itg/import-batch-rows`, `/api/itg/import-batches`, `/api/itg/import-templates`,
`/api/itg/import-batch-errors`), and Tenant Admin holds their permissions through `itg.*` (`baseline-roles.json:49`); a custom role can
be given them too. `itg.import_batch_rows.create` is new in this branch. The slice's own data design comment says "generated writes
closed (CR-020, CR-021)", and every earlier engine closed its tables (CR-046 jobs, CR-048 notifications, S1.20 persons).

Failure scenarios:
- **Arbitrary delete (reproduced, R1).** Tenant Admin commits a one-row users batch, then `POST /api/itg/import-batch-rows`
  `{batchId, rowNo: 999, tableName: "iam.users", recordId: <another Tenant Admin>, action: "created", recordVersion: <its row_version>}`
  and the same for that person's `iam.user_roles` row, then rolls the batch back: 200, the other administrator's account is
  soft-deleted and the role assignment is hard-deleted. `tableName` is any `schema.table` of lower-case letters
  (`ImportService.Safe`), so it reaches every module schema (`hrm.*` included), with no permission of the target table, an audit
  entry of source `import`, and no check that the table belongs to the import type.
- **Forged state (reproduced, R1b).** `PUT /api/itg/import-batches/{id}` sets `status`, `okRows`, `errorRows`, `committedAt`,
  `fileId` freely: a batch with problem rows becomes "validated, 0 errors" and commits without `skipErrors`; an uploaded batch is
  committed without any check; a batch is marked `committed` so it can be "rolled back".
- **Any stored file (by reading the code).** `POST /api/itg/import-batches` with `fileId` of any clean `doc.files` row (an HR
  document, another person's attachment): the check run reads it (`ImportFiles.ReadAsync` checks only the scan status, not
  `owner_type = itg.import_batches` and `owner_id = batch`), and `errors.csv` returns its rows to the caller, outside the document's
  own access rules and access log.
- **Unchecked templates.** `POST /api/itg/import-templates` skips `ImportService.Checked` (mapping against the type, mode against
  `canUpdate`, the code rule) and can set `is_default`.

Suggested fix: `api_actions: [read]` on the four tables (regenerate; retire `itg.import_batch_rows.create` and
`itg.import_batch_errors.create`, keep the others as hand-written codes only if a service needs them), a CR entry as for CR-046. Defence
in depth: rollback deletes only records of tables the type's writer declares (`org.org_units` and `org.org_unit_links` for units, the
type's table otherwise); `ImportFiles.ReadAsync(batchId, fileId)` refuses a file whose owner is not that batch. A test per route that
it is gone.

### 2. HIGH: no limit on what an Excel file unpacks to, and the counting runs in the request

`ImportFileReader.cs:114-149` (`Open`), `:29-48` (`Rows`), `:152-165` (`CountRows`); `ImportService.cs:309-321` (upload counts the
rows in the HTTP request); `ImportJobs.cs:170-171`, `:325` (check and commit read the file again in the worker).

An `.xlsx` is a zip. Sylvan reads the whole shared-strings part into memory and has no limit on a cell's length; `Rows()` skips blank
rows without counting them, so `stopAfter` never stops a file of blank rows. Failure scenario (measured, see Evidence): a 1 MB file
puts 4 GB in the API host's memory for 7 seconds; two at once, or a 2 MB file, exhaust a normal container. The API host is shared by
the customers on it (D-02 separates databases, not processes), so one customer's administrator stops the service for the others. A
5.7 MB file of blank rows keeps a request thread busy for 20 seconds and is read again by every later step.

Suggested fix: before Sylvan opens an `.xlsx`, read the zip central directory and refuse (`errors.import.too_large`) when the
declared uncompressed size of the shared-strings part plus the chosen sheet exceeds a bound (for example 10 times `doc.upload.max_mb`,
at most 200 MB) or the compression ratio of any part is above about 100; count physical rows and stop at `itg.import.max_rows` plus a
margin of blank rows; cap a cell at a fixed length (for example 4,000 characters) and refuse longer ones as a row error; for CSV set
Sylvan's `MaxBufferSize`. Move the row count out of the upload request into the check job (the upload then only checks the headers).
Unit tests with a crafted shared-strings bomb and a blank-row bomb.

### 3. HIGH: the template test reads a file without the virus scan and without the size and row limits

`ImportService.cs:200-274` (`TestTemplateAsync`; `Detect` at `:217`, `Open` at `:225`), `ImportEndpoints.cs:47-53`.

The test endpoint parses the uploaded bytes straight away: no `ImportFiles` store and scan, no `doc.upload.max_mb` (only the 200 MB
form limit), no `itg.import.max_rows` (it counts every row, `:242-248`). Failure scenario (reproduced, R2): the file the fake scanner
calls infected is refused by `POST /batches` with 422, and accepted by `POST /templates/{id}/test` with 200 and `totalRows: 1`. The
acceptance says such a file "is refused before reading"; the test path is also the easiest way to send the bomb of finding 2, since
nothing is stored.

Suggested fix: run the sample through the same gate as an upload (scan through the file store with a short-lived owner, or a
scan-only call of `FileScanning` on the bytes), apply `doc.upload.max_mb` and stop reading after `MaxTestRows` rows; a test with the
infected sample and an oversized sample.

### 4. MEDIUM: a template change after the check changes what the commit writes

`ImportJobs.cs:79-90` (`LoadAsync` reads `t.mapping` from the template at run time); `ImportService.cs:121-124` (a template update
changes `mapping` in place).

The batch copies the template's `mode` at upload, "so a later template change does not alter a running batch" (data design comment),
but not its mapping. Failure scenario (reproduced, R3): a users batch is checked with `display_name` read from the `display_name`
column; a designer then points `display_name` at the `email` column; the commit stores the e-mail address as the person's name. The
rows that the check marked bad are skipped by row number, which no longer matches what the new mapping does.

Suggested fix: copy the mapping (or the template id and version, with versions kept) to the batch at upload, as `mode` is; the check,
the commit and the error file read the batch's copy. A test like R3 that the commit uses the checked mapping.

### 5. MEDIUM: rollback deletes records others now depend on, and needs no delete right

`ImportService.cs:382-416` (`RollbackAsync`), `:605-639` (`RollbackBlockedAsync`).

Q5 allows rollback "only while none of those rows changed". The check compares only each created row's own `row_version`; it does not
look at what refers to it, and the delete is plain SQL, not the table's delete rules. Failure scenarios:
- (reproduced, R6) batch 1 creates unit P; batch 2 creates unit C under P; rolling back batch 1 succeeds, P is soft-deleted, and C's
  live hierarchy link still points to the deleted P;
- by the same rule, a unit or location that an HR assignment now uses (other module, no foreign key) is soft-deleted under the
  employee; a hard delete that an in-schema foreign key refuses ends in a 500 instead of `errors.import.rollback_changed`;
- the rollback needs the type's create right only: a person without `org.org_units.delete` (or without the record's company in
  scope) deletes the records, and a holder of `itg.import_batches.read` can roll back someone else's batch.

Suggested fix: give each writer a rollback step that deletes through the table's delete rules and refuses when a live record refers
to a created one (kernel: in-schema references; modules: an `IImportRollbackGuard` in Kernel.Contracts that HR implements for
assignments); require `<table>.delete` and the record's company scope for each record; lock the records (`for update`) between check
and delete (see finding 15). Tests: R6 refused, rollback without the delete right refused.

### 6. MEDIUM: the import list readers see every type's error files

`ImportService.cs:418-429` (`GetAsync`), `:464-479` (`ErrorsAsync`), `:481-513` (`ErrorFileAsync`), `:540-541` (`MayReadAsync`).

Reading a batch needs `itg.imports.manage` and either being its creator or `itg.import_batches.read`; it does not need the type's
permission (only starting does, `StartableAsync`) and ignores the batch's company. Failure scenario (reproduced, R5): a person holding
only `itg.imports.manage` and `itg.import_batches.read` downloads another person's users error file, which holds the original rows
(names, e-mail addresses). With later types (employees, S1.21) this is personal and pay data.

Suggested fix: for a batch one did not start, also require the type's read permission (for users `iam.users.read`; better a `read`
permission declared per type in `imports.json`) and the batch's company in the scope of `itg.import_batches.read`; the same filter in
`ListAsync`. A test like R5 that answers 404.

### 7. MEDIUM: the check forgets writes older than 500 rows, so other unique values slip through

`ImportJobs.cs:208-216` (a new transaction every 500 rows); `ImportRowPipeline.cs:150-160`, `:190-195` (only the key columns are
remembered).

Failure scenario (reproduced, R4): 600 users where row 601 of the file repeats row 2's e-mail under another username. The check says
600 good, 0 problems; the commit creates 599 and records a commit-phase problem. Within 500 rows the same file is caught. The person
commits believing the file is clean, which is what the check run is for (Build item 2).

Suggested fix: declare the other unique columns per type in `imports.json` (`uniqueColumns`, users: `email`) and check them across
the whole file in the pipeline, as the key is; or keep one transaction and release each savepoint (released savepoints do not pile
up). R4 as a test that the check finds the row.

### 8. MEDIUM: a commit that fails on an error cannot be resumed or rolled back

`ImportJobs.cs:303-312` (any exception except a stop sets the batch `failed` and rethrows), `:279-291` (a later run needs
`committing` or `committed`), `ImportService.cs:388-392` (rollback needs `committed`).

Chunks already written stay (each chunk commits with its checkpoint). Failure scenario: a deadlock, a lost connection or a bug in one
writer at row 20,000 of 50,000: 20,000 records exist, the batch is `failed`, a retry of the job does nothing ("not waiting for a
commit"), and rollback is refused. FR-KRN-INT-04 asks for restart. The restart test covers only a stopped worker.

Suggested fix: on an unexpected error leave the batch `committing` and let the job's retry continue from the checkpoint; after the
last attempt mark it `failed` but keep rollback open for a failed batch with only created rows. A test with a writer that throws once.

### 9. MEDIUM: uploads are buffered whole, up to 200 MB, before the limit is applied

`ImportEndpoints.cs:21`, `:89-105`; `ImportFiles.cs:43-47`.

The form limit is 200 MB; the file is copied into a `MemoryStream` and then `ToArray()` (two copies), encrypted (a third), and only
then compared with `doc.upload.max_mb` (default 20). Failure scenario: a few concurrent 200 MB uploads hold over a gigabyte in the
shared API host before each is refused with 413.

Suggested fix: read `doc.upload.max_mb` first and set the request's `MaxRequestBodySize` (`IHttpMaxRequestBodySizeFeature`) to it;
compare `form.File.Length` with it before copying; copy once into a pre-sized buffer.

### 10. MEDIUM: tests miss parts of the acceptance list and the permission tests

`tests/Erp.IntegrationTests/ImportCentre/*`.

Not tested: the locations type (no test imports one); the size limit (`errors.import.too_large`); an Excel file over the size or row
limit (the acceptance names Excel; the row-limit test uses CSV); FR-ADM-USR-02 is cited by no test name; "seat consumption rises"
is not asserted (seats are taken at activation, `AuthenticationService.cs:395`, so the test should show the count after activation);
server permission refusals for `itg.imports.design` (template create, change), for the rollback, the error list and the error file;
a unit rollback refused after a unit changed. CLAUDE.md asks for permission tests on every new endpoint.

Suggested fix: add these tests, citing the FR ids.

### 11. LOW: formula neutralising misses tab and carriage return, and spoils re-imported values

`ImportService.cs:517-522` (`CsvCell`). A cell starting with a tab or a carriage return followed by `=` is still a formula in some
spreadsheet programs (OWASP CSV injection list). The error file is meant to be corrected and uploaded again, but `-5`, `+92300…` or
`-North` come back as `'-5`, which the import stores or refuses. Fix: also prefix `\t` and `\r`; leave plain numbers alone; strip a
leading `'` before `= + - @` when importing.

### 12. LOW: the error list loses problems at a page boundary

`ImportService.cs:476-478`. The cursor is the last row number and the next page asks `row_no > cursor`; a row with three problems
split across two pages loses the rest. Fix: cursor `(row_no, created_at, id)`.

### 13. LOW: error messages in the error file are keys

`ImportService.cs:488-489`, `:508`. The `message` column holds `errors.import.required` and similar keys, not text in the person's
language; the screen translates them, the file does not. Fix: translate with the person's language when the file is written.

### 14. LOW: `headerRow` is accepted and ignored

`ImportMapping.cs:28`. A template saved with `headerRow: 3` reads row 1 as headers (CR-072 f says only the first row is supported).
Fix: `Check` refuses any other value.

### 15. LOW: rollback runs in the request and does not lock the records

`ImportService.cs:400-410`, `:618-637`. Up to 50,000 records, each with an `information_schema` query, a company read, a delete and an
audit insert, in one HTTP request; and the records are read for the check without `for update`, so a change made between the check
and the delete is lost. Fix: lock with `for update` in the check, cache the table shape, and run large rollbacks as a job.

### 16. LOW: shipped template names carry hard-coded texts

`ImportSetup.cs:42` appends " (shipped template)" and an Urdu suffix in code (CLAUDE.md: no hard-coded user-facing strings). Fix: a
message key, or a separate `is_default` badge in the screen (which already exists).

### 17. LOW: a designer can take a future shipped template's code

`ImportService.cs:79` allows codes starting `default.`; a customer template `default.employees` created before S1.21 makes
`ImportSetup` skip the shipped one (`on conflict do nothing`). Fix: reserve the `default.` prefix.

### 18. LOW: R-095 no longer describes the code

R-095 says the check keeps one transaction from first row to last; the code restarts it every 500 rows (`ImportJobs.cs:208-216`),
which is also the cause of finding 7. Fix: update the register text with the fix of finding 7.


## Checked and found in order
