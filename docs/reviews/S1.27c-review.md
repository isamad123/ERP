**Summary for the product owner.** The sign-in part of this slice is sound. I tried every way I could think of to get a key past its checks and found none:
the customer always comes from the host name and the key is looked up only in that customer's database (a key of one customer is refused on another's
host); revoked and expired keys stop at once because the client row is read on every call; the caller's address is checked before the secret, an empty
allow list refuses everything, and a forged `X-Forwarded-For` is ignored unless the request comes from a proxy the operator listed; the secret is compared
by Argon2id in constant time; a key can reach only an endpoint that names one of its scopes, never anything under `/api/iam` and never a sign-in or
session endpoint, and inside that endpoint it has exactly its scopes and no field rights (a scope whose manifest flag is removed is gone at once). The
secret is never in an answer after the first one, a row, the change log, an event or a log line. Create and rotate wait for a second person while the
approval setting is on, and the requester can never approve their own request (FR-XM-32). All SQL is parameterized, the migration is expand-only, every
date comes from the injected clock, there is no hard-coded user text, and every new test cites its FR id.

No high finding. Two medium points should be fixed before the merge (or ruled on):
- **The usage and rate counters are counted twice when two "flushes" run at the same time.** A flush happens every minute and also every time someone
  opens a client's usage, so this happens in normal use. I reproduced it: 10 calls were recorded as 15, and the error stays for good. The usage page
  then shows wrong numbers, and with more than one API server a client can be refused with "too many requests" before it has used its limit.
- **During the grace period after a new secret is made, every call with the old secret runs the slow password check.** The quick "already checked"
  memory is looked at for the new secret first, misses, and the slow check runs before the old secret is found. I reproduced it. A connected system
  that keeps using its old secret for the grace hour (which is what the grace hour is for) can keep the server's password checker busy, so people
  signing in and other keys can get "busy, try again" errors.

Eight low points can wait or be ruled on; the most notable is that the waiting approval of a new key shows the key's scrambled form (its Argon2id hash) to
anyone who may read approval requests. That does not let anyone use the key, but the handoff says the hash is in no answer.

## Findings, most severe first

### 1. MEDIUM: two flushes at the same time add the same counts twice, and the error never corrects (Build items 12 and 13; FR-KRN-INT-07, FR-ADM-SEC-02; R-208)

`src/Platform/Erp.Kernel.Infrastructure/Access/ApiUsageRecorder.cs` lines 101 to 213: `FlushAsync` takes a copy of each client's unflushed window count
(`Local - Flushed`, line 134) and of each day's delta (line 140) under the lock, writes them to the database, and only after the commit marks them done
(`Flushed += calls`, line 179; `held.Subtract(delta)` and removal of an empty day, lines 190 to 196). Nothing stops a second flush from taking the same copy
while the first is writing. Both write it; the first then subtracts and removes the day, the second finds no day left to subtract from, so the database
keeps the double count for good. Flushes run from the minute timer (`ApiUsageFlushService`), from every usage read (`ApiClientService.UsageAsync` line 160:
two people opening usage, or one doing so while the timer fires) and from `IApiClientMeter.FlushAsync`.

What goes wrong: the usage (calls, 4xx, 5xx, refused, histogram and so p95) shown to the customer and used for limits is inflated permanently; the rate
window of the minute is inflated in `iam.api_client_windows`, so other API hosts read too many remote calls and refuse a client with 429 before it has used
its limit (and this host's `Flushed` runs ahead of `Local`, so its later calls of that minute are not written). Two further effects of the same code: a usage
read of one customer flushes every customer on the host (line 106 copies all tenants), so one administrator's page waits for, and opens connections to,
every other customer's database; and the first write of a day by two hosts at once inserts the same `(client_id, usage_date)` twice (lines 218 to 226 read
then insert, no `on conflict`), the unique key refuses the second, and that host's whole flush of the customer, windows included, is rolled back to the
next minute.

How checked: reproduced (RA).

Suggested fix: make a flush take its counts out of the live state under the lock (move the window remainder and the day deltas into the batch, so a second
flush sees nothing to write) and put them back if the write fails; or serialize flushes with one `SemaphoreSlim` per recorder (and skip, not wait, when a
flush is already running). Let `UsageAsync` flush only the current customer, or none (read the database plus this host's unflushed counts). Write the day
row with `insert ... on conflict (client_id, usage_date) do update` as the windows are. Add a test: two concurrent flushes after N calls write N.

### 2. MEDIUM: during a rotation's grace period every call with the previous secret runs Argon2id (Build item 11; FR-ADM-SEC-02; R-296)

`src/Platform/Erp.Kernel.Infrastructure/Access/ApiClientRuntime.cs` lines 124 to 147: the candidates are the current hash, then the previous one. For each
candidate the loop first asks the cache and then, on a miss, runs `hasher.Verify`. The old key is remembered against the previous hash, so for the current
hash the cache misses and a full Argon2id check (19 MiB, two passes) runs and fails on every call, before the cache hit on the previous hash. CR-115 f says
the slow check "runs once per key and host"; it runs on every call of the old key for the whole grace period (60 minutes by default, up to 7 days by the
setting's maximum).

Two things make this worse than CPU time. The hasher's gate waits synchronously (`Identity/Crypto.cs` line 76, `_gate.Wait(_maxWait)`, up to 10 seconds) on a
request thread, and `AuthenticateAsync` holds its database connection open while it waits and hashes (opened at line 93, used again at lines 160 to 163).
So a gateway that keeps pushing with its old secret during the grace hour, at up to its limit, fills the hasher's slots (as many as the server has
processors), and every other key, password sign-in and password change on the host then waits up to 10 s and gets 503; the waiting requests also hold
pool connections and thread-pool threads. R-296 says the gate "keeps the host up"; for these reasons it does not fully.

How checked: reproduced (RB).

Suggested fix: ask the cache for every candidate before any Argon2id check (`if (candidates.Any(h => cache.Matches(key, h)))`), then verify the candidates
that missed. Release the connection before hashing (read the row, close, verify, open again for the scopes and `last_used_at`), or move the hasher to an
asynchronous wait. Add a test like RB: with the hasher's slots taken, the old key in its grace period still answers at once. R-296 can then keep its current
text for wrong secrets only.

### 3. LOW: the held request of a new client or rotation shows the secret's hash to readers of approval requests (Build item 10, CR-115 h)

`src/Platform/Erp.Kernel.Infrastructure/Access/ApiClientService.cs` lines 65 to 76 (create) and 119 (rotate) put `secretHash` into the maker-checker
payload, which the generated read `GET /api/iam/maker-checker-requests[/{id}]` returns as it is (`MakerCheckerRequestEndpoints.g.cs` line 84) to anyone with
`iam.maker_checker_requests.read` in scope. An Argon2id hash of a 256-bit random secret cannot practically be reversed, so this does not open the key; but the
handoff and the test name say the secret is kept "only as an Argon2id hash in no answer", and S1.34b set the precedent of sealing held payloads with the
customer's data key (`PayHeldChanges.Seal`) so the kernel's request table holds nothing readable.

How checked: reproduced (RC).

Suggested fix: seal the hash in the payload with the data key (as `PayHeldChanges` does) and open it only in `ApplyAsync`; add the generated read to the
"no answer holds the hash" assertion of `S127c_FR_ADM_SEC_02_the_secret_is_shown_once...`.

### 4. LOW: the refusal throttle is shared by all customers on a host (Build item 11, CR-115 d)

`ApiClientRuntime.cs` lines 52 to 74 and 171: the throttle is a host singleton and the kind of an unknown-client refusal is `Unknown|-|<address>`, with no
customer in it. A refusal from an address on customer A's host in a minute suppresses the security event of the same kind from that address on customer B's
host for the rest of the minute. An attacker who sends one bad key to A at the start of each minute keeps B's audit free of its unknown-key probes. Also,
past 10,000 kinds the whole map is cleared (line 60), so callers with many addresses (IPv6) are not throttled at all.

How checked: by reading.

Suggested fix: put the customer code in the kind; evict old minutes instead of clearing the map.

### 5. LOW: the status check lets any status other than revoked and expired through (Build item 11)

`ApiClientRuntime.cs` lines 106 to 116 refuse `revoked` and `expired` and accept everything else. Today the database allows only the three statuses, but a
later status (for example a suspended client) would sign in until someone remembers this line. Sign-in code should fail closed.

How checked: by reading.

Suggested fix: refuse unless `row.Status == "active"` (keep the revoked/expired distinction for the security event).

### 6. LOW: with the flush every minute and a one-minute window, the cross-host limit is weaker than R-208 and R-299 say (Build item 12, INT-07)

`ApiUsageFlushService` flushes every 60 s by default and the read-back is of the current minute only (`ApiUsageRecorder.cs` lines 167 and 200 to 211). A host
learns another host's calls of a minute only if that host flushed earlier in the same minute; a host that has had no call this minute does not read back at
all (line 145) and starts the minute with nothing remote. A burst at the start of a minute spread over N hosts can therefore pass N times the limit, not
"one host's share" more.

How checked: by reading (the multi-host test inserts the other host's count by hand and flushes on demand, so it does not show the timing).

Suggested fix: flush every 5 to 10 s by default (`Api:UsageFlushMilliseconds`), or correct R-208 and R-299 to "up to the limit once per API host".

### 7. LOW: usage figures include refused calls in ways that skew them (Build item 13)

`ApiKeyAuthentication.cs` line 134 records a 429 with an answer time of 0 ms, so under rate limiting the histogram fills with 0 ms calls and the p95
shown drops. `ApiClientRuntime.cs` lines 161 to 164 write `last_used_at` when the key is proved, before the gate, so a call refused by scope (403) or limit
(429) shows as the last use.

How checked: by reading.

Suggested fix: keep refused calls out of the histogram (they are counted in `rate_limited`); write `last_used_at` after the gate lets the call in, or
say in the screen's help that the last use includes refused calls.

### 8. LOW: an outside address learns that a client id exists and is active (Build item 11; for a ruling)

The allow list is checked before the secret (as CR-115 f rules, to keep Argon2id away from strangers) and answers 403 where every other refusal answers 401
(`ApiClientRuntime.cs` lines 118 to 122, `ApiKeyAuthentication.cs` line 72). Anyone who has seen a client id (it is shown in the console, the change log and
the security events) can learn from any address whether it is still active. The slice's acceptance asks for the 403, so this is a ruling, not a defect.

How checked: by reading.

Suggested ruling: keep it (client ids are not secrets; the secret is still needed); or answer 401 for all and keep the reason in the security event.

### 9. LOW: small text and answer points (localization, Build item 10)

`web/apps/web/src/modules/admin/api-clients.tsx` lines 71 to 73 build accessible names as `` `${t('api.usage')}: ${c.name}` ``: the colon and the order are
fixed in code, not in the message (use an ICU message with `{name}`). The 503 `errors.iam.api_key.busy` (`ApiKeyAuthentication.cs` line 73) has no
`Retry-After`, so a gateway does not know when to try again.

How checked: by reading.

## Checked and found sound

- Scheme selection: `ForwardDefaultSelector` sends only `Authorization: ApiKey ...` to the key scheme; several `Authorization` values are joined and
  fail to parse; a failed key leaves the request anonymous, so it gets no more than an anonymous caller.
- Tenant binding: the customer is resolved from the host before authentication (`UseErpTenantResolution`), the row is read through that customer's data
  source only, the `tenant` claim is the bound customer, and the verification cache cannot match across customers (each stored hash has its own salt).
- Address: `UseTrustedProxies` is the first middleware, reads only `X-Forwarded-For` (never the host), with `ForwardLimit = 1` and only the listed proxies;
  IPv4-mapped callers count as IPv4; no other code reads `X-Forwarded-For`; `X-Test-Remote-Address` exists only in the tests.
- Key lookup and compare: exact `client_id`, parameterized; Argon2id with `FixedTimeEquals`; key length capped at 200; the cache keeps only SHA-256 of
  the key and the stored hash.
- Grace, revoke and expiry: the previous hash counts only before `previous_valid_until`; grace 0 clears it; revoke and the daily job clear it; expiry is
  checked on every call, not only by the job.
- Scope: the gate refuses any endpoint without `ApiClientEndpointMetadata`, any permission not among the scopes, and every `/api/iam` path; the scopes are
  re-read on every call and kept only while flagged; the access engine gives a bound client exactly its scopes (scope all, no field rights) and a new
  request scope fails closed (no user roles for a client id); the test asserts every marked endpoint names a flagged permission outside `/api/iam`.
- Maker-checker (FR-XM-32): the kernel refuses the requester; the approver needs `iam.maker_checker.approve` and `iam.api_clients.manage`; the held
  create is checked again at approval (expiry in the past, scope flag, client id unused); a held rotation of a revoked client is refused; the secret is
  not in the held payload.
- Secret leakage: no secret in answers after the first (with `Cache-Control: no-store`), rows, change log, outbox payloads, security events or log lines;
  the web screen keeps the key in component state only and drops it on close.
- Audit: create, rotate, revoke and expire write change-log entries naming no secret or hash; a key's own writes are recorded with actor kind
  `api_client` and source `api`; refusals are security events.
- Data design and migration: expand only, new file only, standard columns, unique keys lead with the indexed foreign key, no `tenant_id`, `is_api_client`
  not null default false; generated code not edited by hand; no package added.
- Tests: every new test cites FR-ADM-SEC-02 or FR-KRN-INT-07; the changed counts in `JobScheduleTests`, `GeneratorTests`, `DataDesignTests` and
  `SettingsTests` follow the new job, settings and tables; the `IdentityTests` change narrows its count to the identity settings and weakens nothing.
