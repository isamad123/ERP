## Summary for the product owner

The sign-in work is sound where it matters most. The server side has **no high and no medium finding**:
- The refresh token never reaches page scripts. A browser receives it only as a cookie that scripts cannot read, that is
  sent only over HTTPS, only to this address and only to the sign-in paths. The server ignores that cookie unless the
  request carries the web application's own header, which another site cannot add, so another site cannot use it.
- A token in the request body is ignored for a browser, so a script cannot plant a token of its choosing.
- A failed refresh and sign-out clear the cookie. A reused (already rotated) token still ends the session.
- "Remember this browser" follows every approved rule: the password is always asked; it works only while the setting is
  above 0 and within the current number of days; it is never offered to or honoured for people whose second step is
  required because of a privileged role; a password change or reset, an MFA reset, revoked sessions, disabling,
  archiving or an administrator lock end it; only a fingerprint (SHA-256) of the browser's token is stored; each use is
  a security event; another person's or another customer's token is simply not trusted.
- The application is served only on a known customer's address, never for an unknown one, and `/api` addresses never
  get the page. The security headers forbid scripts and styles from anywhere else, framing and referrer leaks.

I found **two medium defects in the browser code** and fixed both, each with a test that failed before the fix:

1. **A crafted sign-in link could misuse the "return address".** After sign-in the person goes back to the screen they
   came from; the address is in the link (`/sign-in?return=...`). The check accepted addresses that the browser itself
   turns into another site's address (a hidden tab character, or `/.//`). Today this leaves the person on a "session
   ended" screen after a successful sign-in; any future screen that navigates the same way would open the other site
   (a classic phishing aid). The check now reads the address exactly as the browser does.
2. **A background request could keep a forgotten session alive.** The idle rule (30 minutes) works because the browser
   refreshes the session only after the person did something. But any request that met an expired access token asked
   for a refresh without that condition. Nothing polls in S1.12a, but the notification bell of S1.12b checks every 60
   seconds, so a tab left open would never have timed out. Now a refresh after such an answer happens only after
   activity; otherwise the idle warning and the end come on time.

Ten low findings are listed below. Two small ones I fixed as well (a missing test, and the e-mailed link's secret left
in the address bar, which R-060 asked this slice to remove). Three are raised as risks (R-069 to R-071); the rest are
notes for later parts.
No baseline item (decision, contract, data design, FR-XM rule) changes, so no change request is needed.

## Findings, most severe first

### 1. MEDIUM (fixed): the return-address check can be bypassed
- **Where:** `web/apps/web/src/app/session-context.tsx` `safeReturn` (was lines 36-39), used by
  `pages/sign-in.tsx:62` and `:291`.
- **Scenario:** an attacker sends `https://acme.erp.example/sign-in?return=%2F%09%2Fevil.example%2F`. The old check saw a
  value starting with `/` and not with `//` or `/\` and accepted it. The browser's address parser drops tab and line
  break characters and resolves dot segments, so `/\t/evil.example/` and `/.//evil.example/` become `//evil.example/`.
  After sign-in React Router calls `history.replaceState` with it; the browser refuses a cross-site address and throws,
  the sign-in step's error handler runs after the flow was cleared, and the person sees "You were signed out because
  the session ended" although they are signed in. For `navigate()` without `replace`, React Router's `push` catches that
  error and does `window.location.assign(url)` (`react-router/dist/.../history.js` line 307), so the same unchecked value
  in a push navigation is an open redirect to the attacker's page right after a genuine sign-in.
- **Evidence:** Chromium 1.63 probe: `history.pushState({}, '', '/\t/example.com/')` throws `SecurityError ... URL
  'http://example.com/'`, and `location.replace('/\t/example.com/')` lands on `http://example.com/`. The new browser test
  (below) failed on the old code: after a correct second step the page showed the "session ended" screen instead of home.
- **Fix:** `safeReturn` refuses control characters and backslashes, resolves the value with `new URL(value, origin)`,
  requires the same origin, and returns the normalised path (refusing one that starts with `//`), never a sign-in screen.
- **Tests:** `web/apps/web/src/app/return-address.test.ts` (15 attack forms, legitimate paths kept, sign-in screens
  refused) and browser test `FR-KRN-IAM-01 the return address after sign-in never leaves this site` in
  `web/apps/web/e2e/sign-in.spec.ts` (a fake "other site" answers inside the test browser, so a redirect would show).

### 2. MEDIUM (fixed): a 401 on any request refreshes the session without activity, so a background request defeats the idle timeout
- **Where:** `web/apps/web/src/session/session.ts` `refreshAfterUnauthorized` and `sessionEnded`, called by
  `web/apps/web/src/api/client.ts` `send` on every 401.
- **Scenario:** ruling Q3 and Build item 6 require "a refresh happens only while the person is active, so the server's
  idle timeout keeps working". The timer path honoured that, but the 401 path did not: a request made without the person
  (S1.12b's notification bell, every 60 seconds while the tab is visible, ruling Q16) gets a 401 once the 5-minute access
  token has expired, the client asks for one refresh, the refresh succeeds and resets the server's idle clock. A tab left
  open on a shared office computer would never time out. The acceptance line "with no activity ... the session ends at
  the server's idle time" would fail as soon as anything polls.
- **Evidence:** new unit test `a background request that meets a 401 does not keep an idle session alive` failed on the
  old code (refreshes happened every minute and the session never expired).
- **Fix:** `refreshAfterUnauthorized` refreshes only when there was activity since the last refresh; otherwise it answers
  false. `sessionEnded` likewise ends the session only after activity: without activity no refresh was tried, the
  server session may still be alive, and the idle warning and end come at their time. A click or key press on a
  request's own button is activity, so requests the person makes still get their one refresh.
- **Tests:** `web/apps/web/src/session/session.test.ts`: the background case above, `a request after the person's
  activity still gets its one refresh after a 401`, and `an idle tab is not signed out early by a background 401`.
- **For S1.12b:** this changes shared code (session manager). The API client is unchanged.

### 3. LOW: sign-out that cannot reach the server leaves a resumable session (R-071)
- **Where:** `session.ts` `signOut`: the local state ends in `finally`, whatever the server answered.
- **Scenario:** on a network failure, or a `503 errors.auth.busy` twice, the tab shows "You are signed out", but the
  session and the HttpOnly refresh cookie remain; reloading the page (or the next person on a shared computer) is signed
  straight back in until the browser closes or the idle time passes.
- **Recommendation (S1.12b, shell sign-out):** when the server call fails, keep the person signed in and say "We could
  not sign you out. Try again, or close the browser." with a retry, rather than claiming success. Not fixed here: it is
  a user-facing behaviour choice and needs new texts.

### 4. LOW: any refresh failure signs out every tab
- **Where:** `session.ts` `refreshNow` `catch`: a network error or a `503` after one retry ends the session in all tabs,
  although the server session lives. A reload brings it back (the cookie is still valid), so this is an annoyance, not a
  security gap. **Recommendation:** end only on 401; on other failures keep the state and retry at the next tick.

### 5. LOW: cookie prefix `__Secure-` rather than `__Host-` (R-069)
- **Where:** `src/Platform/Erp.Kernel.Api/Identity/BrowserCookies.cs`.
- **Scenario:** customers share one parent domain (`acme.erp.example`, `other.erp.example`). A response from one host
  could set a cookie for the parent domain with the same name (cookie tossing) and plant its own refresh or device
  cookie in a browser; the planted refresh token would be refused unless it belongs to this customer's database, so the
  worst case is signing the victim into an account the attacker controls on the same customer. Today no customer host
  serves anything but this application (no uploaded files, no customer HTML), so nothing can set such a cookie.
  `__Host-` forbids the domain attribute but requires `Path=/` (the cookie would then go with every request).
- **Recommendation:** revisit when the first slice serves uploaded content from a customer host (serve it from a
  separate domain, or switch to `__Host-`).

### 6. LOW: HTTPS is required at the host, and HSTS is missing behind a TLS proxy (R-070)
- **Where:** `WebHosting.UseErpSecurityHeaders` sends `Strict-Transport-Security` only when `Request.IsHttps`; the host
  configures no forwarded headers. Browsers keep `Secure` cookies only over HTTPS (or `localhost`).
- **Scenario:** an on-premises customer that serves the API over plain HTTP, or behind a proxy that terminates TLS, can
  sign in, but the refresh cookie is dropped (plain HTTP) and the person is signed out after 5 minutes; behind a proxy
  no HSTS header is sent. **Recommendation:** state "HTTPS required" in the installation runbook and set up trusted
  forwarded headers as a hosting setting before the first on-premises installation.

### 7. LOW: remembered browsers are never cleaned up and have no limit per person
- **Where:** `TrustedDevices.AddAsync`. Each "remember" adds a row; ended and expired rows stay. **Recommendation:** a
  housekeeping job (S1.11 job framework) deletes rows ended more than N days ago; consider a cap per person.

### 8. LOW: the idle warning's countdown stops when the person moves the mouse
- **Where:** `session.ts` `tick`: `warningRemainingMs` is updated only while there is no activity, so after a mouse move
  during the warning the seconds shown stop counting down (the session still ends at the right time, and "Stay signed
  in" still works). **Recommendation:** update the remaining time on every tick while the warning is shown.

### 9. LOW: the pseudo-locale can be switched on in a production build
- **Where:** `web/apps/web/public/boot.js` reads `localStorage['erp.test.pseudo']` in every build. Harmless (texts only),
  but ruling Q5 / Build item 4 say "used only in tests". **Recommendation:** read it only in test builds.

### 10. LOW: a deep link whose last part contains a dot answers 404
- **Where:** `WebHosting.UseErpWebApplication`: `Path.HasExtension` sends `/people/a.khan` to 404 instead of the page.
  **Recommendation (S1.12b route table):** route parameters must not end in `.something`, or check for files only under
  `/assets`.

### 11. LOW (test gap, partly fixed): not every path that ends a trust has a server test
- The approved deviation (a) (disabling or archiving ends remembered browsers) had no test: added
  `S112a_ADM_USR_24_a_status_change_that_ends_the_sessions_also_ends_the_trust`. The e-mailed password reset is covered by
  the browser test. Still without a test of the trust ending: the required password change at sign-in
  (`AuthenticationService.ChangeRequiredPasswordAsync`) and the operator's platform-admin revoke
  (`PlatformAdminRecovery`). Both call the same `TrustedDevices.RevokeAllAsync` as the tested paths.

### 12. LOW (fixed): the e-mailed link's token stays in the address bar (R-060 not met)
- **Where:** `web/apps/web/src/pages/account-links.tsx` (`/reset-password?token=`, `/activate?token=`).
- **Scenario:** R-060 (S1.11b2 review) says the S1.12 pages must send `Referrer-Policy: no-referrer` (done) **and remove
  the token from the address bar once read** (not done). Until the form was sent, the secret stayed visible on screen
  (screen sharing, a shoulder), in the history entry and in anything that records page addresses.
- **Fix:** the page keeps the token in memory and replaces the address with the bare path at once. A reload then shows
  "the link is incomplete"; the e-mailed link still works until it is used.
- **Tests:** the browser tests now check that `/activate` and `/reset-password` show no token in the address after the
  page has read it. R-060 can be closed for its first part when this merges (its Urdu-review part stays with R-062).

## Checked and found sound
- Cookie flags (HttpOnly, Secure, SameSite=Strict, Path=/api/iam/auth); the refresh cookie has no expiry; the device
  cookie expires with the trust. The header check is exact (one value, `web`); no CORS is configured anywhere, so a
  cross-site request cannot add the header. Sibling customer hosts are "same site" for SameSite, but the header still
  blocks them (cross-origin, preflight refused).
- `/refresh`: a browser's body token is ignored; a cookie without the header is ignored; a failed browser refresh clears
  the cookie; sign-out clears it. Version 2 clients are unchanged (test `clients_without_the_web_header_keep_the_json_body_form`).
- Remember-device: honoured only after the proven password and before the second-factor challenge; skipped for a person
  without a usable factor; added only when the sign-in ends in `tokens`; `rememberDevice` honoured only for browser
  requests; the trust check is one `update ... returning` (safe under concurrent revoke); the token is 256-bit and only
  its hash is stored; tokens of another person or customer fail the lookup; no timing or enumeration difference before
  the password is proven.
- Tenant resolution: the web bypass applies only after the host was found, never to `/api` (case-insensitive), only to
  GET or HEAD with no matched endpoint, and reads no customer data. Unknown hosts get 404 (tested).
- Browser session: the access token lives in memory and in same-origin `BroadcastChannel` messages only; the refresh is
  serialised by a Web Lock and always reads the browser's one cookie jar, so tabs cannot reuse a rotated token; sign-out
  and expiry reach every tab; no token or personal data in storage (checked by the browser test).
- Sign-in screens: one failure message; forgot password answers the same; the challenge token is in memory; the
  activation link's token leaves the address after activation (`replace`).
- Tests cite FR ids, use the real API and PostgreSQL, and the isolation probe sends customer A's cookies to customer B's
  host as a browser (header included).
