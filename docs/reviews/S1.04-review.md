## Summary for the product owner

The isolation suite does what the slice asked, and it does it well:
- It finds every endpoint by itself.
- It attacks each one with the other customer's ids, web address and tokens.
- It checks that customer A's database is unchanged afterwards.
- It refuses to pass an endpoint it does not know how to test.

I ran a full sweep of every endpoint on a real PostgreSQL 16 database. Every endpoint passed. Customer B's database
held none of customer A's 2,930 record ids afterwards. **No customer data leaks today.**

The suite is the only automated guard behind invariant 10 ("cross-tenant access attempts fail for every API
endpoint"). So I looked for ways a **future** mistake could slip past it. I found **two medium gaps**, and I proved
both with a deliberately broken endpoint:

1. **The suite sends one request at a time, so it cannot see mistakes that only happen when two customers use the
   system at the same moment.** One example of such a mistake: code that remembers "the current customer" in a shared
   place instead of per request. My broken endpoint did exactly that, and the suite passed it with zero failures. When
   I then sent requests from both customers at the same time, customer B read customer A's company in **10 out of 10**
   attempts. In production many customers use the API at once, so this is the most likely way a real leak would
   happen.
2. **For "create" endpoints, the leak check is effectively switched off.** The suite tests a create by sending
   customer A's own record as the request body. Any of A's data in the answer is then treated as "B just got back
   what it sent". I wrote a broken create that answers with customer A's latest company. The suite passed it with
   zero failures.

There are also **four low items**:
- the "A's database is unchanged" check has never been proven to catch a change;
- the customer look-up cache is switched off during the suite;
- one leak exemption is broader than it needs to be;
- the CI job is not yet a *required* check on GitHub.

I recommend fixing both medium items now. Each is a small change to the test suite only, with a self-test that uses
the broken endpoint above. No product code, migration, decision or data design changes.

**Evidence**
- Build: `dotnet build Erp.sln -v q` → 0 errors.
- Proof tests (temporary, not committed; kept for the fix session), run against local PostgreSQL 16:
  - P1 "shared current customer". Probe failures: **0**. Concurrent run: "B read A's company … in **10 of 10**
    interleaved attempts". Test passed, so the gap is proven.
  - P2 "create answers with A's row". Probe failures: **0**. Proven.
  - P3 "full sweep". Every customer endpoint was probed in one run: "endpoints with failures 0; A-only row ids 2930;
    stored in B: **0**".
- CI on `main` (run 44514419713): the `tenant-isolation` job passed. The suite itself took about 5 minutes, against a
  30-minute job limit.

## Findings, most severe first

### 1. MEDIUM: every probe is sequential; a leak that needs two customers at once passes

- **Where:** `CrossTenantProbe.cs:102-204`. Every call is awaited before the next one is sent (`SendAsync`, line 282).
  The same is true of every later probe.
- **Scenario:** a module keeps the request's data source, tenant context or DbContext in a singleton field or a
  `static`. Another way to get this wrong is a cache keyed by something other than the customer, filled during one
  request and read after an `await`.
  - Sequentially, every request sees its own customer, so the suite passes.
  - Under real load, B's request can read through A's connection.
- **Proof:** P1 in the review proof file.
  - The endpoint is `GET /api/test/shared-companies/{id}`. It stores `ITenantConnectionProvider.DataSource` in a
    static, waits 200 ms, then reads `org.companies` by id through the static.
  - `CrossTenantProbe.RunAsync` returned no failures.
  - B then started its request and A started its own 50 ms later. B got 200 with A's company in 10 of 10 tries.
- **Fix (tests only):**
  - Add a concurrent phase to `CrossTenantProbe`, for the generic Get and List kinds at least, and preferably as a
    shared helper the other probes can call. It fires interleaved A-host/A-token and B-host/B-token requests at the
    same endpoint, about 8 pairs, started together. It asserts that every B answer is 404 or holds no A marker, and
    every A answer holds A's row.
  - Add a self-test `FR_KRN_TEN_03_S104_the_suite_catches_an_endpoint_that_keeps_the_customer_in_shared_state` with
    the P1 endpoint, asserting the probe now reports it.
  - Run-time cost: roughly one extra second per probed endpoint.

### 2. MEDIUM: the leak check on create responses can never fire

- **Where:**
  - `CrossTenantProbe.cs:110` (the body is A's own row as A's GET returned it).
  - `:151` (`sent = body + path` for Create and Update).
  - `:237` (a marker found in `sent` is not a suspect).
- **Why:** A's GET answer contains A's row id and every id the row references, which are all the markers. So for a
  Create, every marker is "sent", and `LeaksAsync` cannot report anything. Update is protected by its 404 status check;
  Create has no status expectation except "not 401/403".
- **Proof:** P2.
  - `POST /api/test/echo-companies` writes nothing. It answers 201 with the newest `org.companies` row, read through
    the first customer's data source.
  - Its GET by id is correct, as the positive control needs.
  - Probe failures: 0.
- **Fix (tests only):**
  - Remove `id`, `rowVersion` and the audit columns from the create body before sending it. No create request accepts
    an id, per the probe's own comment at line 233.
  - Treat only the reference ids as "sent". A's row id then stays a marker, and any create answer carrying it is a leak.
  - Add the P2 endpoint as a second self-test.

### 3. LOW: nothing proves the "A's database is unchanged" check catches a change

- **Where:** `IsolationFixture.FingerprintAsync` (line 114) and `Changed` (line 201). All eleven probes use them.
- The only self-test (`..._reads_without_the_customer_connection`) covers a read leak. If the fingerprint broke (for
  example by ignoring partitioned tables, or by returning equal text for different rows), every write-isolation result
  would still pass. I read the code and found it correct today: count plus MD5 of every row of every table, partition
  parents included.
- **Fix:** add a self-test with an endpoint that writes through the first customer's data source. Use a PUT that bumps
  `updated_at` on A's row, and assert the probe reports "customer A's database changed".

### 4. LOW: the suite never probes the production path through the customer look-up cache

- **Where:** `TenancyFixture.cs:77` and `:117` (`HostCacheSeconds = 0`); production default 30 s (`ApiHost.cs:71`).
- The cache in `TenantDirectory.FindByHostAsync` is keyed by the normalized host and looks correct. But the suite only
  ever exercises the uncached branch, so a later change to the cache key would not be caught.
- **Fix:** have the isolation fixture's `App` use the production default (or 30 s). The S1.03/S1.09b tests that need
  fresh look-ups keep 0 through their own hosts, or call `Invalidate`.

### 5. LOW: the "B stores this id too" exemption is broader than needed

- **Where:** `CrossTenantProbe.cs:235-248` and `IsolationFixture.StoredInAsync` (line 162). Any uuid in any column of
  any table of B exempts a suspected leak.
- P3 shows the exemption hides nothing today: B stores none of A's row ids. But it would silently hide a leak of A's
  row id if a future table in B ever recorded the ids B *asked for*, such as a request log, an access log of failed
  look-ups, or a bulk-result table.
- **Fix:** never exempt the probed row's own id (`idA`), only its references. That is the case the exemption was
  written for (`job.run_logs.run_id`).

### 6. LOW: the isolation job is not yet a required check

- The slice said "make the suite a required CI check". The handoff correctly notes that this is a GitHub
  branch-protection setting only the product owner can change. CLAUDE.md's "never merge with failing CI" covers it in
  practice, but GitHub does not enforce it.
- **Action for the product owner:** in GitHub → Settings → Branches → `main`, require the `tenant-isolation` and
  `build-and-test` checks.

## Tests that would pass even if the behaviour were wrong

- **Every probe (finding 1):** a leak that needs two customers at once.
- **Generic Create (finding 2):** an answer carrying A's data.
- **The fingerprint (finding 3):** a write into A's database would pass if the fingerprint itself were broken.
- **The suite overall, with the cached customer look-up path (finding 4).**

## Checked and found correct

- **Discovery** reads the real production composition (`ApiHost.Build`). The coverage test asserts that the host under
  test maps exactly the same endpoints and that more than 400 are found. An endpoint with an unknown shape, or without
  table metadata, fails the suite instead of being skipped (fail closed). `TenantFree` holds only `/health`, and the
  test checks that it is anonymous.
- **Anonymous detection** (`IAllowAnonymous` or no `IAuthorizeData`) fails closed: an endpoint that relies only on a
  fallback policy would be reported, not trusted.
- **Crossed hosts and tokens** (A host + B token, B host + A token, no token, untrusted key) all expect 401 (CR-008).
  An unknown host expects 404. Customer hints in the query string and in six headers (X-Tenant, X-Forwarded-Host,
  Forwarded and others) are tried on every endpoint. Expired, wrong-issuer and wrong-audience tokens are covered by the
  S1.03 tests (`TenantIsolationAndResolutionTests`).
- **Positive controls** stop vacuous passes: A reads, lists, updates and deletes its own row, and B lists its own row.
- **The leak self-test** really fails the broken endpoint (`expected 404, got 200` and `LEAK`). The correct endpoint
  for the same table passes.
- **Database level:** each of A's logins, and each of B's, is refused by the other customer's database and by the
  control-plane database with 42501. The same logins open their own database. Provisioning revokes `connect` from
  `public` on each customer database, and customer logins are created without special powers (R-028 checks
  pre-existing group roles).
- **In-process caches are keyed by customer:**
  - `TenantDataSources` (code + login kind);
  - `SettingsCache` (tenant code);
  - `FieldKeyCache` (tenant code);
  - `LicenceResolver` (by claims text, which is immutable);
  - `TenantDirectory` (host).

  The tenant context and connection provider are scoped per request (`TenancyServices.cs:21-22`). The singleton limit
  counters and `CompanyLimitInterceptor` hold no customer state.
- **The API host only reads the control-plane database** (licence pages and usage statements). Every control-plane
  write is in the migrator, operator commands or worker loops, so not fingerprinting the control plane leaves no API
  gap today.
- **SQL safety in the test helpers:** table and column names come from the catalogue, quoted by `format('%I')`. Values
  are parameters.
- **The CI job** builds and runs the suite on its own PostgreSQL 16 service. The main integration step excludes the
  trait, so nothing runs twice and nothing is skipped.
- **The `RowFactory` change** keeps its defaults, so the S1.02 behaviour is unchanged.

## Not in scope, noted

- FR-KRN-TEN-03 also says no *job* may cross customer databases. The worker host (jobs, event dispatcher,
  notifications, escalation) is not part of S1.04, which covers API endpoints only. Its isolation is tested by the
  S1.10b and S1.11 tests, not by this suite.
