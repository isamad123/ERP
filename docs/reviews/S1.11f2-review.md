Reviewed: `git diff origin/main HEAD` at `25e76ad` (commits `0a256d5`, the merge `264e15b` and `25e76ad`). Reviewer: fresh Opus 5.5
session, class B review (CLAUDE.md, CR-052 Q8).

**Summary for the product owner.** The three changes do what was asked, and the tests for them pass when I run them
(13 of 13). The control-plane database now keeps a record of each setup script, and an existing control plane picks up
that record by itself on its next `migrate`. The database now refuses a second open approval request for the same
document. Two set-up runs for the same customer now take turns. One problem blocks the merge: an older automated test
counts the tables in the design, and nobody updated it for the new table, so the full test suite fails (1 test of 523 in
that group). The fix is a two-line change to that test. There is also a weak spot in the new set-up lock. If the
database server closes the lock's idle connection partway through a run, the lock is lost and nothing notices, so a
second run could start anyway. This needs a server setting or connection pooling that a hosted or on-premises
installation could have. It is easy to harden. The other points are small.

### 2. MEDIUM: the provisioning lock can be lost in the middle of a run without anyone noticing
- `src/Platform/Erp.Kernel.Infrastructure/ControlPlane/Provisioning/ProvisioningLock.cs:29` opens the lock connection,
  takes a session advisory lock and then leaves the connection idle for the whole run. Nothing keeps the session alive
  or checks that it still exists. `DisposeAsync` (lines 55-63) ignores `pg_advisory_unlock`'s answer (`false` means the
  lock was no longer held) and swallows `NpgsqlException`. So a run that lost its lock finishes as if nothing happened.
- Ways the session can end while the run continues on its other connections:
  - `idle_session_timeout` set on the control-plane login or database (`alter role ... set idle_session_timeout`, a
    common hardening setting). I checked on the local PostgreSQL 16.15. Session A ran `set idle_session_timeout = 1000;
    select pg_advisory_lock(...)` and then stayed idle. After 1.8 s, session B's `pg_try_advisory_lock(...)` returned
    `t`, and A was ended with "terminating connection due to idle-session timeout".
  - The server restarts, or an administrator ends the session.
  - The connection goes through PgBouncer in transaction mode. `docs/specs/01-erp-platform-architecture-and-foundation.md` line 313 plans PgBouncer in transaction mode.
    Then the session lock stays on a server connection that PgBouncer hands to other clients, and the unlock may run on
    a different one. The lock then leaks, and later runs for that customer wait with no time limit. The two migrator
    locks (`ERPMIG`, `ERPCPM`) depend on the same thing, but they last only one `ApplyAsync` call.
- In the opposite direction, a `lock_timeout` or `statement_timeout` on the login ends the wait early. I checked this
  too: `set lock_timeout = 500; select pg_advisory_lock(...)` gives `ERROR: canceling statement due to lock timeout`.
  The second run then fails with a raw PostgreSQL error, although the documentation says the wait has no time limit.
- **Failure scenario:** the platform login has `idle_session_timeout = 60s`. Run A of customer `acme` spends more than
  60 s in migrate and seed. Its lock session ends. The operator starts run B (for example after a terminal disconnect),
  B gets the lock, finds the customer still `provisioning`, and works alongside A. This is the R-031 failure the slice was
  meant to remove: two stored passwords and a secret store out of step with the server, or 23505 or 42P04 errors.
- **Fix (small):**
  1. Right after opening the lock connection, run `set idle_session_timeout = 0; set lock_timeout = 0; set statement_timeout = 0`.
     These are session settings any login may change. Also set `KeepAlive` (for example 30 s) and `TcpKeepAlive = true`
     on the builder, so a dead peer is found.
  2. Add `ProvisioningLock.EnsureHeldAsync()`. It runs `select exists (select 1 from pg_locks where locktype = 'advisory'
     and pid = pg_backend_pid() and granted and objsubid = 2 and classid::int = hashtext($1) and objid::int = hashtext($2))`
     on the lock connection, which also fails if the connection is dead, and throws "the provisioning lock was lost;
     run the command again". Call it in `CompletedAsync` before each step is audited, or at least before `activate`.
  3. In `DisposeAsync`, report an unlock that returns `false`. Do not drop it silently.
  4. In `docs/runbooks/tenant-operations.md`, say that the migrator's control-plane connection must be a direct
     connection (or PgBouncer in session mode), never transaction pooling.
  5. Add a test: while run A is paused, end A's lock session with `pg_terminate_backend` (application name
     `erp-provision-lock`) and show that A stops at its next step instead of finishing.

### 3. LOW: part letters a to z let the generator make migration file names that sort in the wrong order
- `tools/Erp.CodeGen/Design/DesignLoader.cs:551` (pattern `[a-z]?`) and `tools/Erp.CodeGen/Emit/SqlEmitter.cs:114`
  now accept any part letter. `LaterPartOffset` (line 120) adds 600 minutes per part. `FileName` (line 353) formats
  hours as `{sequence / 60:00}`, which is not limited to two digits. From part `k` onwards the sequence is at least 6000
  minutes, so the hour field has three digits. For example S1.11k gives 180 + 8 + 6000 = 6188 minutes and
  `V2026111510308__kernel__design_s1_11k.sql`. That name sorts before the merged `V202611151307__kernel__design_s1_10b.sql`.
  A new database would then run a later slice's file before earlier ones, and `SchemaMigrationResult.SchemaVersion`
  (ordinal maximum) would report the wrong version. No such slice exists today. Letters up to `j` (and `-r1` to `-r3`)
  stay within 99 hours.
- **Fix:** in `FileName`, throw a `DesignException`-style error when `sequence >= 100 * 60`. Or limit the pattern to
  `[a-j]` and say so in the README row and in CR-054.

### 4. LOW: the test of two control-plane migrators at once does not control the timing
- `tests/Erp.IntegrationTests/Tenancy/ControlPlaneMigrationTests.cs:164-181` releases two migrators together and expects
  them to collide (the R-028 finding 2 pattern). Without the lock they would most likely clash (23505 on the history
  insert or on the catalogue). But the test can pass without ever making one wait, and it never checks that one did. The
  lock code is shared with the customer migrator, so the risk is small.
- **Fix:** in the test, hold the ERPCPM key (`select pg_advisory_lock(76219836223565)`, which is `0x45_52_50_43_50_4D`) on a separate connection. Start
  `ControlPlaneSchemaMigrator.ApplyAsync` and wait until its session shows `wait_event = 'advisory'`. Assert that
  `cp.schema_history` does not exist yet. Then release the lock and assert that the run completes. Keep the existing test
  as a smoke test.

## Checked and found sound
- **Frozen files.** No merged migration file was renamed or edited (`git diff --name-status`: only the two
  `V202611155508__*_s1_11f_r2.sql` files are added). I ran the generator on a clean export of `HEAD`:
  `Erp.CodeGen: 1073 files (0 written, 1073 unchanged, 0 stale deleted)`. The special case that keeps the
  `S1.09b` control-plane file name works, and the new formula gives the same name for `S1.07` (0304). The
  data-dictionary drift test `S102_committed_data_dictionary_matches_the_live_database` and the catalogue tests pass.
- **Existing control planes without history.** Every earlier run of the old `SqlScriptRunner` re-applied all
  control-plane files, so they are idempotent by construction. The new migrator re-runs them once, each in its own
  transaction, and records them all when `cp.schema_history` first exists. If the run fails before that point, the next
  run repeats the same work. The test `..._an_existing_control_plane_without_history_migrates_cleanly...` simulates
  this, and existing rows are kept. Checksums use the same `MigrationScript.Checksum()` as customer databases (CRLF
  normalized, SHA-256), so a checkout on any system gives the same value. `cp.tg_refuse_change()` in the new file
  has the same body as in `V202611150000__controlplane__cp.sql`.
- **Migrator lock.** `ERPCPM` is a different key from `ERPMIG`, and the two live in different databases anyway. It is
  released in `finally` with `CancellationToken.None`, on the pooled connection. Npgsql's reset on return also releases
  session locks. The history table name reaches SQL only after it is checked against two constants (`TenantSchemaMigrator.cs`
  `ApplyAsync`). `to_regclass` takes it as a parameter. `created_at` uses the injected clock.
- **Provisioning lock.** The two-key form (`hashtext('cp.tenants.provision')`, `hashtext(code)`) cannot collide with
  the single-key migrator locks (a different `objsubid`). A hash collision between two customer codes would only make
  them wait for each other. The lock is taken before any write. It is held until after the `tenant.provision.failed`
  audit row is written, so a waiting run sees a consistent state. It is released on success, on failure and on
  cancellation, and process death ends the session. The run waiting for the lock holds no other lock, and the only
  other lock the run takes is `ERPMIG` in the customer database, so no deadlock is possible. `CommandTimeout = 0` with
  a cancellable token: Ctrl+C sends a PostgreSQL cancel, and the test shows it. Values are parameters, and the
  function name is one of three constants.
- **Open-request index.** The index's statuses (`running`, `returned`) match `WorkflowDb.OpenInstanceAsync` and the
  monitor query. The engine's only insert (`WorkflowEngine.cs:99`) runs after its lock and the open-request check, and
  resubmission updates the same row (`returned` to `running`), so the engine can never trip the index. Generated writes
  are closed (`api_actions: [read]`). A database that already held duplicate open requests would stop that customer's
  migration. The fleet migrator then puts that customer in maintenance and carries on with the next one
  (`FleetMigrator.cs:56-58`). This is recorded as R-034. The index is built without `concurrently`, inside the file's
  transaction, which is acceptable for a small table.
- **Tests.** They use real PostgreSQL and cite FR ids (FR-KRN-TEN-01, FR-KRN-TEN-02, FR-KRN-WFL-01). The provisioning
  race tests control the timing: they pause in a step and wait for `wait_event = 'advisory'`. Without the lock, three
  of them would fail. Every customer code is tracked, so its database and logins are dropped, and `Track` is now
  thread-safe. Scratch control planes are dropped `with (force)` and their temporary folders are deleted. The
  index tests would fail without the migration. Run result:
  `--filter-class ...ControlPlaneMigrationTests --filter-class ...ProvisioningRaceTests --filter-class ...OpenRequestKeyTests`
  → 13 passed, 0 failed. Unit tests: 385 passed.
- **Registers and documents.** CR-054 and R-034 are added within the reserved numbers. CR-006, R-023 and R-031 are
  closed with evidence. The runbook, CLAUDE.md and the handoff are updated. Nothing outside items 4 to 6 was changed.
- **Not done.** I did not build: another full test run was using the build output. I did not re-run the
  tenant-isolation suite. No endpoints were added.

**Finding 2 in detail.**
- *`pg_locks` predicate* (`ProvisioningLock.cs:76-79`). For `pg_advisory_lock(int4, int4)`, PostgreSQL shows the first key
  in `classid`, the second in `objid`, and `objsubid = 2`. The `int4::oid` cast keeps the bits, so a negative hash
  matches. I checked this on PostgreSQL 16.15. `hashtext('cp.tenants.provision') = -1034670512`, and `pg_locks` shows
  `classid = 3260296784` (`= hashtext(...)::oid`). With `hashtext('acme') = -1850687378` (negative) and
  `hashtext('rl1') = 432666513` (positive), the predicate returns `t` while the lock is held and `f` after unlock. A bigint
  lock with the same two halves shows `objsubid = 1`, and the predicate returns `f` for it, as it should. Text
  parameters reach `hashtext(text)` as in `LockAsync`, so both compute the same key. `pid = pg_backend_pid()` limits the
  check to this session, which is in one database. Correct.
- *Session settings* (`ProvisioningLock.cs:43`). `statement_timeout`, `lock_timeout`, `idle_session_timeout` and
  `idle_in_transaction_session_timeout` are all settings any login may change. A session `SET` overrides a login-level
  value. I checked: with `PGOPTIONS='-c idle_session_timeout=1000'` and the four `SET`s, the locking session was still
  alive after 3 s, and a second session's `pg_try_advisory_lock` returned `f`. Without the `SET`s, the second session got
  `t` and the first was ended ("idle-session timeout"). `idle_session_timeout` needs PostgreSQL 14 or later. The product
  already needs 16 (`NULLS NOT DISTINCT`, data-design README rule 11). `KeepAlive = 30` makes Npgsql send a query every
  30 s (Npgsql 10.0.3 docs), which also keeps NAT and firewall idle timers from dropping the TCP connection. If the
  connection is half-open, the check's own command times out (default 30 s) and is reported as a lost lock. That is the
  safe direction. `TcpKeepAlive` was not added; Npgsql advises against it when `KeepAlive` is set. The lock waits already
  had `CommandTimeout = 0`.
- *When the check runs* (`TenantProvisioner.cs:131-148`). The check runs after each step's work, its audit row and the
  progress report, and before the next step starts. There is no check after `activate`. That is right, because nothing
  follows it. Cancellation still comes through as `OperationCanceledException`, because only `NpgsqlException` and
  `InvalidOperationException` are wrapped. A lost lock goes through the existing failure path (`tenant.provision.failed`,
  customer stays `provisioning`), so a rerun resumes. The check cannot cover a step that is already running (finding A).
- *Failed unlock not reported* (item 3 of the suggested fix). This was not done, and the reason is given. I accept it.
  The only unchecked part of the run is `activate`, after which the run is finished anyway.
- *Test* (`ProvisioningRaceTests.cs:230-256`). It pauses after `database`, ends the lock session with
  `pg_terminate_backend`, then resumes. Without the fix, run A completes, so `Assert.ThrowsAsync` fails. With the fix,
  A stops with `ProvisioningLockLostException`, no `tenant.provision.migrate` row is written, and the rerun activates
  the customer. All logins work, and no lock sessions are left. The test is deterministic. The backend ends while idle,
  long before A sends its next query. The test ends every `erp-provision-lock` session in this fixture's own control
  plane and expects exactly one. That is safe because the `Tenancy (S1.03)` collection runs its tests one after another,
  and each fixture has its own `erp_it_cp_<suffix>` database. It passed 4 times, once while a full run with its own
  fixture was going on. The customer code is tracked, and afterwards no `erp_t_rl*` database or login was left.

### New findings

**A. LOW: the check fences between steps, not within them; the runbook promises more than that**
- `TenantProvisioner.cs:143-147` runs `EnsureHeldAsync` only after a step has finished. If the lock session ends while a
  step is running, that step runs to its end without the lock. Meanwhile a second run can take the lock, register (the
  customer is still `provisioning`) and start the same step. The window is one step (for `migrate`, the customer
  database's `ERPMIG` lock serializes the two runs anyway). Session ends from idle limits are now prevented.
  The remaining causes are an administrator or a "kill idle sessions" job ending that one session, a network fault on
  that one connection, or a control-plane restart while the customer database is on another cluster.
- **Scenario:** the customer database is on cluster `pk-2`, and the control plane is restarted while run A is in step
  `database`. Run A's `pk-2` connection survives. The operator, seeing the outage, starts run B. B gets the lock as soon
  as the control plane is back and runs `database` while A is still in it. Both reset login passwords, so the secret
  store and the server can end up out of step (the R-031 symptom). A stops afterwards with "lost its lock", but the
  overlap has already happened. Nothing tells the operator to wait.
- `docs/runbooks/tenant-operations.md:52` says that two runs "never work at once", and line 57 says that a run "stops
  before its next step". Line 57 is accurate; line 52 is not, in this case.
- **Fix (small):** in the runbook, say that the step already under way finishes first. Tell the operator to start a
  new run only after the first one has printed its error or ended. Add the same limit to the R-031 closure note. A
  complete fence (a run token written to `cp.tenants` at `register` and checked in each step's control-plane writes)
  would need a design change and is not proportionate now.

**B. LOW: no test shows that the check notices a missing lock while the connection is alive**
- `ProvisioningLock.cs:76-79` and `89-92`. The new test kills the session, so `EnsureHeldAsync` fails on the dead
  connection (`ProvisioningLock.cs:84-87`) whatever the predicate says. The other tests only show that the predicate
  returns true while the lock is held. A wrong predicate that still matches the held lock would pass every test today,
  for example one that drops the `objid` or `objsubid` condition or matches any advisory lock of the session. Then the
  "returns false" branch would never fire. That branch is the one meant for a proxy that moves the session to another
  server process. The predicate is correct today (verified above). This is a guard against regressions.
- **Fix:** move the SQL into an `internal const` and add an integration test that runs it on a plain connection. It
  should return false before the lock is taken. It should return true after `pg_advisory_lock(hashtext(LockClass),
  hashtext(code))`, for one code with a negative hash and one with a positive hash. It should return false when only
  another code's lock or the bigint form is held. Optionally, in `ProvisioningRaceTests.cs:239-242`, end the session by
  joining `pg_locks` on this code's key instead of by `application_name`. That ends exactly the right session and also
  exercises the key.

**C. LOW: the file-name guard is untested**
- `tools/Erp.CodeGen/Emit/SqlEmitter.cs:353`. The test suite never calls the new `DesignException` branch. A later
  change to `LaterPartOffset` or to the guard could bring back three-digit hour fields without any test failing.
- **Fix:** add a unit test next to `S110b_CR043_...` (`tests/Erp.UnitTests/CodeGen/GeneratorTests.cs:182`). It should
  check that sequence 5999 gives `...9959__` and that 6000 throws with "change request" in the message (through an
  `internal` `FileName` or a design copy with a part-`k` slice key).

**Outside the fixes (LOW, pre-existing, for a follow-up):** the migrators' lock wait
(`TenantSchemaMigrator.cs:58` through `ExecuteAsync`, `:157-167`) sets no `CommandTimeout`. Npgsql's default is 30 s
(Npgsql 10.0.3 docs, `NpgsqlConnectionStringBuilder.CommandTimeout`). A second migrator that waits more than 30 s
therefore fails with a timeout instead of waiting. For `ERPCPM` the wait is short (only the control-plane files run
under it). For `ERPMIG`, a provisioning resume that meets a long `migrate` of the same customer could hit it. I did not
run this case. The fix would be `CommandTimeout = 0` on the lock command only, as `ProvisioningLock.LockAsync` already does.
