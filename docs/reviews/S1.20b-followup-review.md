## Summary for the product owner
The follow-up does what the two rulings ask. (A) If any job-change kind needs approval, a correction of the hire that changes a title,
grade or unit now waits for a second person. A correction that only moves the joining date still applies at once. (B) A correction of a
correction now reports the earliest day of the whole chain, so later modules recalculate from the right day. Both rules are tested.

The review found two more gaps. Neither comes from this diff: both are older code that the follow-up does not reach.
- **HIGH:** HR can still change a job title without approval through a different route. They correct a correction that changed only
  employment fields, such as the employee type. A throw-away test confirmed this (below).
- **MEDIUM:** a correction dated in the future can remove a promotion that is already in force. The past job rows change at once, but
  nothing tells later modules until the correction's own date.

Recommendation: fix the HIGH finding before merging (it is small) and the MEDIUM one with it or under its own CR.

## Findings

### 1. HIGH: job details still change without approval through a correction of an employment-field correction (FR-XM-32, ruling Q11)
- `src/Modules/Hrm/Erp.Hrm.Infrastructure/Employments/EmploymentService.Changes.cs:347-349` holds a correction for approval in three
  cases: its own kind is listed, its root kind (`RootKind`, `:432-434`) is listed, or the root starts the employment. The rule at `:216-218`
  only refuses job details on a correction **without** a target. Take a correction whose target is an untargeted correction: that
  target changed employment fields only, so it carries no `corrects_kind`. `RootKind` returns `"data_correction"`, which is not listed
  and is not a start. If the new correction sets `assignment`, it applies at once.
- Failure scenario: approval of promotions is on (the default). An HR administrator records an untargeted correction of the employee
  type. They then record a `data_correction` of that correction with `assignment: {title: "Manager", gradeId: G7}`. The change is
  effective at once and raises `hrm.employee_changed`. Nobody approves it. The administrator can do this to their own record if they are
  in scope. This undoes review S1.20b finding 1 and ruling A by a different route. The throw-away test above confirms it.
- **Fix:** an untargeted correction changes employment fields only, so its whole chain must too. Refuse `assignment` on a correction
  whose root kind is `"data_correction"`, with the same error as `:218` (`CorrectionNeedsTargetForJob`). A safety net that also works:
  hold any correction with `delta.Count > 0` whose root kind is not itself a job-change kind whenever any job-change kind is listed.
  This means widening `StartsEmployment(rootKind)` at `:349` to `rootKind is null || !AssignmentKinds.Contains(rootKind)`. Add an
  integration test, citing FR-XM-32, that is the probe above turned around.

### 2. MEDIUM: a future-dated correction of an event in force changes past rows now but announces nothing until its date (GHR-04)
- `EmploymentApplier.SetApplied` (`EmploymentApplier.cs:125`) gives a correction dated after today the status `approved`.
  `EmploymentTimeline.ReplacedBy` counts `approved` corrections, so `SyncRowsAsync` removes the replaced event's rows **today**, back to
  its date. `hrm.employee_changed` is raised only when the event is `effective`: at `EmploymentService.Changes.cs:386` and at
  `EmploymentEventHandler.cs:98` after an approval. The daily job raises it later, on the correction's own date. With ruling B that later
  message carries the right `earliestDate`, but it arrives late.
- Failure scenario: a promotion has been in force for 30 days, and payroll and attendance have used it. HR corrects it to start 30 days
  from now. Today the rows for the past 30 days say "Officer", but no message is raised for 30 days. A payroll run in between still works
  from the old picture and is not told to recalculate. The backdated change check did run (its `earliestDate` is right). Only the
  announcement is late.
- **Fix:** in both places, raise `hrm.employee_changed` when the stored rows changed and `EarliestAffected(...) <= today`, not only when
  `e.Status == "effective"`. The daily job's later message then repeats the same news, which is harmless because modules recalculate.
  Add a test: a future correction of an effective promotion raises a message whose `earliestDate` is the promotion's date. The
  integration test `GHR_04_followup_B_…` (`EmploymentServiceTests.cs:733`) documents the present behaviour ("approved, nothing raised")
  and needs that comment updated.

### 3. LOW: the employee-limit test fails when the two employment classes run together (older than this diff)
- `EmploymentServiceTests.cs:207-224` counts the tenant's seats and then sets the limit to that count plus one. Run after
  `EmploymentTermsTests` in the same process, the second hire is accepted. The same thing happens on `origin/main`, so the cause is
  test isolation (shared tenant state), not this change. The CI run on the whole integration suite should show whether it also fails there.
  **Fix:** count the seats the way the licence check counts them, or give the test its own tenant. Record the failure under its own
  issue; it is not a reason to hold this follow-up.

### 4. LOW: test coverage of ruling A misses three paths
- `FR_XM_32_followup_A_…` (`EmploymentServiceTests.cs:694`) covers three things: a direct correction of the hire (held; the requester
  cannot approve; a second HR person can), a date-only move (applies at once), and a company that lists no job-change kind (applies at once).
  It does not cover three paths: the check endpoint (`/events/check` should answer `needsApproval: true`), a correction of a correction
  of the hire with new job details, and the employee as approver. Code reading shows the first two work: the check runs the same
  expression, and `corrects_kind` carries `hire` along the chain. The employee is excluded by the subject list passed to
  `workflow.StartAsync`, as before. **Fix:** add the three assertions.

## Checked and sound
- Ruling A on the save, the check (`save: false` returns the same `needsApproval`) and a correction of a correction of the hire
  (`corrects_kind` is copied from the root, `:245-248`). On approval, the handler applies the event only after the route approves, the
  requester is refused (tested) and the employee is excluded through the subject list. The daily job only moves an event that is already
  approved. It decides no approval, and a future hire correction is possible only before joining (`JoiningAfterToday`).
- `NeedsApprovalAsync` overload: the comparison is ordinal and only array entries that are strings count. The single-kind path is
  unchanged.
- Ruling B: `EarliestAffected` (`EmploymentApplier.cs:397`) follows `CorrectsEventId` through every link. The loop is bounded by the
  event count, so a cycle cannot hang it. It stops at a missing link and never returns a day later than the event's own date. Its callers
  are the impact check and the scope check in the change service (`:291`, started from the target), the impact check in the approval
  handler (`EmploymentEventHandler.cs:82`), and `RaiseChanged` (used by the change service, the handler and the daily job). Every caller
  passes `EventsAsync`, which loads every event, cancelled ones included, so the chain is never cut short. The transfer path raises
  `hrm.employee_separated` and does not use `earliestDate`, so it is unaffected. An earlier day than strictly needed is safe: it only
  means extra recalculation.
- Tests are real. The integration tests go through the HTTP endpoints, the real workflow engine and PostgreSQL and read
  `hrm.outbox_messages`. The unit test covers a chain of two corrections, a target that no longer exists, and a correction dated before
  the whole chain. Test names cite FR-XM-32 and GHR-04.
- The register entry (item **r** of CR-076 S1.20b detail) matches the code.
