- Scope: the merged S1.05 diff only, `git diff f9499c7..bc09db9` (PR #6). This was a class B review (docs/token-strategy.md).
- Read: CLAUDE.md, the slice file with rulings Q1–Q6 and P1–P9, and handoff 2026-11-16-S1.05. No whole specifications were loaded.
- Reviewer: a fresh Claude Code session, 2026-11-16. Nothing was pushed or changed on any branch. This file is in the working copy only.

## Summary for the product owner

Overall the identity work is solid:
- Each customer's passwords, tokens and sessions stay inside that customer's own database.
- An access token from one customer is refused on another customer's web address. Tests check this.
- Passwords, tokens and codes are stored safely.
- Every SQL statement uses parameters.
- The frozen migration files were not touched.

I found **two serious defects**. Both weaken the lockout that protects accounts from guessing:

1. **The second factor can be guessed without limit.** This applies to someone who has already stolen a user's password. Each time they type the correct password, the failed-attempt counter goes back to zero. That happens before the six-digit code is checked. So they can try 4 codes, sign in again, try 4 more, and so on, and the account never locks. With enough tries they will hit the right code. This defeats the purpose of the second factor.
2. **Guesses sent at the same moment are counted as one.** I tested this on the real database: 10 wrong passwords sent at once were counted as 1. An attacker who sends guesses in parallel gets hundreds of tries before the account locks, not 5. I also tested the fix: the same test then counts all 10.

There are also **four medium issues**:
3. Two database operations can block each other. I reproduced this on PostgreSQL. Example: a user refreshes their session at the same moment an administrator disables them, or they sign in on a fourth device. One of the two requests then fails with a server error. The disable can fail and need to be done again.
4. Some self-service actions need only the short-lived access token, with no password or code re-entered. These are making new recovery codes, adding or removing an authenticator, and changing the password. Wrong "current password" attempts are also never counted. Changing your password does not sign out your other sessions. The specification says nothing about this, so **this needs your decision**.
5. Each sign-in attempt takes a fixed amount of memory and processor time on purpose (password hashing). Nothing limits how many run at once. A flood of sign-in requests to one customer's address could slow down or crash the shared server for every customer. R-004 already covers rate limits but not this.
6. Anyone who knows a session's id (it is printed inside the access token) can sign that user out. That event is then recorded as if the user did it themselves.

The low items are listed below. I recommend fixing items 1 and 2 before any real customer signs in, and item 3 at the same time. Each needs a few lines of code and a test.

## Findings, most severe first

### 1. HIGH: a correct password resets the failure count before the second factor (unlimited MFA guessing)

- **Where:** `src/Platform/Erp.Kernel.Infrastructure/Identity/AuthenticationService.cs:82-85`. This step runs before `ContinueAsync` issues the MFA challenge (line 87). The counter is then read again in `CompleteMfaAsync` at lines 125-128.
- **Scenario:** an attacker has phished Alice's password. Alice has an authenticator enrolled. The lockout threshold is 5.
  1. `POST /api/iam/auth/sign-in` with the right password sets `failed_attempts` to 0 and returns `mfa_required` with a challenge.
  2. 4 × `POST /api/iam/auth/mfa` with guessed codes takes `failed_attempts` to 4. That is below 5, so no lock.
  3. Back to step 1, which sets the counter to 0 again.

  The account never locks. With ±1 time step, about 3 of the 10⁶ codes are valid at any moment. Expect about 330,000 guesses (about 83,000 sign-ins), which is hours at modest request rates. Nothing throttles it (R-004).
- **Fix:**
  - Reset `failed_attempts` only when a session is actually issued. Move the reset into `ContinueAsync` just before `InsertSessionAsync`, and remove it from `SignInAsync` lines 82-85. Keep the reset at `CompleteMfaAsync` lines 132-135, or let `ContinueAsync` handle both.
  - Also end a challenge token after a small number of wrong codes, for example 3.
- **Test to add:** password → 4 wrong codes → password → 1 wrong code → the account is `locked`.

### 2. HIGH: concurrent failures are lost, so the lockout threshold can be bypassed with parallel requests

- **Where:**
  - `IdentityDb.cs:82-90` (`FindForSignInAsync`) and `:93-99` (`GetAccountAsync`).
  - `AuthenticationService.cs:371-375` (`CountFailureAsync`).
  - `IdentityDb.cs:120-121` (`SetFailuresAsync`).

  The comment at `IdentityDb.cs:80` says the credential row is locked "so concurrent failures are counted exactly". That is not true: only `u` (users) is locked.
- **Why:** in PostgreSQL READ COMMITTED, a statement waiting on `FOR UPDATE OF u` still returns the `user_credentials` row from its own snapshot. Every waiting request therefore reads the same old `failed_attempts` and writes back the same `+1`.
- **Evidence:** a reproduction with the same statement shapes. The script was run from the scratchpad and the database dropped afterwards.
  - With the code's pattern, 10 concurrent wrong passwords left `failed_attempts = 1`.
  - With the proposed fix (lock the user, then `update user_credentials set failed_attempts = failed_attempts + 1 … returning failed_attempts`), the same 10 left `failed_attempts = 10`.

  (`FOR UPDATE OF u, c` is not an option: PostgreSQL refuses it on the nullable side of the outer join.)
- **Scenario:** an attacker sends batches of 100 parallel guesses. Each batch adds 1 to the counter, so 5 batches = 500 guesses before a 15-minute lock, instead of 5. The same flaw applies to MFA codes (finding 1), through `GetAccountAsync`.
- **Fix:**
  - Do the increment atomically in SQL, with `returning failed_attempts`, and decide the lock from the returned value.
  - Or re-read the credential in a second statement after the user row is locked, because a new statement takes a new snapshot.
  - Correct the comment.
- **Test to add:** fire 10 parallel wrong sign-ins and assert `failed_attempts = 10` and status `locked`.

### 3. MEDIUM: deadlock between refresh and sign-in, administrator revoke or status change (opposite lock order)

- **Where:**
  - Refresh locks the session row first (`IdentityDb.cs:209`, called at `AuthenticationService.cs:226`), then the user row (`GetAccountAsync`, line 257).
  - Sign-in locks the user row (`FindForSignInAsync`), then updates other sessions in `EnforceConcurrentLimitAsync` (`IdentityDb.cs:235-243`).
  - The administrator `RunAsync` locks the user (`AccountServices.cs:254`), then `RevokeAllSessionsAsync` (`:196`, `:227`).
- **Evidence:** a PostgreSQL reproduction of the two orders (session→user against user→session) gave `ERROR: deadlock detected` on the sign-in side.
- **Scenario:** two cases trigger it.
  - A user has 3 sessions. Tab 1 refreshes its session at the moment they sign in on a 4th device, which revokes that same oldest session. One request returns 500.
  - An administrator disables a user while the user's browser refreshes. The disable can fail with 500 and must be repeated.
- **Fix:**
  - Use one lock order everywhere: user, then session. In `RefreshAsync`, read `user_id` of the session without a lock, lock the user, then lock the session `for update` and re-check it.
  - Optionally retry once on SQLSTATE 40P01.

### 4. MEDIUM (needs a product-owner decision): self-service security actions need no re-authentication; password change leaves other sessions open

- **Where:**
  - `AccountServices.cs:20-42`: the wrong "current password" is not counted toward lockout, and other sessions are not revoked after the change.
  - `AccountServices.cs:77-100` (add authenticator), `:102-123` (remove authenticator), `:125-139` (regenerate recovery codes).
- **Scenario:** an attacker gets a 5-minute access token, for example from a shared PC or a future XSS. With only that token they can:
  - Call `POST /api/iam/me/recovery-codes`. They get 10 working second factors and the victim's own codes stop working. Together with a phished password, that bypasses MFA for good.
  - Brute-force the current password through `POST /api/iam/me/password` with no lockout.
  - Keep their stolen session for up to 12 hours (absolute timeout) after the victim changes their password because they suspect a leak.
- **Rule:** spec 02 and spec 04 USR-10 say nothing about step-up for web. Only FR-KRN-IAM-19 (mobile, 1.1) mentions it. R-003 covers enrolment at sign-in only.
- **Suggested:**
  - Require the current password, or a current TOTP code, for recovery-code regeneration and for device add or remove.
  - Count wrong current passwords like sign-in failures.
  - Revoke the user's other sessions after a self-service password change.
  - Record this as a CR if accepted.

### 5. MEDIUM: Argon2 work on anonymous endpoints is unbounded (shared-host memory exhaustion)

- **Where:**
  - `AuthenticationService.cs:46,50`: every sign-in runs 19 MiB Argon2id.
  - `IdentityDb.cs:326-333`: one recovery-code attempt runs up to 10 Argon2id verifications.
  - `Crypto.cs:24`.
- **Scenario:** 1,000 concurrent anonymous sign-in requests to any one customer's host need about 19 GB of hashing memory. The API host is shared, so every customer slows down or the process is killed. R-004 covers password spraying through rate limits but not this.
- **Fix:**
  - Now: put a small process-wide semaphore around `IPasswordHasher.Hash/Verify`, sized to the core count, with a queue timeout that answers the same generic failure.
  - Later: add rate limits with R-004.
  - Recovery codes have 50 random bits, so an HMAC would do. That would change the approved column comment ("Argon2id hash") and so needs a CR. Alternatively keep Argon2 and stop after the first match, which is already done.

### 6. LOW–MEDIUM: "refresh reuse" fires for any wrong secret, so anyone who knows a session id can end that session

- **Where:** `AuthenticationService.cs:239-244`. Refresh tokens are `{session id}.{random}` (`:394`).
- **Scenario:** the session id is not secret. It is the `sid` claim in every access token, and it is returned by `GET /api/iam/users/{id}/sessions`. Posting `"<sid>.x"` to `/api/iam/auth/refresh` revokes the victim's session. The `SessionsRevoked` event names the victim as the actor, which misleads the S1.07 audit trail.
- **Fix:**
  - Keep the previous refresh hash, a new nullable column through a CR.
  - Treat only a match with an earlier token as reuse. Any other mismatch is a plain failure.

### 7. LOW: revoked sessions keep working for up to 6 minutes, not 5 (ruling Q3)

- **Where:** `src/Host/Erp.Host.Api/ApiHost.cs:90`, `ClockSkew = TimeSpan.FromMinutes(1)`, with a 5-minute lifetime (`Crypto.cs:319`).
- **Fix:** the issuer and validator are the same servers, so set `ClockSkew` to `TimeSpan.Zero` or a few seconds. Or shorten the lifetime to 4 minutes. See test gap T3.

### 8. LOW: key rotation needs every API host restarted at once

- **Where:** keys are loaded once at start-up (`ApiHost.cs:62-63`). `auth-key rotate` says "restart the API hosts" (`OperatorCommands.cs:203`).
- **Scenario:** with two or more instances, the first host to restart signs with the new key. Hosts not yet restarted reject those tokens, so users get random 401s until all hosts restart.
- **Fix:** rotate in two phases. Add the new key as validation-only, restart, then promote it. Or reload the index periodically. Describe it in `docs/runbooks/tenant-operations.md`.

### 9. LOW: small timing difference between unknown and known users; malformed attempts not logged

- **Where:** `AuthenticationService.cs:44-48` against `:56,73`.
  - Known users with a wrong password also read the policy and update the credential, which adds a few milliseconds over Argon2. That can be measured over many samples (slice build item 3: "similar timing").
  - The early return at `:35` (empty or over-long input) writes no `iam.login_attempts` row ("every attempt written").
- **Fix:** read the policy on every path, and log the early return as `bad_password`.

### 10. LOW: policy values are used without bounds on read

- **Where:** `IdentitySettings.cs:99-109`, used at `IdentityDb.cs:235-243` and `AuthenticationService.cs:252`.
- **Scenario:** a stored value outside the intended range breaks sign-in:
  - `iam.session.max_concurrent = 0` revokes the session just issued.
  - A negative value gives an SQL error, `OFFSET must not be negative`.
  - A non-integer number makes `GetInt32` throw, so every sign-in of that customer returns 500.

  Write-side validation arrives with S1.15, but `cfg.setting_values` can be written before then.
- **Fix:** clamp to each definition's `Min` on read, and fall back to the default on parse errors.

### 11. LOW (question): a user-level "MFA not required" overrides a customer-wide requirement

- **Where:** `IdentitySettings.cs:82,85`. `coalesce(u.value, t.value, …)` lets a user-layer `false` beat a tenant-layer `true`.
- **Question:** may a per-user setting relax the customer's mandate, or only tighten it? The slice says "enforcement per customer and per user" and does not decide this. If only tightening is intended, compute `required = tenant OR user`.

### 12. LOW: sign-in by e-mail can be shadowed by another user's username

- **Where:** `IdentityDb.cs:86-88`. The lookup orders by username match first, and nothing stops user B's username being equal to user A's e-mail.
- **Scenario:** an administrator creates a user named `alice@corp.pk`. Alice can no longer sign in with her e-mail; it now finds the other account.
- **Fix:** refuse `@` in usernames, or check uniqueness across both columns.

### 13. LOW: some self-service security changes raise no event (CLAUDE.md "every change audited")

- **Where:**
  - Recovery-code regeneration (`AccountServices.cs:125-139`).
  - Self-service session revoke (`:51-59`).
  - Sign-out (`AuthenticationService.cs:278-285`).
- **Fix:** raise `iam.*` outbox events so S1.07 can record them.

### 14. LOW: `iam.one_time_tokens` is never cleaned up

Rows are created on every sign-in step and live forever, so the table grows without bound. Add a retention item for the worker slice.

## Checked and found correct

- **Tenant isolation:**
  - One database per customer.
  - Every identity lookup (account, session, one-time token, recovery code) runs on the host-bound customer's data source.
  - The `tenant` claim is compared with the host-resolved customer for every authenticated request (`TenantResolution.cs:99-102`).
  - Covered by `IdentityTests.cs:72-74,387` and the S1.04 suite. Signing keys are shared across customers, which is safe only because of that claim check.
- **SQL:**
  - All values are parameters. The only interpolated text is the constant `AccountColumns`.
  - One-time tokens use `FOR UPDATE` with `used_at is null`, which is re-evaluated after a wait, so a token cannot be used twice.
  - The seat limit uses an advisory lock.
- **TOTP:** replay protection stores the accepted step's start time and updates it conditionally, so it holds under concurrency. The ±1 step window is correct.
- **Refresh rotation:** the session row lock makes a second concurrent refresh with the same token count as reuse, per P6. S1.12 should know that two browser tabs refreshing at once will end the session.
- **Crypto:**
  - Argon2id with the OWASP minimum, a 16-byte salt, PHC parsing with bounds and fixed-time comparison.
  - AES-256-GCM in a versioned format, with a random 96-bit nonce and the purpose as associated data.
  - 256-bit opaque tokens stored as SHA-256 hashes.
  - ES256 only (`ValidAlgorithms`).
- **Generator and migration:**
  - `added_in`, `updatable_added_in` and `api_read_only` work as described.
  - The validator restricts later changes to expand-only shapes.
  - The new migration is idempotent, and every foreign key has an index.
  - The generated user API no longer accepts `status`, `is_system` or `last_login_at`, and new users start `invited` (P1 / CR-012).
- **Rulings:** P2 transitions, P3 automatic and administrator lock, P4 seat counting, P5 generic failure and P9 grace calculation are implemented as written.
- **Other rules:**
  - Localisation: every `errors.*` key used exists in English and Urdu.
  - No `DateTime.Now`/`UtcNow` in business code.
  - Licences are recorded.
