**Summary for the product owner.** Most of this part is sound. A pack is a zip whose manifest lists the SHA-256 of every file and is signed
with a key registered for packs only; a changed byte, an unlisted or oddly named file, an oversized file, a statutory object type, an
unknown, revoked or expired key are all refused, and the signature is checked again before every install, so a key revoked after
publishing stops its packs. Packs come only from the vendor's catalogue and must be licensed for the customer. The customer's changes are
found by comparing each object with what the installer left, which is a better design than a flag every screen must remember to set, and
for settings, labels, option lists, holidays and banks it works as the slice asks: the customer's value stays and the pack's new value is
shown beside it. Install, upgrade and "take the pack value" need their own permissions, wait for a second person when the new setting is on,
and the requester cannot approve. Provisioning installs the chosen packs; the wizard's step links to the pack manager. All tests pass,
including the tenant-isolation suite.

One high point must be fixed before the merge:
- **An upgrade overwrites HR's own policy version when that version starts in the future.** I reproduced it: HR schedules its own
  version of a pack policy (15 days) from day +30; a pack upgrade on day 0 treats the policy as unchanged, cuts HR's version to one day
  (day +30 only) and puts the pack's new value (12 days) in force from day +31. The report says "updated", not "kept". This is exactly
  what FR-KRN-CFG-02 and FR-HRM-POL-06 forbid (a tenant override silently lost).

Three medium points need a fix or your ruling:
- "take the pack value" on a pack policy lets a tenant administrator who may not manage HR policies replace HR's version in force, in
  any company, without HR's own approval setting (reproduced);
- an upgrade on the same day the pack's latest version started (for example the day of provisioning) makes the pack's own new value
  look like a customer change from the next day on, so the following upgrade is not applied and a false conflict is listed (reproduced);
- a held "take the pack value" shows the approver only the pack id, not the object or the two values, and a held upgrade without a
  version applies whatever is newest when it is approved, which may not be what the requester saw.

## Findings, most severe first

### 1. HIGH: an upgrade overwrites HR's own policy version that starts in the future (FR-KRN-CFG-02, FR-HRM-POL-06, Build item 10)
- `PolicyPackHandler.ReadAsync` (`PolicyPackHandler.cs:85-104`) reads the parameters of the version in force **today** only. A version HR
  activated from a later date is not seen, so the policy hashes like what the installer left and `PackInstaller.ApplyObjectAsync`
  (`PackInstaller.cs:297, 308-316`) takes the "unchanged by the customer" path and writes the new pack value.
- `PolicyPackHandler.ActivateAsync` (`:192-216`) then takes the latest non-draft version, which is HR's future one, starts the pack's
  version the day after its start (`:211`) and sets HR's version's `valid_to` to that day (`:214`). HR's version lasts one day. The
  report counts it as `updated`; nothing is listed as a conflict, and the change log shows only a pack version created.
- Failure scenario (R1): HR has agreed a new notice period (or, from S1.32, a leave policy) with the union from 1 July and activated it in
  June. On 20 June the administrator installs pack 1.0.1 because the pack manager lists the policy as unchanged. From 2 July the
  company runs on the pack's value; HR's version applied for one day. Nobody is told.
- Suggested fix: in `ReadAsync`, read the policy as a whole, not one day of it: every non-draft version from today on (version number,
  start, end, parameters and `is_overridden`) or at least "the version in force today plus any later version"; then any version HR added
  after the installer's write changes the hash. In `ActivateAsync`, never end a version that starts after today; when the latest version
  starts in the future and was not written by the pack, treat the object as changed (keep, record the conflict). Add R1 as a test, and the
  same case with a pending HR draft (drafts are not versions, so they should not count).

### 2. MEDIUM: "take the pack value" and pack upgrades change HR policies without HR's permission, company scope or approval setting (S1.23a ruling Q1; CR-079 (h), (k))
- `POST /api/cfg/packs/items/{id}/take-pack-value` checks only `cfg.installed_packs.update` (`PackEndpoints.cs:39-41`); `PackManager`
  holds it only while `cfg.packs.requires_approval` is on (`PackManager.cs:156-197`); `PackInstaller.TakePackValueAsync`
  (`PackInstaller.cs:193-227`) then writes through `PolicyPackHandler.WriteAsync`, which activates a new version from today
  (`PolicyPackHandler.cs:152-155, 187-227`). None of `hrm.policies.manage`, the company data scope of `hrm.policies`, or
  `hrm.policies.requires_approval` (per company; `PolicyService.cs:306, 486`) is consulted. Tenant Admin holds `cfg.*` but no `hrm.*`.
- The same holds for an upgrade that changes an unchanged pack policy (Build item 11 names the tenant administrator, so that may be
  intended), but "take the pack value" is a deliberate replacement of a value HR set, one object at a time.
- Failure scenario (R2): HR set a 15-day leave policy for company A with their four-eyes setting on. A tenant administrator who cannot
  open HR policies at all presses "take the pack value" on that item; from today company A runs on the pack's 10 days, with no HR approval.
- Suggested fix: ruling needed. Recommended: let each handler state the permission (and scope) its objects need for "take the pack
  value" (a member of `IPackObjectHandler`, for the policy handler `hrm.policies.manage` in the item's company), and hold it under the
  owning module's approval setting when that is on (for policies `hrm.policies.requires_approval`), in addition to
  `cfg.packs.requires_approval`. For upgrades, record in CR-079 that a pack upgrade may change unchanged pack policies under the
  tenant administrator's authority alone, or apply the same rule. Add R2 as a permission test.

### 3. MEDIUM: after an upgrade on the day the latest version started, the pack's own value counts as a customer change (Build item 10, CR-079 (f))
- After writing, the installer records `applied_hash` from `ReadAsync` straight away (`PackInstaller.cs:278-280`). When the new pack
  version starts tomorrow (`PolicyPackHandler.cs:211`: the latest version started today), `ReadAsync` still returns today's (old)
  parameters, so `applied_hash` is the old value's hash. From tomorrow the policy hashes differently from `applied_hash` and is counted as
  changed by the customer.
- Failure scenario (R3): a customer is provisioned with `country-pk` 1.0.0 and the vendor's 1.0.1 is installed the same day (or an
  administrator upgrades twice in a day). From the next day the pack manager lists the policy as "changed by the customer" although
  nobody touched it; the next upgrade keeps the stale value and lists a conflict, so the customer stops receiving that policy's updates
  unless someone presses "take the pack value".
- Suggested fix: the fix of finding 1 (read every version from today on) removes this too, because the version written for tomorrow is
  then part of what the installer left. Add R3 as a test.

### 4. MEDIUM: the approver of a held pack action cannot see what is approved, and may approve something other than what was asked (FR-XM-32 intent, Build item 11)
- `PackChangeHandler.DescribeAsync` (`PackManager.cs:400-415`) shows the action and the pack id, and the version only when the request
  named one. For "take the pack value" the payload holds the item id only (`PackPlan`, `:42`); the approver sees neither the object
  (type, key, company) nor the customer's value and the pack value that will replace it.
- At approval the action is re-planned on the newest data: an upgrade without a version (`UpgradeAsync`, `:150-154`; the API allows it,
  the screen always sends one) loads the newest compatible version at that moment (`PackCatalog.LoadAsync`, `PackCatalog.cs:152-160`), and
  a "take the pack value" takes the item's `conflict_value` as it is then (`PackInstaller.cs:199`), which a later upgrade may have changed.
- Failure scenario: a requester asks to take the pack value of "PK holiday 2027-03-23" in good faith; the approval list says only "Take
  the pack value, country-pk"; the approver approves blind. Or: an upgrade is requested by the API while 1.0.1 is newest, 1.0.2 is
  published the next day, and the approval installs 1.0.2, which the requester never reviewed.
- Suggested fix: at submit, resolve and store the version (upgrade, install) and, for "take the pack value", the item's type, key,
  company, the value to be taken and its hash; show them in `DescribeAsync` (both values for a take); at approval refuse
  (`HeldChangeProblem`) when the stored version or value no longer matches. Add tests for a held upgrade and a held take.

### 5. LOW: the pack manager's read views lock rows and can fail with a serialization error
- `OverviewAsync` and `ItemsAsync` open a `RepeatableRead` transaction (`PackManager.cs:56, 98`) and read every live object through the
  handlers, whose reads take row locks (`for update` in `KernelPackHandlers.cs:297, 325, 399, 476, 572, 662`, `PolicyPackHandler.cs:90`).
  In repeatable read, `select … for update` of a row another transaction changed and committed after the snapshot raises
  "could not serialize access due to concurrent update" (SQLSTATE 40001), which is not caught: the page answers 500. While the view runs
  it also blocks HR and administrators editing those rows (R-263: with thousands of objects this is seconds).
- Suggested fix: give the handlers a read without locks for the views (a flag in `PackObjectContext`, or `ReadAsync` locking only when
  the installer asks), or read in read committed.

### 6. LOW: "today" is the UTC date, and upgrades may add or change past holidays
- `PackInstaller` uses `DateOnly.FromDateTime(now.UtcDateTime)` (`PackInstaller.cs:133, 208, 242`). In Pakistan (UTC+5) an install or
  upgrade between midnight and 05:00 dates pack policy versions the day before and treats today's holiday as "future" when retiring
  (`HolidayHandler.RetireAsync`, `KernelPackHandlers.cs:609`: removed instead of kept).
- Retiring keeps past holidays because "attendance already counted it" (CR-079 (g)), but a new pack version may still add a holiday on a
  past date or change a past holiday's kind or tentative flag (`HolidayHandler.WriteAsync`), which attendance and pay of closed periods
  counted differently.
- Suggested fix: use the company's or the customer's local date (HR's `applier.TodayAsync` does this for pay calendars), and apply the
  "past holidays are kept as they are" rule to add and update as well (record them as conflicts instead), or record the choice in CR-079.

### 7. LOW: "retired" is reported for objects left in place
- When a pack policy is still assigned, `PolicyPackHandler.RetireAsync` leaves it (`:168-173`), but the installer marks the item
  `retired_in` and reports it `retired` (`PackInstaller.cs:166-178`); the policy stays active and nothing retires it once HR moves the
  assignments. The same for a past holiday (kept on purpose). The pack manager then shows "retired" for an object that is still in use.
- Suggested fix: let `RetireAsync` say whether it retired or left the object, report "left in place" separately, and keep such items
  live (not `retired_in`) so a later upgrade tries again.

### 8. LOW: the pack's items view shows HR policy parameters of every company to anyone who may read packs
- `GET /api/cfg/packs/{id}/items` (`PackManager.cs:94-140`) and the generated `GET /api/cfg/pack-items` return `pack_value`,
  `conflict_value` and (the manager) the current value of every company's pack policy to holders of `cfg.installed_packs.read` /
  `cfg.pack_items.read` (the Auditor role has `cfg.*.read`), without `hrm.policies.read` or the company scope. Policy parameters are not
  personal data, but S1.23a scopes them by company.
- Suggested fix: filter company items by the caller's `hrm.policies` read scope (or show only the counts), or record the choice.

### 9. LOW: an install adopts a customer's identical object, and two packs can own one object
- When a customer already has an object with the pack's key and the same value, the install records it as the pack's own (`unchanged`,
  `applied_hash` set; `PackInstaller.cs:292-294`). A later version that drops it then retires the customer's own bank, list or item. Two
  packs that hold the same object (the same bank, or a setting key, R-262) both record it; one pack's upgrade then changes or retires what
  the other pack (or the customer) relies on, and installs of two different packs are not serialized (the lock is per pack id, `:131`).
- Suggested fix: record "existed before the pack" on the item and never retire such objects; take one lock for all pack installs of a
  customer (installs are rare).

### 10. LOW: missing tests for rules CR-079 states
- No test covers: retiring a future and a past holiday, a still-assigned pack policy, a pack-layer setting and a label (only the bank is
  retired in `PackTests`); a held upgrade and a held "take the pack value" (only a held install is tested); a failing object rolling back
  the whole pack (one transaction per pack); a customer object of the same key at first install (kept, value offered); a pack for a
  country with no company (no policy items). Findings 1, 3 and 4 would have been found by such tests.
- Suggested fix: add them, citing FR-KRN-CFG-02 and FR-HRM-POL-06.

### 11. LOW: smaller points
- a) Install and upgrade permissions (`cfg.installed_packs.create|update`) are not sensitive (`PackContracts.cs:23-24`), although an upgrade
  can change HR policies in every company; sensitive permissions require a second factor (S1.06). Consider marking them sensitive.
- b) `PackCatalog.LoadAsync` checks the loaded file's pack id against the catalogue row but not its version (`PackCatalog.cs:170-174`), and
  the listing trusts the unsigned `manifest` column for compatibility and display. Only someone who can write `cp.pack_catalog` could
  exploit it (for example a downgrade); check `pack.Manifest.Version == row.Version` too.
- c) Statutory values can still travel inside policy parameters (a `notice_period` or, later, a leave policy): the forbidden-type list
  (`PackManifest.cs:55-59`) does not see them. S1.23c's content check (Build item 13) should also review policy objects against AS-4.
- d) `cfg.pack_items.content_hash` is described as the hash "from the manifest" (`kernel.yaml`, data dictionary), but it is the hash of the
  normalized value, not the manifest's file hash; correct the comment with the next data-design change.
- e) The change log records the objects written and the installed pack, but not the item-level outcomes (a conflict recorded,
  `retired_in`, `is_overridden`); the install report is the only record of "kept" objects. Consider one change-log entry per kept or
  retired item.

## Checked and found in order
- Tenant resolution: every pack endpoint works on the tenant from the host and token (`ITenantConnectionProvider`); the control plane is
  read only for the shared vendor catalogue and keys. `PackProbe` covers the five routes (crossed host and token, A's item id from B: 404).
- Permissions: read, install, upgrade and take are checked before any work (`PackEndpoints.cs:52-55`); approval needs the sensitive

- Transactional and posted rows: the handlers write only configuration and reference tables (settings, labels, option lists, calendars,
  holidays, banks, policies and versions); a version in force is never edited (subject to finding 1 for future versions).
- D-10: the HR handler lives in HR and is registered by HR (`PolicyServices.cs`); the kernel reaches it only through
  `IPackObjectHandler` (Kernel.Contracts). Architecture tests pass.
- Statutory content: no rate, slab or threshold in code or manifests; statutory object types are refused at build and install.
- Injected clock throughout (`IClock` in the manager, catalogue and provisioning; the context's `Now` in handlers); no floating point; user
  texts are keys with English and Urdu files (`packs.*.json`); the screen uses logical properties and `<bdi>` for codes and values.
- Settings: only `org.time_zone` and `cfg.numbering.fiscal_year_start_month` allow the pack layer, neither needs approval, so the setting
  handler cannot bypass a setting's own maker-checker today.
