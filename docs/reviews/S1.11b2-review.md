## Summary for the product owner

Most of the e-mail work is sound:
- E-mails are queued in the same transaction as the event, so one event never gives a person two e-mails.
- A message is locked while it is sent, so two senders never send the same message twice.
- Links and codes never appear in the delivery log, the outbox or the audit trail. They are stored encrypted and wiped once the message ends.
- Forgot password gives the same answer, after at least the same time, whether or not the account exists.
- A reset link works once, expires, and ends every session.
- An e-mail code works only for the sign-in step it was sent for, once, within its time and within its try limit.
- Links in e-mails always use the customer's registered web address, never one taken from the request.

I found **two serious defects**. The first one breaks the wall between customers, so it should be fixed before any customer goes live, even a pilot:

1. **A customer's Tenant Admin can read secrets of the whole platform.** The mail sender looks up which mail server a customer uses in a table the customer's own Tenant Admin can edit through the normal API. That row also names a secret in the platform's shared secret store (the store that holds every customer's encryption keys, the token-signing keys and the database administrator login). The sender fetches whatever secret the row names and sends it as the mail-server password to whatever server the row names. I proved this on the real database: a Tenant Admin of customer A set up a "mail server" on a machine they control. The next e-mail made the worker send **customer B's field encryption key** to that machine. Naming the token-signing key instead would let them create sign-in tokens for any customer.
2. **An administrator who may edit users can take over a more senior account.** A Company Admin (no sensitive permission) can change a Tenant Admin's e-mail address to their own and then click "forgot password". The reset link comes to them. They set a password, sign in as the Tenant Admin, and the real Tenant Admin is signed out. If the Tenant Admin's second factor is the e-mail code, that code also goes to the new address, so the second factor is no obstacle either. A Tenant Admin can do the same to another Tenant Admin and then approve their own maker-checker requests. Both cases are proved by tests. How to protect an e-mail change is **your decision**; I give options below.

There are also **four medium issues**:

3. "Forgot password" for an account under an automatic lock is meant to work (your choice CR-049 (a)). In practice the e-mail is never sent: the sender drops it because the account is not "active". The slice test only looked at the queue, not at what was sent.
4. Sign-in codes and reset links wait in line behind ordinary notification e-mails. After a burst (for example 1,000 escalation e-mails at 60 a minute), a 10-minute sign-in code can expire before it is sent, so people who use the e-mail code cannot sign in.
5. The bounce reader takes **out-of-office replies** (and ordinary replies) for bounces. It then marks delivered e-mails as "failed" and writes that into the audit trail, which cannot be corrected afterwards.
6. A malformed reply-to address, for example `hr,payroll@acme.test`, passes the setting's check. The mail library then refuses it, and every e-mail of that customer stops, password resets included, until someone notices.

The low items are listed below.

I recommend:
- Fix 1 at once, with a small code guard now and a design change (CR-062).
- Decide 2, and fix it before go-live.
- Fix 3 to 6 in the same pull request. Each needs a few lines and a test.

## Findings, most severe first

### 1. HIGH (critical): the mail connector is customer-writable and names any secret, which the worker sends to a server the customer chose

- **Where:**
  - `src/Platform/Erp.Kernel.Infrastructure/Notifications/Email/MailTransport.cs:62-76`. `MailServerResolver.ResolveAsync` reads `provider`, `config` and `credentials_ref` from `itg.connectors` (kind `email`, code `email`). It calls `secrets.GetAsync(connector.Ref)` with no check, and returns a `MailServer` with that host.
  - `MailTransport.cs:147-150`: the SMTP adapter then authenticates to that host with the secret as password.
  - `itg.connectors` has generated `create`/`update` endpoints (`/api/itg/connectors`). `credentials_ref` is an ordinary writable column there (`docs/data-design/kernel.yaml:1156-1167`; `ConnectorEndpoints.g.cs:237`). Tenant Admin holds `itg.*`.
  - CR-049 (4) says "the customer's own server lives in `itg.connectors` code `email`, its password in the secret store". Only the operator command `mail server` was meant to write it, but the API writes it too.
- **What the secret store holds** (one store for the whole host):
  - Every customer's field and file keys: `tenants/<code>/field-key-v1`, `tenants/<code>/file-key-v1`.
  - The token-signing private keys: `platform/token-signing/<kid>`. The `kid` is in the header of every access token.
  - The database cluster administrator login: `cluster/<name>/admin`.
- **Proof:** `Finding0_a_tenant_admin_reads_another_customers_secret_through_the_mail_connector`.
  1. A `tenant_admin` of customer A posts a connector: `{code: email, kind: email, provider: smtp, config: {host: 127.0.0.1, port: <test listener>, security: none, username: x}, credentialsRef: "tenants/<customer B>/field-key-v1"}`.
  2. A forgot-password request queues an e-mail, and the worker runs.
  3. The listener (it offers `AUTH PLAIN`) receives customer B's field key as the password. The test asserts that it equals `fx.Secrets.GetAsync("tenants/<B>/field-key-v1")`.
- **Consequences:**
  - Cross-customer data exposure: D-02/D-47 isolation is broken.
  - Forged access tokens for any customer.
  - Database administrator access.
  - Also, a `relay` connector written through the API sets any `from_address` on the operator's relay. That bypasses the operator's domain checks, which allows spoofed senders and harms the relay's reputation.
- **Fix:**
  - At once, in code:
    - `ResolveAsync` uses only `MailSetup.PasswordReference(tenantCode)` and ignores any other `credentials_ref`.
    - The connector row is honoured only when the migrator wrote it. For example, `MailSetup` stamps `created_by = BaselineSeed.SystemUserId`, and the resolver requires that stamp and that `updated_by` is unchanged.
  - Design (CR-062):
    - Close generated writes of `itg.connectors` for `kind = email`, or make `credentials_ref` `api_read_only`.
    - More generally, a secret reference is never taken from a customer-writable column: the code derives it from the customer code.
    - Check the biometric connectors (S1.17/attendance), which will read `credentials_ref` too.
- **Tests to add:**
  - The proof, inverted: the listener receives no password, or the customer's own mail password only.
  - A generated `PUT /api/itg/connectors/{id}` that changes `credentials_ref` or a `kind = email` row is refused.

### 2. HIGH (needs a product-owner decision): an e-mail change by an administrator re-points password reset and the e-mail factor, so lower administrators can take over higher accounts

- **Where:**
  - `iam.users.email` is writable through the generated `PUT /api/iam/users/{id}` with `iam.users.update`, which is not a sensitive permission. Baseline Company Admin holds it with scope `all` (`baseline-roles.json`).
  - S1.11b2 made the address a credential:
    - `IdentityEmailService.RequestPasswordResetAsync` (`IdentityEmails.cs:137-175`, anonymous).
    - `IdentityMail.QueueAsync` reads the current address (`:95`).
    - The e-mail factor sends its codes to the current address (`:310-323`). The factor's label still shows the old masked address.
  - Nothing ends open reset links or codes when the address changes, tells the old address, or asks the new one to confirm.
- **Proof:**
  - `Finding1_company_admin_changes_a_tenant_admins_email_and_takes_the_account_by_forgot_password`:
    1. The Company Admin changes the Tenant Admin's e-mail.
    2. Anonymous `POST /api/iam/auth/password/forgot` with the victim's username queues the link to the attacker's address.
    3. The reset succeeds, and the attacker signs in as the Tenant Admin. The victim's refresh token is refused.
  - `Finding1_the_email_factor_follows_a_changed_address`: the same with an e-mail factor enrolled. The sign-in code goes to the new address, and the attacker gets tokens.
  - An authenticator (TOTP) still stops the sign-in, but the victim is locked out.
- **Why HIGH:**
  - Before S1.11b2 no administrator could learn another active user's password.
  - Now one non-sensitive permission is enough to take over any account whose second factor is the e-mail code, or that has no factor yet (grace period, or enrolment after it).
  - It also defeats maker-checker (FR-XM-32, S1.06 Q10): a Tenant Admin who takes a second Tenant Admin's account can approve their own requests.
- **Options (decision needed, CR-062):**
  - (a) Recommended, smallest: an address change of an active user is a security change.
    - It needs a new sensitive permission, `iam.users.change_email`. The generated write of `email` closes, and a hand-written action replaces it.
    - For a user who holds a privileged role, it goes through maker-checker.
    - It ends open reset links and e-mail codes, and suspends the e-mail factor until the person confirms it again.
    - It e-mails a notice to the old address.
  - (b) Like (a), and the new address must also be confirmed by a link sent to it before resets and codes use it. This needs a `pending_email` column (data design change).
  - (c) Keep editing as is, but refuse reset links and e-mail codes for 24 hours after an address change, and tell the old address. This is weaker.

### 3. MEDIUM: the reset e-mail of an automatically locked account is never sent (CR-049 choice (a) does not work)

- **Where:**
  - `EmailSendJob.cs:183-185` (`StillValidRecipientAsync`) sends only to `status = 'active'` (or an invited person's invitation).
  - `IdentityEmailService.MayReset` (`IdentityEmails.cs:293-294`) queues a reset for an account under an automatic lock. The sender then finishes it as `dead`: "no valid e-mail address, or the person can no longer sign in".
- **Proof:** `Finding2_the_reset_email_of_an_automatically_locked_account_is_never_sent`.
  - Five wrong passwords lock the account.
  - Forgot password queues the reset, and the worker runs.
  - The test SMTP server receives nothing, and the row is `dead`.
- **Fix:** in the sender, apply the same rule as `MayReset` to `identity.password_reset`: active, or locked with `locked_until` set. Share one SQL predicate so the two cannot drift.

### 4. MEDIUM: identity e-mails wait behind notification e-mails for the per-minute budget

- **Where:** `EmailSendJob.cs:78-82`. Due messages are taken oldest first, up to `ntf.email.per_minute` (default 60). `RequestSendSoonAsync` starts a run, but that run spends its budget on the older notifications first.
- **Proof:** `Finding3_a_sign_in_email_waits_behind_older_notification_emails`. With `per_minute = 2` and 10 older workflow e-mails, a forgot-password e-mail stays `queued` after the worker is idle.
- **Scenario:** an escalation run queues 1,200 e-mails. For the next 20 minutes:
  - E-mail-factor users cannot sign in, because their codes expire in 10 minutes.
  - Reset links arrive late.
- **Fix:** send messages that carry a secret, or `identity.*` messages, first (`order by (secret is null), coalesce(next_attempt_at, created_at), id`). Optionally exempt them from the budget.

### 5. MEDIUM: out-of-office and ordinary replies are taken for bounces, and the false "failed" goes into the audit trail

- **Where:** `EmailBounceJob.cs:28-51`. Any message whose text contains our Message-ID counts. Without a delivery-status part it becomes `bounced: <subject>`.
  - Auto-replies (RFC 3834) go to the return path, which is the bounce mailbox, and carry `In-Reply-To: <our id>`.
  - So does a person's reply when `ntf.email.reply_to` is empty and the relay's sender is the bounce mailbox.
  - The job then sets the delivered message to `failed` and, for audited events, appends a `failed` entry to the hash-chained change log. That entry cannot be corrected (append-only).
- **Proof:** `Finding5_an_out_of_office_reply_is_taken_for_a_bounce`. An `Auto-Submitted: auto-replied` message with `In-Reply-To` gives `Bounce(id, "bounced: Automatic reply: Task assigned")`.
- **Fix:**
  - Ignore messages with `Auto-Submitted` other than `no`.
  - Ignore messages that refer to our Message-ID only in `In-Reply-To` or `References`.
  - Accept a plain returned message only from a mailer-daemon or postmaster sender. Better: accept only `multipart/report; report-type=delivery-status`.
  - Keep the existing positive test, and add the out-of-office and reply cases.

### 6. MEDIUM: a reply-to value that passes the setting's check stops all e-mail of the customer

- **Where:**
  - The `ntf.email.reply_to` pattern `^$|^[^@\s]+@[^@\s]+\.[^@\s]+$` (`settings.yaml:309-312`).
  - `MailTransport.cs:196-199` calls `MailboxAddress.Parse(email.ReplyTo)` inside `SendAsync`. MimeKit's `ParseException` is not among the caught exceptions (`:157-167`), so it leaves the job. That message's transaction rolls back, and every later run fails on the first message again.
- **Proof (unit):** `a,b@acme.test`, `a;b@acme.test`, `a"b@acme.test` and `a(b@acme.test` all match the pattern and all throw `ParseException`.
- **Fix:**
  - Check the value with `MailboxAddress.TryParse` when the sender job reads it, and ignore an invalid reply-to (log a warning).
  - Tighten the pattern.
  - Treat a message that cannot be built as `dead`, not as an exception that stops the queue.

### 7. LOW: wrong R-003 confirmation codes never count towards the sign-in lockout

- **Where:** `AuthenticationService.cs:243-249`. A wrong e-mailed code in `ConfirmRequiredEnrolmentAsync` counts one try on that code, but never calls `CountFailureAsync`. Choice CR-049 (c) says a wrong e-mail code counts towards the lockout. That is implemented for sign-in codes only.
- **Proof:** `Finding4_wrong_enrolment_codes_do_not_count_towards_the_lockout`. 15 wrong codes over 3 codes leave the account `active` with `failed_attempts = 0`.
- **Effect:** someone with the password can try 50 codes an hour (10 codes × 5 tries) indefinitely, against 5 before a lock for sign-in codes. The odds are small (about 1 in 20,000 an hour), but the victim's mailbox fills with codes.
- **Fix:** call `CountFailureAsync` on a wrong `emailCode` too.

### 8. LOW: forgot password and reset can deadlock (opposite lock order)

- **Where:**
  - `ResetPasswordAsync` locks the token row (`FindTokenAsync … for update`, `IdentityEmails.cs:182`), then the user (`GetAccountAsync`, `:183`).
  - `RequestPasswordResetAsync` locks the user (`FindForSignInAsync`, `:150`), then updates the same token rows (`ExpireTokensAsync` in `SendResetAsync`, `:298`).
  - The same order problem exists for the administrator reset link.
- **Proof:** a two-session reproduction of these statements on PostgreSQL 16 gave `deadlock detected` on the forgot side.
- **Effect:** a double click or a second tab gets a 500. That differs from the normal 202, so it also tells whether the account exists, in that moment only.
- **Fix:** lock the user first in `ResetPasswordAsync`: read the token's `user_id` without a lock, lock the user, then lock and re-check the token. This is the same pattern as S1.05 review finding 3.

### 9. LOW: switching the e-mail method off strands users whose only factor is the e-mail code

- **Where:** `AuthenticationService.cs:397-415`. `HasActiveMfaAsync` counts e-mail devices even when the customer no longer allows the method. Those users then get `mfa_required` with an empty `mfaMethods`, and `/mfa/email-code` refuses them. Only recovery codes or an administrator's MFA reset get them in.
- **Fix:** count only devices of allowed kinds. Such a user then falls into the required enrolment, with the R-003 e-mailed confirmation. Or refuse to remove `email` from `iam.mfa.allowed_methods` while users depend on it.

### 10. LOW: e-mail codes are stored as unsalted SHA-256 of a 6-digit value

- **Where:** `IdentityEmails.cs:28`. `token_hash = SHA-256(binding + ":" + code)`, and the binding (challenge or device id) sits in the same database.
- **Effect:** anyone who can read `iam.one_time_tokens`, for example from a backup copy, finds a live code in a million hashes, which takes milliseconds. They would still need the password for sign-in.
- **Fix:** HMAC with the customer's field key (already loaded on these paths).

### 11. LOW: smaller points

- **Forgot password: no limit per source or overall.** There is no limit per source address and no global limit, only 5 an hour per account. A script can make the platform send 5 e-mails an hour to every known username. This is R-004 (rate limits); I note it here because S1.11b2 added the first anonymous endpoint that sends e-mail.
- **Delivery log: whole-mailbox reads (bounce job).** With the shared operator mailbox (choice (f)), other customers' reports and junk stay unread for good. `UnreadAsync` takes the first 500 unread (`EmailBounceJob.cs:118`). Once 500 such messages pile up, no customer's new bounces are read. Every customer's run also downloads up to 500 whole messages every 15 minutes.
  - **Fix:** search by UID above the last one this customer handled (stored per customer). Or let one operator job read the mailbox and route each report by the customer code in the Message-ID.
- **For S1.12:** the reset and activation pages carry the token in the query string (`/reset-password?token=`). The page should send `Referrer-Policy: no-referrer` and drop the token from the address bar after reading it.

## Checked and found correct

- **Secrets of identity e-mails:**
  - The link or code goes only into `secret` (AES-GCM, customer field key, purpose bound to `ntf.outbound_messages.secret`).
  - The stored subject and body keep a `{code}` / `{link}` placeholder.
  - The secret is wiped on sent, failed and dead (`FinishAsync`).
  - Identity e-mails are never resent (choice (e)).
  - `iam.email_code_sent` and `iam.password_reset_link_sent` events carry no code or token.
- **Links:** the base address is the customer's primary host from the control plane (`TenantHosts.PrimaryAsync`), never a request header, so reset-link poisoning is not possible. `EmailLayout.Absolute` accepts only relative paths and refuses `//`.
- **Forgot password:**
  - The same 202 with an empty body for unknown, disabled, administrator-locked and real accounts.
  - A minimum of 400 ms on every path, including early returns.
  - The hourly limit is counted after the user row is locked, so concurrent requests cannot exceed it.
- **Reset:**
  - The token row is locked and `used_at is null` re-checked, so it is used once.
  - Password policy and history apply. Other reset links end.
  - `failed_attempts` and `locked_until` are cleared. Every session is revoked.
  - An administrator's lock, a disabled, archived or invited account never qualifies.
- **E-mail codes:**
  - From `RandomNumberGenerator`, compared in fixed time.
  - Bound to the challenge or device, so a code for one step fails for another.
  - A new code ends the earlier one. Tries are counted under a row lock and the code ends at the limit.
  - At most 10 codes per person an hour.
  - At sign-in a wrong code counts towards the lockout (choice (c)).
  - R-003: every authenticator enrolled at sign-in after the grace period needs the e-mailed code, and the late-enrolment path issues no session without it.
- **Sender:**
  - Each message is taken with `for update skip locked` in its own transaction.
  - A 4xx retries after 1, 5, 15, 60 and 240 minutes, and a 5xx fails at once.
  - The recipient is re-checked at send time.
  - The Message-ID carries the customer code, so the bounce job of one customer cannot mark another's message.
- **Delivery log:**
  - Permission on every action.
  - Company scope by `CoversCompanyAsync`. Messages without a company need an all-companies role.
  - Test send goes only to the caller's own active address, with sample values limited to the event's declared fields (no salary-class fields).
  - Resend copies to the person's current address, never for identity e-mails.
- **SQL:** every value is a parameter. The only built SQL joins constant fragments (`DeliveryLog.Select`).
- **Rules:**
  - No `DateTime.Now`/`UtcNow` in the business code (the injected clock and `TimeProvider`).
  - Texts in English and Urdu.
  - MailKit, MimeKit and BouncyCastle are MIT and recorded in `docs/registers/dependencies.md`.
  - The new migration is additive, and frozen files are unchanged.
