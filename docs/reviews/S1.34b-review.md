## Summary for the product owner

Most of this part is careful work. Components keep their code and kind for ever and change only through dated versions; the method, the
pro-rata rule and its parameters, the statutory flag codes and the tax label are checked and stored, never evaluated, and no statutory value
appears anywhere. A salary is never edited: a revision ends the old row and opens a new one with its own employment event, and a backdated
one records the pay periods it reaches. The outbox events carry ids, dates and codes only. Amounts are hidden from people without the
salary field class in the compensation endpoint, the generated lists, the exports and the audit search, and the approval of a held change
is checked again in the approval's own transaction, under the employment's lock. All 13 integration tests of the part, the 740 unit tests,
the architecture tests and the generator drift check pass.

I found **3 high, 6 medium and 9 low** points. I reproduced each high point and three of the medium ones with a throwaway test against a
real PostgreSQL (the probe is not committed; the results are quoted under each finding).

The three high points must be fixed before the merge:
- **H1. A "data correction" of a salary revision changes an employee's job without the approval the company set for job changes.** With
  the default settings a promotion that changes the title waits for approval; a data correction that names the salary revision as the event
  it corrects changes the title at once (reproduced). The new event kind opened this gap in the employment rules.
- **H2. Salaries can be read without the salary permission through the kernel's list of held changes.** A tenant administrator (a baseline
  role with no salary access, refused on the compensation screen's API) reads every held salary and structure default, pending or already
  decided, from `/api/iam/maker-checker-requests/{id}` (reproduced). This is the risk R-278 asked this review to check: it is real today.
- **H3. A loop between components is not found when it starts at a later date.** Component B gets a version from day +30 based on A; then A
  gets a version from day +10 based on B. Both are accepted (reproduced), so from day +30 the two components are computed from each other.
  The calculation engine (S1.35) is meant to be able to trust "no cycle".

The medium points (a user without salary edit access can wipe amounts; the database guard protects ended rows only; an approver can approve
amounts they cannot see; the shipped roles cannot complete a salary change; structure changes ignore the salaries that use them and can be
backdated silently; a salary can start after the employment's recorded end) each need a fix or your ruling. The low points can be fixed
here or recorded for a later slice.

## Findings

### High

**H1. A data correction of a `salary_revision` event changes job details without the approval configured for job changes (FR-XM-32).**
`src/Modules/Hrm/Erp.Hrm.Infrastructure/Employments/EmploymentService.Changes.cs:119` (target check), `:217-227` (the job-detail guards),
`:371-373` (`needsApproval`); the kind is added in `Employments/employment-catalogue.json` and recorded by `Payroll/CompensationPlanner.cs:150`.
- Failure scenario: default `hrm.employment_events.approval_kinds` = promotion, demotion, transfer, grade_change. An HR administrator posts
  `POST /api/hrm/employments/{id}/events` with `kind: data_correction`, `correctsEventId` = the id of a `salary_revision` event, and
  `assignment: { title | gradeId | orgUnitId | positionId ... }`. The target check accepts any applied event that is not a separation or a
  transfer start; the guards refuse job details only when there is no target or when the root kind is `data_correction`; `needsApproval`
  asks whether `data_correction` or the root kind `salary_revision` is listed, and neither is. The correction applies at once and the
  timeline treats it as an assignment event from the salary revision's date. Probe: a promotion with a new title answered `202 pending_approval`;
  the correction of the salary revision answered `201 status effective`, and the title in force became "Director (via correction)". Before this
  part every correctable event either set job details itself (so its kind's approval applied) or was a start (covered by the follow-up A rule);
  `salary_revision` is the first applied event with no assignment section and no approval kind. The correction also marks the salary
  revision as replaced in the employment history while the compensation row still points to it.
- Suggested fix: refuse `correctsEventId` whose root kind is `salary_revision` (`CorrectionTarget`): a wrong salary is put right by a new
  revision with reason `correction`, which is what the catalogue already offers. If a correction of a salary revision must stay possible,
  refuse any `assignment` delta on it (as for `rootKind == data_correction`). Add an integration test citing FR-XM-32.

**H2. Held salary amounts and structure defaults are readable without the salary field class through the kernel's held-change records (GHR-06; R-278).**
`src/Modules/Hrm/Erp.Hrm.Infrastructure/Payroll/CompensationService.cs:147` and `Payroll/SalaryStructureService.cs:279` put the whole plan,
amounts and percentages included, in `iam.maker_checker_requests.payload`; `docs/data-design/kernel.yaml` gives that table a generated read
API (`api_actions: [read]`, permission `iam.maker_checker_requests.read`) and no field class on `payload`; the kernel baseline role
`tenant_admin` holds `iam.*` with scope `all` and no salary field rule (salary is hidden by default, `AccessSnapshot.cs:115`).
- Failure scenario (probe): a payroll officer submits a salary of 123456.78 and a structure default of 777777 while approval is on. A user
  with only the baseline `tenant_admin` role gets `403` on `GET /api/hrm/employments/{id}/compensation`, but `GET /api/iam/maker-checker-requests/{requestId}`
  answers `200` with `"payload":{"lines":[{"amount":123456.78,...}]...}`, and the already approved structure request still shows 777777. The
  payload is kept after the decision, so every salary ever held stays readable; the generated list and its export show the same column. The
  approvals inbox hides amounts correctly, but it is not the only reader.
- Suggested fix: keep amounts out of the kernel table. Either (a) hold the plan in an HR table whose amount columns carry `field_class: salary`
  (for example a pending `hrm.compensation_assignments` row with its lines in a `held` state, or a small `hrm.pay_change_requests` table) and
  put only its id in the payload, or (b) encrypt the amount part of the payload with the tenant key and decrypt it only in the handler. A
  narrower stop-gap, which needs a kernel change request: give `iam.maker_checker_requests.payload` a field class (`restricted`) so the
  generated read hides it from everyone without it. Either way add a GHR-06 test that reads the request as a user without the salary class.
  Close R-278 only when that test passes.

**H3. The cycle check looks only at the new version's start date; a loop that starts later is accepted (FR-HRM-PAY-03, "no cycle").**
`src/Modules/Hrm/Erp.Hrm.Infrastructure/Payroll/PayComponentService.cs:353` (`GraphAsync(component.CompanyId, from, ...)`) and `:402-424`
(versions in force on that one day); the database trigger repeats the same single-date walk,
`Migrations/V202611151232__hrm__rules_s1_34b.sql:37` (`v.valid_from <= new.valid_from and (v.valid_to is null or v.valid_to > new.valid_from)`).
- Failure scenario (probe): components A and B, both fixed from day -60. B gets a version from day +30, `percent_of` A (`201`). A gets a version
  from day +10, `percent_of` B (`201`): on day +10 B's version in force has no bases, so neither the service nor the trigger sees a loop, but
  from day +30 A uses B and B uses A. The same happens with formulas. Two requests racing on different components can also build a loop,
  because nothing serialises version writes within a company.
- Suggested fix: check the graph on every date from the new version's start onward where any version of the company starts (the set of
  distinct `valid_from` values `>= from`, plus `from`), in the service and in the trigger (or let the trigger walk versions that overlap
  `[new.valid_from, coalesce(new.valid_to, 'infinity'))` along each path). Take a per-company transaction lock (for example
  `pg_advisory_xact_lock` on the company id, or `select ... for update` on the company's components) in the service before reading the
  graph, and in the trigger. Add the probe's case as a test (FR-HRM-PAY-03).

### Medium

**M1. Salary-class write protection can be bypassed by leaving the amounts out (GHR-06, "not settable without edit access").**
`Payroll/CompensationService.cs:94-108` adds `amount` or `percent` to the "touched" fields only when a line carries one;
`Erp.Hrm.Application/Payroll/ComponentRules.cs:199` accepts a line with units only; `Payroll/SalaryStructureService.cs:229-237` does the same
for `default_amount` and `default_percent`, and `StructurePlanner.ApplyAsync` re-opens a changed row with the defaults the request sent.
- Failure scenario (probe, a user whose salary field rule is `read_only`, which is what the baseline `payroll_officer` has): a revision with an
  amount is refused (`400`), but the same revision with `units: 1` and no amount is applied (`201`), replacing the employee's salary lines
  with lines that have no amount. Re-sending a structure's component list without defaults (the user cannot see them) to change only the
  mandatory flag answered `200` and the structure's default went from 500.0000 to NULL from that date.
- Suggested fix: a new compensation row always writes `amount` and `percent` (null is a value), so require edit access to both for every
  compensation write; for a structure list, treat a default as touched when it differs from the row in force (null included), or carry the
  current default forward when the caller cannot see it.

**M2. `tg_compensation_fixed` protects only rows a revision has already ended; the row in force and its lines can be changed or deleted, and lines can be added to an ended row (FR-HRM-PAY-06, FR-XM-05).**
`Migrations/V202611151401__hrm__functions_s1_34b.sql:14` (`v_ended := old.valid_to is not null`) and `:28-33` (triggers on update and delete only);
source `tools/Erp.CodeGen/rules.yaml:1662`.
- Failure scenario (probe): right after the first salary is recorded, `update hrm.compensation_lines set amount = 999999` and
  `update hrm.compensation_assignments set valid_from = valid_from - 5` both succeed on the row in force. An `insert` into
  `hrm.compensation_lines` for an ended assignment is not checked at all. `CLAUDE.md` and CR-087 k describe "a trigger refuses any edit of a row
  or its lines", which is stronger than what the database does; the next writer (an import, a later slice, the generated API if reopened)
  would not be stopped.
- Suggested fix: on `compensation_assignments`, allow an update only when `old.valid_to is null` and the only changed columns are `valid_to`
  (to a date after `valid_from`) and the audit columns; refuse every delete. On `compensation_lines`, refuse update and delete always (the
  lines are written once with their row) and add `insert` to the trigger, refusing lines for an ended assignment. Extend the PAY-06 test.

**M3. An approver can approve a compensation change without being able to see its amounts (FR-XM-32, GHR-06).**
`Payroll/CompensationChangeHandler.cs:29` (approve permission only), `:31-44` (`VisibleAsync`: data scope only) and `:132-134` (amounts hidden in the
description when the approver lacks the field class).
- Failure scenario: a role with `hrm.pay.change.approve` and the employment in scope but no salary field rule sees "BASIC, HOUSE" without
  values in the approvals inbox and can approve; the second-person check then confirms nothing about the amount, which is the thing that
  matters. Separately, `DescribeAsync` decides with `fields.ForAsync` (company-wide merge of the roles granting `hrm.compensation_lines.read`),
  not the per-row plan, so a role that opens salary on its own rows only (the pattern review S1.06 finding 3 closed) would open other
  people's amounts here once such a role holds `hrm.compensation_lines.read`.
- Suggested fix: refuse the approval (and mark the inbox row not decidable) unless the approver may read `amount` and `percent` on that
  employment's lines, using `fields.PlanAsync(...).ResolveAsync` on a probe line of the employment; use the same per-row answer in
  `DescribeAsync`. Add a test.

**M4. The shipped roles cannot complete a salary change, and the code does not match CR-087 a.**
`src/Modules/Hrm/Erp.Hrm.Infrastructure/Access/baseline-roles.json:316` (`payroll_officer`: `class:salary` `read_only`); no baseline role holds
`hrm.pay.change.approve`; `Payroll/CompensationChangeHandler.cs:43` and `StructureChangeHandler.cs:38` also ask for the `create`/`update` scope.
- Failure scenario: in a new tenant with the default `hrm.pay.change_approval = true`, the baseline payroll officer is refused every amount
  and default (`errors.field.not_editable`, see M1) and nobody can approve a held change until an administrator builds custom roles. CR-087 a
  says the create permissions "double as the edit right on salary-class fields", but the services check the field class, not the
  permission. A pure checker role also needs `hrm.compensation_assignments.create` (or `hrm.salary_structures.update`) to see the request.
- Suggested fix (needs your ruling on who approves): give `payroll_officer` an `editable` rule for `class:salary` on the pay tables, give
  `hrm.pay.change.approve` (with salary read) to a separate baseline role, for example a payroll manager, and correct the CR-087 a wording;
  let `VisibleAsync` use the `read` scope only. Add a test that runs the flow with the baseline roles.

**M5. A structure change ignores the salaries that use the structure and can be backdated without any record (FR-HRM-PAY-04, -06).**
`Payroll/StructurePlanner.cs:97-101` (the only date rule: later than the structure's latest list), `:130-190` (`ApplyAsync`), `:105-123`
(order check on the start date only).
- Failure scenario: today is 24 November; the structure's list started 1 January. A list from 1 June (already paid months) is accepted: it
  changes defaults, order or the mandatory set for those months for every employee on the structure, with no backdated flag, no affected
  periods and no event for S1.39, whereas a salary revision on the same dates records all three. A list that drops a component (even a
  mandatory one) that employees' current salary lines use is accepted too, so their arrangements no longer fit their structure; nothing
  re-checks them until their next revision. A later component version that adds a base can also break the structure's evaluation order,
  because the order check runs on the list's start date only.
- Suggested fix: either refuse a structure date earlier than today (or than the end of the last opened period), or record the backdated
  change as compensation does (affected periods and an event); refuse, or at least report, a list that removes or changes a component used
  by an arrangement in force on or after the date; re-run the order check at every later version start of the structure's components (and
  check the structures that use a component when a version is added).

**M6. A salary can start after the employment's recorded end.**
`Payroll/CompensationPlanner.cs:59-62` checks the status only (`pre_joining`, `active`, `on_notice`).
- Failure scenario: an employee on notice has an approved separation effective 31 December; a revision from 15 January is accepted. The
  employment change service refuses any event on or after a recorded end (`EmploymentService.Changes.cs:138`, `AfterEnd`), but the
  compensation service does not, so a salary row and a `salary_revision` event are left after the end (for a transfer, the approval of its
  separation then fails on the later revision instead).
- Suggested fix: refuse `validFrom` on or after the effective date of a pending, approved or effective separation, with the same query as
  `EmploymentService.Changes.cs:138`, in the service and again in the approval handler.

### Low

**L1. Hard-coded English in the approvals inbox.** `Payroll/CompensationChangeHandler.cs:148` appends `" units"` and `"?"` to the line text
(`StructureChangeHandler` uses `"?"` too). Use a localization key (for example a detail per line with type `text` and a units label) and a
neutral marker for an unknown component.

**L2. Affected periods follow one pay group only, and a future date inside the open period counts as backdated.** `Payroll/CompensationPlanner.cs:138-143`
takes the pay group on `validFrom`; when the employee moved group between that date and today, the new group's opened periods are not listed
for S1.39. `backdated` is also set for a revision dated tomorrow inside an open period. Collect the pay groups of every assignment row that
overlaps `[validFrom, today]` and set `backdated` only for `validFrom < today`, keeping "reaches an opened period" as its own flag.

**L3. Two concurrent version adds on one component answer 500.** `Payroll/PayComponentService.cs:221` catches only a `DbUpdateException` with a
`PostgresException` inside; the row-version conflict on the ended version is a `DbUpdateConcurrencyException`. Catch it and answer the
concurrency conflict.

**L4. A bonus definition can omit the value its basis needs.** `Access/policy-types.json:97` requires `basis` but not `amount` for
`fixed_amount`, nor `percent`/`multiple` and `basisComponentCode` for the other bases (the unit case at
`tests/Erp.UnitTests/Payroll/PayComponentRulesTests.cs:167` shows a `fixed_amount` bonus without an amount passing the schema). Add a
policy-type check (the schema subset has no conditionals) or show the bonus as incomplete, as components are (Q4).

**L5. The assign rule set when a structure is created is not held for a second person.** `Payroll/SalaryStructureService.cs:102-110` applies it
directly; the same rule on update is held. Small today because the rule is not enforced (R-277); hold it, or document the exception in CR-087 i.

**L6. A structure list may mix currencies, and lines are not checked against the component's method.** `Payroll/SalaryStructureService.cs:196`
takes any three letters per item; a mixed list is accepted and then every salary on it fails with `compensation_currency`. A line may carry an
amount for a `percent_of` component or a percentage for a `fixed` one. Refuse a list whose currencies differ from each other or from the
company's, and refuse a line value the component's method in force cannot use.

**L7. With approval switched off, a payroll officer can change their own salary.** `Payroll/CompensationService.cs:43` (`AssignAsync`) has no own-pay check;
only the approval handler refuses the employee (`CompensationChangeHandler.cs:74`). Refuse the caller's own employment in the direct path too,
as the handler does.

**L8. The generated reads of compensation lines and assignments do not need `hrm.pay.compensation.read`.** The slice says amounts "need
permission `hrm.pay.compensation.read`"; the generated `GET /api/hrm/compensation-lines` needs only `hrm.compensation_lines.read` plus the
salary field class (`Erp.Hrm.Api/Generated/CompensationLineEndpoints.g.cs:52`), so a role with `hrm.*.read` and salary read (the auditor)
reads amounts without it. Either record that the permission gates the compensation endpoint only, or make the generated reads of the salary
tables require it.

**L9. Nit: a component code that is also a function name is ambiguous in formulas.** `Erp.Hrm.Application/Payroll/FormulaValidator.cs:20`
matches `min`, `max`, `round` case-insensitively before component codes, so a component coded `Max` cannot be followed by `(` and reads
differently with and without a space. Reserve the three names in `ComponentRules.IsComponentCode`.

## Categories checked

1. **Salary-class protection (GHR-06).** Leaks: H2 (held payloads), M3 (blind or over-open inbox), L8 (permission gate). Writes: M1. No finding
   for the compensation endpoint (gross, amount and percent hidden per row), the structure detail, the generated lists and their exports
   (generator field shaping with the new classes on `default_amount`, `default_percent`, `percent`), the audit search (`AuditQueryService`
   masks classed values per viewer; the kernel writes `iam.maker_checker_requests` with SQL, so its payload is not in the change log; the
   `iam.change_requested` event carries kind and subject only), the employment event `changes` (structure ids, dates, periods only) and the
   outbox events `hrm.compensation.changed` and `hrm.employee_changed` (ids, dates, codes; no amount).
2. **Maker-checker (FR-XM-32).** H1 (job change without approval), M3, M4, L5, L7. Checked with no finding: the requester cannot decide
   (kernel, plus the database check on `decided_by`); the employee cannot approve their own pay; the setting `hrm.pay.change_approval` is
   itself held; every rule is re-run in the approval transaction under the employment lock (compensation) or the structure lock (structure),
   so a stale request (date no longer after the latest row, structure switched off, component gone, employment no longer current) is refused
   and leaves nothing behind; two pending revisions cannot both apply out of order (the second fails "not later"); row versions are
   concurrency tokens on the structure and the version rows.
3. **Effective dating and immutability.** H3, M2, M5, M6, L2. Checked with no finding: a version must start after the latest one and ends it
   on its start date (exclusion constraint as a backstop); structure lists keep unchanged rows and end left-out ones; a revision must start
   after the latest row and ends the row in force; a future revision's event is `approved` and the daily job makes it effective without
   touching assignments (`EmploymentTimeline.Plan` skips events without an assignment section); the approval of a transfer's separation is
   refused while a revision dated after it exists (`EmploymentEventHandler.cs:166`).
4. **Formula, cycle and pro-rata validation; statutory content (AS-4).** H3, L9. Checked with no finding: unknown names, unknown functions,
   bad characters and unbalanced brackets are refused; bases must be components of the same company and never the component itself
   (service and trigger); the order check refuses a component evaluated before its base on the list's date; `custom` pro-rata needs a
   divisor 1 to 366 and an optional day count and the other rules take no parameters. No rate, slab, threshold or statutory value is stored
   or coded: flags, table codes and tax treatments are free codes, the "incomplete" marker only reads whether a table code exists.
5. **Tenant isolation, permissions, scope, localization, CLAUDE.md rules.** L1. Checked with no finding: every new endpoint asks its
   permission and the record's data scope (company for components and structures, employment scope plus the assignment create scope for
   compensation); writes check that bases, components, grades and structures belong to the record's company; the tenant comes from the
   host only (one database per customer). Every `errors.hrm.pay.*` key used by the server has an English and an Urdu text (checked with a
   script against all `*.en.json` and `*.ur.json` files); permission descriptions and reason names exist in both. The injected clock is used
   throughout; money columns are `numeric(19,4)` and amounts are rounded to four decimals with `decimal`, never floating point; the three
   migrations are new generated files (expand only); `dotnet run --project tools/Erp.CodeGen -- generate` leaves no diff.
