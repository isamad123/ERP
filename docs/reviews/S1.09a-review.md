## Summary for the product owner

Overall the settings and flags work is sound:
- Each customer's settings stay in that customer's own database. The in-memory copy each server keeps is filed under
  the customer's code, so one customer can never see another's. The isolation suite probes all 11 new endpoints.
- The "most specific value wins" rule (product, pack, customer, company, role, user) is in one place and well tested.
- Every change, reset and undo writes a history row, an event and audit rows in the same database transaction.
- A setting that needs approval waits for a second administrator; nobody can approve their own request.
- The way changes reach the other servers (a change counter raised inside the database) is correct: I checked the
  ordering under concurrent changes and found no way for a server to keep an old value for good.
- All SQL uses parameters. The two migration files are new; no frozen migration was touched.

I found **no high-severity defect**. There are **two medium issues**:

1. **The settings centre shows the wrong fiscal-year start for a Pakistani company.** If nobody has set it, the
   settings centre says the fiscal year starts in **January** ("product default"). Document numbering actually uses
   **July**, the Pakistan default kept since S1.08. An administrator reading the settings centre is told something
   that is not true. I proved this with a test. **This needs your decision** on how to fix it (options below).
2. **A Company Admin can read every company's and every user's setting values** through an older, automatically
   generated list (`/api/cfg/setting-values`). The new settings centre correctly refuses the same person ("not your
   company"). The values are not very sensitive (options such as time zone or e-mail sender name), but the rule
   "a Company Admin sees only their own companies" is broken. I proved this with a test.

There are **six low issues** (items 3 to 8). Two are traps for future work rather than live defects. Item 3: if an
`iam.*` setting is ever marked "needs approval", it would be applied without approval. Item 8: a few manifest
combinations are not refused by the generator. The others are small: concurrent first changes can record a wrong "old
value" in the history; a short window where the server that made a change still shows the old value; the layered view
shows any user's values to a Company Admin; the history list can hide a Company Admin's own rows.

I recommend fixing 1 and 2 now, and 3 to 7 in the same pull request (each is a few lines and a test).

## Findings, most severe first

### 1. MEDIUM (needs a product-owner decision): the settings centre does not show the numbering value in force

- **Where:** `src/Platform/Erp.Kernel.Infrastructure/Numbering/NumberingSettings.cs:52-56`. When the resolver answers
  "product layer", numbering replaces the value with the company's **country default** from `country-defaults.json`
  (S1.08 ruling P4; Pakistan: fiscal year from month 7). The settings resolver (`SettingsService.ResolveAsync`,
  `SettingsStore.ResolveAsync`) knows nothing of country defaults, so `GET /api/cfg/settings/cfg.numbering.fiscal_year_start_month?companyId=…`
  answers `1`, source `product`.
- **Why it matters:** slice goal and Q11: "one kernel service gives the effective value … and the layer it came from";
  "the system always says where the value in force came from". For Pakistani customers (the first market) the
  settings centre (S1.15) would show January while invoices and documents are numbered by a July fiscal year.
  Other readers of `org.time_zone` (licence states, jobs calendar) also ignore the country default. Today this is
  harmless only because the Pakistan and product time zones are the same.
- **Fix options (your decision):**
  - **(a) Recommended:** treat the country default as the **pack layer** for the company in context. It is pack data
    ("country-pack data until country packs exist", says the file), and the pack layer already exists in the
    resolver. The store and the settings service add a computed pack value for the company's country. The layered
    view then says `pack`, and numbering, the settings centre and the other readers give one answer. When S1.23 brings
    the pack loader, the values become stored pack values and the computed step is removed. No table changes. The
    resolution rule changes, so this is recorded as CR-061.
  - (b) Keep the code and only document the difference. Not recommended: the settings centre would keep showing a
    wrong value.
- **Test to add:** a PK company with nothing set → the settings centre shows `7` with source `pack`, and numbering uses
  7; a company value of 3 → both show 3.

### 2. MEDIUM: the generated read of `cfg.setting_values` ignores company scope (Company Admin reads everything)

- **Where:** `src/Platform/Erp.Kernel.Api/Generated/Cfg/SettingValueEndpoints.g.cs:46-47` (`GET /api/cfg/setting-values`,
  `GET /api/cfg/setting-values/{id}`), from `docs/data-design/kernel.yaml:518` `api_actions: [read]`.
- **Why:** the generated endpoint checks only the permission `cfg.setting_values.read`. The table has no `company_id`,
  so no data scope applies. S1.09a gave Company Admin this permission's write twin and built company filtering into
  the purpose-built reads (`SettingsAdministrationService.cs:362-369` and `:104-114`). The generated list bypasses that
  filter: every company's company-layer values, every user's user-layer values, and values of hidden settings.
- **Scenario:** Proof 1 above. The same person gets 403 from `/api/cfg/settings/{key}?companyId=B` and 200 with B's
  value from `/api/cfg/setting-values`.
- **Fix:** close the generated reads of `cfg.setting_values` (`api_actions: []`). Everything they offer is in
  `/api/cfg/settings` and its layered view, which apply the rules. This is a data-design change (CR-036 part 4 chose
  `[read]`), so it is recorded in CR-061. `cfg.setting_value_history` and `cfg.feature_flag_overrides` generated reads
  are not reachable by Company Admin (Tenant Admin and Auditor read everything anyway) and can stay.
- **Test to add:** Company Admin → `GET /api/cfg/setting-values` answers 404 (route gone). The isolation inventory then
  has two fewer endpoints.

### 3. LOW (latent): an `iam.*` setting marked "needs approval" is applied at once

- **Where:** `SettingsAdministrationService.cs:220-226` sends every `iam.*` key to the access settings service before
  `RequiresApproval` is looked at (line 253). `ValidateHeldSettingAsync` refuses `iam.*` keys, so they can never be
  held. The generator (`tools/Erp.CodeGen/Design/SettingsManifest.cs:164-165`) accepts `requires_approval: true` on an
  `iam.*` key.
- **Today:** no setting has `requires_approval: true`, so nothing is wrong yet. Proof 4 shows what would happen.
- **Fix:** the generator refuses `requires_approval` on `iam.*` keys (they have the S1.06 two-person rule instead), and
  `ChangeAsync` refuses such a definition at run time rather than applying it.

### 4. LOW: two first changes of the same layer at the same moment record a wrong "old value"

- **Where:** `src/Platform/Erp.Kernel.Infrastructure/Settings/SettingWrites.cs:25-57`. `select … for update` locks
  nothing when the row does not exist yet. The second writer's insert waits on the unique key, then `on conflict do
  update` overwrites the first value. Its history row says `old_value = null`.
- **Effect:** Proof 3. History shows `null→22` instead of `11→22`. Reverting that row removes the value instead of
  restoring 11. Rare (two administrators setting the same new layer within the same instant), but history is the
  audit record of the change.
- **Fix:** take `pg_advisory_xact_lock(hashtext(key || '|' || layer || '|' || coalesce(scope_id::text, '')))` before
  the read, or `insert … on conflict do nothing` first and then `select … for update`. The same applies to
  `ApplyFlagAsync` (lines 94-127).
- **Test to add:** the Proof 3 shape: two overlapping transactions; the second history row has `old_value = 11`.

### 5. LOW: the server that made a change can show the old value for up to one refresh interval

- **Where:** `SettingsCache.cs:71-73` and `:83-89`. A request already loading a snapshot when the change commits can
  store its older snapshot after `Invalidate` has cleared it. That server then serves the old value until the next
  check (default 1 second). Other servers are unaffected; the counter design guarantees they catch up.
- **Fix:** keep a generation number per customer. `Invalidate` raises it. A load stores its result only if the
  generation has not moved since it started; otherwise it leaves `Current` empty so the next read reloads.
- **Test:** hard to make deterministic. A unit test of `SettingsCache` with a fake load can show it.

### 6. LOW: the layered view shows any user's or role's values to a Company Admin

- **Where:** `SettingsAdministrationService.cs:64-68`. With `?companyId=<own>&userId=<anyone>&roleId=<any>` a Company
  Admin sees the user-layer and role-layer values of users and roles outside their companies. Only the company is
  checked.
- **Fix:** when `userId` or `roleId` is given, require the read permission for all companies, or require that the user
  holds an assignment in a covered company.

### 7. LOW: a Company Admin's history list can miss their own rows

- **Where:** `SettingsAdministrationService.cs:85` (`limit 500`) runs before the company filter at lines 104-114.
  With many changes in other companies, a Company Admin sees fewer than 500 of their own rows, possibly none.
- **Fix:** filter in SQL (`layer = 'company' and scope_id = any(<covered companies>)`) before the limit.

### 8. LOW: manifest combinations the generator does not refuse

- `self_service: true` with `requires_approval: true`: the self-service change is held through
  `HoldSettingChangeAsync`, which needs `cfg.setting_values.update`, so the user gets 403. The request would also carry
  a null reason (`SettingsAdministrationService.cs:266`, `reason!`). The generator should refuse the combination.
- A flag removed from a manifest is not hidden or marked (`SettingsSetup.cs:185-198`); it keeps resolving and being
  listed. Settings are hidden (ruling Q10). Recommend the same for flags when ADM-SET-07 (Later) adds the flag list; until
  then, record it.

## Checked and found correct

- **Tenant isolation:** the cache is keyed by tenant code (`SettingsCache.cs:50`). Connections come from the resolved
  tenant data source. Context (company, user) is never taken from the tenant hint headers. The isolation probe covers
  all 11 settings endpoints with crossed hosts, tokens and ids, and checks A's database is unchanged.
- **Propagation (Q13):** the statement-level triggers raise `cfg.config_versions` inside the writing transaction. The
  counter row stays locked until commit, so any snapshot that reads version N also sees every change up to N. The
  cache loads counters and values in one repeatable-read transaction. It compares with `==`, so a restore that moves
  the counter back still causes a reload. The trigger is `security definer` with a fixed `search_path`; `public` has
  no execute right.
- **Resolver:** order product → pack → tenant → company → role → user; invalid and not-allowed values are skipped and
  reported; role rules any, all, lowest and highest; tighten-only for `iam.mfa.required` matches sign-in
  (`IdentitySettings.MfaRequirement`). Only roles valid today and covering the company count
  (`SettingsStore.RoleIdsAsync`; "today" is the UTC date, the same convention as the access engine since S1.06).
- **Writes:** hidden settings and the pack layer are refused. Scope rows must exist. Values are checked against type
  and rules. A Company Admin can change only the company layer of covered companies. `iam.*` changes need all
  companies (CR-038). Generated writes on values, history and overrides are closed (test `CR_036_CR_037_…`).
- **`iam.*` rules:** the two-person rule for switching off maker-checker or privileged MFA is kept for set, reset
  (compared with the shipped default) and revert, because revert goes through the same path. Those keys allow only
  the tenant layer, so it cannot be bypassed at company level.
- **Approval:** a held change is written nowhere until approved (the first transaction is rolled back). Self-approval
  is refused (`ApproveAsync`, also a database check). The approver must cover the company. The change is validated
  again at approval, and history, event and audit are written at approval.
- **Audit:** every change, reset, revert and flag change writes an outbox event, a security event and change-log rows
  in the same transaction (test `FR_KRN_SET_04_FR_ADM_SET_06_…` counts all three).
- **SQL safety:** every value is a parameter. The only interpolated identifiers are table names chosen from constants
  (`SettingWrites.cs:156-163`, `SettingsAdministrationService.cs:290`) and the outbox table chosen from two constants.
- **Registration:** `SettingsSetup` is idempotent and serialized by an advisory lock. It never touches customer values
  and hides settings no longer declared. The 22 earlier settings are proven unchanged against a captured file.
- **Generator:** keys must start with the module's id; a duplicate key across manifests is refused; defaults are
  checked against their own rules; a role layer needs a role rule; tighten-only is for yes/no settings only;
  self-service needs the user layer.
