# Release 1.0 data design (D-35 gate)

Status: **approved by the product owner on 15 November 2026** (D-50). Changes need a change request (D-39).

This is the column-level design for the shared foundation (kernel) and HRMIS tables needed by the 369 requirements
tagged Release 1.0 (204 tables in all). It follows `docs/specs/03-…` sections 3 to 10, with section 14 as amended by D-47
(separate database per customer; no `tenant_id`).

The YAML files are written so a code generator can read them directly (token strategy, section 1). The same files are
the source for the generated data dictionary, which the build compares against the real database.

| File | Holds | Tables |
| --- | --- | --- |
| `control-plane.yaml` | The single small database that lists customers, their databases, licences and usage | 13 |
| `kernel.yaml` | Shared foundation tables inside every customer database | 81 |
| `hrm-people.yaml` | Persons, employment, organization structure, policies, documents, self-service, onboarding and exit | 31 |
| `hrm-time.yaml` | Devices, shifts, rosters, attendance, overtime, leave | 17 |
| `hrm-pay.yaml` | Payroll, statutory tables, tax, payments, final settlement, loans, expenses, compensation and benefits, compliance, parallel run | 47 |
| `hrm-talent.yaml` | Forms, performance management, learning | 15 |
| `diagrams.md` | Entity relationship diagrams per area | — |

## How to read a table entry

```yaml
- table: hrm.leave_requests          # schema.table
  purpose: An employee's request for leave
  traits: [std, co, cust]            # standard column sets, below
  status: [draft, submitted, approved, rejected, cancelled]
  columns:
    - [employment_id, uuid, req, fk hrm.employments]
    - [leave_type_id, uuid, req, fk hrm.leave_types]
    - [start_date, date, req]
    - [days, qty, req, "check > 0"]
  unique: [[company_id, request_no]]
  indexes: [[employment_id, start_date]]
  reqs: [LVE-04, LVE-05]
```

Column tuple: `[name, type, req|opt, notes]`. `req` means NOT NULL.

| Shorthand | PostgreSQL type |
| --- | --- |
| uuid | uuid (UUIDv7, generated by the application) |

| text | text |
| i18n | jsonb of language code to text, for example `{"en":"Annual leave","ur":"سالانہ چھٹی"}` |
| date | date |
| ts | timestamptz, always UTC |
| int | integer |
| big | bigint |
| bool | boolean not null default false (unless noted) |
| money | numeric(19,4), always beside a `currency_code char(3)` column on the same row or its header |
| qty | numeric(19,6) |
| rate | numeric(19,10) |
| pct | numeric(9,6), stored as a fraction (0.15 means 15 percent) |
| json | jsonb, only for user-defined or sparse data, never used in joins or constraints |
| enc | bytea ciphertext (field-level envelope encryption) |
| hmac | bytea blind index for exact-match lookup of an encrypted value |
| enum(...) | text with a check constraint listing the allowed values |

## Traits (standard column sets)

| Trait | Columns added | Rule |
| --- | --- | --- |
| std | `id uuid pk`, `created_at ts req`, `created_by uuid req`, `updated_at ts req`, `updated_by uuid req`, `row_version big req default 1` | Every mutable table. Updates use `where row_version = expected` |
| app | `id uuid pk`, `created_at ts req`, `created_by uuid req` | Append-only: application role has no UPDATE or DELETE; a trigger also refuses them. Corrections are new rows |
| co | `company_id uuid req fk org.companies`, leading column of company-scoped indexes | Every company-scoped table |
| br | `branch_id uuid opt fk org.branches` | Transactional headers (C-39). Small customers get one default branch |
| soft | `is_deleted bool`, `deleted_at ts`, `deleted_by uuid`; unique indexes are partial on `not is_deleted` | Master data |
| eff | `valid_from date req`, `valid_to date opt`, `check (valid_to is null or valid_to > valid_from)`, exclusion constraint on the listed key over `daterange(valid_from, valid_to, '[)')` | Effective-dated rows; `valid_to` null means open-ended |
| cust | `custom json req default '{}'` validated against `cfg.custom_field_defs` | Entities customers can extend |
| name | `code code req`, `name_i18n i18n req`, `is_active bool default true` | Lookup and master tables |

Every table also follows: primary key on `id` (or the composite key given); every foreign key indexed; constraint names
`pk_`, `fk_`, `uq_`, `ck_`, `ex_` + table + columns; index names `ix_` + table + columns.

## Rules applied throughout

1. **No `tenant_id` anywhere** (D-47). Isolation is the database. Control-plane tables are in their own database.
2. **No foreign key between business-module schemas.** HRMIS references kernel tables by foreign key; references to
   modules that may not exist (Finance cost centres, Assets) are plain `uuid` columns named `*_ref`.
3. **Statutory values are data.** Tax slabs, contribution rates and ceilings live in pack-supplied tables
   (`hrm.statutory_tables`, `hrm.statutory_table_rows`), never in code.
4. **Money is never floating point.** Rounding is applied by rule in the engine and recorded in the calculation trace.
5. **Salary amounts are not encrypted** (the payroll engine must aggregate them in SQL). They are protected by field
   security, data scopes and the access log. National ID numbers, bank account numbers and similar identifiers are
   encrypted with a blind index.
6. **Personal data in the audit log** is encrypted per person (`aud.subject_keys`) so that erasure can destroy the key
   without breaking the audit hash chain (spec 03 section 14.3).
7. **Append-only:** audit, attendance events, leave ledger, provident fund ledger, loan ledger, liability accruals,
   workflow history, accounting events, payslip reversals. **Locked after the event:** pay runs, run employees, results,
   result lines and traces once the run locks; attendance and leave days once their attendance period locks; final
   settlements once approved; statutory table rows once effective or used.
8. **Partitioned by month from the first migration:** `aud.change_log`, `aud.access_log`, `iam.login_attempts`,
   `hrm.attendance_events`, `hrm.attendance_days`, `job.run_logs`, `ntf.outbound_messages`. Unique keys on partitioned
   tables always include the partition column. `itg.accounting_events` is not partitioned (low volume, needs a global
   unique key). `hrm.pay_result_lines` carries its period so it can be partitioned yearly when volume requires.
9. **Outbox and inbox** tables (`outbox_messages`, `inbox_messages`, spec 03 section 7.5) exist in every module
   schema and are not repeated in the files.
10. **Reporting views** named `rpt.v_hrm_<entity>` are generated for every master and transactional table; they apply
    data scopes and hide salary columns from roles without salary permission.

11. **Unique keys with nullable columns** use `NULLS NOT DISTINCT` (PostgreSQL 16 or later), so a null company, branch
    or scope cannot create a duplicate. Exclusion constraints use a generated `coalesce(..., nil uuid)` column.
12. **No cross-company references.** Every company-scoped parent table has `unique (company_id, id)`, and company-scoped
    children reference it with a composite foreign key `(company_id, parent_id)`. A row can never point at another
    company's employee, pay group, component, bank account or leave type.
13. **Hierarchies** (org unit parents, managers, position reporting lines, cascading goals) have cycle-check triggers.
14. **Idempotency.** Anything that can be fed twice into payroll, leave or loans has a unique source key
    (`source_type, source_id, ...`), so retries never double-count.

## Access-control keys (slice S1.06, CR-018, CR-020, CR-021, CR-025)

| Key | Example | Meaning |
| --- | --- | --- |
| `scope` | `scope: {company: company_id, employment: employment_id, attributes: [status]}` | The uuid columns that locate a row for data scopes: `company`, `branch`, `org_unit`, `employment`, `person`, `user`; `attributes` lists text columns that scope conditions ("equals / is one of") may test. A table without `scope` is not scoped: the permission alone decides. |
| `scope: {via: …}` | `scope: {via: declaration_id}` | The row is located through its parent (a foreign key to a table of the same schema with its own `scope`): the child's permission and the role's scope for the child's resource apply to the parent's locators (CR-025). Used for detail lines without their own employment or company column. |
| `field_class` | `field_class: {gross_amount: salary}` | `salary`, `personal` or `restricted`. Salary fields are hidden from every role unless a field rule opens them (GHR-06); in Release 1.0 only salary is marked (ruling B, CR-022). |
| `api_actions` | `api_actions: [read]` | The generated API actions kept (read is required); the closed ones are replaced by purpose-built services. |

The generator emits, per table, `<Entity>Access` (scope locators and field catalogue) in the module's Application
layer, a resource catalogue in its Infrastructure layer, and the module's permission manifest
`Infrastructure/Access/permissions.g.json`. None of these keys changes the database.

## Audit keys (slice S1.07, CR-026, CR-029, CR-030)

| Key | Example | Meaning |
| --- | --- | --- |
| `audit` + `audit_reason` | `audit: false` / `audit_reason: "append-only: …"` | The change log skips the table. Every table is audited unless it says so; append-only tables and tables without a uuid key must say so, with a reason (the generator stops otherwise). Outbox and inbox tables are never audited. |
| `field_class: personal` | `field_class: {date_of_birth: personal}` | The audit log encrypts the field's before and after values with the data subject's key (`aud.subject_keys`, R-21); the subject is the row's `person` locator, or its `employment` through the HR module. `salary` values are encrypted with the customer's field key. Only `salary` makes a permission sensitive (CR-030). |
| `indexes_added_in` | `indexes_added_in: {S1.07: [[occurred_at]]}` | An index added after the release's first migrations; the slice's design migration creates it. |
| `added_in` on an optional enum column | `added_in: {S1.07: [source]}` | The column and its value check are added by the slice's design migration (NULL passes the check, so existing rows stay valid). |

The generator also writes each module's audit catalogue (`<Module>AuditCatalog.g.cs`: table, audited or not, row key,
company and subject locators, field classes), which the kernel's change-log writer reads. Database functions a slice
needs (S1.07: the audit writers) are reviewed SQL in `tools/Erp.CodeGen/rules.yaml` under `functions` and are emitted as
the slice's `functions_<slice>` migration, so every migration file stays generated. Control-plane tables can be added
later too (`added_in: <slice>`, file `V…__controlplane__design_<slice>.sql`).

## Numbering keys (slice S1.08, CR-033, CR-035)

| Key | Example | Meaning |
| --- | --- | --- |
| `numbering` | `numbering: {column: employee_no, type: hrm.employee_no, assign: create, override: yes, default: "EMP-{seq:5}", reset: never}` | The column's number comes from the kernel numbering service. `type` is the document type code; `assign` is `create` (the generated create fills it) or `post` (the module's post service does; until then the generated create numbers it while the series is gap-allowed, ruling P5); `gap_free: yes` lets customers switch the series to gap-free (never with `assign: create`); `override: yes` allows a typed-in number (HRM-EMP-04); `tenant_wide: yes` for one series per customer (no company); `default` and `reset` give the default scheme (Q7); `date` names the column with the business date that decides the period (Q5). The column becomes read-only in the generated API (FR-KRN-NUM-03). The default pattern is checked by the same rules as a customer's pattern. |
| `optional_added_in` | `optional_added_in: {S1.08: [company_id]}` | A required column made optional later: the frozen file keeps NOT NULL, the slice's design migration drops it. |
| `enum_added_in` | `enum_added_in: {S1.08: {reset_rule: [fiscal_yearly]}}` | Values added to an existing enum: the column lists all values; the frozen file keeps the first list, the slice's design migration replaces the check. |
| `checks_added_in` | `checks_added_in: {S1.08: [a branch scheme belongs to a company]}` | Checks the slice's design migration adds, each translated by a reviewed rules.yaml entry. |
| `uniques_added_in` | `uniques_added_in: {S1.08: [[scheme_id, number]]}` | Plain unique keys the slice's design migration adds; the foreign-key index of the frozen file stays. |

The generator writes each module's document types as `<Module>NumberingTypes.g.cs` (read by the API host) and
`Infrastructure/Access/numbering.g.json` (read by provisioning and `migrate` to seed default schemes).

## Cross-module rules enforced in the data design

| Rule | Where |
| --- | --- |
| FR-XM-05, 06 Finalized is immutable; numbers never reused | Lock triggers on payroll, settlement and statutory tables; `cfg.numbering_voids`; status models with `cancelled` |
| FR-XM-26 Attendance lock at payroll | `hrm.attendance_periods` (one per pay period, never reopened once its run locks); lock trigger on attendance days, leave days, overtime and regularizations; later changes go to `hrm.retro_adjustments` |
| FR-XM-27 One summarized journal per company; payslip reversal before payment | `itg.accounting_events` unique per source and posting version; `hrm.pay_result_reversals` |
| FR-XM-28 One person, several roles | `hrm.persons` separate from `hrm.employments`; kernel parties link later by `party_ref` |
| FR-XM-29 Final settlement blocked by open items | `hrm.final_settlements.clearance_status`; settlement completes only when the clearance check view returns no open loans, advances, unreturned items, unsubmitted claims or pending approvals |
| FR-XM-30 Transfer between companies | New `hrm.employments` row with `previous_employment_id` and carry-over rules recorded in `hrm.employment_events` |
| FR-XM-32 No self-approval, escalation | `wf.workflow_tasks` check `assignee_user_id <> requester`; escalation timestamps |

## Not in Release 1.0 (tables deliberately absent)

Geo-fences and location evidence, field tasks, mobile devices and sync, recruitment, employee relations, asset custody,
workforce planning, timesheets by project, travel requests, multi-currency payroll, fiscal calendars, parties and item
catalog, webhooks, configuration packages, custom record types. Columns that those features will need later are
**not** added now; expand-and-contract migrations add them when their release starts.
