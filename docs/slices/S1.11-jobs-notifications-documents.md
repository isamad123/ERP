## Goal
Three things every later slice needs. **Jobs:** work that runs in the background (payroll calculation, imports,
nightly checks) runs exactly once even with several servers, survives a restart by carrying on from where it stopped,
shows its progress, and can be cancelled or run again; one customer's big job never blocks another customer.
**Notifications:** when something happens (a request waits for your approval, a request escalated, the licence is
about to expire) the right people get an item in the application and an e-mail, in their own language, with a link
that opens the right screen; people choose which e-mails they want, and nothing that matters is lost or sent twice.
**Documents:** any record can carry files (with versions, expiry dates and retention), files are stored encrypted per
customer and checked for viruses, and the product can produce letters and similar documents as PDF from templates in
English and Urdu.

## Build
Part **S1.11a — jobs and events**
1. **Job catalogue (KRN-JOB-01, Q3, Q4).** Each module declares its jobs in a manifest (code, what it does in English
   and Urdu, default schedule, parameters, permissions it needs, retry policy, time limit, priority, concurrency,
   whether it runs in read-only or locked mode). `migrate` and provisioning seed `job.definitions` by code; a
   customer's schedule and on/off choices are kept on upgrade.
2. **Scheduler and runner (KRN-JOB-02, KRN-JOB-04, KRN-JOB-05, Q2, Q5, Q6).** One scheduler in the worker host:
   schedule slots become runs once (unique slot), runs are taken under a lease so only one worker runs each, the lease
   is renewed while it works and taken over when a worker dies. Chunks commit their work and checkpoint together, so a
   restarted run continues from the last checkpoint without doing anything twice. Progress, logs, time limit, cancel,
   retry with back-off, priority, fair shares between customers.
3. **Who a job acts as (R-009, Q4).** Explicit job actor with exactly the declared permissions; runs requested by a
   person run with that person's rights, checked again when the run starts. Audit source `job`.
4. **Event dispatcher (spec 03 section 7.5, Q7).** Reads every schema's outbox in each customer database, hands each
   event to the consumers registered for its type, records each delivery in that schema's inbox so a consumer never
   handles an event twice, retries failures with back-off, marks the event published.
5. **Existing loops and maintenance as jobs.** Licence refresh (hourly), workflow escalation (every minute),
   `audit anchors-publish` (daily), `audit verify` of the previous day plus the chain-ahead-of-clock check (nightly,
   R-012, R-014), monthly partitions three months ahead (through a database function owned by the migration login),
   expiry of maker-checker requests (daily). The two hand-written loops are removed; the operator commands stay.
6. **Alerts (KRN-JOB-06, Q8, Q9).** Failed, stuck and overdue jobs, event backlog, critical audit events, unusual
   access: each raises an alert event (sent by part b).
7. **Job centre API (KRN-JOB-03, ADM-OPS-01).** List runs with filters, run detail with logs, run now, rerun, cancel,
   change schedule or switch off (permitted jobs only), download a result file (when part c exists), health numbers
   (queue depth, event backlog, worker heartbeat).

## Acceptance
- Spec 02 JOB AC, with a test job (no import centre yet): a 50,000-row job interrupted by stopping its worker resumes
  on another worker from its last checkpoint and ends with exactly 50,000 rows, none twice.
- Two workers started together never run the same scheduled slot or the same queued run twice; a run whose worker
  dies is taken over after its lease expires; a run past its time limit stops and is retried or failed per its policy;
  cancel stops a run at its next chunk.
- Fair shares: with one customer's queue full of long runs, another customer's run starts within one poll interval.
- A job of an unlicensed module does not run; in read-only and locked mode only jobs marked for it run.
- A scheduled job writes with its declared permissions only (a write outside them is refused); a run requested by a
  person who loses the permission before it starts fails with the reason; the audit log shows source `job`.
- The licence, escalation, audit, partition and maker-checker jobs do what the loops and commands did (the S1.09b and
  S1.10b tests keep passing, now through jobs).
- Spec 02 NTF AC, in 1.0 channels: a workflow task assigned to a manager whose language is Urdu gives an in-app item
  and an e-mail in Urdu with a working link; an e-mail refused by the mail server is retried with back-off and then
  shown as failed with the reason in the delivery log; resend creates a new message.
- One event never gives the same person two items or two e-mails, even when the dispatcher handles it twice.
- Quiet hours delay a non-mandatory e-mail to the end of the quiet period; a mandatory one is sent at once; switching
  off e-mail for an event group stops those e-mails but not the in-app items.
- A template that uses a salary-class field is refused; an e-mail never contains a personal-class value.
- Delivery results of events marked audited are in the audit log with time and result.
- Forgot password answers the same whether or not the account exists; a reset link works once and expires; the e-mail
  code is accepted once, within its time, within the attempt limit.
- Spec 02 DOC AC, with 1.0 content (no invoices): a letter template with a QR code renders in English and in Urdu
  (right to left, joined Nastaliq script) on the company letterhead, is stored against its record, and a prior version
  of an attachment can be restored.
- A file is not downloadable until scanned clean (when scanning is required); an infected file is quarantined with a
  security event and an alert; a file whose content does not match an allowed type is refused.
- A user who cannot read the record cannot read its files; downloads of sensitive files are in the access log; a
  file under legal hold survives its retention rule.
- File contents in the store are encrypted and another customer's key cannot read them; one customer cannot list or
  open another's files (tenant-isolation suite).
- Every new endpoint passes the tenant-isolation suite and has permission tests; tests cite the FR ids.

## Questions as put to the product owner

- **Q0 One slice or three.** *Recommendation:* one slice file, three sessions and three pull requests, in this order:
  **S1.11a** jobs and events (items 1 to 7), **S1.11b** notifications and identity e-mails (8 to 16), **S1.11c** files
  and templates (17 to 20). Notifications need the event dispatcher of a; expiry reminders of c need b. Alternative:
  four parts, with identity e-mails on their own.
- **Q1 Channels in 1.0 (finding 1).** *Recommendation:* in-app and e-mail only. The sending side is a provider
  contract, so SMS, WhatsApp and push plug in later without changing any module. KRN-NTF-01 is read as 1.0 for in-app
  and e-mail (as CR-009 did for MFA methods).
- **Q2 Our own scheduler instead of Quartz.NET (finding 2).** *Recommendation:* build a small scheduler on the
  approved `job.*` tables. Quartz would add eleven tables per customer outside the approved design and one scheduler
  per customer database. No new package.
- **Q3 How schedules are written.** *Recommendation:* simple choices instead of cron text: every N minutes, hourly,
  daily at a time, weekly on chosen days at a time, monthly on a day (or the last day) at a time; in the customer's
  time zone (`org.time_zone`); option "working days only" using the company calendar of S1.10. Alternative: cron text.
- **Q4 Who a job acts as (R-009).** *Recommendation:* a scheduled job acts as a reserved system user with exactly
  the permissions its manifest declares, never a general bypass; the audit log shows "job: <name>". A run a person
  asked for (an import, a payroll calculation) acts with that person's rights, checked again when it starts; if they
  lost the right, the run fails and says why.
- **Q5 Fair shares between customers (KRN-JOB-04).** *Recommendation:* each worker runs at most 4 jobs at once
  (`Jobs:Slots`), at most 2 of one customer (`Jobs:PerTenantSlots`), taking customers in turn; higher priority first
  within a customer. The same for every customer in 1.0.
- **Q6 Jobs when a customer is read-only, locked or suspended.** *Recommendation:* read-only and locked: only jobs
  that keep the system healthy run (licence refresh, audit checks, partitions, purges); business jobs wait. Suspended:
  only licence refresh. Jobs of an unlicensed module never run.
- **Q7 How quickly events are handled.** *Recommendation:* the worker checks each customer database every 2 seconds
  (`Events:PollMilliseconds`), so a notification normally leaves within about 5 seconds. A consumer that fails is
  retried with growing waits (up to 1 hour apart) and raises an alert after 1 hour; events are never dropped. Risk to
  record: polling every customer database costs more as the number of customers grows (revisit before large SaaS).
- **Q8 Operational alerts (KRN-JOB-06).** *Recommendation:* alert on: a job failed after its last retry; a job still
  running past its time limit or whose worker stopped; a scheduled job not started 15 minutes after its time; events
  waiting more than 5 minutes; critical audit events (tamper attempt, chain broken, anchor copy mismatch) and the
  nightly check failing. Who: Tenant Admins (in-app and e-mail, mandatory) and the job's owner; a stopped worker also
  to the operator e-mail address of the deployment (`Alerts:OperatorEmail`).
- **Q9 What counts as unusual access (HRM-PRV-05, finding 4).** *Recommendation:* one rule in 1.0: a user who opens or
  exports sensitive data (salary, personal, sensitive files) of more than 50 different people within one hour; the
  number is a setting (`aud.alerts.sensitive_people_per_hour`). Alert to Tenant Admins and Auditors. Alternative: no
  rule in 1.0 (the access log exists; alerts in 1.1).
- **Q10 Sending e-mail (KRN-NTF-07).** *Recommendation:* one SMTP adapter (works with almost every mail service).
  SaaS: our mail relay, set by the operator; the customer sets sender name and reply-to address; a sender address on
  the customer's own domain only after the operator marks the domain checked (runbook: SPF and DKIM steps). On-premises:
  the customer's own mail server in `itg.connectors`, password in the secret store. Bounces: a refusal at sending ends
  the message as failed with no retry; later bounce messages are read from a bounce mailbox every 15 minutes when one
  is configured. At most 60 e-mails a minute per customer (setting). Alternative: no bounce mailbox in 1.0.
- **Q11 Preferences and quiet hours.** *Recommendation:* in-app items are always delivered (the centre is the
  record); a user can switch e-mail off per event group (approvals, my requests, documents, system); quiet hours hold
  e-mails until they end. Mandatory notifications ignore both: security alerts, sign-in codes and links, licence
  read-only and locked, operational alerts. E-mail is on by default.
- **Q12 Which notifications go into the audit log (HRM-NTF-16).** *Recommendation:* those that carry a decision or a
  deadline: approval assigned, escalated, information requested, returned, decided; licence state changes; document
  expiry; alerts. One audit entry per delivery result (sent or failed, with time). Others are kept only in the
  delivery log (30 days, spec 03 section 8).
- **Q13 Sensitive content (GHR-06).** *Recommendation:* no notification ever carries salary-class values; e-mails
  carry no personal-class values either (the link shows them after sign-in); the template check refuses such fields.
- **Q14 Who gets what (KRN-NTF-03).** *Recommendation:* by default the people the event names (the approver, the
  requester). Administrators can add rules: event, company (or all), optional condition on the event's fields, and
  audience (users, roles, groups, the line manager of the person concerned once HR provides it), channels, mandatory or
  not. Example: "when a request is escalated in company A, also tell the HR Managers role".
- **Q15 Notification templates and where they are edited.** *Recommendation:* the product ships default texts in
  English and Urdu for every event; a customer may edit them (each edit a new version; the product's later changes do
  not overwrite a customer's edit; "back to product text" possible); preview and test send to oneself. A simple
  template editor screen (text with placeholders and preview, no visual designer) is added to **S1.15**, for
  notification and document templates. Urdu default texts need a native speaker's review.
- **Q16 Identity e-mails.** *Recommendation:* all five in 1.0: invitation or activation link (existing setting
  `iam.activation.token_hours`); "forgot password" (same answer whether the account exists or not; link valid 60
  minutes, one use; at most 5 requests an hour per address); administrator "send reset link"; e-mail code as second
  factor (6 digits, 10 minutes, 5 tries, CR-009); after the MFA grace period an authenticator enrolment is confirmed by
  an e-mailed code (R-003). All times are settings.
- **Q17 How PDFs are made.** *Recommendation:* as spec 01 says: templates produce HTML, and headless Chromium (the open
  part of the Chrome browser) prints it to PDF. It is installed on the servers as a separate program, like the
  PostgreSQL backup tools, and driven by PuppeteerSharp (MIT). It handles Urdu script and right-to-left correctly.
  Chromium is BSD-licensed with bundled parts under other open licences; because we do not build it into our code it is
  recorded as a server tool. Alternative: a pure .NET PDF library (PDFsharp, MIT), which cannot shape Urdu script
  correctly.
- **Q18 Fonts (finding 5).** *Recommendation:* allow the SIL Open Font Licence 1.1 for fonts only (it allows bundling
  and embedding in documents; it only forbids selling the font on its own) and ship Noto Sans and Noto Nastaliq Urdu
  with the product. This is a reading of D-09, recorded in CR-045. Alternative: use whatever fonts the server has
  (Urdu output then differs by server and may be wrong).
- **Q19 Output formats (finding 6).** *Recommendation:* PDF and HTML in 1.0 (and plain text, CSV and fixed-width for
  bank files, used by the payroll slices). Word output later. Password-protected PDFs come with the payslip slice
  (HRM-PAY-28), which chooses how.
- **Q20 Where files are stored.** *Recommendation:* both a local folder (which can be a mounted network share, for
  on-premises) and an S3-compatible store (for SaaS), chosen per deployment by the operator. Each customer has its own
  prefix and its own file key; contents are encrypted before they leave the server. S3 through AWSSDK.S3 (Apache-2.0).
- **Q21 Virus scanning.** *Recommendation:* a scan hook with a ClamAV adapter (ClamAV runs as its own service; we only
  talk to it over the network). Setting `doc.scan.mode`: `required` (default; files are not downloadable until clean;
  if the scanner is down they wait) or `off` (an on-premises customer may choose; the health page shows "not
  scanned"). An infected file is quarantined, with a security event and an alert.
- **Q22 Upload limits and types.** *Recommendation:* at most 20 MB per file (setting); allowed types PDF, JPEG, PNG,
  Word, Excel, plain text and CSV (setting); the type is checked from the content, not only the name.
- **Q23 Who may see and change attachments.** *Recommendation:* files follow their record: whoever may read the record
  may download its files; whoever may change it may add, replace or delete them. Files of a sensitive document type
  also need the record's sensitive-data right, and every download is in the access log. Delete hides the file; the
  content stays until retention removes it.
- **Q24 Retention and legal hold (finding 7).** *Recommendation:* the months count from the upload date unless the
  owning module sets the end date (for example HR from the end of employment). After it: archive (kept, hidden from
  normal lists), delete (content destroyed, the record of the file kept) or review (listed for an administrator). A
  legal hold (new, CR-045) stops all of these. A country pack's minimum cannot be shortened. No rules ship by default,
  so nothing is deleted until a customer or pack sets a rule. Runs daily.
- **Q25 Expiry reminders (KRN-DOC-08).** *Recommendation:* reminders 30 days, 7 days and on the day of expiry (setting),
  to the person who uploaded the file and to any subscription rule; HR adds the employee and HR audience in S1.24.
- **Q26 Salary in documents (HRM-DOC-08).** *Recommendation:* template fields come from the owning module with their
  field class; a template using salary fields can be generated only by users with the salary right, each generation
  is in the access log, and the generated file is marked sensitive.
- **Q27 Where documents are produced.** *Recommendation:* previews and single documents right away in the request;
  batches (letters to many people, later payslips) as jobs. Both server programs (API and worker) need Chromium.
