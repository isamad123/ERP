## Goal
The customer's rules become data that is assigned to the right people and can be explained. HR defines a policy (for
example "Head office leave policy"), says who it is for (company, location, grade, employee type, department or a custom
field), and in which order rules win; anyone allowed can ask "which leave policy applies to Ali on 1 March, and why" and get
the rule and the layer that decided it. Country packs bring the country's ready-made content (holidays, banks, identifier
formats, lists, default settings and, later, statutory rules) as a signed bundle; the customer may change any of it, and a
newer pack never overwrites what the customer changed. This slice builds the engine and the loader, and the first Pakistan
pack with content that needs no legal validation.

## What exists already (and stays)
- Tables `hrm.policies` (type, source pack or tenant), `hrm.policy_versions` (parameters as JSON, override flag, draft,
  active, retired, effective-dated when active), `hrm.policy_assignments` (rule JSON, precedence, effective-dated);
  generated reads; writes closed.
- `cfg.installed_packs`, `cfg.pack_items` (object type and key with override flag), `cp.pack_catalog` (signed packs and
  versions), `cp.signing_keys` (purpose `pack`); the entitlement signature check (ECDSA P-256, canonical JSON; S1.09b).
- Settings already resolve by layer including "country pack"; labels have a `pack` layer; `ref.calendars.source` is
  `pack` or `tenant`; leave, attendance, loan and expense tables already point to `hrm.policies` and `hrm.policy_versions`.

## Found while preparing (needs a ruling)
1. **No statutory content exists to put in the pack** (R-002, AS-4): leave statutes, working-time limits, tax tables and
   contribution rates are not written or validated; this slice must not invent them (Q11).
2. **Policy parameters have no schema.** `policy_versions.parameters` is "validated against the policy type schema", but no
   type or schema is defined; each owning slice (leave S1.32, attendance S1.29, pay S1.34 and so on) knows its parameters
   (Q2).
3. **Where packs come from.** `cp.pack_catalog` holds signed packs in the control plane, but nothing builds, signs or uploads
   a pack (Q8).
4. **"Field requirements"** in FR-HRM-POL-04 (for example "religion required for Hajj leave") have no mechanism (Q10).

## Build
### Part S1.23a: policy framework (Opus, fresh review)
1. **Policy types (Q2, D-10).** Each module declares its types in `<module>.Infrastructure/Access/policy-types.json`: code,
   names, a JSON Schema for parameters, which attributes rules may use, and whether one policy or several may apply (one for
   leave per leave type, for example). This slice registers a test type only in tests, and the types `probation` and
   `notice_period` (replacing the S1.20 settings, Q3); later slices add theirs.
2. **Policies and versions.** Create a policy of a type for a company; versions as drafts edited freely, validated against the
   schema, activated from a date (the previous version ends the day before; running results keep the version they used);
   retire. Pack-sourced versions are marked; a tenant edit of a pack version creates a tenant version with `is_overridden`.
3. **Assignments (FR-HRM-POL-02, Q4).** Rules over employee attributes valid on a date: company, location, branch, grade,
   employee type, unit (with "and its sub-units"), custom field of the employment; operators equals, in, not in; all
   conditions joined by "and" (several assignments give "or"); precedence unique per type and company; effective-dated.
4. **Resolution (Q5).** `IPolicyResolver.ResolveAsync(employmentId, policyType, asOf)` (HR contract, used by every HR engine):
   collect the employee's attributes on the date, evaluate active assignments of the type in precedence order, first match
   wins (or all matches for multi types); answer the policy version and the reason (assignment, conditions met, layer pack or
   tenant). No match gives "no policy" (callers decide; never a silent default). Cached per request; deterministic.
5. **Activation checks.** Activating an assignment set refuses two assignments of the same precedence, and warns when an
   active employee would match no assignment of a required type.
6. **Resolution view and screens (FR-HRM-POL-03).** Policies, versions (with a difference view between versions), assignments
   (rules in plain sentences); "Which policy applies?": pick an employee, a type and a date, see the version, the rule that
   matched, the rules that did not and why, and the layer.

### Part S1.23b: pack loader (Opus, fresh review)
7. **Pack format (FR-KRN-CFG-01, Q6).** A pack is a zip with `manifest.json` (id, kind, version, compatible product versions,
   dependencies, objects list with type, key and content hash, merge rule per object type) and one file per object; signed
   with the vendor's pack key (ECDSA P-256 over the canonical manifest, which hashes every file); keys in `cp.signing_keys`
   (purpose `pack`).
8. **Signing and catalogue (Q8).** Operator commands `pack build <folder>` (writes the manifest), `pack sign` (offline, with
   the private key outside the repository, like `entitlement sign`), `pack publish` (verifies and stores in
   `cp.pack_catalog`); the pack source folders live in the repository under `packs/<pack-id>/`.
9. **Object handlers (D-10).** Each object type has a handler in its owning module: kernel (holiday calendar, bank list,
   option list, setting default at the pack layer, label at the pack layer, numbering default, identifier kind), HR (policy
   type defaults: policies and versions with source `pack`, policy assignments), later modules add theirs.
10. **Install and upgrade (FR-KRN-CFG-02, FR-HRM-POL-06, Q7).** Install creates objects through the handlers in one
    transaction per pack and records each in `cfg.pack_items`; a tenant change to a pack object sets `is_overridden`;
    upgrade compares by key and hash: new objects added, unchanged-by-tenant objects updated, overridden objects kept and
    listed as conflicts with both values, removed objects retired (never deleted when referenced); nothing touches
    transactional rows; every install and upgrade audited and in `cfg.installed_packs`.
11. **Pack manager (FR-ADM-PKG-01, FR-HRM-POL-06).** Installed packs with version, contents summary, compatibility, objects
    overridden by the customer (diff view: pack value against customer value), conflicts of the last upgrade, available
    newer versions with release notes; "install update" (tenant administrator; maker-checker when on).
12. **Provisioning and wizard.** `tenant provision --packs country-pk` installs packs after migrations (FR-KRN-TEN-02); the
    S1.18 wizard gains the pack step (choose country and industry packs from the catalogue; installed ones shown).

### Part S1.23c: Pakistan pack, first content (Sonnet)
13. **`packs/country-pk` 1.0.0 (Q11, Q12).** Content that is public fact and needs no practitioner judgement, each file
    marked with its source and "verify before go-live": identifier kinds and formats (from S1.20), banks of Pakistan (names
    and codes), provinces and region codes, Urdu labels at the pack layer where the pack's terms differ, option lists
    (reason codes, relationships, marital status, exit reasons taxonomy proposal), setting defaults (time zone, currency,
    week start, digits and grouping), the federal public holidays of the next calendar year with Islamic dates marked
    tentative. **No** leave statute, working-time limit, tax table, contribution rate or statutory form: those come with
    their slices and AS-4 validation.

## Acceptance
- Two leave-type test policies assigned by grade (precedence 1: grade G5 and above; precedence 2: everyone): a G6 employee
  resolves to the first, a G3 to the second; the view explains both, including the rule that did not match.
- A promotion from G4 to G6 dated 1 March: resolution as of 28 February gives the second policy, as of 1 March the first.
- A custom field condition ("Shift worker = yes") resolves correctly; a rule on a retired custom field is refused at
  activation.
- Two assignments with the same precedence are refused; an employee matching nothing is reported at activation.
- Activating version 2 from 1 April leaves resolution before 1 April on version 1.
- A signed pack installs on a fresh customer through provisioning; a pack with one changed byte is refused; a pack signed by
  an unknown or revoked key is refused.
- The customer renames a pack option-list item and changes a pack setting default; upgrading to pack 1.0.1 (which changes
  both and adds a holiday) keeps the customer's two values, lists them as conflicts with both values, and adds the holiday.
- The pack manager shows version, overrides and conflicts; the S1.18 wizard installs the pack for a new customer.
- Pack content files each name a source and carry "verify before go-live"; the pack contains no rate, slab or threshold
  (a test scans the pack for the forbidden object types).
- Every endpoint: tenant-isolation suite, permission tests; resolution is deterministic (same inputs, same answer, repeated
  1,000 times); tests cite the FR ids.
- Fresh Opus reviews of S1.23a and S1.23b with high and medium findings fixed or ruled on before their merges.

## Questions for the product owner
Each question has a recommendation; answering "accept all" takes every recommendation.

- **Q0 Parts, models and reviews.** *Recommendation:* S1.23a and S1.23b on Opus (high) each with a fresh Opus review; S1.23c
  on Sonnet (medium), content only, no review beyond the checks. CR-079 records the Sonnet part. Alternative: all on Opus.
- **Q1 Who manages policies.** *Recommendation:* HR administrators (`hrm.policies.manage`, company scope); maker-checker on
  activation when the customer's maker-checker setting is on. Alternative: tenant administrators only.
- **Q2 Policy types and schemas (D-10).** *Recommendation:* each module registers its policy types with a JSON Schema of
  parameters in `policy-types.json`; the framework validates parameters against it; the type's owning slice writes its
  schema (leave S1.32, attendance S1.29, shifts S1.28, pay S1.34, loans S1.41, expenses S1.42, performance S1.49).
  Alternative: one fixed list of types in the kernel (against D-10).
- **Q3 Probation and notice as policies.** *Recommendation:* types `probation` (months, extension limit, who reviews) and
  `notice_period` (days by employee type and length of service band) are registered here and replace the S1.20 settings;
  defaults are customer choices, not statutory values. Alternative: keep settings until a later slice.
- **Q4 Rule conditions.** *Recommendation:* the attributes of Build item 3 with equals, in and not in, joined by "and";
  "or" by adding another assignment; no expressions (rules engine is Later). Alternative: and/or trees as in workflow
  conditions (more power, harder to explain in the resolution view).
- **Q5 No match.** *Recommendation:* the resolver answers "no policy" and each engine decides what that means (for example
  leave refuses the request with "no leave policy applies; ask HR"); the activation check warns HR in advance. Alternative:
  a company default policy per type that always matches last (equivalent when HR adds a catch-all assignment).
- **Q6 Pack signature (D-09).** *Recommendation:* the same ECDSA P-256 and canonical JSON as entitlements (no new package);
  the manifest lists the hash of every file; private keys never in the repository or the control plane.
  Alternative: a separate signing format (more code to review).
- **Q7 Upgrade conflicts (FR-KRN-CFG-02).** *Recommendation:* the customer's value always stays; the conflict list shows the
  pack's new value with "take the pack value" per item (an ordinary audited change); preview before upgrade and dated
  activation are 1.1 (FR-HRM-POL-05). Alternative: block the upgrade until every conflict is decided.
- **Q8 Building and publishing packs.** *Recommendation:* pack sources in the repository (`packs/<pack-id>/`), built and signed
  by operator commands, published into `cp.pack_catalog`; customers receive new versions as "available" in the pack manager.
  Alternative: packs installed only from files uploaded by the customer (on-premises style; 1.1).
- **Q9 Several countries in one customer (GHR-07).** *Recommendation:* packs install per customer; country objects are keyed by
  country (calendars, banks, identifier kinds), and policies from a pack are created per company of that country.
  Alternative: one country pack per customer only.
- **Q10 Field requirements (FR-HRM-POL-04).** *Recommendation:* a pack object type "field requirement" that sets a field
  policy default (required, hidden) for a table at the pack layer, for example religion shown only where a pack needs it;
  the customer may override. Alternative: leave field requirements to the statutory slices.
- **Q11 What the first Pakistan pack contains (R-002, AS-4).** *Recommendation:* only the public-fact content of Build item 13,
  each item with its source and "verify before go-live"; every statutory rule arrives with its own slice after you obtain
  the practitioner validation (AS-4). CR-079 records that FR-HRM-POL-04's statutory contents are delivered by S1.32,
  S1.36, S1.37 and S1.46. Alternative: draft statutory defaults now for practitioners to correct (risk that unvalidated
  numbers reach a customer).
- **Q12 Holiday dates.** *Recommendation:* federal public holidays of the next calendar year from the government's published
  list; Islamic holidays marked tentative and confirmed by the customer (S1.14). Provincial holidays left to customers.
  Alternative: none.
- **Q13 Urdu texts.** *Recommendation:* drafted with the glossary and marked for review (R-062).
- **Q14 Change request CR-079.** *Recommendation:* approve: `policy-types.json` and the `IPolicyResolver` contract (Q2, Q5);
  policy types `probation` and `notice_period` (Q3); pack format, signing, commands `pack build|sign|publish`, object
  handlers and the `packs/` folder (Q6, Q8); field-requirement object type (Q10); first Pakistan pack content and the
  delivery of statutory contents by later slices (Q11); S1.23c on Sonnet (Q0); contracts register rows added at build.
