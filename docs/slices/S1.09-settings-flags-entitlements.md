## Goal
Two things the whole product leans on. **Settings:** every option a customer can change (password length, fiscal-year
start, time zone, and the many options later slices add) is declared once, with its type, default, allowed values and
help text in English and Urdu. A value can be set for the whole customer, one company, one role or one user, and the most
specific one wins; the system always says where the value in force came from. Every change is recorded, can be undone,
and reaches every server within seconds without a restart. Sensitive settings need a second person's approval. **Feature
flags** switch a capability on or off for the customer, a company or a user group. **Entitlements** say what the customer
has bought: edition, modules, features, limits and term. The system serves only licensed modules, stops at the bought
limits with a clear message (warning first at 90 percent), counts usage every month, and moves through the licence states
Active → Warning → Grace → Read-only → Locked as the end date passes. Customer data is never deleted or hidden: in
read-only users still sign in, read and export; in locked the administrator still sees the licence page and can export.
A new signed entitlement restores full use within minutes, without downtime.

## What exists already (and stays)
- Tables for settings, history, flags and overrides exist (S1.02); settings are seeded by hand-written code for `iam.*`
  (S1.05), `cfg.numbering.*` and `org.time_zone` (S1.08), and each reads its own layers.
- `iam.*` settings change through `PUT /api/iam/settings/{key}` with the S1.06 rule that switching off maker-checker or
  privileged MFA needs a second tenant admin (CR-025). The generated `cfg.setting_values` API refuses `iam.*` keys.
- The signed entitlement (ECDSA, S1.03) is checked at provisioning; `cp.entitlements.status` drives the access mode;
  nothing moves the status yet. The user limit reads `claims.limits.users` (S1.05 ruling P4).
- Read-only refuses every change except sign-in steps (CR-015). **Locked and suspended refuse every request, sign-in and
  licence page included**, which contradicts spec 01 section 7.3 and KRN-ENT-04 ("allow exporting data in … locked
  states"). This slice corrects it (Q5).

## Build
1. **Setting manifests (KRN-SET-01, KRN-SET-03, Q10).** One manifest file per module declares its settings; `migrate`
   and provisioning register them. The existing hand-coded settings move into manifests with identical keys, defaults and
   texts.
2. **Resolver (KRN-SET-02, Q11).** One kernel service gives the effective value of a setting for a context (company, the
   user and their roles) and the layer it came from. Existing readers (`IdentitySettings`, `NumberingSettings`) use it.
3. **Changes (KRN-SET-04, ADM-SET-04, ADM-SET-06, Q12).** One service to set, reset to inherited and revert, with
   validation, a history row and a reason for each change, and maker-checker where the setting requires approval.
4. **Propagation (KRN-SET-06, Q13).** Cached values are refreshed on every host within seconds of a change.
5. **Feature flags (KRN-SET-05, Q14).** Registry from manifests, overrides per customer, company and user group,
   resolver and change service.
6. **Entitlement model and templates (KRN-ENT-01, Q1, Q2).** The claims format, following the D-24 key catalogue; three
   edition templates used only to pre-fill a new entitlement.
7. **Applying entitlements (ADM-PLT-03, KRN-TEN-02, Q3).** Operator command to apply a newly signed entitlement:
   checks, history, scheduled start date, schema install for newly licensed modules.
8. **Licence states (KRN-ENT-04, KRN-TEN-09, Q4 to Q6).** The state follows from the dates and the injected clock;
   transitions are recorded and announced; locked behaves as the specification says.
9. **Module and feature gate (KRN-ENT-03, Q9).** Endpoints of an unlicensed module or feature do not exist for the
   customer; a capabilities endpoint tells the web shell which menus to show.
10. **Limits (KRN-ENT-05, KRN-IAM-18, ADM-USR-08, Q7).** One kernel limit guard with warning and hard stop, used for named
    users, concurrent users and companies now, and offered to later slices for employees, storage and API calls.
11. **Usage metering (KRN-ENT-06, Q8).** Daily readings, monthly values in `cp.usage_meters`, usage statement per month.
12. **Endpoints, permissions and texts (Q16).** All texts as localisation keys (English and Urdu).

## Acceptance
- Spec 02 SET AC: a company-level value of a customer-wide setting applies only to that company and is shown with its
  source; resetting it restores the inherited value.
- For every layer combination the resolver returns the most specific allowed value and names its layer; a stored value
  that is no longer valid is ignored with the next layer used (and reported in the layered view); a layer the setting
  does not allow is refused when written.
- A setting that needs approval is not changed until a different administrator approves it; self-approval is refused.
- Every change, reset and revert writes a history row with old value, new value, reason, who and when, and appears in the
  audit log; reverting a history row restores that value as a new change.
- A change made through one API host is seen by a second host (separate process, same customer database) within the
  agreed time (Q13), with no restart.
- Moving the existing `iam.*`, `cfg.numbering.*` and `org.time_zone` settings into manifests changes no key, default,
  validation or text (tested against the values S1.05 and S1.08 seed today).
- A feature flag resolves by layer (Q14); a flag whose entitlement key is not licensed is off whatever its overrides say.
- Spec 02 ENT AC: with an expired entitlement, after the grace period the customer is read-only, users can still sign in
  and export, and applying a new signed entitlement restores full use within minutes without downtime.
- Entitlement testing (spec 02 section 25): valid, expired, tampered (signature), wrong customer, lower or equal version,
  unknown signing key, revoked key and over-limit entitlements each give the documented result; rolled-back clock is
  1.1 (KRN-ENT-07).
- Each state (Active, Warning, Grace, Read-only, Locked) is reached on the right day for a dated entitlement, recorded once
  in `cp.license_events` and the customer's security events, and published as an event; a perpetual entitlement stays
  Active.
- In locked state a tenant admin can sign in, read the licence page and run an export the specification allows; every
  other request is refused with "the licence is locked"; data is untouched.
- An endpoint of an unlicensed module answers exactly like an endpoint that does not exist; adding the module through a
  new entitlement installs its schema and the endpoint starts answering; removing it keeps the data.
- Limits: at 90 percent a warning is returned and announced once; at the limit, creating or activating a user, signing
  in beyond the concurrent limit, and creating or reactivating a company are refused with a message naming the limit;
  two administrators taking the last seat at the same time cannot both succeed.
- Monthly usage values and the usage statement match counted test data.
- Each new endpoint passes the tenant-isolation suite and has permission tests; tests cite the FR ids.

## S1.09b build-plan rulings (product owner, 2026-11-17; plan approved with its recommendations)
- **B1** `expires_at` is the last licensed day; a day ends at midnight in the customer's time zone. With E the end date:
  Active until E−30, Warning E−29 to E, Grace E+1 to E+14, Read-only E+15 to E+44, Locked from E+45 (default periods).
  Before a later entitlement's start date the previous one stays in force; the first entitlement is in force from provisioning.
- **B2** Concurrent users are the distinct users with an open session; a user already signed in may sign in again.
- **B3** A listed module needs its base key (`hrm` needs `hrm.core`); a feature key needs its module and its parent key;
  `hrm.core` without `hrm.payroll` may be sold.
- **B4** `entitlement apply` (and provisioning) refuses an entitlement whose end date has passed.
- **B5** Counted companies are active and not deleted; reactivation is inactive → active or a restore.
- **B6** Limit events are copied once each to `cp.license_events` (CR-039; built as a column, see there).
- Design notes D1 (time zone from the settings cache, no new column), D2 (control plane decides; customer copy kept in
  step) and D3 (existing tests reach states through dates). Build deviations recorded in CR-040; risks R-020 to R-022.

## Questions as put to the product owner

- **Q0 One slice or two.** This is the widest kernel slice so far. *Recommendation:* keep one slice file but build it in
  two sessions and two pull requests: **S1.09a** settings and flags (items 1 to 5), then **S1.09b** entitlements,
  states, gate, limits and metering (items 6 to 12). Each part is reviewed on its own. Alternative: one session.
- **Q1 What an entitlement contains.** *Recommendation:* the signed claims follow the D-24 catalogue:
  `deployment` (saas or on_prem), `modules` (module ids, for example `hrm`), `features` (keys such as `platform.base`,
  `hrm.core`, `hrm.payroll`, `hrm.performance`, `hrm.learning`), `packs` (for example `pack.country.pk`), `addons`,
  `limits` (keys `users.named`, `users.concurrent`, `companies`, `employees.active`, `storage.gb`, `api.calls`,
  `ai.tokens`; a missing limit means no limit), `term` (`maintenance_expires_at` and the state periods of Q4),
  `support_tier` and `source` (yes or no). Edition, effective date and end date stay where they are today. A feature key
  needs its parent (`hrm.payroll` needs `hrm.core`, every key needs `platform.base`); an entitlement that breaks this is
  refused. The S1.05 key `limits.users` is renamed `users.named` (no customer is live, so test files are simply
  re-signed). Server binding is 1.1.
- **Q2 Editions.** D-26 makes Starter, Business and Enterprise entitlement templates; names, limits and prices are
  commercial choices. *Recommendation:* three template files in the repository whose values are marked "placeholder,
  to be set by the product owner"; the operator command uses a template only to pre-fill a new entitlement, and every
  value is written out in full in the signed entitlement, so changing a template later never changes what a customer
  already has. No code anywhere tests the edition name (spec 16 rule SC-3); behaviour follows keys and limits only.
- **Q3 Applying a new entitlement, effective dates and approval (ADM-PLT-03).** *Recommendation:* operator command
  `entitlement apply --tenant <code> --file <signed.json>`: checks the signature against an active signing key, the
  customer code and a version higher than the last; refuses a module whose features are not all present. If the start
  date is today or earlier it takes effect at once and the previous one is marked superseded; a future start date is
  stored as **scheduled** and takes effect on that day (CR-036). Newly licensed modules get their schema installed
  first; if that fails nothing changes. A module that is no longer licensed keeps its schema and data; its screens and
  endpoints disappear, and licensing it again brings them back unchanged. The approval is the separation already in the
  design: the person who signs (holds the private key, off-line) is not the operator who applies; the vendor console
  with platform approvals is S1.17. History: `entitlement history --tenant <code>`.
- **Q4 Licence state periods.** Spec 01 gives "about 30 days" of warning and a "short fixed period" of grace; spec 02
  says periods follow the signed contract. *Recommendation:* periods are claims in the entitlement (`term.warning_days`,
  `term.grace_days`, `term.read_only_days`), with product defaults **30, 14 and 30 days**: Warning from 30 days before
  the end date, Grace for 14 days after it, then Read-only for 30 days, then Locked. A day ends at midnight in the
  customer's time zone (`org.time_zone`, customer layer; default Asia/Karachi). No end date means perpetual: always
  Active. Alternative: fixed product periods, not per contract.
- **Q5 What each state allows.** *Recommendation:* Active, Warning and Grace: full use (banners from S1.12: Warning for
  administrators, Grace for everyone). Read-only: as built (sign-in, read, export; no change; CR-015). Locked: sign-in
  stays possible; only endpoints marked "allowed when locked" answer, for users with the permission: the licence page
  and the exports (today the audit export; S1.16 marks the export centre); everything else answers 403 "the licence is
  locked". An operator suspension (`tenant suspend`) behaves exactly as Locked, as KRN-TEN-09 says; no state deletes or
  hides data. Alternative: keep suspension as a total block for security incidents.
- **Q6 How state changes happen before the jobs slice.** *Recommendation:* the state is worked out from the dates and the
  injected clock every time it is read (control plane and customer database use the same rule), so it is right even if
  nothing runs; a small hourly loop in the worker host records each change once (`cp.entitlements.status`,
  `meta.local_entitlement.state`, `cp.license_events`, customer security event) and publishes
  `kernel.licence.state_changed` for the e-mails of S1.11. S1.11 later moves the loop into the jobs framework. The same
  loop activates scheduled entitlements (Q3) and takes usage readings (Q8). Operator command `licence refresh` runs it
  at once.
- **Q7 Limits.** *Recommendation:* one kernel limit guard: check and take a seat in the caller's transaction, under a
  lock per customer and limit so two people cannot take the last seat. Warning at **90 percent** (customer setting
  `cfg.limits.warning_percent`, ADM-USR-08 "configurable thresholds"), returned with the response and announced once per
  crossing; hard stop at the limit with a message naming the limit and "contact your provider to raise it". What counts:
  named users as ruled in S1.05 (P4); concurrent users = sessions open now, checked at sign-in; companies = active
  companies, checked on create and reactivate (KRN-IAM-18). Employees, storage and API calls are wired by their slices.
  A limit lowered below current use blocks only new seats; nothing is switched off.
- **Q8 Usage metering.** *Recommendation:* daily readings; the monthly value is the **highest** daily reading for users,
  companies, employees and storage, and the **total** for API calls. Storage = database size plus stored files. Active
  employees come from the HR module through a kernel contract (counted only when HR is licensed; S1.20 provides it).
  Values go to `cp.usage_meters`; the usage statement for a month lists each meter, its limit and the highest
  percentage. AI tokens are Later (the meter list has no AI entry; nothing to change now).
- **Q9 Licensed modules and features (KRN-ENT-03).** *Recommendation:* an endpoint of a module or feature the customer is
  not licensed for answers 404 exactly as if it did not exist, and is left out of the customer's API description. The
  data design gets a key `entitlement:` (file default, table override, CR-036): people and time tables `hrm.core`,
  payroll tables `hrm.payroll`, forms and performance `hrm.performance`, learning `hrm.learning`; hand-written endpoints
  declare their key. Kernel endpoints need `platform.base`. New endpoint `GET /api/kernel/capabilities` gives the web
  shell the licensed modules and features, the flags on for the caller and the licence state, so menus and screens of
  unlicensed parts are never shown. Background work and event consumers of an unlicensed module do not run (S1.11
  keeps the rule).
- **Q10 How settings are declared.** *Recommendation:* one manifest per module (`<module>/Settings/settings.yaml`) with:
  key, type (bool, int, decimal, text, choice, list, json), default, validation (min, max, choices, pattern, list item
  type and length), unit, allowed layers, role rule (Q11), self-service flag, visibility, needs approval, area, and name
  and help in English and Urdu. Visibility: visible settings appear in the settings centre; hidden ones (product
  machinery) can only be changed by migrations and packs. `cfg.settings` gains the missing columns (CR-036). Removing a
  setting from a manifest never deletes stored values; the definition is kept and marked hidden.
- **Q11 Layers and how they combine.** Order, most specific last: product default, pack, customer, company, role, user.
  A user often has several roles, and S1.06 already had to decide this for MFA ("required if any role requires it").
  *Recommendation:* a setting may allow the role layer only if its manifest gives a role rule: `any` or `all` (yes/no
  settings), `lowest` or `highest` (numbers); the S1.06 MFA behaviour is `any`. Only roles in force today and covering
  the company in context count. The user layer is set by an administrator, or by the user themself where the setting
  is marked self-service (for example language and time zone, ADM-USR-10). The context comes from the server (the
  caller and the document's company), never from request input.
- **Q12 Changing settings.** *Recommendation:* one change service and API for all settings. `iam.*` keys keep the S1.06
  rules by delegating to the access settings service (so the existing endpoint and the "second tenant admin" rule are
  kept). Each change: validate type and rules, write the value and a history row with reason, change-log entry; a setting
  marked "needs approval" creates a maker-checker request (the S1.06 mechanism) and applies only when another
  administrator approves. Reset to inherited removes the layer's value (with history). Revert writes the old value of a
  history row as a new change. Generated writes on values and flag overrides are closed (CR-036).
- **Q13 How fast a change reaches every server (KRN-SET-06).** *Recommendation (A):* a tiny table `cfg.config_versions`
  (one counter for settings, one for flags) raised by a database trigger on every change; each host keeps resolved values
  in memory and compares the counter at most once per second per customer, so a change is in force everywhere within
  **about 1 second** (at once on the host that made it). Cost: one indexed one-row read per customer per second, only
  while requests arrive. New table, CR-036. Alternative (B): no new table; cached values expire after 30 seconds.
- **Q14 Feature flags.** *Recommendation:* flags are declared in the module manifest (key, default, module, optional
  entitlement key, name and help in English and Urdu). Override order: customer, company, user group; the most
  specific wins; if the user's groups disagree, **on wins** (flags open a capability to a pilot group). A flag whose
  entitlement key is not licensed is always off. Changes are audited and propagate as in Q13. Release 1.0 has no
  requirement that needs a specific flag yet, so this slice ships the mechanism and tests with a test flag only; the
  flag list screen with owner and removal date is Later (ADM-SET-07).
- **Q15 Two 1.0 requirements that lean on 1.1 or Later items.** KRN-SET-04 (1.0) says settings are "exportable in
  configuration packages", but packages are Later (KRN-CFG-04) and settings import/export is 1.1 (ADM-SET-09).
  ADM-OPS-07 (1.0) includes "upload of a new license file", but licence files and upload are 1.1 (KRN-ENT-02, ENT-08).
  *Recommendation:* 1.0 builds versioned, audited and reversible settings and records the package export with ADM-SET-09
  (1.1); the 1.0 licence page shows everything else and says that a new entitlement is applied by the provider; upload
  comes with on-premises licence files in 1.1. Both recorded in CR-036.
- **Q16 Endpoints, permissions and roles.** *Recommendation:*
  - Settings: `GET /api/cfg/settings` (search, module, area, company: name, help, effective value, source, default, last
    change and who), `GET /api/cfg/settings/{key}` (layered view for a company, role or user), `PUT /api/cfg/settings/{key}`
    (layer, scope, value, reason; 202 when approval is needed), `POST /api/cfg/settings/{key}/reset`,
    `GET /api/cfg/settings/{key}/history`, `POST /api/cfg/settings/history/{id}/revert`, and self-service
    `GET`/`PUT /api/cfg/me/settings/{key}`.
  - Flags: `GET /api/cfg/feature-flags`, `PUT /api/cfg/feature-flags/{key}`, `POST /api/cfg/feature-flags/{key}/reset`.
  - Licence: `GET /api/kernel/capabilities` (any signed-in user), `GET /api/cfg/licence` (edition, modules, features,
    limits with use and percentage, dates, maintenance date, state and next state date),
    `GET /api/cfg/licence/usage?from=&to=` (monthly statements).
  - Permissions: existing generated codes `cfg.setting_values.read` and `cfg.setting_values.update` (settings),
    `cfg.feature_flag_overrides.read` and `cfg.feature_flag_overrides.update` (flags); new `cfg.licence.read`. Roles (spec 02 section 23): Tenant Admin all; Company Admin reads
    settings and changes the company layer of its own companies only (existing company scope); Auditor reads settings,
    flags and the licence page. The licence page and exports are "allowed when locked".
  - Operator commands (control plane): `entitlement draft --edition --tenant`, `entitlement apply`,
    `entitlement history`, `licence refresh`, `usage statement --tenant --month`.
