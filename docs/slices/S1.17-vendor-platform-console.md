## Goal
Vendor staff manage customers from a browser instead of the migrator's command line: sign in with a password and an
authenticator, see every customer with its state, licence and health, create a customer through a guided wizard, change
what a customer has bought with a second person's approval, and suspend or resume a customer. Each person may do only what
their platform role allows, and everything they do is in the platform audit. The console never shows a customer's
business data.

## What exists already (and stays)
- Control plane tables and services: `ControlPlaneAdmin`, `TenantProvisioner` with `IProvisioningProgress`,
  `TenantLifecycle` (suspend, resume, backup records, list), `TenantBackup`, entitlement draft, apply and history
  (`EntitlementApplier`), usage statements, `PlatformAudit` (every operator action), `ProvisioningLock`.
- `cp.platform_users` (email, name, role `platform_admin | provisioning | support | read_only`, `mfa_enrolled`, status);
  **no credential, MFA device or session tables**. Operator commands act as a named platform user but nothing proves who
  typed them (R-037).
- The customer sign-in engine (passwords, TOTP, lockout, sessions, refresh rotation) of S1.05, reviewed.

## Found while preparing (needs a ruling)
1. **Platform users cannot sign in.** The data design has no place for their password, second factor or sessions (Q2).
2. **No "licensing" role.** FR-ADM-PLT-10 separates provisioning, licensing and support; the role list has no licensing
   role (Q3).
3. **One API host.** The architecture reference names one API host; the console must not be reachable at customer
   addresses (Q1).
4. **The command line bypasses roles** (R-037) (Q5).

## Build
### Part S1.17a: platform sign-in and roles (Opus, fresh review)
1. **Data design (Q2, D-35).** New control-plane tables `cp.platform_credentials`, `cp.platform_mfa_devices`,
   `cp.platform_sessions` (same shape and rules as the `iam` ones); role value `licensing` added (Q3); new migration files
   only.
2. **Platform sign-in (Q1, Q4).** The API host answers platform endpoints only on the host names in `Platform:HostNames`
   (never on a customer address, and customer endpoints never on a platform host); tokens with their own audience and
   signing key id; password plus authenticator always (no e-mail code, no remember-device); lockout; idle 15 minutes and
   absolute 8 hours; activation by a one-time link created by an existing platform admin (the first one from the migrator).
3. **Roles and separation of duties (FR-ADM-PLT-10, Q3).** `platform_admin` (platform users, approvals), `provisioning`
   (create, suspend, resume), `licensing` (entitlements), `support` (read, backups), `read_only`; one role per person; a
   person cannot approve their own request; the last active platform admin cannot be disabled.
4. **Platform audit.** Every sign-in, failure and action in `cp.platform_audit` with the person, address and correlation id;
   an audit screen with filters (Build item 9 shares the list engine).
5. **Command line (R-037, Q5).** Operator commands that change customers or entitlements require `--as <email>` and a
   current authenticator code of that platform user with the needed role, checked against the same tables; the migration,
   cluster and signing-key commands stay host-only (they run before any platform user exists).

### Part S1.17b: console screens (Sonnet)
6. **Customer list (FR-ADM-PLT-01).** Name, code, status, region, cluster, edition, modules, users, storage, licence state,
   version, last activity, health; filters and saved views; export (S1.16 engine on the control plane, CSV).
7. **Provisioning wizard (FR-ADM-PLT-02, Q6).** Steps: details (code, name, country, currency, size profile), cluster,
   modules and entitlement template (edition), domain, first administrator; progress from `IProvisioningProgress`; smoke test
   (health and sign-in page reachable); on failure: what failed and "retry" (the provisioner is idempotent under its lock).
8. **Entitlements (FR-ADM-PLT-03, Q7).** Current entitlement and history; a change (modules, limits, term, maintenance date,
   add-ons) is drafted with an effective date, shown as a difference, and applied only after a second platform user with
   the licensing or admin role approves (platform maker-checker held in a new `cp.platform_requests`).
9. **Lifecycle (FR-ADM-PLT-11, Q8).** Suspend and resume with reason and approval; legal hold on and off (admin only); backup
   now and backup history; delete, offboard and move are not offered in 1.0.

## Acceptance
- A platform admin activates their account from the one-time link, enrols an authenticator and signs in on the platform
  host; the same address on a customer host name answers "not found", and a customer token is refused by every platform
  endpoint (and a platform token by every customer endpoint).
- Five wrong passwords lock the platform account; a session idle 15 minutes ends; a disabled platform user is signed out.
- A provisioning user creates a customer through the wizard, sees each step's progress and the smoke test pass; a forced
  failure in a step shows the step and a working "retry".
- A licensing user drafts adding a module from next month; the draft waits; the same user cannot approve it; a platform
  admin approves; the customer's capabilities show the module from the effective date; the history lists both people.
- A support user cannot suspend; a provisioning user suspends with reason after approval; the customer shows the suspended
  page; resume works the same way.
- `entitlement apply` on the command line without `--as` and a valid code is refused; with them it is in the platform audit.
- The platform pages: accessibility, keyboard, English (Urdu labels drafted, Q9), three widths, states, screenshots.
- A tenant-isolation style suite proves every platform endpoint is unreachable on customer hosts and with customer tokens.
- Fresh Opus review of part S1.17a in `docs/reviews/S1.17a-review.md` with high and medium findings fixed before merge.

## Out of scope
Everything under "Not built here". Any access to customer business data (support grants, 1.1).

## Questions for the product owner
- **Q0 Parts, model and review (changes the build plan).** *Recommendation:* S1.17a on Opus (high) with a fresh Opus review,
  because vendor sign-in controls every customer; S1.17b on Sonnet (medium). CR-073 records the change. Alternative: keep
  the whole slice on Sonnet with a fresh Opus review of S1.17a.
- **Q1 Where the console runs.** *Recommendation:* the same API host process (architecture reference section 3), answering
  platform endpoints and the platform web pages only on configured platform host names (for example
  `console.<vendor-domain>`), with its own token audience; a deployment may also run the host on a private network for these
  names only. Alternative: a separate console host project (changes the architecture; needs a decision).
- **Q2 Platform credentials (D-35).** *Recommendation:* three new control-plane tables mirroring `iam.user_credentials`,
  `iam.mfa_devices` and `iam.sessions`, reusing the S1.05 password hashing and TOTP code paths. Alternative: sign vendor staff
  in through an outside identity provider (SSO is Later).
- **Q3 Platform roles.** *Recommendation:* add `licensing`; one role per person; approvals by `platform_admin` (and by
  `licensing` for entitlement changes made by someone else). Alternative: several roles per person (weaker separation).
- **Q4 Platform sign-in policy.** *Recommendation:* authenticator always required (FR-ADM-PLT-10), no e-mail codes, no
  remember-device, idle 15 minutes, absolute 8 hours, lockout after 5 failures for 15 minutes, fixed (not settings).
  Alternative: the customer defaults (30 minutes idle).
- **Q5 Command line (R-037).** *Recommendation:* customer and entitlement commands need `--as <email>` plus a current
  authenticator code, checked against the platform tables and roles; host-only commands (migrate, cluster add, signing-key
  add) stay as they are. R-037 closes. Alternative: retire those commands once the console exists (no fallback if the web
  console is down).
- **Q6 Smoke test.** *Recommendation:* after provisioning, the wizard checks the customer's health endpoint and that its
  sign-in page answers on the new domain, and shows the invitation was queued. Alternative: health only.
- **Q7 Entitlement approval.** *Recommendation:* every entitlement change needs a second platform user (licensing or admin);
  requests expire after 7 days; held in `cp.platform_requests` (new table). Alternative: approval only for downgrades and
  limit reductions.
- **Q8 Lifecycle actions in 1.0.** *Recommendation:* suspend, resume, legal hold and backup now; offboard, delete and move are
  not offered (offboarding rules and retention windows are not specified; moves are FR-KRN-TEN-06, 1.1). CR-073 records
  that FR-ADM-PLT-11 is partly 1.0. Alternative: add delete after a retention window (needs rules from you).
- **Q9 Console language.** *Recommendation:* English first; Urdu catalogue kept complete for consistency (the check of
  S1.12c applies) and marked for review. Alternative: English only (would need an exception to the localization rule).
- **Q10 Export of the customer list.** *Recommendation:* CSV of the shown columns, recorded in the platform audit.
- **Q11 Urdu texts.** *Recommendation:* drafted and marked for a native speaker's review (R-062).
- **Q12 Change request CR-073.** *Recommendation:* approve: model and review change for S1.17a (Q0); platform tables
  `cp.platform_credentials`, `cp.platform_mfa_devices`, `cp.platform_sessions`, `cp.platform_requests` and role `licensing`
  (Q2, Q3, Q7); platform host names (Q1); command-line rule and closing R-037 (Q5); FR-ADM-PLT-11 partly in 1.0 (Q8).
