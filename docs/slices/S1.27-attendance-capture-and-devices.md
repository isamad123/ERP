## Goal
Punches arrive from the web, a shared kiosk screen, a QR code posted at a gate, and biometric clock machines, all as one append-only list of events with
the time the person punched and the time the server heard of it. A device that sends the same punch twice, or arrives hours late after being offline,
causes no duplicate and no loss. HR sees which devices are online and which failed, and no fingerprint or face template ever lives in the system.

## Build
### Part S1.27a
1. **Event store (DAT-01, DAT-02).** `POST /api/hrm/attendance/events` (internal contract) appends; never updates; corrections are new events with `supersedes_event_id`;
   idempotency key unique per source; `event_at` (when punched) and `received_at` (server clock, injected) kept apart; future-dated beyond a tolerance setting refused.
2. **Duplicates (ATT-03).** Same employment, direction and a window of N seconds (setting) marks the later one `is_duplicate` (kept, never counted).
3. **Web check-in and out (ATT-01).** Signed-in employee punches from the portal; resolved from the token; allowed network ranges optional (setting); recorded with IP.
4. **Kiosk and QR (ATT-01, Q5).** Kiosk mode: a station login (device user) shows a PIN or badge entry screen and punches for the employee; QR: a rotating code per location (changes every N minutes)
   scanned by the employee's signed-in session. Both write events with their source.
5. **Partitions and purge (DAT-04).** Monthly partitions three months ahead (existing job pattern); retention setting; purge job removes only whole expired partitions.
### Part S1.27b
6. **Device registry (ATT-02).** Register by location with model, serial, connection (host, port, protocol), credentials reference to the secret store; status online or offline from last seen.
7. **Driver interface and reference connector (ATT-03, Q4).** `IAttendanceDeviceDriver` (pull logs, accept push, health check); one reference driver (a generic push endpoint with signed requests, plus a
   pull driver for one popular device family chosen in Q4); offline buffer is the device's, replayed with original times; failures recorded on the device row.
8. **Device-user mapping and consent (ATT-03, ATT-20).** Map device user number to employment effective-dated; consent date required before mapping when the entity switch `hrm.att.biometric_enabled` is on;
   deletion on leaving: leaving an employment raises a task to remove the user from the device and ends the mapping; no template is read, stored or logged.
9. **Console screens.** Device list with status, last sync, last error and sync now; mapping screen; event search (punch log) with filters; English and Urdu.
### Part S1.27c (CR-095; fresh Opus review)
10. **API clients (SEC-02).** `POST /api/iam/api-clients` {name, scopes, ipAllow, rateLimitPerMinute, expiresAt} returns the client id and the secret **once** (random,
    stored only as a salted hash with the S1.05 hasher); list and read never return the secret; `rotate` (new secret; the old one stays valid for the setting
    `iam.api_client.rotation_grace_minutes`, default 60), `revoke` (immediate); a daily job marks expired clients; maker-checker on create and rotate when the S1.06
    privileged-change setting is on; every action audited. Screen "API clients" in Administration (secret shown once with a copy button).
11. **Key authentication.** Scheme `Authorization: ApiKey <client_id>.<secret>` beside the session scheme; the customer comes from the host name (D-02) and the key is
    looked up in that customer's database only; checks: active, not expired, caller IP in the allow list (an empty list refuses every call), constant-time compare;
    the principal is a client with only its scopes, limited to permission codes flagged `api_client` in the permission manifests (the S1.27b push permission is the
    first); a key never opens a web session and never reaches `/api/iam/*` writes; failures are security events (S1.07); `last_used_at` written at most once a minute.
12. **Rate limits (INT-07).** Fixed window per client per minute from `rate_limit_per_minute` and a per-customer ceiling `itg.api.tenant_rate_per_minute` (default 600);
    over the limit gives 429 with `Retry-After`; counters per host reconciled through the database every minute (R-181).
13. **Usage and alerts (SEC-02, INT-07).** Per client and day: calls, 4xx and 5xx errors, p95 latency, last use (`GET /api/iam/api-clients/{id}/usage`); notification
    events `iam.api_client.limit_reached` and `iam.api_client.expiring` for holders of `iam.api_clients.manage`.

## Acceptance
- DAT-01/02: the database refuses update and delete of events; the same idempotency key twice gives one event; a late batch keeps the original times.
- ATT-03: pull and push each ingest a batch with duplicates removed; an unmapped device user lands in an "unmapped punches" list, not lost.
- ATT-20: mapping without consent is refused while biometric is on; leaving ends the mapping and creates the removal task; no credential or template in any response, log or audit entry.
- ATT-01: web, kiosk and QR punches appear as events with their source; a replayed QR code beyond its window is refused.
- DAT-04: partitions exist three months ahead; purge drops an expired partition only.
- SEC-02 (S1.27c): the secret is shown once and never again; a rotated key works and the old one stops after the grace period; revoked or expired keys get 401; an IP
  outside the allow list gets 403; usage shows calls, errors and p95; every action is audited; a key from one customer is refused on another customer's host; a key
  cannot use a permission outside its scopes, any `/api/iam` write or a web session.
- INT-07 (S1.27c): 61 calls in a minute against a limit of 60 give one 429 with `Retry-After`; the per-customer ceiling applies across two clients; one limit notification.
- Tenant-isolation test for every endpoint; permission tests; FR ids in test names.

## Questions (recommendations are rulings under CR-083, except Q2)
- **Q0 Parts.** *Recommendation:* two parts.
- **Q1 Time source.** *Recommendation:* server time is the authority for `received_at`; the device's time is `event_at` with the drift stored.
- **Q2 Selfie and geo-fence in ATT-01 (needs the product owner).** *Recommendation:* release 1.0 delivers web, kiosk, QR and biometric devices; selfie capture and geo-fence validation arrive with
  geo-attendance in 1.1 (KRN-GEO and the mobile app are 1.1). This narrows a 1.0 requirement, so it waits for your ruling; building proceeds on the rest.
- **Q3 Partitioning.** *Recommendation:* monthly range partitions on `event_at`, retention default 7 years (setting).
- **Q4 Reference device.** *Recommendation:* a generic signed-push endpoint plus one pull driver for the ZKTeco-family protocol; others later through the interface. (Licence of any package checked first, D-09.)
- **Q5 QR.** *Recommendation:* rotating signed code per location, default 60 seconds, requires a signed-in session so a photo of the code is useless.
- **Q6 Change request CR-088.** *Recommendation:* approve: settings `hrm.att.biometric_enabled`, `hrm.att.duplicate_window_seconds`, `hrm.att.future_tolerance_minutes`, `hrm.att.event_retention_years`,

- **Q7 API clients (CR-095, approved by the product owner).** *Recommendation:* part S1.27c as items 10 to 13, Sonnet with a fresh Opus review, built before S1.27b; adds the `ApiKey`
