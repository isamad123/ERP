## Goal
A tenant administrator can run people's access without help: find a user, invite one, see everything about an account
(roles, scopes, sessions, second factors, sign-ins, recent changes), unlock or disable it safely, build roles from the
permission catalogue, decide which records and which fields each role sees, and check afterwards who changed what. Every
screen uses the list and form engine of S1.12c, works in English and Urdu, and shows only what the administrator may do.

## What exists already (and stays)
- User administration endpoints under `/api/iam/users`: status (`/{id}/status`, answers `{openWorkflowTasks}`), invitation,
  password reset link, force password change, unlock, revoke sessions, reset MFA, sessions, guarded e-mail change
  (`/{id}/email`, `iam.users.change_email`, maker-checker for privileged users). `email` is create-only on the generated
  update (CR-062).
- Access endpoints of S1.06: permission catalogue, roles (create or copy, permissions, data scopes, field policies, summary,
  compare, field preview, archive), user roles (`/api/iam/user-roles`, `/{id}/end`), groups and group roles, data scopes
  (`POST` only; scopes are never edited), data scope preview. A change that needs a second person answers 202
  `{outcome: "pending", requestId}`; the Tenant Admin role is protected; the last tenant admin cannot be removed.
- Open tasks of a user (`/api/wf/users/{id}/open-tasks`, `/reassign-open-tasks`), delegations (`/api/iam/delegations`).
- Audit search, security events, access log and export (`/api/aud/*`, S1.07); record history panel (S1.12c).
- Licence usage (`GET /api/cfg/licence/usage`) for seat consumption.
- The browser tests run with an allow-all permission double (R-072, R-082).

## Found while preparing (needs a ruling)
1. **API clients have no engine.** FR-ADM-SEC-02 (screen) is 1.0, but FR-KRN-IAM-05 (issuing API keys) is 1.1 and no key
   authentication exists. `iam.api_clients` is in the data design. Building it is new sign-in code (Q2).
2. **Username and e-mail clash** was deferred to this slice by S1.05: a new user's username may equal another user's e-mail
   (Q6).
3. **Approvers cannot look people up** (`iam.users.read` is an admin permission), so the inbox cannot offer "reassign"
   (S1.12d). A minimal people lookup is needed by this slice's pickers too (Q7).
4. **The browser host uses allow-all permissions** (R-072, R-082). With this console an administrator can be created
   through the real screens, so the browser tests can move to the real engine (Q10).

## Build
### Part S1.13a: users
1. **User list (FR-ADM-USR-01, -08).** Columns name, username, e-mail, status, roles, companies, last sign-in, MFA state;
   filters on each; saved views; seat bar "N of M named users" with the 90 percent warning from licence usage (shown only
   to licence readers).
2. **Create and invite (FR-ADM-USR-02, FR-KRN-IAM-18).** Form with name, username, e-mail, language, time zone, default
   company, optional access end date, first role assignment; "send invitation" (and resend); the limit refusal shown in
   plain words with a link to the licence page.
3. **User record (FR-ADM-USR-04).** Tabs: profile; roles (with company, dates, reason, ended ones greyed); groups; data scopes
   (effective, from roles and groups); delegations; sessions and remembered devices (revoke one or all); second factors
   (method and date only, never secrets); sign-ins (security events of the user); recent activity (audit search for the
   user); history panel.
4. **Account actions (FR-ADM-USR-03, -05).** Activate, lock, unlock, disable, archive (only the allowed transitions are
   offered, each with a reason); disabling a user with open approval tasks shows the count and offers "reassign to" (Q7)
   before or after the change; reset link, force password change, reset MFA, revoke sessions, change e-mail (guarded,
   pending answer shown as "waiting for a second administrator"). Every action asks for confirmation stating its effect.
5. **Bulk actions (FR-ADM-USR-09).** Assign role, end role, change default company, disable, extend access end date, over a
   selection: preview of the count, one result per user, failures listed. Export is added by S1.16.

### Part S1.13b: access
6. **Permission catalogue (FR-ADM-ROL-01).** Browse by module and resource, search, sensitivity marks, "held by" roles.
7. **Roles (FR-ADM-ROL-02, -03, NAV-03).** List with user counts and status; create, copy (from baseline or any role),
   rename, archive; permission picker grouped by module with search and "select all in resource"; compare two roles side by
   side; baseline roles marked "shipped" and editable (Tenant Admin protected, shown as such).
8. **Data scopes (FR-ADM-ROL-06).** Create a scope (company, branch, department list, own, team, subtree, as the engine
   allows), attach to roles; "test": pick a user and a table, see the count and first rows the preview returns.
9. **Field security (FR-ADM-ROL-07).** Matrix of fields (by table, with field class) against roles: hidden, masked,
   read-only, editable; "preview the form as this role" from the field preview endpoint. Custom fields appear once S1.15
   defines them.
10. **Assignments, groups, delegations (FR-ADM-ROL-04, -09, FR-ADM-USR-06).** Assign a role to users or a group with company,
    start and end dates and reason; group members and group roles; admin-made delegations with dates and audit.
11. **Reports and audit search (FR-ADM-ROL-11, FR-KRN-AUD-04, Q8, Q9).** Permission change report (who changed which role or
    assignment when, from the audit log); role usage report (permissions held by no active user, users with no sign-in for
    N days); audit search screen (user, table, record, date, action) with export through the existing audit export.

## Acceptance
- An administrator invites a user from the console; the e-mail arrives (`TestMailServer`); the user activates and signs in;
  the list shows status active, the role and last sign-in; seat consumption rises by one.
- At the user limit the create form shows the plain-language refusal; nothing is created.
- Disabling a user with two open approval tasks shows "2 approvals are waiting for this person" and reassigns them to the
  chosen person; the person's sessions end (sign-in in another browser is refused).
- Unlock, reset link, force password change, reset MFA and revoke sessions each produce the server's effect and an audit
  entry visible in the user's recent activity.
- A copied role with two permissions removed compares correctly against its source; giving a sensitive permission while
  maker-checker is on shows "waiting for a second administrator" and appears in the approvals of changes; the other
  administrator approves and the role changes.
- A data scope "own branch" tested for a sample user lists only that branch's records; the field matrix set to "masked"
  for a salary-class field shows the masked value in the role's form preview.
- The permission change report lists the role change with who and when; the role usage report lists an unused permission.
- Every screen: no serious or critical accessibility finding, keyboard only, English and Urdu (right to left), 360, 768
  and 1280 pixels, loading, empty, error and permission-denied states, screenshots in both languages, light and dark.
- Any new server endpoint passes the tenant-isolation suite and has permission tests; tests cite the FR ids.

## Questions as put to the product owner
Each question has a recommendation; answering "accept all" takes every recommendation.

- **Q0 Parts.** *Recommendation:* two parts in two fresh sessions (S1.13a users, S1.13b access), each ending with
  screenshots. Alternative: one session (breaks the CR-047 size rule).
- **Q1 Where the console lives.** *Recommendation:* menu group "Administration" with "Users", "Roles", "Groups", "Data
  scopes", "Field security", "Delegations", "Access reports" and "Audit search", each shown only with its permission.
  Alternative: one "Users and access" page with tabs.
- **Q2 API clients (FR-ADM-SEC-02).** Issuing and checking API keys is new sign-in code, and its engine requirement
  (FR-KRN-IAM-05) is 1.1. *Recommendation:* build API clients with the first slice that needs a machine client: the
  biometric device connector **S1.27** (Opus, with a fresh review). CR-069 moves FR-ADM-SEC-02 there; nothing is built
  here. Alternative: an extra part S1.13c on Opus with a fresh review.
- **Q3 Bulk user import (FR-ADM-USR-02).** *Recommendation:* built as the first import type of the import centre (S1.16);
  imports create invitations, never passwords. Alternative: a one-off user import here (would be rebuilt in S1.16).
- **Q4 Password, MFA and session policy (FR-ADM-USR-20, -21, -24).** They are registered settings (`iam.*`). *Recommendation:*
  the settings centre (S1.15) edits them through the existing `PUT /api/iam/settings/{key}`; this console links to that
  group as "Sign-in and security". Alternative: special policy pages here.
- **Q5 Link to an employee (FR-ADM-USR-07).** *Recommendation:* built with the employee screens (S1.21), from both sides,
  when employee records exist; the user record here shows the link read-only once it exists. Alternative: none (no employees
  exist before S1.20).
- **Q6 Username and e-mail clash (S1.05 deferral).** *Recommendation:* refuse a username that equals another user's e-mail
  and an e-mail that equals another user's username, case-insensitive, with the message "already used to sign in"; a small
  server check in the user create and update paths (and in the e-mail change), with tests. Alternative: allow it (sign-in
  could match the wrong person; not recommended).
- **Q7 People lookup.** *Recommendation:* new `GET /api/iam/people-lookup?search=` for any signed-in person who holds a
  permission that needs a person picker (admin and approver baselines): name, username and id only, active users of the
  caller's companies, 20 at a time; used by the reassign prompt here and by the inbox's reassign (S1.12d gap). Alternative:
  keep pickers admin-only and leave "reassign" out of the inbox.
- **Q8 Role usage report (FR-ADM-ROL-11).** *Recommendation:* "inactive users" means no sign-in for 90 days (setting
  `iam.report.inactive_days`, default 90); "unused permission" means held by no role that an active user holds. Both are
  read-only lists with export (S1.16). Alternative: fixed 90 days without a setting.
- **Q9 Audit search screen.** The full audit viewer (FR-ADM-OPS-02) is Later, but FR-KRN-AUD-04 (searchable, exportable) is
  1.0 and S1.07 left its screen to S1.13. *Recommendation:* one plain search screen over `/api/aud/changes` and
  `/security-events` with the existing export; no chain verification button (operator command stays). Alternative:
  leave it to Later (FR-KRN-AUD-04 would have no screen).
- **Q10 Browser tests on the real access engine (R-072, R-082).** *Recommendation:* from S1.13b the browser test host uses
  the real access engine, with the test administrator made through this console's screens; the allow-all double stays only
  in the tenant-isolation suite. Alternative: keep allow-all (the web keeps being tested against assumed rules).
- **Q11 Urdu texts.** *Recommendation:* drafted in the same session and marked for a native speaker's review (R-062).
- **Q12 Change request CR-069.** *Recommendation:* approve: FR-ADM-SEC-02 moves to S1.27 (Q2); people lookup endpoint (Q7);
  username and e-mail clash rule (Q6); setting `iam.report.inactive_days` (Q8); contracts register rows added at build.
