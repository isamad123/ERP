## Goal
A calculated payroll is checked before anyone approves it: every employee with negative pay, missing bank or tax data, a big change from last month, a possible
duplicate payment or no attendance is flagged, and each flag is fixed, excluded, held or accepted with a reason. Payroll staff compare this run with the last one,
employee by employee and component by component, and open the calculation behind any difference. Approval goes to the right people, two of them above the
company's threshold, never to the person who prepared it. Once approved the payroll is locked and finalized: nothing in it can change, the bank file, payslips and
journal can be produced, and if something is wrong before any money leaves, a person with special permission can reopen it with a recorded reason.

## What exists already (and stays)
Run statuses `created` to `closed` and `cancelled` with a stage log; flags column; reopen reason column; approval threshold per pay group; calculation, recalculation
of a subset, trace and the result guard on locked runs (S1.35a item 7); attendance lock (S1.31); go-live milestone (S1.18a); workflow routes, escalation and the
approvals screen (S1.10, S1.12d); remaining lock functions are todo stubs owned by this slice.

## Found while preparing (needs a ruling)
1. **PAY-14 reopening against PAY-33 and the data design:** results of a locked run are immutable and the lock trigger lets the status only "advance", yet a locked run
   may be reopened and `reopened_reason` exists (Q3).
2. **Thresholds** for "change above a threshold" and dual approval by variance have no values (Q2).
3. **"Duplicate payments"** is not defined (Q4).
4. **Who sets "paid" and "posted"** (S1.40, S1.45) and when a run may close (Q5).
5. **S1.35a already guards locked results;** the other lock stubs remain (Q7).

## Build
### Part S1.38a: validation, variance, review, approval (Opus, fresh review)
1. **Validate (PAY-11).** `POST /api/hrm/pay/runs/{id}/validate` (status `calculated` → `validated`): flags per employee: `negative_net` (blocking), `missing_bank`
   (no active payout account for the payment mode, S1.20d; blocking), `missing_tax_id` (no tax identifier on the person; warning), `missing_statutory_id` (S1.37;
   warning), `variance_above_threshold` (net or any component differs from the previous regular run of the pay group by more than the setting; warning),
   `duplicate` (Q4; blocking), `no_attendance` (the attendance totals in the employee's snapshot, S1.35 item 3, show no processed day; warning), `incomplete` (S1.35/S1.36/S1.37 missing rule; blocking);
   recalculation clears and re-runs validation.
2. **Resolving flags.** Per employee: fix the data and recalculate (S1.35 subset), exclude with reason, hold (S1.39), or accept a warning with a reason; blocking flags
   cannot be accepted; accepting needs `hrm.pay.flags.accept` and is a security event of kind `override` on the FR-XM-32 exception report; validation passes when no
   blocking flag is left (BR-10: no approved run with a negative net).
3. **Variance report (PAY-12).** `GET /api/hrm/pay/runs/{id}/variance?compareTo=` by employee and component (current, previous, difference, percent), with the cause
   when known (new joiner, leaver, revision, inputs, attendance, tax) taken from the snapshots of both runs, and a link to each result's trace; scoped and salary class.
4. **Review.** `validated` → `in_review`: the run summary (totals, counts, flags resolved, variance top list) is fixed as a review document; returning to `calculated`
   for changes clears approval.
5. **Approval (PAY-13, FR-XM-32, Q2).** Document type `hrm.pay_run` (default route: payroll approver role); a second approval step is required when total net exceeds
   the pay group's `approval_threshold` or the run's total variance exceeds the setting `hrm.pay.dual_approval_variance_percent` (route conditions on context fields
   `total_net` and `variance_percent`); the users who calculated or validated the run are never approvers; escalation per route, never auto-approve; `in_review` →
   `approved` on the last approval; rejection returns to `calculated`.
### Part S1.38b: lock, finalize, reopen, close (Opus, fresh review)
6. **Lock and finalize (PAY-10, PAY-30, PAY-33).** `POST .../lock` (status `approved` → `locked`) refuses when the company's payroll go-live milestone is missing
   (S1.18 Q4) or when any result changed after approval (row versions in the approval context); publishes `hrm.pay_run.finalized` {run, company, pay group, period,
   totals by component, cost centre, department, project and company; no employee amounts} consumed by S1.40, S1.44b and S1.45; consumed inputs and adjustments stay
   marked.
7. **Reopen (PAY-14, Q3).** `POST .../reopen` {reason} with permission `hrm.pay.run.reopen` and maker-checker (S1.06), allowed only while the run is `locked` and no
   payment line of the run exists in a batch that is not cancelled (S1.40), and nothing is posted; `locked` → `calculated`, `reopened_reason` and the stage log
   record it, approval is cleared, event `hrm.pay_run.reopened` (S1.40 and S1.45 discard drafts); a security event of kind `override`; the attendance period stays
   locked (FR-XM-26). After a payment line exists, a correction is an adjustment or an off-cycle run (S1.39, FR-XM-27).
8. **Paid, posted, close (Q5).** Contract `IPayRunStages`: `MarkPaidAsync(run)` called by S1.40 when every payment line is paid or written off; `MarkPostedAsync(run,
   exportId)` called by S1.45 after the journal export; `POST .../close` by a payroll officer when paid and (if the company setting `hrm.pay.journal_required`, default
   on, says so) posted; closing the run closes its pay period when it is the regular run (status `closed`), and opens the next period.
9. **Database guards (Q7).** Implement the remaining todo stubs as rules.yaml `functions` (new migration file): `hrm.todo_pay_runs_lock()` (no update or delete once
   locked, except the status moves of items 7 and 8 made through the run service's function with the reason set), `hrm.todo_pay_run_employees_lock()`,
   `hrm.todo_pay_traces_lock()`, `hrm.todo_pay_result_lines_lock()` and `hrm.todo_pay_results_lock()` unless S1.35a implemented them (then nothing to do), and
   `hrm.todo_pay_periods_closed_period_guard()` (no new pay inputs, retro adjustments or loan installments targeting a closed period).
10. **Stage log (PAY-10).** Every stage move appends {stage, user, time, reason} to `stage_log` through one function; the log is part of the run's audit trail.
### Part S1.38c: screens (Sonnet)
11. **Run screens.** Payroll runs list per pay group and period with status; run page with a stage bar, totals, counts, stage log, inputs summary, flags table with
    resolve actions, variance report with drill-down to the trace (S1.35 trace view), lock, reopen dialog (reason, shows why it is refused when it is), close;
    approval from the approvals screen through `workflow.json` fields (period, count, total net, variance, flags accepted).
12. **Checks.** English and Urdu, right-to-left, three widths, loading, empty, error and permission-denied states, axe checks, budgets; no amount shown without the
    salary permission (GHR-06).

## Acceptance
- PAY-11: a seeded run with one employee per flag shows each flag; blocking flags stop validation until fixed, excluded or held; an accepted warning appears on the
  exception report with its reason.
- PAY-12: the variance report explains a joiner, a leaver, a revision and an input change by cause and links to the trace.
- PAY-13/FR-XM-32: a run under the threshold needs one approval, above it two; the preparer cannot approve; nothing is approved by timeout (escalation only).
- PAY-10/PAY-30: locking without go-live is refused; locking publishes one finalized event whose totals equal the results; every stage move is in the log.
- PAY-14: reopen before any payment line returns the run to `calculated` with the reason, keeps the attendance period locked and is on the exception report; after a
  payment line exists it is refused with "use an adjustment or an off-cycle run".
- PAY-33/FR-XM-05: once locked, update and delete of runs, members, results, lines and traces are refused for every login; a closed period refuses new inputs.
- Close: refused until paid and (with the setting) posted; closing the regular run closes the period.
- Tenant-isolation test for every endpoint; browser tests (`Suite=WebE2E`) for validate, approve and lock with English and Urdu screenshots; FR ids in test names.

## Questions (each recommendation is the ruling, CR-083)
- **Q0 Parts.** *Recommendation:* three parts: a and b on Opus with fresh reviews, c (screens) on Sonnet. Alternative: two Opus parts including screens (more Opus use).
- **Q1 Stage order.** *Recommendation:* the data design's statuses in order; "bank files and payslips" are S1.40 actions on a locked run, not a status. Alternative: a
  status per document (more states, same control).
- **Q2 Thresholds.** *Recommendation:* settings `hrm.pay.variance_threshold_percent` (flag) and `hrm.pay.dual_approval_variance_percent` (second approver) per pay
  group with no default (empty means the check is off and the readiness checklist says so); the total-net threshold is the pay group's `approval_threshold`.
  Alternative: product defaults (invented business rules).
- **Q3 Reopening a locked run.** *Recommendation:* allowed only before any payment line exists and before posting, with elevated permission, maker-checker and a reason,
  as one recorded backward move `locked` → `calculated`; results become editable only by recalculation; this reads PAY-14 together with PAY-33, FR-XM-27 (reversal only
  before payment) and the design's `reopened_reason`. Alternative: never reopen (PAY-14 unmet; corrections only by off-cycle runs).
- **Q4 Duplicate payment.** *Recommendation:* the same bank account (blind index) on two employees in one run, or the same employee and component paid by another run of
  the same period that is not cancelled (one-time components only). Alternative: same account only.
- **Q5 Paid and posted.** *Recommendation:* the `IPayRunStages` contract called by S1.40 and S1.45; close needs paid, and posted when `hrm.pay.journal_required` is on.
  Alternative: payroll officers set paid and posted by hand.
- **Q6 Go-live.** *Recommendation:* lock (finalize) checks the payroll go-live milestone of the company (S1.18 ruling Q4); calculation and validation do not, so parallel
  test runs work before go-live. Alternative: check at calculation (blocks rehearsals).
- **Q7 Guards.** *Recommendation:* implement every S1.38 todo stub not already implemented by S1.35a; the build session checks `rules.yaml` first. Alternative: none.
- **Q8 Variance baseline.** *Recommendation:* the previous regular run of the same pay group that is locked or later; the user may choose another locked run.
  Alternative: always the previous period.
- **Q9 Notifications.** *Recommendation:* catalogue entries `hrm.pay_run.validated`, `hrm.pay_run.approved`, `hrm.pay_run.finalized`, `hrm.pay_run.reopened` for payroll
  officers and approvers. Alternative: workflow notifications only.
- **Q10 Change request CR-111.** *Recommendation:* approve: endpoints validate, variance, review, lock, reopen, close; document type `hrm.pay_run` with route conditions on
  `total_net` and `variance_percent`; contract `IPayRunStages`; events above; permissions `hrm.pay.flags.accept`, `hrm.pay.run.reopen`, `hrm.pay.run.close`; settings
  `hrm.pay.variance_threshold_percent`, `hrm.pay.dual_approval_variance_percent`, `hrm.pay.journal_required`; the lock functions (implemented entries replacing todo
  stubs, new migration file); parts a and b Opus with reviews, c Sonnet; expand-only.
