## Goal
Every document that needs a number (employee number, letter, leave request, payroll run, loan, expense claim) gets it
from one kernel service, following a pattern the customer sets per company (and optionally per branch), for example
`EMP-00042` or `LTR-2026-00017`. Two kinds of number series exist. A **gap-allowed** series is fast and never makes
users wait; if a save fails, the number it took is simply skipped and never reused. A **gap-free** series, for
documents where the law or the customer's auditors require an unbroken run, hands out numbers only at the moment the
document is posted, in the same database transaction, so a failed post gives the number back and the series never
skips; users posting at the same time take turns for a fraction of a second. Two people can never get the same
number, even under heavy load. Once given, a number can never be edited. A document cancelled after it was numbered
keeps its number, and the number is listed in a void report with the reason, so an auditor can account for every
number in a gap-free series.

## Build
1. **Document-type registry (Q1).** Each numbered column is declared once in the data design (new key `numbering:`,
   change request CR-033): the document type code, when the number is given (on create or on post), whether gap-free
   is allowed, whether a manual override is allowed, and the default pattern. The generator emits a registry per
   module, makes the column read-only in the generated API (FR-KRN-NUM-03) and fills it on create for "on create"
   types. Types numbered "on post" call the allocator from the module's own post service (later HR slices).
2. **Allocator (KRN-NUM-02, KRN-NUM-06).** One kernel interface in `Erp.Kernel.Contracts` (`INumberAllocator`):
   given document type, company, optional branch and the document's business date, it finds the scheme (Q6), works
   out the period (Q5), takes the next value and renders the number (Q4). Gap-allowed: a PostgreSQL sequence per
   scheme and period (Q2). Gap-free: the counter row is locked and advanced inside the caller's transaction, as late
   as possible before commit (Q3).
3. **Schemes (KRN-NUM-01).** Purpose-built create, edit (only before first use) and retire services with pattern
   validation, replacing the generated create and update endpoints (Q8, Q11). Default schemes are seeded (Q7).
4. **Manual override (HRM-EMP-04, Q9).** A kernel check that a typed-in number is safe to use (not a number the
   scheme could still produce). The HR permission and screen come with S1.20/S1.21.
5. **Voids and void report (KRN-NUM-05, FR-XM-06, Q10).** Kernel operation to record a void (number, reason,
   document), called by modules when a numbered document is cancelled; void report per scheme and date range.
6. **Endpoints and permissions (Q11).** All texts as localisation keys (English and Urdu).

## Acceptance
- Spec 02 AC: 100 concurrent transactions posting into one gap-free series produce exactly 1 to 100 with no
  duplicates; when some of them roll back on purpose, the committed numbers are still continuous (tagged as
  integrity invariant 6).
- 100 concurrent transactions on a gap-allowed series produce no duplicates and never wait on each other; a rolled-back
  transaction leaves a gap that is never filled later.
- Every pattern token renders correctly; a yearly or monthly series starts again at the start value in a new period
  and never repeats a number from an earlier period; invalid patterns are refused with a clear message (Q4).
- A branch scheme wins over the company scheme; a document type with no scheme gets its default scheme (Q6, Q7).
- A number cannot be changed through any update endpoint once given (FR-KRN-NUM-03).
- A scheme's pattern, reset rule, gap-free flag and start value cannot be edited after first use; retiring it and
  creating one with the same pattern continues the series without repeating numbers (Q8).
- A manual employee number that the scheme could still produce is refused; one outside the series is accepted (Q9).
- Cancelling a numbered document records a void; voiding the same number twice is refused; void rows cannot be
  changed or deleted; the void report lists voids and the issued range for a gap-free series (Q10).
- Creating an employment through the generated API gives it the next employee number for its company.
- Each new endpoint passes the tenant-isolation suite and has permission tests; scheme changes appear in the audit
  log; tests cite the FR ids; measured time per allocation (both kinds) is reported.

## Product-owner rulings (2026-11-17)
All eleven questions were answered "accept all": each *Recommendation* below is the ruling; the alternatives are

## Questions as put to the product owner

- **Q1 Where document types are declared.** Today the approved design only says "assigned by numbering" in a column
  note, and the generated API lets a caller type any employee number. *Recommendation:* new data-design key on the
  table (CR-033), for example
  `numbering: {column: employee_no, type: hrm.employee_no, assign: create, gap_free: no, override: yes, default: "EMP-{seq:5}"}`.
  The generator makes the column read-only in the generated API, fills it on create, and lists all document types in
  a registry the kernel reads. All nine numbered HR columns listed above get the key now (it changes no table);
  "on post" types (leave requests, payroll runs, loans, expense claims, letters) are wired by their own slices. Keys
  only, no new column.
- **Q2 How gap-allowed numbers are taken.** The approved design says "a PostgreSQL sequence per scheme". The
  application login cannot create sequences. *Recommendation:* follow the design: a database function (owner login,
  `security definer`, same pattern as S1.07 ruling P1) creates the sequence on first use for a scheme and period and
  returns the next value; the application can only call it. Sequences are not rolled back, so users never wait on each
  other. No number caching across connections, so numbers come out in time order. New migration only. Alternative: a
  counter row advanced in a separate short transaction (no sequences, but one extra database round trip per number).
- **Q3 How gap-free numbers are taken, and how long a user may wait.** *Recommendation:* the counter row is locked and
  advanced in the same transaction as the document, as the last step before commit, so the lock is held for
  milliseconds; if another user holds it for more than 5 seconds, the post fails with "numbering is busy, please try
  again" and nothing is saved. A gap-free number is only ever given at posting or finalizing, never when a draft is
  saved, so a deleted draft cannot leave a gap. Gap-free is allowed only for document types declared to allow it
  (Q1); in Release 1.0 none of the HR types needs it by law, so all are gap-allowed by default and the customer may
  switch on gap-free where allowed.
- **Q4 Pattern rules.** *Recommendation:* tokens `{seq:N}` (the running number padded to N digits, 1 to 12; exactly
  once), `{yyyy}`, `{yy}`, `{mm}`, `{fy}` (fiscal year, for example `2026-27`, see Q5), `{company}` (company code),
  `{branch}` (branch code); all other characters are literal text, so prefix and suffix need no separate fields.
  Refused: a yearly series without a year token, a monthly series without both year and month tokens (otherwise the
  same number would be issued again next period), `{branch}` for a document type that has no branch, and numbers longer than 40
  characters. Numbers always use Latin digits, also in the Urdu interface, because they are identifiers that must
  match printed documents and other systems.
- **Q5 Reset periods, fiscal year, and which date counts.** The spec says schemes are per fiscal year, but Release 1.0
  has no fiscal calendar (Finance is Phase 3). *Recommendation:* `yearly` means the calendar year; add reset rule
  `fiscal_yearly` using a company setting "fiscal year starts in month" (default from the country pack: July for
  Pakistan), registered by this slice and edited in the settings centre (S1.09/S1.15). The period is decided by the
  document's business date passed by the module (for example the letter date or leave start), never by the server
  clock; if a document has no date, today in the company's time zone from the injected clock. Needs CR-033 (new
  enum value). Alternative: calendar year only in 1.0 and fiscal year with Finance.
- **Q6 Which scheme applies, and tenant-wide numbers.** *Recommendation:* the active scheme for the document's branch
  wins; otherwise the company-wide scheme (no branch). Person numbers are a problem: a person belongs to the whole
  customer, not one company (FR-XM-28), but every scheme must have a company. Proposal (CR-033): allow a scheme
  with no company only for document types declared tenant-wide (person number only in 1.0); expand change, new
  migration only. Alternative: person numbers use the scheme of the first company the person joins (risk of
  collisions between companies with the same pattern).
- **Q7 Default schemes.** *Recommendation:* provisioning and `migrate` create, for every company and every registered
  document type, the default scheme if none exists (idempotent, keyed by company and document type), so new document
  types from later releases appear automatically. If a company was added after the last `migrate`, the allocator
  creates the default on first use (audited, actor "system"). Proposed defaults, all gap-allowed, company-wide:

  | Document type | Default pattern | Reset |
  | --- | --- | --- |
  | Person number (tenant-wide) | `P-{seq:6}` | never |
  | Employee number | `EMP-{seq:5}` | never |
  | Employment contract | `CON-{yyyy}-{seq:5}` | yearly |
  | Service request | `SR-{yyyy}-{seq:5}` | yearly |
  | Employee letter | `LTR-{yyyy}-{seq:5}` | yearly |
  | Leave request | `LV-{yyyy}-{seq:6}` | yearly |
  | Payroll run | `PR-{yyyy}{mm}-{seq:2}` | monthly |
  | Loan or advance | `LN-{yyyy}-{seq:5}` | yearly |
  | Expense claim | `EXP-{yyyy}-{seq:5}` | yearly |

- **Q8 Changing a scheme after use.** Versions applying from a chosen date are Later (ADM-STU-32). *Recommendation for
  1.0:* while a scheme has issued no number, everything may be edited. After first use, pattern, reset rule, gap-free
  flag and start value are locked; the only change is to retire it and create a new active scheme. If the new
  pattern is identical to the retired one, the new scheme continues the old series (never starts again at 1).
  Existing documents are never renumbered.
- **Q9 Manual override of employee numbers (HRM-EMP-04).** Needed above all when importing existing staff with their
  current numbers. *Recommendation:* allowed only for document types declared `override: yes` (employee number only)
  and only on gap-allowed schemes; a typed number that the scheme could still produce later (matches the pattern with
  a running number at or above the next value) is refused with "raise the starting number first", so an automatic
  number can never collide with it. Duplicates are stopped by the table's existing unique key. Permission
  `hrm.employments.number_override` (S1.20); every override is in the audit log.
- **Q10 Voids and the void report.** Spec: voided numbers are kept with status and reason, with a void report for
  gap-free series. *Recommendation:* when a numbered document is cancelled, the document keeps its number with
  status "cancelled" (FR-XM-06) and the module records a void through the kernel (number, reason, document id).
  No manual "void a number" action in 1.0 (gap-free numbers cannot be lost, so there is nothing to void by hand); the
  generated void create endpoint is closed. Add to `cfg.numbering_voids` an optional `document_id` and a unique key
  on scheme and number (CR-033, new migration only). Void report: for a scheme and date range, the first and last
  number issued per period, how many, and each void with reason, who and when. Alternative: also keep a log of every
  gap-free number issued (new table) so the report can prove continuity on its own; proposed for when a legal
  gap-free series arrives (Phase 2 invoices).
- **Q11 Permissions, roles and endpoints.** *Recommendation:* keep the generated read endpoints for schemes and voids;
  close generated create and update (`api_actions: [read]`) and add `POST /api/cfg/numbering/schemes`,
  `PUT /api/cfg/numbering/schemes/{id}` (before first use only), `POST /api/cfg/numbering/schemes/{id}/retire`,
  `GET /api/cfg/numbering/document-types` (registered types and, per company, whether an active scheme exists; used by
  S1.15 and the readiness check of S1.18) and `GET /api/cfg/numbering/void-report`. Permission codes: existing
  `cfg.numbering_schemes.read/create/update`, new `cfg.numbering_schemes.retire` and `cfg.numbering.void_report`.
  Roles (spec 02 role table): Tenant Admin all; Company Admin all, for its own companies only (existing company
  scope); Auditor read and void report. No maker-checker on scheme changes in 1.0 (each change is audited).
  No number is ever handed out through the API; allocation is in-process only.
