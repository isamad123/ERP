## Goal
Everything a customer may change without a programmer, in one place: settings with where each value comes from, the
words the product uses, extra fields on records, dropdown lists, document numbering, approval routes, and the texts of
notifications and documents. Each change is checked, audited, reversible where the engine allows, and held for a second
person when the setting says so.

## What exists already (and stays)
- Settings service and endpoints (`/api/cfg/settings`, `/{key}`, `/{key}/history`, `/history/{id}/revert`, reset,
  company and user layers; `iam.*` keys only through `PUT /api/iam/settings/{key}`); feature flags and overrides;
  maker-checker answers 202 for held settings.
- Labels read endpoint (`GET /api/kernel/labels`) and generated `cfg.labels` writes; generated endpoints for
  `cfg.custom_field_defs`, `cfg.option_lists`, `cfg.option_list_items`. No service checks custom field **values**, and the
  form engine reserves the custom section (S1.12c).
- Numbering endpoints (document types, schemes, retire, void report) with the refusals of CR-058.
- Workflow definitions and versions (create, edit draft, check, activate), condition shape (depth 3), approver kinds.
- Notification text templates (draft, preview, test send, restore), rules (subscriptions); document templates and
  versions (Scriban, preview, activate, generate; S1.11c2).

## Found while preparing (needs a ruling)
1. **Custom field types are narrower than the requirement.** FR-KRN-MET-01 lists money, date-time, lookup to any entity and
   formula; the approved data design (D-50) has text, long text, number, decimal, date, yes/no, choice, multi-choice, user,
   employee and file. The data design is the higher source (Q5).
2. **No server checks custom values.** Rows carry `custom jsonb`; nothing validates it against the definitions or applies
   field security to it (FR-KRN-MET-02) (Q6).
3. **Option lists are needed but their management is Later** (FR-KRN-MET-03, FR-ADM-STU-11 Later), while HR reason codes use
   them (Q7).
4. **Login branding is 1.0 (FR-ADM-SEC-08) but tenant branding is 1.1 (FR-KRN-TEN-08)** (Q3).

## Build
### Part S1.15a: settings centre and branding
1. **Settings centre (FR-ADM-SET-01 to -04, -06, FR-KRN-SET-02, -03).** Grouped by module and area, searchable; each row:
   name, help, effective value, source layer, default, last change and who; typed editors (switch, number with unit and
   range, choice, list, company, user and calendar pickers) built from the setting definitions; layered view (product,
   pack, customer, company, role, user as the definition allows) with "override" and "reset to inherited"; history with
   revert; held changes shown as "waiting for a second administrator".
2. **Feature flags (FR-KRN-SET-05).** List with description, scope and state; overrides per company or group.
3. **Sign-in and security group (FR-ADM-USR-20, -21, -24, FR-ADM-LOC-05).** The `iam.*` keys (password, MFA, session,
   remember device) edited through the `iam` service; number and date format settings (`loc.number.digits`,
   `loc.number.grouping`).
4. **Login branding (FR-ADM-SEC-08, Q3).** Product name (S1.12 Q21), customer logo (file store), login banner text and terms
   notice in English and Urdu; a public, cached `GET /api/kernel/branding` for the sign-in page (no other data).

### Part S1.15b: labels, option lists, custom fields
5. **Labels (FR-ADM-STU-25, -05, FR-KRN-MET-22).** Searchable table of every label key with English and Urdu side by side,
   the product text, the override per layer (customer, company) and "where it appears" (screen and table from the label
   catalogue); reset to product text.
6. **Option lists (Q7).** Lists and items with code, English and Urdu names, order, active switch; system lists can be
   extended, not removed.
7. **Custom field definitions (FR-KRN-MET-01, -05, Q5).** Per extensible table (those with the `cust` trait): key, type,
   labels and help in both languages, required, unique, default, validation (min, max, length, pattern, option list),
   section and order; retire (hidden, data kept); purge not offered in 1.0.
8. **Custom values on the server and on screens (FR-KRN-MET-02, Q6).** Generated create and update check `custom` against
   the active definitions (type, required, unique, validation) with field errors; field policies (hidden, masked,
   read-only, editable) apply to custom keys like columns, so they show in the field matrix of S1.13; the form engine renders
   the custom section; lists can show custom columns. Imports and exports carry them from S1.16.

### Part S1.15c: numbering and routes
9. **Numbering (FR-KRN-NUM-01 to -03, -05).** Per company: document types and their scheme (pattern, reset rule, gap-free
   flag, start), the next number, retire and replace; warnings of the S1.08 review (pattern too close, code renames);
   void report for gap-free series.
10. **Route step-list editor (FR-KRN-WFL-01 to -03, -10).** Per document type: versions (draft, active, retired); steps
    listed top to bottom: approver kind (named user, role queue, document user field, manager, manager's manager,
    department head, position), optional condition built from the document's declared fields with and/or (depth 3), due
    time and escalation; "check" shows the engine's problems; activate (maker-checker when the setting says so); running
    instances stay on their version (shown).

### Part S1.15d: templates
11. **Notification texts and rules (FR-KRN-NTF-02, -03).** Per event and language: subject and body with a placeholder
    list from the event catalogue, preview with sample data, test send to oneself, restore the product text; rules: who is
    told (audience kinds of S1.11b1) per company.
12. **Document templates (FR-KRN-DOC-05, FR-KRN-LOC-07).** Per template: versions, text editor with placeholders, language
    variants, letterhead choice, preview as PDF with sample data, activate.

## Acceptance
- The settings centre finds "idle timeout" by searching "idle"; shows the effective value, its layer and who set it; a
  company override wins for that company only; reset returns the inherited value; history reverts a change; a setting that
  needs approval shows "waiting" until another administrator approves.
- Changing the minimum password length makes the next password change follow it (end to end).
- The sign-in page shows the customer's logo, banner and terms in the chosen language, with nothing else revealed.
- Renaming "Department" to "Wing" for Urdu and English changes the label on every screen showing it within the settings
  refresh time.
- A required custom field "Blood group" (choice from an option list) on employments is refused when missing on create
  (field error in both languages), hidden from a role by the field matrix, shown in the form's custom section; retiring it
  hides it and keeps the stored values.
- A numbering scheme change shows the next number; a too-close pattern shows the S1.08 warning; the void report lists voids.
- A three-step route with a condition on a declared field is checked and activated; a running instance stays on the old
  version; a step that could resolve the requester shows the engine's refusal.
- A notification text edited in Urdu previews with sample data, test-sends to the administrator (`TestMailServer`), and
  restores; a document template previews as PDF.
- Every screen: accessibility, keyboard, English and Urdu, three widths, states, screenshots.
- New endpoints pass the tenant-isolation suite and have permission tests (the branding endpoint is added to the
  anonymous-endpoint inventory); tests cite the FR ids.

## Out of scope
Everything listed under "Not built here". Option-list effective dates and import. Purging custom field data.

## Questions for the product owner
- **Q0 Parts.** *Recommendation:* four parts as above (a settings and branding, b labels and custom fields, c numbering and
  routes, d templates). Alternative: three parts (c and d together).
- **Q1 Menu.** *Recommendation:* group "Administration": "Settings", "Feature flags", "Labels", "Option lists", "Custom
  fields", "Numbering", "Approval routes", "Notification texts", "Document templates", "Sign-in page". Alternative: one
  "Configuration" page with tabs.
- **Q2 Which settings are shown.** *Recommendation:* every registered setting whose definition says it is visible to
  customers; operator-only settings (hosts, mail servers) never appear. Alternative: none.
- **Q3 Login branding (FR-ADM-SEC-08 1.0 against FR-KRN-TEN-08 1.1).** *Recommendation:* in 1.0 only logo, product name,
  login banner and terms notice, as settings and one file; custom domains, colours and e-mail sender identity stay 1.1.
  The public branding endpoint returns only these. Alternative: colours too (needs contrast checks per customer).
- **Q4 Where `iam.*` policies are edited.** *Recommendation:* in the settings centre's "Sign-in and security" group through
  the existing `iam` settings service (S1.13 Q4). Alternative: separate policy pages.
- **Q5 Custom field types (D-50 data design against FR-KRN-MET-01).** *Recommendation:* build the approved data design's
  types; money, date-time, lookup to any entity and formula follow by change request when a customer needs them (CR-071
  records the narrowing for 1.0). Alternative: add the four types now (data design change; formula needs the rules engine,
  which is Later).
- **Q6 Checking custom values (FR-KRN-MET-02).** *Recommendation:* the generated create and update paths validate `custom`
  against the active definitions and apply field policies to custom keys (one shared kernel service; generator change);
  values of retired fields are kept but not editable. Alternative: check only in the web form (the API would accept bad
  data; not recommended).
- **Q7 Option lists.** *Recommendation:* a plain list-and-items screen (codes, two languages, order, active) because HR
  reason codes need it; effective dates and import stay Later with FR-ADM-STU-11. Alternative: seed lists only (no screen).
- **Q8 Unique custom values.** *Recommendation:* "unique" checked by the server per table (and per company for company
  tables) before saving, under an advisory lock per table and field so two saves at once cannot both pass (custom keys have
  no database index). Alternative: drop "unique" from 1.0.
- **Q9 Route editor conditions.** *Recommendation:* conditions only on the document type's declared fields and the
  operators the engine supports (equals, in, greater or less than, between), shown as plain sentences ("when Amount is more
  than 50,000"). Alternative: free expressions (rules engine is Later).
- **Q10 Template editing.** *Recommendation:* a text editor with a placeholder picker and live preview; no visual designer
  (Later). Placeholders the template uses but the event does not give are refused by preview. Alternative: none.
- **Q11 Numbering changes after use.** *Recommendation:* a used scheme is never edited in place: "retire and replace" from a
  date, as S1.08 allows; the screen explains it. Alternative: none (versions from a date are FR-ADM-STU-32, Later).
- **Q12 Urdu texts.** *Recommendation:* drafted in the session and marked for a native speaker's review (R-062).
- **Q13 Review.** *Recommendation:* no fresh Opus review (screens over reviewed engines; part b's custom-value check is
  covered by tests, including field-security and isolation tests). Alternative: a fresh Opus review of part b.
- **Q14 Change request CR-071.** *Recommendation:* approve: public branding endpoint (Q3); custom-field type narrowing for
  1.0 (Q5); custom-value check and field policies on custom keys in generated writes (Q6, generator change); option-list
  screen in 1.0 (Q7); contracts register rows added at build.
