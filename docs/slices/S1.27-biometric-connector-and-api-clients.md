## Goal
Punches reach the system from every 1.0 source and each one is kept exactly as received: from fingerprint and face devices at each
site, from a shared kiosk, from the employee's own check-in button on the web, from HR on behalf of someone, or from a file. An
administrator sees every device, whether it is online, when it last synchronized and what went wrong. Device user numbers are
mapped to employees, biometric consent is recorded and no fingerprint or face template is ever stored. Machines (device
middleware, HR data feeds) sign in with API keys an administrator creates, scopes, limits, rotates and revokes, and can see used.

2. **Mobile-dependent capture sources** of ATT-01 (selfie, QR on the phone, geo-fence validation) need the 1.1 app (Q2).
3. **Reference device type** is not named by the specification; the build plan says "one reference device type first" (Q3).
4. **Pull from SaaS** cannot reach a device inside the customer's network; pull works on-premises or through middleware (Q4).
5. **Kiosk identity:** a shared kiosk has no user per employee; ATT-01 names it without saying how a person is identified (Q5).
6. **Consent wording and template rules** are privacy content for counsel (spec 06a section 34.3), not product text (Q7).
7. **Rate limits per customer** (INT-07) have no licence key yet (Q9).

## Build
### Part S1.27a: API clients and keys (fresh Opus review)
1. **Clients (SEC-02).** `POST /api/iam/api-clients` {name, scopes, ipAllow, rateLimitPerMinute, expiresAt} returns the client id
   and the secret **once** (32 random bytes, base64url; stored as a salted hash with the same hasher as passwords, S1.05); list,
   read (never the secret), `rotate` (new secret, the old one valid for a grace period setting, Q8), `revoke` (immediate), expiry
   job marks `expired`. Maker-checker on create and rotate when the S1.06 setting for privileged changes is on; every action audited.
2. **Key authentication (Q1).** Header `Authorization: ApiKey <client_id>.<secret>`; the tenant comes from the host name as for
   users (D-02), the key is looked up in that customer's database only; checks in order: active, not expired, IP in the allow list
   (empty list refuses all, Q6), constant-time secret compare; the principal is a **client** (no person, no data scope beyond its
   scopes); scopes are permission codes the client may use, limited to codes marked `api_client: true` in the permission manifests
   (S1.27b marks `hrm.attendance.events.push`; generated read codes may be marked later by their slices); `last_used_at` written at
   most once a minute. A key never opens a web session, never reaches `/api/iam/*` writes, and failures are security events (S1.07).
3. **Rate limits and throttling (INT-07).** Fixed window per client per minute from `rate_limit_per_minute`, plus a per-customer
   ceiling setting `itg.api.tenant_rate_per_minute` (Q9); over the limit returns 429 with `Retry-After`; counters in memory per host
   with the database as the shared truth every minute (Q10).
4. **Usage and alerts (SEC-02, INT-07).** Per client and day: calls, errors (4xx, 5xx), p95 latency, last use; `GET
   /api/iam/api-clients/{id}/usage?from=&to=`; notification events `iam.api_client.limit_reached` and `iam.api_client.expiring`
   (catalogue entries, audience: users holding `iam.api_clients.manage`); screen in Administration "API clients" (list, create with
   the secret shown once and a copy button, rotate, revoke, usage chart from the design system).
### Part S1.27b: devices, driver interface, reference driver, mapping and consent
5. **Driver interface (ATT-03, INT-05, D-10).** Kernel contract `IConnectorAdapter` (kind, provider, `HealthAsync`, configuration
   schema) and HR contract `IAttendanceDeviceDriver` (provider code, capabilities push/pull/delete-user, `PullAsync(device, since)`
   returning raw punches, `ParsePush(request)`, `DeleteUserAsync`); drivers are registered by provider code; adding a model is a
   new driver class only (no core change, tested by a second test driver).
6. **Devices console (ATT-02).** Register a device under a location: serial number, model, provider, connection (host, port,
   protocol; never a secret), credentials through an operator command into the secret store (as `mail server`, CR-062); status
   `active`, `offline`, `retired`; `last_seen_at`, `last_sync_at`, `last_error`; a health job `hrm.device_health` (every 5 minutes)
   marks a device offline after the setting `hrm.att.device_offline_minutes` and raises `hrm.device.offline` once per outage.
7. **Reference driver (Q3, Q4).** Provider `push.json`: the device middleware or the vendor's software posts punches to
   `POST /api/hrm/attendance/push` with an API key holding `hrm.attendance.events.push` and the device serial number; batches of up
   to 1,000 punches; each punch carries the device's own record id, used as the idempotency key (`device:<serial>:<record id>`), so a
   repeated upload (the device's offline buffer) is accepted once. Pull runs through the job `hrm.device_pull` only for drivers that
   declare pull (on-premises installations or middleware); the test driver proves the pull path. A named-vendor driver is a later
   driver class, added when a device and its protocol document are available (R-154).
8. **Device user mapping (ATT-03).** Map device user numbers to employments from a date (one device or all devices of the company);
   bulk map from a file (import type `hrm.device_user_maps`); unmapped punches are kept with `employment_id` resolved later: they wait
   in `hrm.device_unmapped_punches` (Q11) and are moved into `attendance_events` when a mapping valid on the punch date appears.
9. **Consent and deletion (ATT-20, Q7).** `consent_at` recorded on the mapping with the consent document version (a S1.24 policy
   publication the customer writes); company setting `hrm.att.biometric_enabled` (default on) refuses new mappings and pushes for a
   company that has switched biometrics off; on separation (event `hrm.employee_separated`) mappings end on the last working day and,
   for drivers that can, a delete-user command is queued; no template, image or biometric score is accepted by any endpoint (the push
   schema has no such field; a test posts one and is refused).
### Part S1.27c: web, kiosk, HR entry, file import, duplicates
10. **Web check-in (ATT-01).** `POST /api/hrm/me/attendance/check` {direction in or out} from the signed-in employee (employment
    resolved from the token, S1.26 rule); source `web`; server time is the event time (the client sends none); IP kept; a home-page
    button "Check in / Check out" shows the last punch; setting `hrm.att.web_checkin` per company (default off, Q2).
11. **Kiosk (Q5).** A kiosk is an attendance device of provider `web.kiosk` with its own API key; the kiosk page (full screen, no
    menu) accepts a badge code typed or read by a card or QR reader acting as a keyboard; the code resolves through the device user
    mapping; source `kiosk`; the page shows only the person's name and the time, never other data.
12. **HR entry and file import (ATT-01, GHR-09).** HR records a punch for an employee with a reason (source `hr_entry`, acting user
    in `created_by`, audited); import type `hrm.attendance_events` in the import centre (CSV and Excel, S1.16a) with columns employee
    number or device user number, date-time, direction; source `import`; validation preview and the import batch id on each row.
13. **Duplicates and corrections (ATT-03).** A punch of the same employee within the setting `hrm.att.duplicate_window_seconds`
    (default 60, Q10) of an earlier one with the same direction is stored with `is_duplicate = true` and ignored by S1.29; a wrong
    punch is never edited: HR enters a correcting punch with `supersedes_event_id` and a reason.

## Acceptance
- SEC-02: a client is created, its secret is shown once and never again (API and screen); a rotated key works and the old one stops
  after the grace period; a revoked or expired key gets 401; a call from an IP outside the allow list gets 403; usage shows calls,
  errors and p95 for a day; each action is in the audit log.
- INT-07: 61 calls in a minute against a limit of 60 give one 429 with `Retry-After`; the per-customer ceiling applies across two
  clients; the limit-reached notification is raised once.
- Key security: a key from customer A is refused on customer B's host (tenant-isolation suite covers the push endpoint and every new
  endpoint); a key cannot call an endpoint outside its scopes or any `/api/iam` write; a key never gets a web session cookie.
- ATT-03: 1,000 punches pushed twice give 1,000 events; an unmapped punch waits and is moved when a mapping from an earlier date is
  added; a second test driver is added without changing core code; a pull of the test driver resumes after a failure.
- ATT-02: a device that stops reporting is marked offline after the setting and one notification is raised; the console shows last
  sync and last error.
- ATT-20: a push with a template field is refused; with biometrics off for the company, mapping and push are refused; separation
  ends the mapping and queues a delete-user command for a capable driver.
- ATT-01: web check-in uses server time; a kiosk badge creates a kiosk punch; HR entry records the acting user; an import of 500 rows
  previews errors and loads; a duplicate within 60 seconds is flagged; a superseding punch keeps the original.
- Tests cite the FR ids; English and Urdu keys for every new text; fresh Opus review of S1.27a in `docs/reviews/`.

## Questions (each recommendation is the ruling, CR-083)
- **Q0 Parts.** *Recommendation:* three parts as above; S1.27a first because b and c need key authentication. Alternative: two parts
  (keys; everything else), over the CR-047 size.
- **Q1 Key authentication.** *Recommendation:* a separate authentication handler for the `ApiKey` scheme beside the session handler;
  clients are principals of kind `client` with only their scopes; same audit and security-event paths as users. Alternative: OAuth
  client credentials now (FR-KRN-IAM-05, 1.1; larger).
- **Q2 Capture sources.** *Recommendation:* 1.0 builds web, kiosk, biometric, card reader (through devices or the kiosk), HR entry and
  file import; selfie, phone QR and geo-fence validation follow the mobile app (D-48, already 1.1); web check-in is off by default per
  company because it proves no presence. Alternative: web check-in on by default.
- **Q3 Reference device type.** *Recommendation:* the generic JSON push driver (`push.json`) as the reference: every vendor's middleware
  or a small on-site script can post to it, it needs no vendor SDK or package (D-09), and it works for SaaS through TLS and API keys; a
  named-vendor driver (for example the push protocol of a common brand in Pakistan) is a separate driver class once a test device and
  its protocol document are supplied (R-154). Alternative: start with one named vendor's protocol (needs the device now).
- **Q4 Pull.** *Recommendation:* the pull path and job exist and are proven with the test driver; real pull drivers are used on-premises
  or by middleware; SaaS customers push. Alternative: none (ATT-03 requires both).
- **Q5 Kiosk identity.** *Recommendation:* badge code only, through the device user mapping (same assurance as a card reader); no PIN
  (a PIN is a new credential type). Alternative: badge plus a personal PIN (new credential, fresh review).
- **Q6 Empty IP allow list.** *Recommendation:* refuses every call (safe default); the screen asks for at least one address or range.
  Alternative: empty means any address.
- **Q7 Consent text.** *Recommendation:* the customer publishes its own consent notice through S1.24 publications; the product ships no
  legal wording; the pack may later carry a reviewed default (counsel, spec 06a section 34.3; R-155). Alternative: a product default text.
- **Q8 Rotation grace.** *Recommendation:* setting `iam.api_client.rotation_grace_minutes` (default 60, tenant layer). Alternative: none.
- **Q9 Per-customer throttle.** *Recommendation:* setting `itg.api.tenant_rate_per_minute` (default 600) now; usage is metered per day so a
  licence limit can be added later as a D-24 key by change request. Alternative: wait for the licence key.
- **Q10 Defaults.** *Recommendation:* `hrm.att.duplicate_window_seconds` 60, `hrm.att.device_offline_minutes` 30, both company settings;
  in-memory rate counters per host, reconciled every minute (a burst across hosts may exceed the limit by one host's share; R-153).
  Alternative: database counter per call (slower).
- **Q11 Unmapped punches.** *Recommendation:* new table `hrm.device_unmapped_punches` (company, device, device user number, punch time,
  direction, record id, received at; append-only; moved rows marked with the event id), because `attendance_events.employment_id` is
  required. Alternative: refuse unmapped punches (data lost when HR maps late).
- **Q12 Change request CR-088.** *Recommendation:* approve: `ApiKey` authentication scheme and client principal; endpoints
  `/api/iam/api-clients*`, `/api/hrm/attendance/push`, `/api/hrm/me/attendance/check`, device and mapping endpoints; contracts
  `IConnectorAdapter` (kernel) and `IAttendanceDeviceDriver` (HR); permission manifest flag `api_client`; table
  `hrm.device_unmapped_punches` (D-35, new migration file); settings `iam.api_client.rotation_grace_minutes`,
  `itg.api.tenant_rate_per_minute`, `hrm.att.web_checkin`, `hrm.att.biometric_enabled`, `hrm.att.duplicate_window_seconds`,
  `hrm.att.device_offline_minutes`; jobs `hrm.device_health`, `hrm.device_pull`, `iam.api_client_expiry`; events
  `iam.api_client.limit_reached`, `iam.api_client.expiring`, `hrm.device.offline`; import types `hrm.device_user_maps`,
  `hrm.attendance_events`; fresh Opus review of S1.27a. Expand-only.
