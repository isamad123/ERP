## Goal
Every change to data is written down, at the moment it happens and in the same transaction, with who did it, when,
from where, and the value before and after. Nobody, not even the customer's own administrator, can change or delete
these records, and if someone with direct database access tampers with them, a check shows exactly where the chain
of records was broken. Every time someone sees unmasked salary or other sensitive fields, that is written down too.
Personal details inside the audit log are locked with a key that belongs to that one person, so if the law ever
requires their data to be erased, destroying the key makes the values unreadable without breaking the chain.
Authorized users can search the log and see the full history of any record they are allowed to see.

## Build
1. **Audit writer (KRN-AUD-01, GHR-09).** One kernel service collects change entries during a unit of work and writes
   them just before commit, in the same transaction. Generated repositories feed it automatically from the EF change
   tracker (create, update with field-level before/after, soft delete, status change); hand-written services (identity,
   access, settings, platform recovery) call it explicitly. Each entry carries actor, actor kind, source (Q8),
   correlation id (new: one id per request, returned in the `X-Correlation-Id` answer header), client address and the
   company of the row. Which tables are audited: Q4.
2. **Tamper-proof storage and hash chain (KRN-AUD-03).** Rows are appended through a database function the
   application login may call but cannot bypass (Q1); the function computes the chain hashes itself (Q2). Existing
   triggers already refuse update, delete and truncate. Chain anchors per day in `aud.chain_anchors`. A verifier
   recomputes the chain for a date range and names the first broken row; it runs as a migrator command and an API
   endpoint for auditors. A refused attempt to change an audit row through the application is itself logged (Q9).
3. **Per-person keys (R-21, the "per-person keys" of the build plan).** Fields classed `personal` or `restricted`
   (Q5) are encrypted in `changes` with the data subject's key (`aud.subject_keys`, key wrapped by the customer's
   field key from S1.05). The subject is found through the row's scope locator (`person`, or `employment` through the
   HR module's Contracts interface, D-10). A kernel operation destroys a person's key (used later by retention and
   erasure, HRM-PRV-04 and ADM-SEC-06); after that, history shows "erased" for those values and the chain still
   verifies.
4. **Access log (KRN-AUD-02, GHR-02, HRM-PRV-05).** When a read answer contains unmasked `salary`, `personal` or
   `restricted` fields, one `aud.access_log` row is written per request (Q6). Hook: `FieldShaping.Shape` already knows
   which fields were shown. Exports and prints log through the same service when those features arrive.
5. **Security events (KRN-AUD-02).** Sign-in success and failure, lockout, MFA and password changes, session
   revocation, role, permission, scope and field-rule changes, maker-checker decisions, platform admin recovery,
   key and licence events go to `aud.security_events` with a severity (Q7). The `iam.*` events already written to
   `iam.outbox_messages` stay as they are (published contract).
6. **Search, export and record history (KRN-AUD-04, KRN-AUD-07, ADM-USR-04).** Endpoints (Q10):
   `GET /api/aud/changes` (filter by user, entity, record, date range, action, source), `GET /api/aud/history/
   {entityType}/{id}` (one record's history), `GET /api/aud/access-log`, `GET /api/aud/security-events`,
   `GET /api/aud/export` (CSV, logged in the access log), `POST /api/aud/verify`. History shows values through the
   same field security as the record itself (a line manager sees no salary before/after).
7. **Permissions and roles.** New codes `aud.changes.view`, `aud.history.view`, `aud.access_log.view`,
   `aud.security_events.view`, `aud.export`, `aud.verify` (sensitive: export, access log). Auditor and Tenant Admin
   baseline roles get them as in Q10. All texts as localisation keys (English and Urdu).

## Acceptance
- Spec 02 AC: changing an audited field writes an entry with both values in the same transaction; if the business
  change rolls back, no audit entry remains; if the audit write fails, the business change rolls back.
- Updating, deleting or truncating an audit row fails for the application login and for `app_audit`; the attempt
  through the application is recorded as a critical security event.
- Changing one byte of any audit row directly in the database (as owner, triggers disabled) makes the verifier report
  that row; an untouched log verifies.
- Concurrent writers (for example 20 parallel sessions) produce one unbroken chain.
- A personal field's before/after value is unreadable in the raw table, readable in history for an allowed user,
  and shows "erased" after the person's key is destroyed while the chain still verifies.
- A salary read by a Payroll Officer writes one access-log row; the same read by a role that sees it masked or hidden
  writes none.
- Each `iam.*` change of S1.05 and S1.06 (sign-in, lockout, role and permission changes, maker-checker decisions,
  setting changes) produces its change-log or security-event row with the right actor.
- Search by user, entity, record, date and action returns exactly the expected rows; export needs `aud.export`.
- Every new endpoint passes the tenant-isolation suite; tests cite the FR ids; measured overhead per write reported.

## Build-plan rulings (2026-11-16, build session; product owner: "accept all")
The build plan was presented in plan mode and approved. These rulings bind the build (CR-028):
- **P1 Function owner.** The audit functions (`aud.append_changes`, `aud.ensure_subject_key`, `aud.destroy_subject_key`,
  `aud.append_security_event`, `aud.append_access`) are `security definer` functions owned by the customer database's
  owner login (the migrator's login), with a fixed `search_path`. `app_rw` gets EXECUTE only; it still cannot update,
  delete or truncate audit rows. (Q1 said "owned by the audit role": the migrating login cannot give ownership to
  `app_audit`, and `app_audit` cannot update a day's anchor or destroy a key.)
- **P2 Chain order.** The append function keeps `occurred_at` non-decreasing along the chain: a row whose time is
  earlier than the chain head's is moved forward to the head's time (milliseconds under concurrency). A date range is
  then one contiguous piece of the chain. No sequence column.
- **P3 Chain scope.** Only `aud.change_log` is hash-chained (the only table with hash columns in spec 03 6.2).
  `aud.access_log` and `aud.security_events` are protected by grants and the append-only triggers. The acceptance line
  "one byte of any audit row" means any change-log row.
- **P4 Missing column.** Spec 03 6.2 lists `correlation_id` on `aud.access_log`; the approved design omitted it. Add it
  (amends CR-026), new migration only.
- **P5 Control-plane anchor copy.** Operator command `audit anchors-publish` (migrator) copies the anchors of finished
  days of every customer into `cp.audit_anchors`; a mismatch with an earlier copy is a critical finding. The verify
  endpoint and command compare against the copy. Running it daily comes with S1.11 (jobs).

## Questions as put to the product owner

- **Q1 How audit rows are written.** The application connects as `app_rw`, which may only read audit tables
  (S1.03). *Recommendation:* a database function `aud.append_changes(...)` owned by the audit role, which the
  application may call; it inserts the rows and computes the hashes. The application can add entries but never
  choose hashes, change or delete rows. New migration file only; no table changes. Alternative: give `app_rw` insert
  rights (simpler, but the application could then insert rows with forged hashes).
- **Q2 Hash chain and many users at once.** A single chain needs writers to take turns. *Recommendation:* one
  continuous chain per customer database; entries are collected during the work and written in the last moment before
  commit under a short lock, so a long job (payroll, import) holds the lock only for its final write, not for its
  whole run. Each day's last hash goes to `aud.chain_anchors`. Hash: SHA-256 over the row's fields in a fixed
  canonical form plus the previous hash. Overhead measured and reported.
- **Q3 What the chain protects against.** *Recommendation, stated honestly:* the chain proves that rows were not
  changed, removed or inserted in the middle. Someone with full database owner rights could rewrite the whole chain
  from a point onward; protection against that needs the daily anchor stored outside the customer database. Proposal:
  also copy each daily anchor into the control plane (new table `cp.audit_anchors`, change request CR-027), so a
  customer-side database owner cannot rewrite history unnoticed. Alternative: anchors only in the customer database
  in 1.0, external copy later.
- **Q4 Which tables are audited.** *Recommendation:* every table in the kernel and HR data design, except (a)
  append-only tables (they never change; the row itself is the record, for example payroll results, attendance events,
  stock-style ledgers), (b) machinery (outbox, inbox, sessions `last_seen_at`, login attempts, job logs, the audit
  tables). Opt-outs are declared with a new data-design key `audit: false` with a reason (CR-026), so the list is
  visible and reviewed. Every audited generated table gets an automatic test that create, update and delete write
  their entries.
- **Q5 Which fields get the per-person key.** The data design marks salary fields only (S1.06); nothing is marked
  `personal` or `restricted` yet. *Recommendation:* add `field_class: personal` to identifier values, date of birth,
  religion, contacts, addresses, bank account fields, emergency contacts and dependants' details, and `restricted` to
  case and investigation fields when they arrive (CR-026, keys only, no new column). Salary fields are encrypted with
  the customer key, not the person key, because payroll records must be kept by law (spec 03 14.3: financial and
  statutory records are excluded from erasure). Names stay readable in the log (needed to make it useful); erasure of
  names is handled by the erasure flow on the live record, not the log. Users who are not employees (no person record)
  have no person key; their email is not classed personal in 1.0.
- **Q6 What counts as a "view" for the access log.** *Recommendation:* one row per request that returned at least
  one unmasked sensitive field (salary, personal or restricted): the fields shown, the record id for a single record
  or the row count for a list. Masked or hidden fields are not logged. Viewing the audit history itself with decrypted
  personal values is also logged. Payslips and documents log when those features arrive.
- **Q7 Security events.** *Recommendation:* write `aud.security_events` directly in the same transaction as the
  identity or access action (no event dispatcher exists yet; it comes with S1.11), keep `iam.login_attempts` as is,
  and also write a security event for each sign-in success and failure so there is one place to search. Severity:
  critical for tamper attempts, Super Admin recovery and switching off maker-checker or privileged MFA; warning for
  lockouts and repeated failures; info for the rest.
- **Q8 Missing "source" column.** Spec 02 AUD-01 requires the source (UI, API, import, job, AI) but the approved
  `aud.change_log` has no `source` column. *Recommendation:* add `source` (`ui`, `api`, `import`, `job`, `system`) by
  change request CR-026, new migration only (expand). `ai` and `confirmed_by` come with KRN-AUD-06 in 1.1. Rule: a
  person signed in through the web is `ui`; API clients are `api` when they exist; jobs and imports set their own.
  The source is decided by the server, never taken from request input.
- **Q9 Logging a refused tamper attempt.** The database refuses the change and rolls the transaction back, so the
  attempt cannot be logged in that same transaction. *Recommendation:* the application catches the refusal and writes a
  critical security event in a new transaction. An attempt made directly in the database (outside the application)
  shows in the PostgreSQL server log and is caught by the chain check; we say so in the runbook rather than claim more.
- **Q10 Who sees the audit log.** *Recommendation:* the Auditor baseline role gets all `aud.*` view permissions,
  export and verify; Tenant Admin gets the same except the access log of salary views (it holds no salary permission,
  S1.06 Q2); every role that can read a record gets `aud.history.view` for that record's history through its own data
  scope and field security. Export capped at 10,000 rows per request in 1.0 (larger exports with S1.16). Everyone may
  see their own sign-in history.
