## Goal
A person can ask what the company holds about them and receive it, correct it, and have it erased or anonymised where the law and the retention rules allow, with an audit trail; retention rules purge what has expired; the product passes a documented security review; a customer can be restored from backup within the stated objectives; and a release package can be built and installed from scratch.

## Build
### Part S1.53a
1. **Subject access and export (GHR-05, Q1).** Request registered by HR for an employee; the system gathers the person's data across modules through a registered `IPersonalDataSource` per module (export as JSON and PDF summary, sensitive fields included only for the subject); delivered through the vault with expiry.
2. **Correction.** Corrections go through the S1.26 change request route; the request records the original.
3. **Erasure and anonymisation (Q2).** Per data category rules: erase, anonymise (irreversible replacement keeping statistics) or keep with reason; blocked by legal hold and by retention periods from packs or tenant settings; payroll results after close are never erased (append-only, statutory), only anonymised after the period when permitted; every action audited and approved (maker-checker).
4. **Retention and purge (PRV-04).** Settings per category with pack defaults (none shipped until validated); job `hrm.retention_purge` finds expired records, lists them for approval or purges automatically per setting, audits each run; legal holds respected.
5. **Classification check (GHR-02).** Architecture test lists every column with field class sensitive or restricted and proves encryption, masking default and access logging; fails on an unclassified personal column.
### Part S1.53b
6. **Security review checklist (Q4).** A checked, evidence-linked list: authentication, sessions, MFA, permissions on every endpoint (generated test), tenant isolation, secrets scan, dependency licences and known vulnerabilities, headers and CSP, file-upload scanning, audit chain verification, backups encrypted, least-privilege database logins; results in `docs/security/release-1.0-review.md`.
6a. **Remaining release-1.0 NFRs (CR-113).** Checked with evidence in the same review: **NFR-04** no accepted event is lost (outbox and inbox at-least-once with
    idempotency, S1.11a; punches by idempotency key, S1.27; a test kills the worker mid-dispatch and finds every event handled once); **NFR-14** documented module
    boundaries and contract tests (architecture tests, contracts register, a contract test per published HR contract); **NFR-15** the current and the previous major
    API version are served for at least one release (version policy written in `docs/runbooks/api-versioning.md`; 1.0 is the first version, so the test proves the
    version route and the policy only); **NFR-16** e-mail and device connectors retry with back-off and a circuit breaker and their failures never block a
    business action (tests with the test mail server down and a device driver failing). The mobile parts of these four (offline queues, push, SMS, WhatsApp,
    geocoding) are Release 1.1.
7. **Backup and restore drill (NFR-17).** Using the runbook: back up a tenant with files, restore into a fresh server, verify audit chain, payroll totals and file checksums; measure recovery point and time against 15 minutes and 4 hours; record in the drill report.
8. **Release packaging.** Reproducible build of API, worker, migrator and web into versioned artefacts with checksums and the licence and dependency inventory; install-from-scratch script and test (SaaS and on-premises profiles); signing of the entitlement and release manifest per the S1.03 key tools.
9. **Release notes and handover.** Release 1.0 notes, known limits (what is 1.1), operator runbooks index, risk register state, and the list of items that need a person (professional validation, bank templates, penetration test).

## Acceptance
- GHR-05: an export for a test employee contains data from each module and omits other people's data; an erasure request on a person with payroll history anonymises where allowed and refuses where retention blocks, with the reason.
- PRV-04: an expired test category is purged only after approval or per setting; a legal hold stops it; each run is audited.
- GHR-02: the classification test fails when a new personal column lacks a class.
- GHR-14: no location evidence table has rows in 1.0 (test).
- NFR-17: drill meets or documents the miss against 15 minutes and 4 hours.
- NFR-04, -14, -15, -16 (item 6a): each has its test or evidence line in the review; a worker killed mid-dispatch loses no event; a failing mail server or device driver
  blocks no business action.
- Packaging: a clean machine installs the release and passes the smoke suite; checksums verify.
- Tenant-isolation test for every endpoint; FR ids in tests; fresh Opus review of each part.

## Questions (recommendations are rulings, CR-083)
- **Q0 Parts.** *Recommendation:* two parts, Opus, fresh review each.
- **Q1 Data sources.** *Recommendation:* each module registers `IPersonalDataSource`; a module without one fails an architecture test.
- **Q2 Erasure.** *Recommendation:* anonymise rather than delete wherever other records depend on the person; hard delete only for data with no dependants.
- **Q3 Statutory periods.** *Recommendation:* pack data; until validated, the longest customer-entered period applies and the tool warns.
- **Q4 Checklist owner.** *Recommendation:* the review is produced by Claude and signed off by the product owner; recorded evidence, not assurances.
- **Q5 External test.** *Recommendation:* an outside penetration test before the first production customer (a person to arrange); the product owner decides.
- **Q6 Residency.** *Recommendation:* hosting region is a tenant setting (PRV-12); the release checks that files and backups use the tenant's region setting.
- **Q7 Packaging.** *Recommendation:* container images plus a plain archive for on-premises; no new packaging tool beyond what S1.01 CI uses.
- **Q8 Change request CR-108.** *Recommendation:* approve: contract `IPersonalDataSource`; job `hrm.retention_purge`; settings `hrm.privacy.retention.*`; document types `hrm.privacy_request`, `hrm.erasure_approval`; table `hrm.privacy_requests`; docs under `docs/security`; expand-only.
