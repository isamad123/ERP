## Goal
The first thing people see and touch. A person opens the customer's address, signs in (with a second factor when
required), and lands in one consistent application: a top bar with the company they are working in, their notifications
and their menu; a side menu that shows only what their customer has bought and what they are allowed to use; banners
when the licence needs attention; and screens that all look and behave the same, in English and in Urdu (right to left),
on a laptop or a phone, by keyboard or mouse. This slice builds that frame, the design system (colours, type, spacing,
buttons, fields, tables, dialogs) and three model screens that every later slice copies: a **list** (branches), a
**form** (create and edit a branch, with its change history) and an **approval inbox** (decide what waits for you).
Later screen slices (S1.13 onward, mostly Sonnet) only add their own menus, metadata and business screens.

## What exists already (and stays)
- `web/generated/`: the generated TypeScript client of every generated endpoint (`api/*.ts`, `http.ts`) and one metadata
  file per table (`metadata/*.json`: route, actions with permission codes, scope, list fields, field kinds, references,
  options, field class). CI type-checks it (`typescript@6.0.2`). No web application, design system or web test exists.
- Hand-written endpoints (sign-in, `/api/iam/me/*`, capabilities, inbox, notification centre, history) have no generated
  client; their shapes are in `docs/registers/contracts.md`.
- Sign-in answers `mfa_required` (with `mfaMethods`), `password_change_required`, `mfa_enrolment_required` (with
  `mfaEnrolBy`) or `tokens`; access tokens live 5 minutes; refresh tokens rotate and a reused one ends the session, so two
  tabs refreshing at once sign the person out (S1.05 review). The refresh token travels in the JSON body today.
- The idle timeout (30 minutes) counts from the last **refresh** (`iam.sessions.last_seen_at`), not from the last request.
- `iam.session.remember_device_days` is registered (default 0 = off) "for S1.12" (S1.05 ruling P9); no code uses it.
- Server texts are localisation keys; English and Urdu catalogues live in `Erp.Kernel.Contracts/*/Localization/*.json`.
  Problem answers (RFC 9457) carry the key in `title`; every answer carries `X-Correlation-Id`.
- `GET /api/kernel/capabilities`: modules, features, flags, licence state, next state, limit warnings (only for holders of
  `cfg.licence.read`). It answers in locked state.
- Notification deep links of non-workflow events are provisional (`/settings/licence`, `/admin/jobs/health`,
  `/admin/audit`) until this slice fixes the route table (S1.11b1 handoff).
- No real workflow document type exists yet (the first arrive with S1.21 and S1.26); workflow tests register test types.
  Maker-checker requests (settings, access changes, route activation) are real today and are counted in the inbox as
  "approvals of changes".

## Build
### Part S1.12a: foundation and sign-in
1. **Web workspace (Q1, Q2).** pnpm workspace under `web/`: `apps/web` (the application), `packages/ui` (design system),
   `packages/engine` (list and form engine, from S1.12c), `packages/i18n` (catalogues and formatting), and the existing
   `web/generated` as a package. Vite build, strict TypeScript, ESLint and Stylelint rules of spec 13 section 24 (no
   literal user-facing strings in components, logical CSS properties only, token values only, accessibility rules).
2. **Design tokens and themes (spec 13 section 6, Q7).** Tokens as CSS variables (spacing, radius, elevation, type scale
   with script-specific line heights, control and row heights for compact, standard and comfortable density, motion,
   layers, neutral, primary and status colours); light, dark and high-contrast themes following the system setting by
   default; theme, density, language and direction applied before first paint. A build step checks every text and
   boundary colour pair against 4.5:1 and 3:1 and fails the build below them. Fonts bundled, none fetched from outside.
3. **Components (spec 13 section 7, first set).** Built on the accessible primitives of Q1 and the tokens: button, icon
   button, link, status chip (text and icon, never colour alone), badge, tooltip, menu, tabs, dialog (focus trap, escape),
   drawer and side panel, banner, toast (at least 6 seconds, announced), skeleton, spinner (after 300 ms), page header,
   breadcrumb, empty state, error panel with reference code, text, number, date, select, combobox with server lookup,
   checkbox, switch, text area, one-time code input, password input (password managers and paste allowed). A component
   catalogue page (development builds only) shows every component in every state, in English and Urdu, both directions,
   all themes and densities; Playwright screenshots it (Q19).
4. **Localisation (Q5, Q6).** ICU message catalogues in English and Urdu; the server catalogues are collected at build
   time so problem titles show in the user's language; a pseudo-locale (accented, 40 percent longer, right-to-left) used
   only in tests to catch hard-coded strings and mirroring faults. Shared formatting of numbers, money (exact decimal
   strings, never floating point), dates and times in the user's time zone, with the digit and grouping choices of Q6.
   Directional icons tagged and mirrored. Unicode isolation for codes, numbers, e-mail addresses and names.
5. **API layer.** One client over the generated client and small hand-written modules for the hand-written endpoints:
   access token in memory only, problem answers turned into typed errors with message key, field errors and correlation
   id; 401 leads to one refresh attempt, then to sign-in with a return address; 503 `errors.auth.busy` retried once.
6. **Session handling (Q3).** Refresh token in a cookie scripts cannot read; one tab at a time refreshes (browser lock)
   and shares the new access token with the other tabs; a refresh happens only while the person is active, so the
   server's idle timeout keeps working; a warning two minutes before the idle end offers "Stay signed in"; after expiry
   the person signs in again and returns to the same screen. Sign-out ends the session on the server and in every tab.
7. **Sign-in screens (FR-KRN-IAM-01, -02, FR-ADM-USR-02).** Sign in; second factor (authenticator code, e-mail code with
   "send code", recovery code); required password change; enrolment (authenticator with QR code and secret, or e-mail
   code; shows the enrolment deadline); forgot password (always the same answer); reset password (`/reset-password`);
   activate account (`/activate`); "Remember this device" when Q4 allows. Messages never reveal whether an account exists.
8. **Hosting (Q2) and server changes (CR-063).** The API host serves the built application at `/` (unknown non-API paths
   answer the application, so deep links work) with strict security headers (content security policy allowing only own
   scripts, no framing, no referrer leakage). Server side: the refresh cookie (Q3) and remember-device (Q4), each with
   integration tests and the isolation and anonymous-endpoint inventory updated.

### Part S1.12b: shell, navigation, banners, notifications
9. **Session context endpoint (Q9).** `GET /api/kernel/me` for the signed-in person (allowed when locked).
10. **Shell (spec 13 section 5).** Top bar (product name, company switcher, notification bell with unread count, user
    menu with language, theme and density, sign out), collapsible side menu, content area with page header, skip link,
    landmarks; responsive at 360, 768 and 1280 pixels; the side menu becomes a drawer on phones.
11. **Navigation (Q8).** Each web module package declares its routes and menu entries (label key, icon, group,
    permission, feature key); the shell shows an entry only if the feature is licensed (capabilities) and the person
    holds the permission (`/api/kernel/me`); a route whose feature is not licensed answers "not found", exactly like a
    route that does not exist. A simple home page ("waiting for you": approvals and unread notifications). The route
    table fixes the deep links of S1.11b1; links to screens of later slices open a "not available yet" page.
12. **Company switcher (FR-ADM-ORG-06, Q10).**
13. **Banners and states (FR-KRN-ENT-04, FR-KRN-TEN-09, Q17)** and the **notification centre (FR-HRM-NTF-09, Q16)**:
    bell panel with the latest items, read and unread, read all, deep links; full page with search, group filter and
    paging. Error pages: not found, permission denied (with what the person can do instead), server error with reference.

### Part S1.12c: list and form engine, first list and form screen, record history
14. **Generator extension (Q11).** Generated list endpoints gain sorting on indexed columns and a text search on code and
    name; the generator also writes English labels for every table and column and a validation schema per table for
    the web forms (type, required, length, pattern, choices), so client and server checks cannot drift.
15. **Labels (Q11).** English labels from the generator, hand-kept Urdu labels per module, tenant overrides from
    `cfg.labels` (customer and company layers) applied everywhere a label is shown; a check lists missing Urdu labels of
    every screen that is in a menu.
16. **Grid wrapper (spec 13 section 8: GRD-01, -02 without grouping, -03 column filters, -07, -09, -12, -13, -14, -16).**
    The product's own grid API over the grid library of Q1: server keyset paging with "load more" and row
    virtualisation, column choice, resize and order, sort, typed column filters, single and multiple selection with a
    bulk bar, keyboard navigation, phone card layout, loading, empty and error states.
17. **List engine and saved views (FR-ADM-NAV-02, Q12).** A list page made from metadata: title, saved view picker,
    filters, search, grid, create button (only with the create permission). Saved views per person, or shared with a role.
18. **Form engine (FR-ADM-UXA-02 to -05, Q13).** A form page made from metadata: one field renderer per field kind
    (lookups for references, two-language inputs for names, switches, dates, numbers, money as exact decimals, codes;
    JSON and binary fields shown read-only), required markers, help text, validation on leaving a field and on save,
    server errors mapped to fields and to a summary, read-only fields and hidden or masked values as the server sends
    them, "last changed by and when", unsaved-changes warning, concurrent-change view when the row version is stale
    (yours next to the saved one: keep yours or take the saved one), confirmation for delete stating what is removed.
19. **First list and form screen and history (FR-KRN-ORG-02, FR-KRN-AUD-07, FR-ADM-OPS-03).** Branches: list, create,
    edit, deactivate and delete (the database rule "every company keeps at least one branch" shown as a clear message).
    A history side panel on the detail page from `GET /api/aud/history/{table}/{id}` (shows "hidden", "erased",
    "redacted" as the server marks them), offered only to holders of the history permission.

### Part S1.12d: first approval screen
20. **Inbox (FR-KRN-WFL-08, FR-HRM-SSP-02, Q15).** Master-detail page: task list with counts per document type, filters
    (module, document type, company, requester, step, waiting for information, overdue, received between), sort by
    received or due, "for Sara" on delegated tasks, overdue and escalation marks; task detail without leaving the page:
    the module's declared fields, the requester, the history of decisions and questions, attachments when the module
    gives them, and a link to the module's own screen.
21. **Decisions.** Approve, reject and return (reason required where the engine requires it), ask for information,
    claim and release queue tasks, bulk approve where the document type allows it (preview of the count, a result per
    task, failures listed). Only the actions the engine allows for this person and task are shown; the server's answer
    is shown as confirmed, never assumed (spec 13 STA-06).
22. **Approvals of changes (Q15).** Pending maker-checker requests the person may decide: what will change in plain
    words, who asked and when, approve or reject with reason (S1.06 endpoints); the person's own requests are listed
    without decision buttons.

## Acceptance
- A tenant admin of a freshly provisioned customer opens the customer's address, activates the account from the e-mailed
  link, sets a password, enrols an authenticator, signs out, signs in with the code, and lands on the home page. With
  `iam.mfa.allowed_methods` including e-mail, the same works with an e-mailed code (Playwright, real API, real PostgreSQL,
  `TestMailServer`).
- Forgot password gives the same message and timing for a known and an unknown login; the reset link sets a new password.
- The refresh token cannot be read by page scripts (test reads `document.cookie` and storage); two tabs stay signed in for
  30 minutes of activity with no "reused token" sign-out; with no activity the idle warning appears two minutes before the
  idle end and the session ends at the server's idle time; after signing in again the person is back on the same screen.
- With remember-device on (Q4) a second sign-in from the same browser skips the second factor until the period ends, a
  password change or MFA reset ends it, and another browser still asks for the code.
- Every screen of the slice: no automated accessibility violation of serious or critical level; fully usable by keyboard
  with visible focus; correct in English and Urdu (mirrored layout and icons, Urdu digits and grouping as ruled in Q6);
  no hard-coded string (pseudo-locale run shows none); works at 360, 768 and 1280 pixels; loading, empty, error and
  permission-denied states shown; screenshots captured in both languages, light and dark.
- Token contrast check fails the build when a token pair is below 4.5:1 (text) or 3:1 (large text, boundaries) (test with
  a deliberately failing pair).
- The side menu of a customer without `hrm.payroll` shows no payroll entry, and typing a payroll address gives the same
  "not found" page as a nonsense address; a user without `org.branches.read` sees no Branches entry.
- Banners: Warning only for holders of `cfg.licence.read`; Grace and Read-only for everyone; in Read-only no create,
  edit or decide button is offered and data stays readable; in Locked a tenant admin sees the locked page with the
  licence page and exports, everyone else a "licence locked" page. Limit warnings show for licence readers only.
- Notification bell shows the unread count; opening an item marks it read and follows its deep link after the permission
  check; a link to a record the person may not see shows the permission-denied page, not the record.
- Branches: list sorted and searched on the server, filtered by company, columns chosen and saved as a view, shared
  with a role; create, edit with validation errors next to the fields (English and Urdu), stale-version conflict view,
  delete of the last branch refused with a clear message; the history panel lists the changes with who and when.
- Inbox: with a test document type in the end-to-end host, a manager sees an assigned task, its context and history,
  approves it; a requester never sees decision buttons on their own request; a delegate sees "for Sara"; bulk approval
  reports one result per task; a maker-checker settings change requested by one admin is approved by another from the
  inbox and the setting changes.
- Performance (measured in CI on the production build): shell script under 300 KB compressed, each module route chunk
  under 200 KB; first page of 100 branch rows rendered within 1 second on the CI machine.
- Every new server endpoint passes the tenant-isolation suite and has permission tests; tests cite the FR ids.
- Licence gate covers the npm packages (all, including transitive ones) and fails on a licence outside the policy.

- **Q2 Where the application runs.** *Recommendation:* the API host serves the web application from the same address
  (for example `acme.erp.example`), so the customer is found from the address exactly as today, cookies stay on that
  address, and on-premises customers install nothing extra. Alternative: a separate web server or CDN (needs
  cross-address cookies and CORS; more to secure).
- **Q3 Keeping the sign-in safe in the browser.** *Recommendation:* the refresh token is sent as a cookie that page
  scripts cannot read (HttpOnly, Secure, SameSite Strict, only for the sign-in paths), and the request must carry a header
  that other sites cannot send; the short access token is kept in memory only. One tab refreshes at a time; tabs refresh
  only while the person is active (mouse, keyboard, touch), so the 30-minute idle rule still ends forgotten sessions; a
  warning two minutes before. This changes the published identity contract (CR-063). Alternative: keep the token in
  browser storage (any injected script could steal it; not recommended).
- **Q4 "Remember this device" (FR-ADM-USR-24; S1.05 ruling P9).** The specification only says the duration is
  configurable. *Recommendation:* when the customer sets `iam.session.remember_device_days` above 0, the second-factor
  screen offers "Remember this device for N days"; on that browser the person then signs in with the password only
  until the period ends. The password is always asked. Trust is kept as a hashed token in a new table
  `iam.trusted_devices` (CR-063, data design approval) and ends early on password change or reset, MFA reset, "revoke
  sessions" by an administrator, or the person removing it; privileged roles with `iam.mfa.required_for_privileged`
  are never remembered; every use is a security event. Default stays 0 (off). Alternatives: (B) postpone to 1.1 (the
  setting stays unused); (C) only remember the user name.
- **Q5 Languages in 1.0.** *Recommendation:* English and Urdu, right to left for Urdu; no Arabic and no Hijri in 1.0
  (D-42), and correct FR-KRN-LOC-01, FR-HRM-SSP-08 and the spec 13 checklist accordingly (CR-063). The design stays ready
  for Arabic (logical layout, script tokens). Alternative: add Arabic texts now (needs translation and review; contradicts
  D-42).
- **Q6 Numbers and dates in Urdu and English (spec 13 section 26 leaves this open).** *Recommendation:* two new settings
  at customer, company and user layers: `loc.number.digits` (`western` or `eastern_arabic_indic`) and
  `loc.number.grouping` (`international` 1,234,567 or `lakh_crore` 12,34,567); defaults **Western digits and
  international grouping** for both languages until tested with users; dates shown as day, month name, year in the
  person's language and time zone (`iam.users.time_zone`); stored and exported values never change. The user's own
  choice screen comes with S1.26 (FR-ADM-USR-10). Alternatives: Eastern Arabic-Indic digits by default for Urdu; lakh and
  crore by default for Pakistani companies.
- **Q7 Fonts and look.** *Recommendation:* Noto Sans for English and Noto Naskh Arabic for Urdu on screens (Naskh is
  easier to read in dense tables than Nastaliq; spec 13 TOK-11), Nastaliq remains for documents (S1.11c2) and can be
  offered on screens after tests with Urdu speakers (S1.19); a calm neutral palette with one primary colour (placeholder
  blue, replaceable by tenant branding later) and fixed status colours. Alternative: Nastaliq on screens too (needs much
  more line height; slower in tables).
- **Q8 Menus and the home page.** *Recommendation:* menus are declared by each module's web package and grouped by area
  (Home, Approvals, People, Time, Payroll, Administration) in a fixed product order; an entry shows only when licensed
  and permitted (the server still checks every request). The home page shows "waiting for you" (approvals count,
  unread notifications) and nothing else until role home pages (1.1). Alternative: a server-side menu manifest per
  module (more machinery, same result for 1.0).
- **Q9 Who is signed in.** *Recommendation:* new `GET /api/kernel/me` (any signed-in person, also in locked state):
  user id, display name, language, time zone, default company, the companies where the person holds any permission, the
  permission codes held with the companies they cover, MFA state and enrolment deadline. It is used only to show or hide
  menus and buttons; the server keeps deciding. Alternative: add these fields to `/api/kernel/capabilities`.
- **Q10 Company switcher (FR-ADM-ORG-06; the specification gives no detail).** *Recommendation:* the active company is a
  screen choice, not a server session: it pre-fills the company of new records and filters lists; lists also offer "all
  my companies"; it starts from the user's default company, is remembered per person in the browser, and is always shown
  in the top bar; changing it shows "Now working in <company>". Shown only to people with more than one company.
  Alternative: no "all companies" view (one company at a time everywhere).
- **Q11 First list and form screen, sorting and labels.** *Recommendation:* branches (`org.branches`, FR-KRN-ORG-02):
  small, company-scoped, has a lookup, two-language names, an active switch, delete, and a database rule to show.
  S1.14 later adds the organization screens with the same engine. To meet FR-ADM-NAV-02, the generator adds sorting on
  indexed columns and a search on code and name to generated list endpoints, writes English labels from the data
  design (a column `company_id` reads "Company"), and writes a validation schema per table for the forms; Urdu labels
  are kept by hand per module and drafted now for the tables on screens, marked for native review. Alternatives:
  locations or holidays as the first screen; sorting only within the loaded page (misleading on large lists).
- **Q12 Saved views, bulk actions and export on lists (FR-ADM-NAV-02).** *Recommendation:* saved views now, kept on the
  server in a new small table `cfg.saved_views` (owner, list, name, filters, sort, columns; personal or shared with a
  role; CR-063), so every later list has them; selection and the bulk bar are built in the grid and first used by bulk
  approval (S1.12d); the export button arrives with the export centre (S1.16). Alternative: personal views in the
  browser only (lost on another computer; no sharing) until S1.15.
- **Q13 Unsaved work (FR-ADM-UXA-05).** *Recommendation:* every form warns before leaving with unsaved changes (built
  here); automatic drafts are built with the first long form (employee profile, S1.21) and kept on the server, because
  browser storage on shared office computers could expose personal data. Alternative: browser drafts now for every form.
- **Q14 Record history.** *Recommendation:* every detail page of the engine has a "History" side panel (who, when, what
  changed, old and new values as the server allows); shown only to people allowed to read the record's history.
  Alternative: a separate history page.
- **Q15 What the first approval screen covers.** *Recommendation:* the workflow inbox for all document types (none is
  live yet; tested end to end with a test document type in the test host, so leave, profile changes and the rest appear
  without screen work when their slices register them) plus "approvals of changes" (maker-checker requests: settings,
  access changes, route activation), which are real today, in the same inbox. "My requests" comes with self-service
  (S1.26). Alternative: workflow tasks only; maker-checker decisions in the admin console (S1.13).
- **Q16 Notifications in the shell.** *Recommendation:* the bell shows the unread count, refreshed every 60 seconds while
  the tab is visible and on every page change (no live connection in 1.0); the panel lists the latest 10; the
  notification centre page has search, group filter and paging. Preferences and quiet hours are on the self-service
  profile (S1.26). Alternative: refresh only on page change.
- **Q17 Licence banners (S1.09 ruling Q5).** *Recommendation:* Warning (licence readers only, can be hidden for the day);
  Grace and Read-only for everyone, cannot be hidden, saying what still works ("you can read and export") and whom to
  contact; Locked: a full page for everyone, with the licence page and exports for tenant admins; limit warnings (licence
  readers) beside the Warning banner. Alternative: Warning for everyone.
- **Q18 Errors.** *Recommendation:* every error says what happened and what to do in the person's language, with
  "Reference: <correlation id>" for support (FR-ADM-UXA-04); permission denied explains what is missing and offers the way
  back; nothing technical is shown. (No alternative proposed; confirm.)
- **Q19 Spec 13 rules and checks in CI.** *Recommendation:* treat the spec 13 FR-UX rules as design rules this and every
  later screen slice follow (they are not release-tagged requirements; CR-063 notes it, R-063); tests cite the register
  FR ids. A new CI job `web` runs: install from the lockfile, licence gate for npm, lint, type check, unit and component
  tests, token contrast check, production build with size budgets, and Playwright end-to-end tests (sign-in, list and
  form, approvals) against a real API host and PostgreSQL with accessibility checks; screenshots (English and Urdu, both
  themes, three widths) are kept as CI artifacts and attached to each part's report for you to look at. Automatic pixel
  comparison is left out for now (font rendering differs between machines; R-064). Alternative: pixel comparison now
  (fragile, many false failures).
- **Q20 Licences of development tools (D-09).** The automated accessibility checker axe-core is MPL-2.0 (not on the
  permissive list), and build tools commonly bring data packages such as `caniuse-lite` (CC-BY-4.0). *Recommendation:*
  the npm licence gate applies the D-09 list strictly to everything shipped to browsers; development-only packages may
  also be MPL-2.0 (unchanged, never shipped), CC0-1.0 or CC-BY-4.0 (data), each named in the register. Alternative:
  IBM `accessibility-checker` (Apache-2.0; downloads its rules from the internet when it runs) instead of axe-core.
- **Q21 Name and branding.** *Recommendation:* the shell and sign-in page show the product name from one setting
  (placeholder "ERP", to be chosen by you) and the customer's company name; logo, colours, login banner and terms
  (FR-ADM-SEC-08) come with the settings centre (S1.15), which has file upload screens. Alternative: build login branding
  here.
- **Q22 Texts.** *Recommendation:* English texts written in plain language; Urdu drafted in the same session and marked
  for a native speaker's review before go-live (as for every earlier slice). Alternative: none.
