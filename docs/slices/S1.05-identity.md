## Goal
A person can sign in to their own customer's web address with username or email and password, prove a second factor
when required, and get a session that times out, can be listed and can be revoked. Wrong passwords lock the account
under the customer's policy. Admins can unlock, force a password change, reset MFA and revoke sessions.
The API then trusts only tokens it issued itself.

## Build
1. Password hashing: Argon2id with per-user salt, algorithm recorded in `user_credentials.hash_algorithm` so it can be
   upgraded on next sign-in. Licence check of the library (D-09), recorded in `docs/registers/dependencies.md`.
2. Password policy (ADM-USR-20): length, complexity, history count, expiry days, lockout threshold and lockout duration,
   read per customer, with an optional stricter policy for privileged roles once roles exist (S1.06). Enforced on set,
   change and reset; history checked against `password_history`.
3. Sign-in endpoint (anonymous, tenant from host only): username or email + password. Same response and similar timing
   for unknown user, wrong password and disabled user (no account enumeration). Every attempt written to
   `iam.login_attempts` with the outcome. Failed attempts counted in `user_credentials`; at the threshold the user is
   locked until `locked_until`. `must_change` and expired passwords force a change before any other call.
4. MFA (KRN-IAM-02, ADM-USR-21): methods per Q1. Enrolment (pending → active), verification at sign-in, recovery codes
   (see Q5), revoke. Secrets stored in the encrypted `secret` column. Enforcement per customer and per user now; per role
   when S1.06 lands. Grace period for enrolment.
5. Sessions (KRN-IAM-04, ADM-USR-24): issue short-lived ES256 access tokens with `sub` (user id) and `tenant` (customer
   code) as agreed in S1.03, plus a refresh token bound to an `iam.sessions` row. Idle timeout, absolute timeout and
   concurrent-session limit from policy; oldest session revoked when the limit is exceeded. Revoked or expired sessions
   are refused on the next call (see Q3 on how fast). Signing keys loaded from the secret store; key id in the token
   header so keys can rotate.
6. Self-service (ADM-USR-10, API only): change password, list and revoke own sessions, enrol and remove own MFA devices.
7. Admin actions (ADM-USR-05, ADM-USR-03): unlock, force password change, reset MFA, revoke all sessions, and status
   transitions invited → active → locked / disabled → archived with a reason; disabling or archiving revokes sessions.
   Each action guarded by a permission code registered now; until S1.06 the endpoints answer 403 like every other
   business endpoint, and tests use a test permission checker. The last active tenant admin cannot be disabled (spec 02
   section 5 BR) once roles exist; recorded as an S1.06 follow-up.
8. First tenant admin activation: the `invited` user created by provisioning sets a password through a one-time,
   expiring, single-use activation token (see Q2 for where the token lives and Q6 for how it is delivered).
9. User limit (KRN-IAM-18): activating a user beyond the entitlement's user limit is refused with a clear message.
10. Injected clock everywhere; all user-facing messages as localisation keys (English and Urdu).

## Acceptance
- Sign-in with a correct password returns a token the API accepts; the same credentials on another customer's host fail.
- Unknown user and wrong password give identical responses (test compares body and status).
- N wrong passwords lock the account; sign-in refused until the lock ends or an admin unlocks (clock moved in the test).
- A password reused within the history count is refused; an expired password forces a change.
- MFA required: sign-in without the second factor gets no access token; a valid code completes it; a replayed TOTP code
  is refused.
- Idle and absolute timeout end the session; exceeding the concurrent limit revokes the oldest; a revoked session's
  token is refused within the agreed time (Q3).
- Disabling a user revokes all their sessions.
- Activation token works once, expires, and cannot be used on another customer's host.
- Every new endpoint passes the tenant-isolation suite (S1.04); anonymous endpoints are registered with the suite.
- Every login attempt and admin action is recorded (where, per Q4).
- Tests cite the FR ids.

## Out of scope
SSO, OIDC, SAML, LDAP (KRN-IAM-03, Later). API keys and OAuth clients (KRN-IAM-05, 1.1). Mobile device-bound sessions
and biometric unlock (KRN-IAM-19, MOB-*, 1.1). Invitations by email in bulk and user import (ADM-USR-02, later admin slice).
Roles, permissions, data scopes, field security (S1.06). Hash-chained audit log (S1.07). Settings screens (S1.15).
Login screen (S1.12). Admin user screens (S1.13). Platform-operator sign-in (S1.17). Email and SMS sending (S1.11).

## Open questions for the product owner
- **Q1 MFA methods in 1.0.** Spec lists authenticator app (TOTP), SMS, email code, hardware key. Proposal: TOTP only
  in S1.05; email code added with S1.11; SMS and hardware key raised as a change request for 1.1 (SMS needs a paid
  provider; hardware keys need WebAuthn). Is that acceptable?
- **Q2 Missing table.** The approved data design has no table for one-time tokens (account activation, password reset,
  refresh tokens, MFA recovery codes). Under D-35 no table may be created without an approved design. Proposal: add
  `iam.one_time_tokens` (id, user_id, purpose, token_hash, expires_at, used_at) and `iam.mfa_recovery_codes`
  (user_id, code_hash, used_at), and a `refresh_token_hash` column on `iam.sessions`, through a change request in
  `docs/registers/risks-and-changes.md` and a new migration. Approve?
- **Q3 Revocation speed and Valkey.** The design says active sessions are "cached in Valkey", but no Valkey service
  exists yet. Proposal: in 1.0 check the session row in PostgreSQL on each refresh, with access tokens living 5 minutes,
  so a revoked session stops working within 5 minutes; Valkey added later without changing behaviour. Or must
  revocation be immediate (session checked on every call)?
- **Q4 Security events before S1.07.** Proposal: S1.05 writes `iam.login_attempts` and raises domain events for admin
  actions; S1.07 records those events in the hash-chained audit log. Until S1.07 lands, admin actions are not audited
  beyond the event. Acceptable, or must S1.07 come first?
- **Q5 Default policy values.** The specs do not give defaults. Proposed shipped defaults (customers can change them):
  minimum length 10, at least 3 of 4 character kinds, history 5, no forced expiry, lock after 5 failures for 15 minutes,
  idle timeout 30 minutes, absolute timeout 12 hours, 3 concurrent sessions, MFA grace period 7 days, 10 recovery
  codes. Where do settings live before S1.09: proposal is the existing `cfg` tables, seeded idempotently by code.
- **Q6 Delivering activation and reset links before email exists (S1.11).** Proposal: S1.05 creates the token and
  raises an event; the operator CLI can print the first admin's activation link for the customer; email delivery and
  self-service "forgot password" arrive with S1.11. Acceptable?
