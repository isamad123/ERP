# S1.02 Code generator from the approved data design
Class: A        Model: Opus 5.5 (high effort)
Requirements: enabling slice for all tables. Decisions: D-35, D-39, D-47, D-50; `docs/token-strategy.md` section 1.
Spec to read: `docs/data-design/README.md` (all of it) and the YAML files as input data.
Depends on: S1.01.

## Goal
`tools/Erp.CodeGen` reads `docs/data-design/*.yaml` and writes the repetitive code, so later slices only add business
logic. Generated files are marked `// <auto-generated>` and are never edited by hand.

## Generate, per table
1. **SQL migration** (per schema, one file per release): table with expanded traits; types per the README type table;
   primary, unique (including partial and `NULLS NOT DISTINCT`), check and exclusion constraints; composite company
   foreign keys `(company_id, x_id)` with `unique (company_id, id)` on company-scoped parents; an index for every
   foreign key plus listed indexes; monthly partitioning where `partition` is given; append-only guard triggers for
   `app` tables; generated columns. Lock triggers and other rules stated only in `notes` or `checks` are emitted as
   named TODO stubs that fail a test until the owning slice implements them.
2. **C# entity and EF Core configuration** in the module's Infrastructure project (schema, keys, row_version
   concurrency token, json columns, encrypted value converter placeholders).
3. **Repository interface and implementation** with standard queries by id, by company and by listed indexes.
4. **Minimal API endpoints** (list with paging and filters, get, create, update, soft delete where `soft`) with a
   permission check per action registered as `module.resource.action`, and data-scope filtering hook.
5. **TypeScript types and API client** for the web app, and JSON metadata for the schema-driven list and form screens.
6. **Tests:** a migration test that applies all migrations to an empty database and to a database migrated from the
   previous release; a test per table that the generated constraints exist.
7. A **data dictionary** generated from the live database after migration, and a CI step that fails if it differs
   from the YAML design.

## Rules
- Deterministic output: running the generator twice gives identical files. CI runs the generator and fails if the
  working tree changes.
- The YAML design is read-only for this slice. If a table entry is ambiguous or inconsistent, stop and list it in
  the slice report instead of guessing (change request, D-39).

## Acceptance
- All 204 tables migrate cleanly on PostgreSQL 16; constraint tests pass.
- Generator re-run produces no diff; CI step proves it.
- Report lists every TODO stub with its table and rule.

## Out of scope
Business rules, triggers beyond append-only guards, screens (S1.12 builds the screen engine that reads the metadata).
