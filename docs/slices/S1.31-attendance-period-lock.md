## Goal
When payroll is calculated for a period, attendance and leave for that period freeze together. If something wrong is found later, the locked days stay as they were, and the
correction is recorded as a separate adjustment that payroll pays or recovers in the next open run. The lock and any reopen announce themselves as events so payroll never
works from numbers that changed underneath it.

## What exists already (and stays)
`hrm.attendance_periods` (pay group, pay period, lock fields); engine and leave contract double; pay periods (S1.34a).

## Found while preparing (needs a ruling)
1. Who may lock: payroll only through the engine, or also manually before the cut-off (Q1). 2. Reopen of a lock with a finalized run (Q2). 3. Leave lock scope (Q3). 4. Adjustment record has no table (Q4).

## Build
1. **Real `IAttendancePeriodLock`.** `IsLocked(employment, date)`, `Lock(period, run)`, `Reopen(period, reason, approval)`; replaces the test doubles of S1.29 and S1.32; refuses locking a period whose days are not all processed or that has open exceptions unless the caller passes the explicit "accept exceptions" flag (recorded).
2. **Lock (ATT-17, FR-XM-26).** Locks attendance days and leave days of the pay group's period together; stamps `locked_at`, `locked_by_run_id`; publishes `hrm.attendance.locked`; the database refuses changes to locked day rows and leave entries dated in the period (guard trigger, rules.yaml `functions`).
3. **Manual lock before payroll (Q1).** HR may lock after the cut-off with approval; payroll's calculation locks automatically if not yet locked.
4. **Reopen (ATT-21, Q2, CR-095).** Only as part of cancelling the run that locked the period (`locked_by_run_id`), while that run has not reached `locked` itself
   (data design of `hrm.attendance_periods`: "a locked period never reopens; unlocking is allowed only if the locking run is cancelled before it is locked itself");
   the cancellation needs approval (workflow, maker-checker setting) and the run is cancelled, never left as a stale draft; publishes `hrm.attendance.reopened` with
   the affected employment list. A period locked by HR (item 3, no run) never reopens; a later change is an adjustment (item 5). Any other reopen is refused with
   "use a retroactive adjustment".
5. **Retroactive adjustments (FR-XM-26, Q4).** For a change to a locked date: a request (new table `hrm.attendance_adjustments`: employment, date, kind, old and new result summary, reason, status, target pay period = next open period) approved through workflow; on approval it is exposed to payroll through `IAttendanceAdjustments` and the original day stays unedited; a leave correction posts reversal and new entries dated in the next open period, never inside the lock.
6. **Impact analysis (GHR-04).** For a backdated change request, a preview shows affected attendance days, leave balance effect, overtime and the pay periods touched; shown before submit.
7. **Lock console.** List of periods with state, who locked and why, open adjustments; lock, reopen and adjustment screens (small, engine screens).

## Acceptance
- FR-XM-26: after lock, an attempt to change a day, a punch result or a leave entry in the period is refused at the API and by the database; the same change as an adjustment request is accepted into the next open period.
- ATT-21: lock and reopen publish their events with the right employment list (checked from the outbox); cancelling the locking run before it is locked reopens
  the period; a reopen while the locking run stays open, after that run is locked, or of an HR lock without a run is refused.
- GHR-04: the preview names every affected module and period for a three-day backdated change.
- Locked leave: unpaid leave days in the period cannot be altered; cancellation of approved leave in a locked period becomes an adjustment.
- Concurrency: a punch ingested for a locked date after the lock still appends the event (events are append-only) but the day is not reprocessed; it appears in "late events after lock".
- Tenant-isolation test for every endpoint; permission tests; FR ids in test names; fresh Opus review.

## Questions (recommendations are rulings, CR-083)
- **Q0 Single part.** *Recommendation:* one part.
- **Q1 Who locks.** *Recommendation:* payroll calculation locks automatically; HR may lock early with approval after the cut-off date.
- **Q2 Reopen.** *Recommendation (corrected by CR-095 to the approved data design):* only by cancelling the locking run before it is locked itself; an HR lock
  never reopens; otherwise adjustments only.
- **Q3 Scope of lock.** *Recommendation:* attendance days, leave entries and overtime of the pay group's period lock together.
- **Q4 Adjustments.** *Recommendation:* the new table `hrm.attendance_adjustments`, append-only status history.
- **Q5 Late events.** *Recommendation:* kept as events, listed for HR, handled by adjustment if they matter.
- **Q6 Events.** *Recommendation:* `hrm.attendance.locked`, `hrm.attendance.reopened`, `hrm.attendance.adjustment_approved`.
- **Q7 Change request CR-091.** *Recommendation:* approve: table `hrm.attendance_adjustments`; guard triggers on locked day rows and leave entries; contracts `IAttendancePeriodLock` (real), `IAttendanceAdjustments`; document type `hrm.attendance_adjustment`; the three events; expand-only.
