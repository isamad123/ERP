## Goal
After a run is approved, payroll staff produce the bank's salary file in the bank's own layout, check it before download, and later load the bank's reply so each payment shows paid or failed. A failed payment goes to a queue
and is paid again by a new line. Every employee receives a bilingual payslip (a PDF protected by a password only they know) by e-mail and in the portal, with year-to-date totals, and payroll can run the standard reports.

## What exists already (and stays)
Payment tables, templates and PDF service (S1.11c2), file store, e-mail queue, results and lines (S1.35), employee bank accounts with encrypted numbers (S1.20d).

## Found while preparing (needs a ruling)
1. **Bank file formats** are not in the specification; each bank supplies one (Q1). 2. **Password rule** for PDFs (Q2) and a **PDF encryption tool** needs a licence check (Q3). 3. **Reply file** layouts also vary (Q1).
4. Cheque and cash have no file (Q4).

## Build
### Part S1.40a
1. **Modes and splits (PAY-24).** Per employee payment instruction effective-dated: mode, bank account, split by percentage or amount (sums to net; remainder rule recorded); cheque and cash produce lines without a file.
2. **Templates (PAY-23, Q1).** Bank file templates are data: delimiter or fixed width, header, detail and trailer layouts, field sources, padding and formats, value date rule; defined in the template editor (S1.15 host), versioned, previewed on sample data; none shipped except a neutral CSV example marked as example.
3. **Batches and validation (PAY-23).** Create a batch per run, company bank account and mode; lines from net pay and splits; validation before download: IBAN or account format per bank template, missing bank data, zero or negative amounts, totals equal run totals, duplicates; download stores the file with checksum and records who and when.
4. **Status import (PAY-25).** Upload the bank reply through the import centre mapping (S1.16); lines become paid or failed with bank reference and reason; unknown references listed, not guessed.
5. **Failed payments (PAY-25).** Queue with reason; correct bank data (maker-checker as set), then "re-pay" creates a new line in a new batch referencing the failed one (`reissued_in_line_id`); paid lines are never edited.
### Part S1.40b
6. **Payslip templates (PAY-28, Q5).** Design in the S1.11c2 template system: company letterhead, English and Urdu blocks, earnings, deductions, employer lines (setting hides employer cost), net, year-to-date, leave balances optional; preview.
7. **Generation (PAY-28).** Job `hrm.payslips_generate` per finalized run, chunked and resumable; one PDF per employee stored against the result; regeneration creates a new version.
8. **Protection and delivery (Q2, Q3).** PDF password from a rule (setting: national ID last digits plus birth year, or a user-set slip password), applied with the approved tool; e-mail through the queue with the PDF attached or a secure link per setting; self-service download after sign-in without password; delivery log; resend.
9. **Year-to-date (PAY-28).** Totals from locked results in the tax year; no tax rule computed here.
10. **Reports (PAY-29, Q6).** Payroll register, component summary, bank advice, department and cost-centre costing, employer cost, headcount-to-payroll reconciliation, tax summary and statutory summaries **as read views of existing results** (the statutory layouts arrive with S1.46); scoped, permissioned, exported through S1.16.

## Acceptance
- PAY-23: a template produces the expected file for a sample batch byte for byte; every validation rule has a failing case; totals mismatch blocks download.
- PAY-24: a 60/40 split and an amount split produce correct lines; cheque and cash lines have no file entry.
- PAY-25: a reply with 3 paid, 1 failed, 1 unknown reference updates lines and lists the unknown; re-payment creates a new line; the old line is untouched.
- PAY-28: payslip PDF opens only with the password rule's value in a test PDF reader; Urdu and English render; year-to-date equals the sum of locked results; an employee sees only their own payslips.
- PAY-29: each report's totals equal run totals; no report without its permission; GHR-06 holds in exports.
- Tenant-isolation test for every endpoint; permission tests; FR ids in test names; fresh Opus review of S1.40a.

## Questions (recommendations are rulings, CR-083)
- **Q0 Parts.** *Recommendation:* two parts; fresh Opus review of part a.
- **Q1 Bank layouts.** *Recommendation:* template data supplied per customer and bank; none invented; the first customer's bank templates are loaded as tenant data.
- **Q2 PDF password.** *Recommendation:* setting `hrm.pay.slip_password_rule` with the two rules above, default the user-set slip password with first-use prompt; never stored in clear.
- **Q3 PDF encryption tool.** *Recommendation:* a permissively licensed tool or library (candidate: QPDF, Apache-2.0, run as a process, or an MIT library); licence check and `docs/registers/dependencies.md` entry before adding (D-09).
- **Q4 Cheque and cash.** *Recommendation:* lines with their own status (issued, cleared or paid) set manually by payroll.
- **Q5 Employer cost on slip.** *Recommendation:* hidden by default, setting per company.
- **Q6 Statutory summaries.** *Recommendation:* generic summaries by component flag now; official return formats in S1.46.
- **Q7 Retention.** *Recommendation:* payslip PDFs follow the payroll record retention (S1.11c1 policy); regenerated versions kept.
- **Q8 Change request CR-094.** *Recommendation:* approve: settings `hrm.pay.slip_password_rule`, `hrm.pay.slip_show_employer_cost`; jobs `hrm.payslips_generate`, `hrm.payslips_email`; table `hrm.payment_instructions` (effective-dated modes and splits) if the approved design lacks it; permissions `hrm.pay.bankfile.download`, `hrm.pay.payslip.read_all`; expand-only.
