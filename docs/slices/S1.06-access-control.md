## Goal
Every call to the API is checked against what the signed-in person is allowed to do, which records they may see and
which fields they may see or change. A customer's administrator can build roles from a catalogue of permissions, give
roles to users for one company or all companies with start and end dates, limit a role to "own records", "my team",
"my department and below", chosen branches or chosen companies, and hide or mask fields such as salary per role.
Sensitive changes (for example giving someone a powerful role) can be held until a second person approves them.
The 403 answer that every business endpoint gives today is replaced by real decisions.

## Build
1. **Permission registry (KRN-IAM-10, ADM-ROL-01, HRM-ROL-01).** At start-up and on `migrate`, every module's
   permission list (kernel generated, HRM generated, identity, and the new access-control codes of this slice) is
   written into `iam.permissions` idempotently by code. Codes that disappear are marked retired, never deleted, so
   roles keep their history. Catalogue endpoint: by module and resource, with description key, sensitivity flag and the
   roles holding each permission.
2. **Roles and permission sets (KRN-IAM-11, ADM-ROL-02).** Create, copy (from a baseline or another role), rename,
   archive; set the permission list; compare two roles; count of users holding the role. Rule (spec 02 BR): nobody can
   give a role a permission they do not hold themselves, and nobody can give a user a role containing a permission they
   do not hold.
3. **Baseline roles (spec 02 section 23, spec 06a section 28, ADM-ROL-03).** Shipped as data, seeded into every customer
   database idempotently by code at provisioning and `migrate`, marked `source = module`, then editable by the
   customer. Which roles and which permissions: see Q2. Every baseline role gets `iam.self.manage` (S1.05 handoff).
4. **Role assignment (ADM-ROL-04).** Give a role to a user for one company or all companies, with start date, optional
   end date and a reason; end an assignment early. Overlaps for the same user, role and company are refused by the
   existing exclusion constraint. An assignment only counts on the dates it is valid (injected clock).
5. **Authorization engine (HRM-ROL-02).** One service answers three questions for the current user and company: may
   they do action X (permission), which rows of resource R may they see (data scope), and what may they do with field F
   of resource R (field access). The same service is used by generated endpoints, hand-written endpoints, exports and
   later reports, AI and mobile. How several roles combine: Q4. How fast a change takes effect: Q9. Replaces
   `NoGrantsPermissionChecker` and `DataScopesNotConfigured`; the isolation suite keeps its allow-all doubles (S1.04).
6. **Data scopes (KRN-IAM-12, ADM-ROL-06).** Kinds already in the design: own, direct_team, subtree, org_units,
   branches, companies, all. Each scoped table declares which of its columns locate a row (company, branch, org unit,
   employment); see Q3 for how the kernel learns the HR manager chain without crossing the module boundary. A role with
   no scope set for a resource sees nothing of it (deny by default). Preview endpoint: "records user U would see of
   resource R" (count and first page). Attribute conditions: Q5.
7. **Field security (KRN-IAM-13, KRN-MET-02, ADM-ROL-07, GHR-06).** Per role, resource and field: hidden, masked,
   read-only or editable, for standard and custom fields. Applied on every read (hidden fields are left out of the
   response, masked fields are shown masked) and every write (a change to a field the caller may not edit is refused
   with a field-level error, never silently dropped). Salary fields hidden by default: Q5. Preview endpoint: "the fields
   of resource R as role X sees them".
8. **Maker-checker (KRN-IAM-14).** A general engine on `iam.maker_checker_requests`: an action marked as needing a
   second person is stored as a pending request instead of being applied; another user holding the approve permission
   (and every permission the change would grant) approves or rejects with a reason; approval applies the change in the
   same transaction; pending requests expire. In this slice it guards role permission changes and role assignments for
   roles holding sensitive permissions, switched by a setting (Q6). Other actions (payroll finalization, bank details,
   bulk export) attach to the engine in their own slices.
9. **Leftovers from S1.05.** Per-role MFA requirement and stricter password policy for privileged roles (Q10) through
   the role layer of `IdentitySettings.ReadAsync`; the last active tenant admin cannot be disabled or archived, and the
   last active `tenant_admin` assignment cannot be ended (spec 02 BR).
10. **System administrator (HRM-ROL-06).** The baseline System Administrator role holds no business-data permission.
11. **Replace unsafe generated writes.** The generated create/update endpoints for `iam.permissions`, `iam.user_roles`,
   `iam.role_permissions` and `iam.maker_checker_requests` would bypass the rules above; they are switched off with the
   generator's `api_read_only` key or replaced by the hand-written services (same approach as CR-012). See Q8.
12. Every change raises an `iam.*` event in `iam.outbox_messages` (actor in `headers.actor`) for S1.07 to record in the
   audit log; all messages as localisation keys (English and Urdu); injected clock everywhere.

## Acceptance
- An endpoint answers 403 to a user without the permission and 200 to one with it; ending the role assignment (or
  reaching its end date with the clock moved) removes access within the agreed time (Q9).
- A role assigned for company A grants nothing in company B.
- Spec 02 AC: a line manager sees only their team's employment records and no salary fields; a payroll officer sees
  salary but only for assigned companies (test data seeded straight into the HR tables).
- Own / direct team / subtree / branches / companies / all each return exactly the expected rows; no scope = no rows.
- Hidden fields are absent from responses, masked fields are masked, a write to a read-only field is refused.
- A user cannot add to a role, or assign, a permission they do not hold.
- With maker-checker on, a sensitive role change stays pending, the requester cannot approve it, a second admin's
  approval applies it, rejection and expiry leave nothing applied.
- The last active tenant admin cannot be disabled, archived or have the role removed.
- Seeding baseline roles twice changes nothing; a customer's edits to a baseline role survive `migrate`.
- Every new endpoint passes the tenant-isolation suite; tests cite the FR ids.

## Questions as put to the product owner
- **Q1 Permission names.** The generator already created one permission per table and action (for example
  `hrm.attendance_days.read`, 504 in all). Spec 06a section 28.2 proposes business names (for example
  `hrm.attendance.view`, `hrm.payroll.view`). *Recommendation:* register the generated ones now (they guard the
  endpoints that exist); each HR slice registers the section 28.2 names for the business actions it builds and adds
  them to the HR baseline roles. Section 28.2 calls its codes "proposals", so this is not a change to the baseline.
- **Q2 Baseline roles shipped now.** *Recommendation:* kernel roles Tenant Admin, Company Admin, Business User, Approver,
  Auditor, System Administrator (spec 02 section 23, 06a HRM-ROL-06) with their kernel permissions; HR roles Employee,
  Line Manager, HR Admin, Payroll Officer, Auditor (spec 06a 28.1) created now with `iam.self.manage` and the read
  permissions the 28.1 matrix clearly gives, filled further by each HR slice. Supervisor, Department Head, HR Business
  Partner, Regional Manager and Senior Management (28.2) arrive with the HR slices that need them. Tenant Admin gets no
  HR salary permission (28.1 "View salary data: No").
- **Q3 Team and department scopes.** "My team" and "my department and below" need the manager and org unit of each
  employee, which belong to the HR module; the kernel may not read HR tables (D-10). *Recommendation:* the kernel
  defines a small Contracts interface "which employments are in this user's team / subtree"; the HR module answers it
  from `hrm.employment_assignments` (manager chain, org unit) as of today; the kernel never joins HR tables. Each
  scoped table declares its locating columns with a new data-design key `scope:` (for example
  `scope: {company: company_id, employment: employment_id}`); the generator emits the filter. Adding this key to the
  approved data design files needs a change request (CR-018); it adds no table or column.
- **Q4 Several roles.** *Recommendation:* permissions are the union of all valid roles for the current company; a row
  is visible if any role that grants the read permission on that resource has a scope covering it; for a field the most
  open access among those roles wins (editable > read-only > masked > hidden). A role with a field rule but without the
  resource permission does not widen anything.
- **Q5 Field defaults and attribute conditions.** The data design marks no field as "salary" or "personal".
  *Recommendation:* add a data-design key `field_class:` (salary, personal, restricted) per column (part of CR-018),
  and default every `salary` field to hidden for every role unless a field rule opens it (GHR-06); masking shows the
  last 4 characters. Attribute conditions in scopes (KRN-IAM-12 "attribute conditions") limited in 1.0 to "column equals
  / is one of" on columns the table declares in `scope:`; full expressions wait for the rules engine.
- **Q6 Maker-checker in this slice.** *Recommendation:* setting `iam.maker_checker.sensitive_roles`, default **on**
  (customer can switch off), guarding (a) permission changes to a role holding any sensitive permission and (b)
  assigning or ending such a role. Pending requests expire after 7 days (setting). The approver needs permission
  `iam.maker_checker.approve` and every permission the change grants. With only one administrator (micro customers),
  the change cannot be approved until a second administrator exists; the customer can switch the setting off.
- **Q7 User groups.** ADM-USR-06 (1.0) wants roles and scopes assignable to a group in bulk, but the design has groups
  and members only, no "group roles" table. *Recommendation:* add table `iam.user_group_roles` (group, role, company,
  valid from/to, reason) by change request CR-019, new migration only; a user's roles = own assignments + their groups'.
  Alternative: groups for notifications only in 1.0, and bulk role assignment by the admin screen (S1.13).
- **Q8 Pack upgrades and the generated write endpoints.** ADM-ROL-03 says a pack upgrade proposes changes to baseline
  roles rather than forcing them. *Recommendation:* in S1.06, `migrate` adds new baseline roles and adds new permissions
  only to baseline roles the customer has never edited; for edited roles it records nothing yet, and the "proposed
  changes" list comes with the pack loader (S1.23). Generated create/update endpoints of `iam.permissions`,
  `iam.role_permissions`, `iam.user_roles` and `iam.maker_checker_requests` are closed and replaced by the services of
  this slice (CR-020, same pattern as CR-012).
- **Q9 How fast changes apply.** *Recommendation:* permissions are read from the database on each request through a
  cache that is cleared the moment any role, assignment, scope or field rule changes in that customer database, so a
  change applies on the very next call (no 5-minute delay); date-based start and end of assignments apply on the first
  call after the date.
- **Q10 Privileged roles.** *Recommendation:* a role is privileged if it holds any permission flagged sensitive.
  Shipped defaults (customer-changeable, seeded like the S1.05 settings): MFA required for users holding a privileged
  role (`iam.mfa.required_for_privileged` = on), privileged minimum password length 14, same grace period as S1.05.
