## Goal
Every employee signs in and sees their own world: profile, documents, letters, requests and their status, policies, directory and
org chart. They ask HR to change their details or issue a letter without paper, set who covers their approvals while away, and see a
home page that shows what needs their attention. Managers see their team, their approvals and requests on behalf. HR and payroll
staff get a work queue with exceptions and deadlines. All of it uses the same services any later mobile app will use.

## What exists already (and stays)
`hrm.change_requests`, `hrm.service_requests` tables; delegation API (S1.10b); approvals screen (S1.12d); profile sections and own-record
commands (S1.20, S1.21); letters and document requests (S1.24); notification centre (S1.12b).

## Build
### Part S1.26a
1. **Own profile (SSP-01).** Read own person, employment, contacts, identifiers (masked per field class), documents, letters, policies
   acknowledged; one endpoint set `GET /api/hrm/me/*` that resolves the employee from the token only, never from input.
2. **Change requests (EMP-08, SSP-12, Q1).** Employee proposes new values for fields in the allowed list (setting
   `hrm.ssp.changeable_fields`, per field: direct, needs approval, not allowed); stored with a snapshot; routes through the workflow
   (document type `hrm.change_request`); on approval the S1.20 command applies it as of today; rejection and return for correction work.
3. **Service requests (SSP-12, DOC-07, Q2).** Kinds as an option list; letters kinds create the S1.24 letter request; other kinds go to the HR queue;
   status visible; cancel while pending.
4. **Delegation and out-of-office (SSP-07, ROL-05).** Screen over the existing delegation API: choose person, dates, scope; shows active and
   ended delegations; audit shown; the delegate sees only the delegator's approval permissions during the period.
5. **Home page.** Fixed role-aware widgets: my requests, pending approvals count, notices, upcoming probation or contract dates for managers,
   birthdays; other slices register widgets through `web/apps/web/src/modules/*.ts`.
### Part S1.26b
6. **Manager portal (SSP-02, Q3).** Team list, approvals inbox link, team calendar of what exists (holidays, shifts, leave when S1.33 registers),
   request-on-behalf (change request, service request) recorded with the acting user (GHR-09).
7. **HR and payroll workspaces (SSP-03).** Task queues from registered sources: open change and service requests, expiring documents,
   probation and contract ends, readiness checks (S1.34); each item has owner, due date and a quick action.
8. **Client availability (SSP-10, Q6).** Setting `hrm.ssp.function.<code>.web` per function (on by default for licensed modules); a function whose
   module is not licensed is hidden (existing gate).
9. **Cross-cutting checks (ROL-02, ROL-04, ROL-06, GHR-12).** Tests: the same endpoint with the same token gives the same data through any client
   header; own-request approval refused; System Administrator role sees no personal or salary data by default; every `me` endpoint probed by the isolation suite.
10. **Performance and access (SSP-14, GHR-10).** Route chunks within budget, list pages paginate, images lazy; axe checks on the new screens; English and Urdu keys complete; Hijri date shown where a date is shown when the user setting asks.

## Acceptance
- EMP-08: change of address needs approval, applies on approval, appears in the record timeline; a direct field applies at once and is audited; rejected change leaves the record untouched.
- SSP-12: a salary certificate request creates the letter request and shows its status; cancel works while pending.
- SSP-07/ROL-05: a delegate approves only inside the dates; the audit shows the delegate and the delegator.
- ROL-04: an employee cannot approve their own change or service request. ROL-06: system administrator gets 403 on personal and salary reads by default.
- Browser tests (`Suite=WebE2E`): sign in as employee, change a phone number, request a letter, delegate; as manager approve on behalf; Urdu and English screenshots.
- Tenant-isolation test for every endpoint; FR ids in test names.

## Questions (each recommendation is the ruling, CR-083)
- **Q0 Parts.** *Recommendation:* two parts as above.
- **Q1 Changeable fields.** *Recommendation:* setting with defaults: contact details and emergency contacts direct; address, bank account, marital status and
  dependents need approval; name, identifiers, employment data not allowed.
- **Q2 Service kinds.** *Recommendation:* option list `hrm.service_kinds` seeded with salary certificate, employment letter, experience letter, address
  proof, other; letters kinds map to S1.24 letter types.
- **Q3 Team dashboard.** *Recommendation:* build the widget host now with the sources that exist; attendance and leave widgets arrive with S1.30 and S1.33.
- **Q4 Arabic.** *Recommendation:* not built; Phase 1 is English and Urdu (CLAUDE.md); SSP-08's Arabic part moves to Later through a change request in the register. **Confirmed by the product owner (2026-11-22): release-scope change recorded as "CR-084 (S1.26 Q4 confirmation)".**
- **Q5 Hijri.** *Recommendation:* use the S1.28 conversion service; display only.
- **Q6 Availability setting.** *Recommendation:* web only is enforced; the mobile keys are reserved names for 1.1.
- **Q7 Employee resolution.** *Recommendation:* `/me` resolves the employment from the signed-in user's link (S1.20 ruling Q7); several employments show a picker.
- **Q8 Notifications.** *Recommendation:* events `hrm.change_request.decided` and `hrm.service_request.updated` added to the catalogue.
- **Q9 Change request CR-084.** *Recommendation:* approve: option list `hrm.service_kinds`, settings `hrm.ssp.changeable_fields`, `hrm.ssp.function.*.web`, the two
  events, document type `hrm.change_request` in `workflow.json`, `/api/hrm/me/*` endpoints, and the Arabic move to Later (SSP-08 text part only), expand-only.
