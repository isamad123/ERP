# Data Architecture Standards and Kernel Data Model (v0.2)

Document 3 of the planning set | Prepared for Ibrahim | 10 November 2026 | Companion to Architecture and Foundation v0.2 and the Platform Kernel Functional Specification

## 1. Purpose and scope

This document turns the database architecture of the Architecture document (section 5) into enforceable standards and a table-level design of the control plane and of the kernel schemas in each tenant database. Claude Code builds migrations from it, and reviewers audit against it. Business-module tables (Finance, HRMIS and so on) follow the same standards and are designed in their own specifications; section 7 gives the patterns they must reuse.

Column lists show the important columns. Standard columns (section 3.2) are not repeated in each table. Final column types are fixed in the migrations, which must conform to this document or record an ADR for any deviation.

## 2. Principles

1. The database is a product asset. Its integrity does not depend on application code being correct.
2. Constraints belong in the database (not null, check, unique, foreign key, exclusion), and the application mirrors them for friendly errors.
3. History is never rewritten: posted ledger rows, audit entries and stock movements are append-only.
4. Every table is owned by exactly one schema and one module; ownership is recorded in the module manifest.
5. Anything that can grow without bound is partitioned or has an archival rule from day one.
6. Migrations are reviewed code, tested on two tenant databases, and reversible for one release.

## 3. Standards

### 3.1 Naming

| Object | Rule | Example |
| --- | --- | --- |
| Schema | Short lowercase module code | fin, hrm, prc, inv, ast, sal, scm, iam, org, ref, cfg, wf, aud, doc, ntf, itg, job, rpt, ai, meta |
| Table | snake\_case, plural | fin.journal\_entries |
| Column | snake\_case, singular | posting\_date |
| Primary key | id (uuid) | id |
| Foreign key column | referenced table singular plus \_id | company\_id, business\_partner\_id |
| Constraints | pk\_, fk\_, uq\_, ck\_, ex\_ prefixes with table and columns | uq\_business\_partners\_code |
| Indexes | ix\_ prefix with table and columns | ix\_journal\_lines\_account\_id\_posting\_date |
| Booleans | is\_ or has\_ prefix | is\_deleted |
| Timestamps | \_at suffix, timestamptz | created\_at |
| Dates | \_date suffix, date | posting\_date |
| Money and quantity | amount, quantity, rate with a unit or currency column beside them | amount, currency\_code |
| Status | status text with check constraint | status |

### 3.2 Standard columns

| Column | Type | Applies to | Notes |
| --- | --- | --- | --- |
| id | uuid | All tables | UUIDv7 generated by the application, never by the client |
| company\_id | uuid | Company-scoped tables | Leads composite indexes; foreign key to org.companies |
| created\_at, created\_by | timestamptz, uuid | All tables | UTC; created\_by is a user id, or a reserved system user id for jobs |
| updated\_at, updated\_by | timestamptz, uuid | Mutable tables | Not on append-only tables |
| row\_version | bigint | Aggregate roots | Starts at 1, incremented on every update; updates use where row\_version equals expected |
| is\_deleted, deleted\_at, deleted\_by | boolean, timestamptz, uuid | Master data | Soft delete; unique indexes are partial on not is\_deleted |
| custom | jsonb not null default '{}' | Extensible entities | Validated against cfg.custom\_field\_defs |
| valid\_from, valid\_to | date | Effective-dated tables | valid\_to null means open-ended |
| name\_i18n | jsonb | Master data with names | Keys are language codes |

### 3.3 Types

| Concern | Type |
| --- | --- |
| Money amount | numeric(19,4) with currency\_code char(3) |
| Exchange rate | numeric(19,10) |
| Quantity | numeric(19,6) with uom\_id |
| Percentage and ratio | numeric(9,6) |
| Text identifiers (codes) | text with check on length; trimmed; case-insensitive uniqueness through lower() indexes |
| Enumerations | text with check constraint (not PostgreSQL enum types, which are hard to alter) |
| Flexible structures | jsonb, only where the structure is user-defined or sparse; never for data used in joins or constraints |
| Large text | text; files are never stored in tables, only metadata |
| Sensitive fields | bytea ciphertext plus a blind-index column (bytea HMAC) for exact lookup |

### 3.4 Constraint and index rules

- R-01 Every table has a primary key; every foreign key is indexed.
- R-02 Foreign keys exist within a schema and from a module to kernel schemas. A module never has a foreign key to another module.
- R-03 Business uniqueness uses unique indexes scoped by company where relevant, partial on not is\_deleted for soft-deleted tables.
- R-04 Status and type columns have check constraints; transitions are enforced in the domain and workflow engine.
- R-05 Amounts that must be non-negative or in ranges have check constraints.
- R-06 Effective-dated tables use exclusion constraints on (business key, daterange(valid\_from, valid\_to)) with btree\_gist to forbid overlaps.
- R-07 Composite indexes lead with company\_id when queries are company-scoped, then the most selective equality column, then range columns.
- R-08 No index without a query that needs it; every migration that adds an index states the query it serves.
- R-09 Partial indexes are preferred for status-filtered lists (for example open documents).
- R-10 jsonb columns get a GIN index only after measured need.

### 3.5 Concurrency, transactions and time

- R-11 One command, one transaction, one aggregate root; domain changes, outbox rows and audit rows commit together.
- R-12 Default isolation is read committed. Use SELECT FOR UPDATE, advisory locks or serializable isolation only for numbering, stock availability, period close and similar documented invariants.
- R-13 Optimistic concurrency by row\_version on all aggregate roots; a lost update returns a conflict error with the current version.
- R-14 All timestamps are UTC timestamptz. Business dates are date. No local-time storage.
- R-15 Application code never calls now() in business logic; it uses an injected clock so tests control time.

### 3.6 Append-only and immutable tables

Posted journal entries and lines, stock movements, audit log, AI tool-call log, payroll results after close, and license events are append-only. They are protected by revoking update and delete from the application role, and by triggers that raise an error as a second barrier. Corrections are new rows that reference the original.

### 3.7 Database roles

| Role | Rights |
| --- | --- |
| app\_owner | Owns schemas; used only by the Migrator |
| app\_rw | Read and write on business tables; no DDL; no update or delete on append-only tables |
| app\_ro | Read-only, used by reporting and replicas |
| app\_audit | Execute the audit append functions only (amended by CR-031: no direct insert on audit tables) |
| backup | Read for logical backups |

Row-level security is not used for tenant isolation in this design (databases are isolated), but may be used for data scopes in reporting views if the semantic layer cannot enforce them alone. A reporting\_ext role, limited to the reporting schema and scoped views, is created only on request for on-premise and private-cloud tenants (document 9, ADH-11); it has read access to reporting views only, with network allow lists and audit.

### 3.8 Example table conforming to the standards

```sql
CREATE TABLE ref.business_partners (
  id            uuid PRIMARY KEY,
  code          text NOT NULL CHECK (length(code) BETWEEN 1 AND 40),
  name_i18n     jsonb NOT NULL,
  legal_name    text NOT NULL,
  partner_kind  text NOT NULL CHECK (partner_kind IN ('organization','person')),
  status        text NOT NULL CHECK (status IN ('draft','active','on_hold','blocked','archived')),
  currency_code char(3),
  payment_terms_id uuid,
  tags          text[] NOT NULL DEFAULT '{}',
  custom        jsonb NOT NULL DEFAULT '{}',
  row_version   bigint NOT NULL DEFAULT 1,
  is_deleted    boolean NOT NULL DEFAULT false,
  deleted_at    timestamptz, deleted_by uuid,
  created_at    timestamptz NOT NULL, created_by uuid NOT NULL,
  updated_at    timestamptz NOT NULL, updated_by uuid NOT NULL
);
CREATE UNIQUE INDEX uq_business_partners_code ON ref.business_partners (lower(code)) WHERE NOT is_deleted;
CREATE INDEX ix_business_partners_status ON ref.business_partners (status) WHERE NOT is_deleted;
```

## 7. Patterns every module must reuse

### 7.1 Document header and lines

Transactional documents (purchase order, invoice, journal, leave request, stock transfer) use a header table and one or more line tables. Header columns: id, company\_id, document\_no (assigned by numbering), document\_date, status (from the status model), currency\_code, exchange\_rate, totals, reference fields, workflow\_instance\_id, custom, standard and audit columns. Line columns: id, header\_id, company\_id, line\_no, item or account reference, quantity and uom, unit price, amounts, tax code and amount, dimension columns, custom, and a source\_line\_id where created from another document. Unique (header\_id, line\_no). A posted or finalized document is immutable apart from fields the module marks as adjustable; corrections are reversals or new documents linked through ref.document\_links.

### 7.2 Dimensions

Financial and analytical dimensions use explicit columns for the common ones (cost\_center\_id, department\_id, project\_id, business\_partner\_id, item\_id, location\_id) and a dimensions jsonb for tenant-defined extra dimensions. Dimension values are validated against Finance (when licensed) or kernel option lists. Dimension columns exist on journal lines, document lines and reporting views from the first migration so later modules do not require schema surgery.

### 7.3 Effective-dated tables

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE hrm.employee_assignments (
  id uuid PRIMARY KEY,
  company_id uuid NOT NULL,
  employee_id uuid NOT NULL,
  org_unit_id uuid NOT NULL,
  position_id uuid,
  valid_from date NOT NULL,
  valid_to date,
  CHECK (valid_to IS NULL OR valid_to > valid_from),
  CONSTRAINT ex_employee_assignments_period
    EXCLUDE USING gist (employee_id WITH =, daterange(valid_from, valid_to, '[)') WITH &&)
);
```

As-of queries filter valid\_from less than or equal to the date and valid\_to null or greater than the date. A change closes the current row and inserts the new one in one transaction; a correction updates the row and is audited.

### 7.4 Append-only ledger sample

```sql
CREATE TABLE fin.journal_entries (
  id uuid PRIMARY KEY,
  company_id uuid NOT NULL REFERENCES org.companies(id),
  ledger_id uuid NOT NULL,
  entry_no text NOT NULL,
  posting_date date NOT NULL,
  period_id uuid NOT NULL REFERENCES org.fiscal_periods(id),
  source_module text NOT NULL,
  source_ref text NOT NULL,
  posting_version int NOT NULL DEFAULT 1,
  status text NOT NULL CHECK (status IN ('draft','posted','reversed')),
  reverses_id uuid REFERENCES fin.journal_entries(id),
  created_at timestamptz NOT NULL, created_by uuid NOT NULL,
  UNIQUE (company_id, source_module, source_ref, posting_version)
);

CREATE TABLE fin.journal_lines (
  id uuid NOT NULL,
  entry_id uuid NOT NULL,
  company_id uuid NOT NULL,
  posting_date date NOT NULL,
  line_no int NOT NULL,
  account_id uuid NOT NULL,
  debit numeric(19,4) NOT NULL DEFAULT 0 CHECK (debit >= 0),
  credit numeric(19,4) NOT NULL DEFAULT 0 CHECK (credit >= 0),
  currency_code char(3) NOT NULL,
  exchange_rate numeric(19,10) NOT NULL,
  base_debit numeric(19,4) NOT NULL DEFAULT 0,
  base_credit numeric(19,4) NOT NULL DEFAULT 0,
  cost_center_id uuid, department_id uuid, project_id uuid,
  business_partner_id uuid, dimensions jsonb NOT NULL DEFAULT '{}',
  CHECK ((debit = 0) <> (credit = 0)),
  PRIMARY KEY (id, posting_date)
) PARTITION BY RANGE (posting_date);
```

A deferred constraint trigger checks that the base debits and credits of each posted entry are equal. An update-and-delete guard trigger raises an error on posted entries and on all journal lines. The posting transaction also updates fin.account\_balances.

## 9. Migration standards

- Scripts live per module under migrations/ with names V{yyyymmddHHmm}**{module}**{description}.sql, plus an optional U script for the documented rollback.
- Each script is idempotent where possible and runs in a transaction, except operations such as CREATE INDEX CONCURRENTLY, which have their own scripts.
- Expand and contract: a destructive change (drop, rename, type narrowing) is allowed only one release after the code stopped using the old structure.
- Large backfills are jobs, not migration statements.
- Every migration is tested in CI on a fresh database and on a database populated from the previous release, on two tenants with different licensed modules.
- A migration review states the lock impact on large tables and the plan for on-prem customers with limited maintenance windows.
- Seed data is idempotent and keyed by stable codes, never by generated ids.

## 10. Integrity invariants tested on every build

1. Every posted journal entry balances in base currency and in each currency where required.
2. The trial balance equals the sum of subledger control accounts for each company and period.
3. No posted journal, stock movement, audit entry or AI tool-call row can be updated or deleted through the application role.
4. Posting is idempotent: replaying an event produces no new entry.
5. Effective-dated tables never overlap for the same key.
6. Gap-free numbering has no gaps and no duplicates under concurrent load.
7. Stock on hand equals the sum of movements for each item, location and batch.
8. No foreign key crosses between business-module schemas.
9. Every foreign key has an index, and every table has a primary key.
10. Cross-tenant access attempts fail for every API endpoint.

## 11. Review checklist for Claude Code and human reviewers

- Table follows naming and standard columns (sections 3.1 and 3.2).
- Money, quantity and date types are correct; no floating point.
- Constraints in the database, not only in code.
- Indexes justified by named queries.
- Partitioning and retention decided for growing tables.
- Sensitive columns encrypted with blind index where searchable.
- Soft delete and partial unique indexes where needed.
- Effective-dating uses exclusion constraints.
- Reporting view and semantic definitions included.
- Migration is expand and contract safe, tested on two tenants.
- Events and outbox written in the same transaction as the change.

### 14.1 Tenant identifier on every tenant-scoped table (proposed D-30)

| Rule | Text |
| --- | --- |
| R-16 | Every table in a tenant database carries `tenant_id uuid not null`. It is the leading column of every unique constraint and of the main access indexes, ahead of `company_id`. |
| R-17 | `tenant_id` is set by a column default bound to the session's tenant and is never taken from application input. |
| R-18 | Every tenant-scoped table has a row-level security policy `tenant_id = current tenant of the session`. In dedicated mode the policy is present and trivially true; in pooled mode it is the isolation boundary. The application role does not own the tables and cannot bypass policies. |
| R-19 | Foreign keys include `tenant_id` (composite keys), so a row can never reference another tenant's row. |
| R-20 | Partitioned tables in pooled mode partition by time first; tenant is an index prefix, not a partition key. A tenant that outgrows pooled mode is moved to dedicated mode (kernel TEN-16). |

This replaces the sentence in section 3.7 that row-level security is not used for tenant isolation. The standard columns table (3.2) gains `tenant_id` as its second row. Control-plane tables are not tenant-scoped in this sense and are unchanged.

### 14.3 Personal data in append-only tables

Append-only audit rows can hold personal data in their before and after values, while privacy laws in the target markets give people a right to erasure in some cases. Rule R-21: fields classified as personal or sensitive are written to `aud.change_log` encrypted with a per-data-subject key; erasing the subject destroys the key, which leaves the audit chain and its hashes intact and the values unreadable. Financial and statutory records that law requires to be kept are excluded from erasure and are listed per country pack. The legal position for each country needs local counsel (gap G-01).

### 14.4 Geospatial columns (proposed D-36)

No database geospatial extension is used. Latitude and longitude are `numeric(9,6)`, accuracy is `numeric(7,2)` meters, and fence shapes are stored as standard geometry text with a bounding box (four numeric columns) for index pre-filtering. Containment and distance are computed in the application.

### 14.5 Module data design gate (proposed D-35)

No migration is written for a module before its data design is approved. The design is an appendix to the module specification and contains: entity list with owning schema; every column with type, nullability and default; primary, unique and foreign keys; check and exclusion constraints; indexes with the query each serves; partitioning and retention; append-only tables; sensitive columns; reporting views; an entity relationship diagram; and a statement of how each FR-XM rule that touches the module is enforced. The checklist of section 7.6 is the acceptance checklist. Kernel data design (sections 4 to 6 and 13 of this document, brought to column level) is the first gate and a condition for Phase 1.
